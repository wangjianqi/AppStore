# 附录 D：App Store 审核指南精要

> 📖 本附录将 Apple 官方审核指南（App Store Review Guidelines）的核心内容提炼为通俗易懂的版本，帮助零基础开发者快速理解审核规则，避免踩坑。
>
> ⚠️ 注意：本附录为精要解读，不能替代官方指南。提交审核前，建议通读 [Apple 官方审核指南原文](https://developer.apple.com/app-store/review/guidelines/)。

---

## 审核指南结构概览

Apple 审核指南分为 **5 大板块**，涵盖从安全到法律的方方面面。下表帮你一目了然：

| 板块 | 英文名 | 条款范围 | 条款数量 | 核心关注点 |
|------|--------|---------|---------|-----------|
| 安全性 | Safety | 1.1 – 1.7 | 7 条 | 内容安全、用户保护、开发者行为 |
| 性能 | Performance | 2.1 – 2.7 | 7 条 | App 质量、元数据准确、平台规范 |
| 商业 | Business | 3.1 – 3.4 | 4 条 | 支付规则、订阅、商业模式 |
| 设计 | Design | 4.1 – 4.8 | 8 条 | UI 原创性、功能完整性、用户体验 |
| 法律 | Legal | 5.1 – 5.7 | 7 条 | 隐私、知识产权、数据安全 |

> 💡 小贴士：被拒最多的条款集中在 **1.1（内容）、2.1（崩溃/Bug）、2.3（元数据）、3.1（支付）、4.2（最小功能）、5.1（隐私）**，务必重点关注。

---

## 安全性（Safety）

安全性是审核的第一道门槛。Apple 希望确保 App Store 上的所有内容都是安全的，不会对用户造成伤害。

### 1.1 令人反感的内容

#### 条款要点

Apple 不允许 App 中出现令人反感、厌恶或不安的内容，包括但不限于：

| 禁止内容类型 | 具体说明 |
|-------------|---------|
| 暴力内容 | 鼓励暴力、描绘虐待、极端血腥画面 |
| 仇恨言论 | 基于种族、性别、宗教等的歧视或仇恨 |
| 性暗示内容 | 色情、性暗示、未经同意的性内容 |
| 虚假信息 | 误导性的健康/医疗信息、虚假新闻 |
| 鼓励违法行为 | 教唆犯罪、鼓励非法药物使用等 |

#### 常见违规

- App 内有用户发布的色情图片，即使不是开发者主动放的
- 健康类 App 传播未经证实的"偏方"治疗信息
- 社交 App 中存在大量仇恨言论但未处理
- 游戏中包含过度血腥暴力的画面

#### 应对方法

1. **建立内容审核机制**：对 App 内所有展示内容进行审核
2. **设置内容过滤**：使用关键词过滤 + 人工审核双重保障
3. **添加举报功能**：让用户可以举报不当内容
4. **及时处理举报**：收到举报后迅速下架违规内容
5. **避免打擦边球**：拿不准的内容，宁可不放

---

### 1.2 用户生成内容

如果你的 App 允许用户发布内容（文字、图片、视频等），就必须满足额外要求。

#### 条款要点

包含用户生成内容（UGC）的 App **必须**具备以下功能：

| 必须功能 | 说明 | 优先级 |
|---------|------|-------|
| 内容过滤 | 对敏感内容进行自动过滤 | ⭐⭐⭐ 必须 |
| 举报机制 | 用户可以举报不当内容 | ⭐⭐⭐ 必须 |
| 人工审核 | 对举报内容进行人工审核处理 | ⭐⭐⭐ 必须 |
| 用户封禁 | 可以封禁违规用户 | ⭐⭐⭐ 必须 |
| 联系方式 | 提供开发者联系方式 | ⭐⭐⭐ 必须 |

#### 应对方法

1. **在提交审核前就实现所有必须功能**，不要等被拒后再补
2. **举报按钮要显眼**，不要藏在深层菜单里
3. **过滤系统要有效**，至少包含敏感词过滤
4. **审核流程要可演示**，审核员可能会测试举报功能
5. **保留审核记录**，以备审核员要求提供

> 💡 实操建议：即使是简单的社交功能（如评论、头像），也属于 UGC，需要遵守此条款。

---

### 1.3 儿童类别

如果你的 App 面向儿童（特别是 Kids 类别），需要满足更严格的要求。

#### 条款要点

| 要求 | 详细说明 |
|------|---------|
| 内容适龄 | 所有内容必须适合目标年龄段 |
| 不得包含广告 | Kids 类别的 App 不得包含第三方广告 |
| 不得包含外链 | 不得包含跳转到 App 外的链接 |
| 不得包含 IAP | Kids 类别的 App 不得包含应用内购买（注：此规则已更新，允许有限 IAP，但需特别谨慎） |
| 隐私保护 | 不得收集儿童个人信息 |
| 第三方 SDK | 不得使用不符合儿童隐私标准的第三方 SDK |

#### 特殊要求

- 选择 Kids 类别意味着你**主动承诺**遵守更严格的规则
- App 需要通过儿童在线隐私保护法（COPPA）相关审查
- 任何可能收集数据的行为都会被严格审查

#### 应对方法

1. **不确定是否属于儿童 App 时，不要选择 Kids 类别**
2. 如果选择 Kids 类别，确保 App 内**完全没有**广告和外链
3. 仔细检查所有第三方 SDK，确保它们不收集儿童数据
4. 在隐私政策中明确说明如何保护儿童隐私

---

### 1.4 人身伤害

#### 条款要点

Apple 禁止可能对用户造成人身伤害的 App，包括：

| 禁止类型 | 举例 |
|---------|------|
| 鼓励自残 | 宣扬自残、厌食等内容 |
| 鼓励非法药物 | 教唆使用毒品、非法药物 |
| 危险挑战 | 鼓励用户参与危险活动 |
| 不安全的健康建议 | 提供可能造成伤害的医疗建议 |

#### 应对方法

1. 健康类 App 的建议**必须**有专业医学依据
2. 在健康建议旁添加免责声明
3. 明确标注"不能替代专业医疗意见"
4. 不鼓励任何可能造成身体伤害的行为

---

### 1.5 开发者行为

#### 条款要点

Apple 不仅审核 App，也审核开发者行为。以下行为会被处罚：

| 违规行为 | 处罚方式 |
|---------|---------|
| 伪造评价 | 刷好评、买评论 | 移除 App，可能封号 |
| 操纵排名 | 通过不正当手段提升排名 | 移除 App，可能封号 |
| 重复提交 | 被拒后不做修改反复提交 | 延长审核时间，可能封号 |
| 欺骗审核 | 隐藏功能绕过审核 | 移除 App，可能封号 |
| 垃圾提交 | 大量提交相似 App | 移除所有 App，可能封号 |
| 冒充他人 | 冒充其他开发者或品牌 | 移除 App，可能封号 |

#### 应对方法

1. **永远不要试图欺骗审核员**——他们比你想象的更聪明
2. 被拒后认真修改，不要原封不动重新提交
3. 不要刷评论、买下载量
4. 如果 App 有特殊功能，在审核备注中主动说明
5. 保持诚实和透明，这是最安全的策略

## 性能（Performance）

性能板块关注 App 的质量和稳定性。一个经常崩溃或功能不完整的 App 是无法通过审核的。

### 2.1 App 崩溃与 Bug

#### 条款要点

- App **不能崩溃**，不能有明显的 Bug
- App 的所有功能**都必须可用**
- App 的描述和截图中的功能**都必须实现**

#### 预防方法

| 预防措施 | 具体做法 |
|---------|---------|
| 充分测试 | 在多种设备上测试（至少 iPhone 和 iPad） |
| 处理网络异常 | 网络断开时不要崩溃，给用户友好提示 |
| 处理空数据 | 列表为空时不要崩溃，显示空状态页面 |
| 边界测试 | 测试极端输入、超长文本、特殊字符 |
| 使用崩溃收集 | 集成崩溃报告工具（如 Crashlytics） |

#### 应对方法

1. **被拒后先复现问题**：Apple 通常会提供崩溃日志，仔细阅读
2. **修复后充分测试**：确保同样的问题不再出现
3. **在审核备注中说明**：告诉审核员你修复了什么
4. **提供测试账号**：如果 App 需要登录，务必提供测试账号和密码

> 💡 最常见的崩溃原因：网络请求未做错误处理、数组越界、强制解包空值（Swift 的 `!`）。

---

### 2.2 软件要求

#### 条款要点

| 规则 | 说明 |
|------|------|
| 不得使用 Beta 版 API | 不能使用 Apple 尚未正式发布的 API |
| 不得使用热更新 | 不能通过下载代码来改变 App 行为（如 JSPatch、Rollout.io） |
| 不得自更新 | App 不能绕过 App Store 自行下载安装更新 |
| 不得安装其他 App | App 不能下载或安装其他可执行代码 |
| 使用公共 API | 只能使用 Apple 文档中公开的 API，不能用私有 API |

#### 应对方法

1. **不要使用任何热更新框架**——这是硬性红线
2. 检查代码中是否使用了私有 API（Xcode 可以检测）
3. 如果需要更新功能，必须通过 App Store 提交新版本
4. 使用 `#available` 检查 API 可用性，而非使用 Beta 版 API

---

### 2.3 元数据

#### 条款要点

元数据是指 App 在 App Store 上展示的所有信息，包括名称、描述、截图、关键词等。

| 元数据类型 | 要求 |
|-----------|------|
| App 名称 | 必须准确反映 App 功能，不得堆砌关键词 |
| 描述 | 必须真实描述 App 功能，不得夸大 |
| 截图 | 必须是 App 的真实截图，不得虚假 |
| 关键词 | 不得包含竞品名称或无关词汇 |
| 分类 | 必须选择最匹配的分类 |
| 预览视频 | 必须展示 App 的真实使用场景 |

#### 常见违规

- App 名称中堆砌关键词，如"天气-日历-计算器-手电筒"
- 截图中展示了 App 内不存在的功能
- 描述中声称"最好的""第一的"等无法证实的说法
- 关键词中包含竞品 App 的名称
- 预览视频中使用了非 App 内的真实画面

#### 应对方法

1. **名称简洁准确**：App 名称 = 品牌名 + 简短功能描述
2. **截图真实**：只展示 App 实际有的功能
3. **描述务实**：描述 App 能做什么，不要吹嘘
4. **关键词相关**：只使用与 App 功能相关的关键词
5. **避免价格信息**：不要在元数据中写价格（价格会变动）

---

### 2.5 iOS App

#### 条款要点

| 规则 | 说明 |
|------|------|
| 多任务 | 后台任务必须合理，不能无故常驻后台 |
| 网络要求 | 如果 App 需要网络，必须在无网络时给出提示 |
| 签名 | App 必须正确签名，不能绕过系统安全机制 |
| 存储 | 必须使用正确的目录存储数据，不能随意写文件 |
| 后台下载 | 后台下载必须使用系统提供的 API |

#### 应对方法

1. 在 `Info.plist` 中正确声明后台模式
2. 网络不可用时显示友好提示，而不是白屏或崩溃
3. 数据存储到正确的目录（Documents / Library / tmp）
4. 不要在后台做不必要的工作，节省用户电量

---

### 2.6 游戏

#### 条款要点

| 规则 | 说明 |
|------|------|
| Game Center | 使用 Game Center 的游戏必须正确实现相关功能 |
| 多设备 | 游戏应支持多种 iOS 设备 |
| 控制器 | 如果支持游戏控制器，还必须支持触控操作 |
| 内容 | 游戏内容不得违反 1.1 条款 |
| IAP | 游戏内虚拟物品必须使用 IAP |

#### 应对方法

1. 如果使用 Game Center，确保登录、排行榜等功能正常
2. 游戏在 iPhone 和 iPad 上都要能正常玩
3. 即使支持手柄，也要确保纯触控可以玩
4. 游戏内的金币、钻石等虚拟货币必须通过 IAP 购买

## 商业（Business）

商业板块是审核被拒的"重灾区"，尤其是支付和订阅相关的规则，务必仔细阅读。

### 3.1 支付

#### 条款要点

这是审核指南中**最重要、最常被违反**的条款之一：

| 规则 | 说明 |
|------|------|
| 虚拟商品必须用 IAP | App 内的虚拟商品、数字内容必须使用 Apple 内购 |
| 实物商品不能用 IAP | 实物商品（如外卖、电商）不能使用 IAP，用其他支付方式 |
| 不得绕过 IAP | 不得引导用户到网页或其他方式购买虚拟商品 |
| 不得提及其他支付 | App 内不能显示"去网页购买更便宜"等提示 |

#### 虚拟商品 vs 实物商品

理解虚拟商品和实物商品的区别是通过审核的关键：

| 类型 | 定义 | 支付方式 | 举例 |
|------|------|---------|------|
| 虚拟商品 | 在 App 内消费的数字内容/服务 | **必须使用 IAP** | 游戏金币、VIP 会员、电子书、课程视频 |
| 实物商品 | 现实世界中的实体商品/服务 | **不能使用 IAP** | 外卖、服装、打车、酒店预订 |
| 混合型 | 同时包含虚拟和实物 | 分别处理 | 订餐 App 中会员用 IAP，餐品用其他支付 |

#### 应对方法

1. **拿不准就用 IAP**——宁可多走 IAP，也不要在虚拟商品上用第三方支付
2. App 内**不要出现**任何引导用户到外部购买的文字或链接
3. 如果同时有虚拟和实物商品，分别使用不同的支付方式
4. IAP 的价格要合理，与 App 内体验匹配

> ⚠️ 重要提醒：3.1 条款是 Apple 执行最严格的条款之一。任何"绕过内购"的尝试几乎都会被发现并拒绝。

---

### 3.2 订阅

#### 条款要点

| 规则 | 说明 |
|------|------|
| 必须使用 IAP | 自动续期订阅必须通过 IAP 实现 |
| 订阅内容明确 | 必须清楚说明用户订阅后能获得什么 |
| 价格合理 | 订阅价格必须与提供的内容价值匹配 |
| 不得重复收费 | 同一内容不能通过多个订阅重复收费 |
| 退款政策 | 必须遵守 Apple 的退款政策 |
| 免费试用 | 免费试用必须明确说明试用时长和后续费用 |
| 升级/降级 | 必须提供订阅升级和降级的选项 |

#### 常见违规

- 订阅描述含糊，用户不知道花钱买了什么
- 免费试用后自动扣费，但没有明确告知
- 同一功能既卖一次性购买又卖订阅
- 订阅价格远超内容价值（如每月 99 元看几篇文章）

#### 应对方法

1. **订阅说明要详细**：写清楚用户能得到什么、多少钱、多久扣费一次
2. **免费试用要醒目提示**：明确告知试用结束后会自动扣费
3. **提供管理入口**：让用户可以方便地查看和管理订阅
4. **定价合理**：参考同类 App 的定价，不要定得过高
5. **在 App 内展示订阅详情**：不要让用户猜

---

### 3.3 其他商业模式

#### 条款要点

| 商业模式 | 规则 |
|---------|------|
| 免费App + 广告 | 广告必须使用 Apple 推荐的广告框架，不得过于干扰 |
| 付费下载 | 付费 App 必须提供足够的价值 |
| App 内购买 | 非消耗型项目和消耗型项目要正确分类 |
| 慈善捐赠 | 必须使用 IAP，且必须说明捐赠去向 |
| 借贷 App | 必须在 App 内展示所有费用和还款条件 |

#### 应对方法

1. 广告不能遮挡核心内容，不能伪装成系统通知
2. 付费 App 要确保功能完整，不能付费后还需要再付费解锁核心功能
3. 慈善捐赠类 App 要提供透明的资金流向说明
4. 借贷类 App 必须清晰展示年化利率和还款计划

---

## 设计（Design）

设计板块关注 App 的原创性、功能完整性和用户体验。

### 4.1 模仿

#### 条款要点

- App 不得模仿其他 App 的外观和功能
- 不得使用与知名 App 相似的图标和名称
- 不得声称是某个 App 的官方版本（除非你确实是）

#### 如何避免

| 避免模仿的方法 | 具体做法 |
|--------------|---------|
| 独特的设计 | 使用自己的配色、图标和布局 |
| 独特的功能 | 提供与竞品不同的功能或体验 |
| 独特的名称 | 不要使用与知名 App 相似的名称 |
| 独特的图标 | 图标要有辨识度，不要与知名 App 撞脸 |

#### 应对方法

1. 如果你的 App 确实是原创的，只是恰好与某个 App 功能类似，在审核备注中说明你的差异化
2. 不要在名称或图标上"碰瓷"知名 App
3. 如果收到模仿被拒，重新设计 UI 使其与被模仿对象有明显区别

---

### 4.2 最小功能

#### 条款要点

App 必须具有**实质性的功能**，不能只是一个包装的网页或过于简单的工具。

#### 什么算最小功能

| 类型 | 是否通过 | 说明 |
|------|---------|------|
| 完整的原创 App | ✅ 通过 | 有独特功能和完整体验 |
| 简单但有用的工具 | ✅ 通过 | 如单位换算器，虽简单但实用 |
| 纯网页打包 | ❌ 不通过 | 只是套了个壳的网页 |
| 白标/模板 App | ❌ 不通过 | 用同一模板生成的多个 App |
| 过于简单的 App | ❌ 不通过 | 如只有一个按钮的 App |
| 纯资讯聚合 | ❌ 不通过 | 只是抓取网页内容展示 |

#### 应对方法

1. **确保 App 有原生功能**：不要只是把网页包一层壳
2. **增加独特功能**：即使是简单工具，也要有差异化
3. **利用 iOS 特性**：使用推送通知、小组件、Siri 等原生功能
4. **提供完整体验**：App 内的功能要完整可用，不能只是个入口

> 💡 判断标准：如果你的 App 去掉壳子就是一个网页，那大概率会被拒。

---

### 4.3 垃圾 App

#### 条款要点

- 不得创建多个功能相同或高度相似的 App
- 不得为同一 App 创建多个版本（如分"免费版"和"付费版"）
- 不得使用模板批量生成 App

#### 如何避免

| 避免做法 | 正确做法 |
|---------|---------|
| 创建多个功能相似的 App | 合并为一个 App，用 IAP 区分功能 |
| 分免费版和付费版 | 使用一个 App + IAP 解锁 |
| 用模板批量生成 | 为每个 App 做定制化开发 |
| 只改名称和颜色就提交 | 每个App都要有独特的功能和设计 |

#### 应对方法

1. 如果你确实需要多个 App，确保它们之间有**实质性的功能差异**
2. 使用单一 App + IAP 模式替代多版本
3. 如果被判定为垃圾 App，需要证明你的 App 与其他 App 有本质不同

---

### 4.8 登录服务

#### Apple 登录要求

如果你的 App 支持第三方社交登录（如微信、Google、Facebook），就**必须**同时提供"通过 Apple 登录"选项。

| 要求 | 说明 |
|------|------|
| 必须提供 | 如果有第三方登录，就必须有 Apple 登录 |
| 同等地位 | Apple 登录按钮不能比其他登录按钮小或隐蔽 |
| 不得附加条件 | 不能要求用户先做其他事才能用 Apple 登录 |
| 隐藏邮箱 | Apple 登录支持隐藏邮箱功能，你的 App 必须支持 |

#### 第三方登录规范

- 所有第三方登录方式必须正常工作
- 不能只提供一种登录方式
- 登录后不能强制要求提供额外的个人信息

#### 应对方法

1. **先判断是否需要**：如果你的 App 不需要第三方登录，就不需要 Apple 登录
2. **如果需要第三方登录**：确保 Apple 登录按钮和其他登录按钮一样显眼
3. **实现 Sign in with Apple**：使用 Apple 提供的 AuthenticationServices 框架
4. **支持隐藏邮箱**：确保你的后端能处理 Apple 的代理邮箱

## 法律（Legal）

法律板块涉及隐私、知识产权和数据安全，是合规的底线。

### 5.1 隐私

#### 条款要点

| 规则 | 说明 |
|------|------|
| 必须有隐私政策 | 所有 App 都必须有隐私政策 |
| 数据收集需同意 | 收集用户数据前必须获得用户同意 |
| 数据收集需声明 | 必须在 App Store Connect 中声明收集了哪些数据 |
| 最小化收集 | 只收集实现功能所必需的数据 |
| 不得偷偷收集 | 不能在用户不知情的情况下收集数据 |
| 儿童数据 | 不得收集儿童个人信息 |

#### 隐私政策要求

隐私政策必须包含以下内容：

1. **收集哪些数据**：列出所有收集的用户数据类型
2. **为什么收集**：说明每种数据的收集目的
3. **如何使用**：说明数据如何被使用
4. **是否共享**：说明数据是否分享给第三方
5. **如何存储**：说明数据存储在哪里、存储多久
6. **用户权利**：说明用户如何查看、修改、删除自己的数据
7. **联系方式**：提供开发者的联系方式

#### 应对方法

1. **写一份完整的隐私政策**，不要用模板敷衍
2. **在 App 首次启动时展示隐私政策弹窗**
3. **在 App Store Connect 中如实填写 App Privacy 营养标签**
4. **只收集必要的数据**，不要"先收集再说"
5. **隐私政策链接要有效**，确保审核员能打开

---

### 5.2 知识产权

#### 条款要点

- App 不得侵犯他人的知识产权
- 不得使用未经授权的商标、版权内容
- 不得使用未经授权的第三方素材

#### 如何避免侵权

| 侵权类型 | 避免方法 |
|---------|---------|
| 商标侵权 | 不使用知名品牌名称、Logo |
| 版权侵权 | 不使用未经授权的图片、音乐、视频 |
| 专利侵权 | 不复制他人的核心功能实现方式 |
| 外观侵权 | 不模仿其他 App 的 UI 设计 |

#### 应对方法

1. **使用原创素材**：自己设计图标和界面，或使用明确允许商用的素材
2. **使用正版资源**：图片用 Unsplash 等免费商用图库，音乐用免版权音乐
3. **不要用品牌名**：App 名称和关键词中不要包含他人品牌名
4. **收到侵权投诉及时处理**：如果被投诉，立即移除侵权内容

---

### 5.3 数据收集与存储

#### 条款要点

| 规则 | 说明 |
|------|------|
| 数据安全 | 用户数据必须安全存储和传输 |
| 最小化访问 | 只请求实现功能所必需的权限 |
| 透明度 | 必须告知用户数据如何被使用 |
| 数据删除 | 用户应能请求删除自己的数据 |
| 不得售卖数据 | 不得将用户数据出售给第三方 |
| IDFA 使用 | 使用广告标识符必须获得用户授权 |

#### 数据安全要求

1. **网络传输加密**：所有网络通信必须使用 HTTPS
2. **本地存储加密**：敏感数据应使用 Keychain 存储，不要明文存储
3. **日志安全**：不要在日志中记录密码、Token 等敏感信息
4. **第三方 SDK**：确保第三方 SDK 也遵守数据安全规范

#### 应对方法

1. 使用 `HTTPS` 进行所有网络请求
2. 密码和 Token 存入 Keychain，不要存 UserDefaults
3. 在 `Info.plist` 中为每个权限请求提供清晰的使用说明
4. 实现"删除账号"功能，让用户可以彻底删除数据
5. 如果使用 IDFA，必须弹出 App Tracking Transparency 授权弹窗

## 应对策略速查

以下速查表帮你快速定位常见被拒原因和应对方法：

| 条款号 | 常见被拒原因 | 快速应对方法 |
|-------|------------|------------|
| 1.1 | 含有令人反感的内容 | 移除违规内容，添加内容过滤和举报机制 |
| 1.2 | UGC App 缺少举报/过滤/审核功能 | 补充举报、过滤、封禁、审核四大功能 |
| 1.3 | 儿童类别 App 包含广告或外链 | 移除所有广告和外链 |
| 1.4 | 包含鼓励自残/非法药物的内容 | 移除相关内容，添加专业免责声明 |
| 1.5 | 刷评论/伪造评价/反复提交 | 停止违规行为，认真修改后重新提交 |
| 2.1 | App 崩溃或有 Bug | 根据崩溃日志修复 Bug，充分测试后重新提交 |
| 2.2 | 使用了热更新/私有 API | 移除热更新框架，替换私有 API 为公共 API |
| 2.3 | 元数据不准确/堆砌关键词 | 修改名称和描述，使用真实截图，清理关键词 |
| 2.5 | 后台模式使用不当 | 只声明真正需要的后台模式，优化后台任务 |
| 2.6 | 游戏不支持触控/仅支持手柄 | 添加触控操作支持 |
| 3.1 | 虚拟商品未使用 IAP | 虚拟商品改用 IAP，移除外部支付引导 |
| 3.1 | 引导用户绕过 IAP | 移除所有"去网页购买"等引导文字和链接 |
| 3.2 | 订阅说明不清晰 | 详细说明订阅内容、价格、续费规则 |
| 3.2 | 免费试用未说明后续扣费 | 醒目提示试用结束后自动扣费 |
| 3.3 | 广告过于干扰 | 减少广告频率，不遮挡核心内容 |
| 4.1 | 模仿其他 App | 重新设计 UI，体现差异化 |
| 4.2 | 功能过于简单/网页打包 | 增加原生功能，提供完整体验 |
| 4.3 | 提交多个相似 App | 合并为一个 App，使用 IAP 区分功能 |
| 4.8 | 有第三方登录但无 Apple 登录 | 添加 Sign in with Apple |
| 4.8 | Apple 登录按钮不够显眼 | 确保与其他登录按钮同等大小和位置 |
| 5.1 | 缺少隐私政策 | 编写完整的隐私政策并在 App 内展示 |
| 5.1 | 未声明数据收集 | 在 App Store Connect 中如实填写 App Privacy |
| 5.2 | 使用了未经授权的素材 | 替换为原创或正版商用素材 |
| 5.3 | 未实现删除账号功能 | 添加账号删除功能，确保数据彻底删除 |
| 5.3 | 使用 IDFA 未弹授权窗 | 实现 App Tracking Transparency 授权流程 |

> 💡 使用方法：收到被拒通知后，先找到对应的条款号，然后在上表中查找应对方法。
