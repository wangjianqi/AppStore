# 58-TestFlight 测试

## 本章目标

- 理解 TestFlight 是什么，为什么上架前必须用它测试
- 学会从 Xcode 上传构建版本到 App Store Connect
- 掌握内部测试和外部测试的区别与操作方法
- 了解测试流程管理、反馈收集、公开链接等功能
- 掌握多平台测试和最佳实践

---

## 1. TestFlight 简介

### 什么是 TestFlight？

TestFlight 是苹果官方提供的 **App 测试分发平台**。你可以把它理解为一个"试吃台"——在菜品正式上菜单之前，先让一部分人尝尝，提提意见，确保味道没问题再正式推出。

| 对比项 | 正式上架 | TestFlight 测试 |
|--------|---------|----------------|
| 获取方式 | App Store 搜索下载 | 邀请链接 / 邮件邀请 |
| 是否需要审核 | 需要 | 内部测试不需要，外部测试需要 |
| 用户范围 | 所有用户 | 受邀测试员 |
| 目的 | 正式发布 | 找 Bug、收集反馈 |

### 为什么上架前必须测试？

> 💡 想象一下：你开了一家餐厅，菜没尝过就直接端给客人——万一盐放多了呢？App 也一样，不测试就上架，可能会出现闪退、界面错乱、功能异常等问题，轻则差评如潮，重则被苹果下架。

测试的核心价值：

| 价值 | 说明 |
|------|------|
| 发现 Bug | 真实设备上的问题，模拟器测不出来 |
| 验证体验 | 操作是否流畅、界面是否正常 |
| 收集反馈 | 用户真实想法，比你自己猜的准 |
| 降低风险 | 避免上架后出问题被差评或下架 |

## 2. 上传构建版本

### 整体流程

上传构建版本就像把做好的菜送到"试吃台"，整个流程如下：

```
Xcode 项目 → Archive（打包）→ 上传到 App Store Connect → 等待处理 → 可用于测试
```

### 2.1 在 Xcode 中 Archive

**第一步：选择真机设备**

```bash
# ❌ 错误：选择模拟器无法 Archive
# ✅ 正确：选择 "Any iOS Device (arm64)" 或连接的真机
```

在 Xcode 顶部工具栏，将设备选择器从模拟器切换为：

| 选项 | 说明 |
|------|------|
| Any iOS Device (arm64) | 通用选项，无需连接真机 |
| 你的 iPhone | 连接了真机时可选 |

**第二步：执行 Archive**

菜单路径：**Product → Archive**

或者使用命令行：

```bash
# 进入项目目录
cd /Users/你的用户名/Projects/MyApp

# 执行 Archive
xcodebuild archive \
  -project MyApp.xcodeproj \
  -scheme MyApp \
  -archivePath ./build/MyApp.xcarchive \
  -configuration Release \
  CODE_SIGN_IDENTITY="Apple Distribution" \
  DEVELOPMENT_TEAM="你的TeamID"
```

> ⚠️ Archive 之前确保：
> - Scheme 选择的是 **Release** 配置（不是 Debug）
> - 证书和描述文件配置正确（Apple Distribution 证书 + App Store 描述文件）
> - 版本号和构建版本号已更新

**第三步：在 Organizer 中上传**

Archive 完成后，Xcode 会自动弹出 Organizer 窗口：

```
Organizer 窗口
  → 选择刚才的 Archive
  → 点击 "Distribute App"
  → 选择 "App Store Connect"
  → 选择 "Upload"
  → 按照向导完成上传
```

上传选项说明：

| 选项 | 建议设置 | 说明 |
|------|---------|------|
| Upload your app's symbols | ✅ 勾选 | 用于崩溃日志符号化 |
| Manage Version and Build Number | 按需 | 可自动管理版本号 |

### 2.2 在 App Store Connect 中查看

上传后，登录 [App Store Connect](https://appstoreconnect.apple.com)，进入你的 App：

```
App Store Connect
  → 我的 App
  → 选择你的 App
  → 左侧菜单 "TestFlight"
  → 可以看到构建版本列表
```

> 💡 上传后构建版本需要 **5-30 分钟** 处理时间，状态从"正在处理"变为"可测试"后才能使用。

构建版本状态说明：

| 状态 | 含义 |
|------|------|
| 正在处理 | 苹果服务器正在验证和编译 |
| 可测试 | 处理完成，可以分配给测试员 |
| 缺少合规信息 | 需要填写出口合规信息 |
| 无效 | 构建版本有问题，无法使用 |

### 2.3 版本号管理

每次上传的构建版本必须有 **唯一的构建版本号**：

```bash
# 查看当前版本号
agvtool what-marketing-version
# 输出: 1.0.0

# 查看当前构建版本号
agvtool what-version
# 输出: 1

# 递增构建版本号
agvtool next-version -all
# 构建版本号从 1 变为 2
```

| 概念 | 格式 | 示例 | 修改频率 |
|------|------|------|---------|
| 版本号（Marketing Version） | 主.次.补丁 | 1.0.0 | 每次发版 |
| 构建版本号（Build Number） | 递增整数 | 1, 2, 3... | 每次上传 |

> ⚠️ 同一个版本号下，构建版本号必须递增。如果上传 Build 5 后又上传 Build 3，会被拒绝。

## 3. 内部测试

### 什么是内部测试？

内部测试就像"家人试菜"——只有你信任的团队成员才能参与，不需要苹果审核，上传后立即可用。

### 3.1 添加内部测试员

内部测试员就是 App Store Connect 账户中的团队成员：

```
App Store Connect
  → 用户和访问
  → 点击 "+" 添加用户
  → 输入邮箱和姓名
  → 分配角色（至少需要"管理员"或"开发"角色）
```

> 💡 内部测试员必须是 App Store Connect 团队成员，不能随意添加。添加团队成员后，他们会自动出现在内部测试员列表中。

### 3.2 内部测试的特点

| 特点 | 说明 |
|------|------|
| 人数上限 | 最多 **100 人** |
| 审核要求 | **无需审核**，上传即可测试 |
| 生效时间 | 构建版本处理完成后 **即时可用** |
| 测试员身份 | App Store Connect 团队成员 |
| 适用场景 | 开发团队内部快速验证 |

### 3.3 开始内部测试

```
App Store Connect
  → TestFlight
  → 选择构建版本
  → 内部测试组
  → 添加测试员
  → 点击"测试"开始测试
```

测试员会收到邮件和 TestFlight App 推送通知：

```
📧 邮件内容示例：
━━━━━━━━━━━━━━━━━━━━
MyApp (1.0.0 Build 5) 现已可供测试。

请打开 TestFlight App 安装并测试。

如不想再收到通知，请在 TestFlight 中取消订阅。
━━━━━━━━━━━━━━━━━━━━
```

### 3.4 测试员如何安装

测试员需要在 iPhone 上安装 **TestFlight App**（从 App Store 免费下载）：

```
1. 从 App Store 下载 TestFlight
2. 打开邮件中的邀请链接
3. 在 TestFlight 中点击"安装"
4. 安装完成后点击"打开"即可测试
```

> ⚠️ TestFlight 安装的 App 有 **90 天有效期**，过期后需要重新安装新版本。App 图标上会有橙色圆点标记，表示这是测试版。

## 4. 外部测试

### 什么是外部测试？

外部测试就像"免费试吃活动"——邀请更多人品尝，但需要先通过"卫生检查"（苹果审核）。

### 4.1 创建外部测试组

```
App Store Connect
  → TestFlight
  → 外部测试
  → 点击 "+" 创建测试组
  → 输入组名（如"公测第一组"）
  → 添加测试员邮箱
  → 选择构建版本
  → 提交审核
```

### 4.2 外部测试的特点

| 特点 | 说明 |
|------|------|
| 人数上限 | 最多 **10,000 人** |
| 审核要求 | **需要苹果审核**（通常 1-2 天） |
| 生效时间 | 审核通过后才可测试 |
| 测试员身份 | 任何人（只需 Apple ID） |
| 适用场景 | 大规模公测、种子用户测试 |

### 4.3 内部测试 vs 外部测试

| 对比项 | 内部测试 | 外部测试 |
|--------|---------|---------|
| 人数上限 | 100 人 | 10,000 人 |
| 是否需要审核 | ❌ 不需要 | ✅ 需要 |
| 生效速度 | 即时 | 1-2 天 |
| 测试员要求 | 团队成员 | 任何 Apple ID |
| 适合阶段 | 开发阶段 | 发布前验证 |
| 反馈质量 | 专业 | 更贴近真实用户 |

> 💡 建议先用内部测试快速验证，确认没有明显问题后再开启外部测试，避免浪费审核时间。

### 4.4 外部测试审核要点

外部测试的审核比正式上架审核宽松，但仍需注意：

| 会拒绝的情况 | 说明 |
|-------------|------|
| 明显崩溃 | App 打不开或频繁闪退 |
| 核心功能不可用 | 主要功能无法使用 |
| 占位内容 | "即将推出"等未完成内容 |
| 违反审核指南 | 含有违规内容 |

审核时需要提供 **测试信息**：

```
App Store Connect
  → TestFlight
  → 选择构建版本
  → 填写"测试信息"
    → 测试账号（如需登录）
    → 测试步骤
    → 备注
```

示例测试信息：

```
测试账号：test@example.com
密码：Test1234!

测试步骤：
1. 打开 App，使用上述账号登录
2. 在首页点击"创建新笔记"
3. 输入标题和内容，点击保存
4. 验证笔记出现在列表中

备注：首次登录可能需要等待几秒加载
```

## 5. 测试流程管理

### 5.1 测试组

测试组就像把试吃的人分成不同小组——"辣味组""清淡组""甜品组"，每个组可以测试不同的版本。

```
App Store Connect
  → TestFlight
  → 外部测试
  → 可以创建多个测试组
    ├── 核心用户组（测试最新版本）
    ├── 普通用户组（测试稳定版本）
    └── 特定功能组（测试某个功能）
```

测试组管理：

| 操作 | 说明 |
|------|------|
| 创建组 | 点击 "+" 新建测试组 |
| 添加测试员 | 输入邮箱，批量添加 |
| 分配构建版本 | 选择该组要测试的版本 |
| 启用/禁用 | 控制测试组是否活跃 |
| 删除组 | 移除整个测试组 |

### 5.2 分阶段发布

分阶段发布就像"逐步扩大试吃范围"——先让少数人尝，没问题再让更多人尝。

```
App Store Connect
  → TestFlight
  → 外部测试
  → 选择测试组
  → 开启"分阶段发布"
  → 设置每日新增测试员数量
```

分阶段发布设置：

| 阶段 | 新增人数 | 累计人数 | 说明 |
|------|---------|---------|------|
| 第 1 天 | 100 | 100 | 小范围验证 |
| 第 2 天 | 200 | 300 | 扩大范围 |
| 第 3 天 | 500 | 800 | 继续扩大 |
| 第 4 天 | 1000 | 1800 | 大规模测试 |
| 第 5 天 | 剩余全部 | 全部 | 全量发布 |

> 💡 分阶段发布的好处：如果新版本有严重问题，只影响少数人，可以及时止损。

### 5.3 构建版本管理

每个上传的构建版本都有生命周期：

```
上传 → 处理中 → 可测试 → 过期（90天）
                  ↓
              替换为新版本
```

构建版本操作：

| 操作 | 说明 |
|------|------|
| 添加到测试组 | 将版本分配给测试员 |
| 过期设置 | 默认 90 天，可自定义 |
| 替换版本 | 用新版本替换旧版本 |
| 使版本过期 | 手动让某个版本失效 |

> ⚠️ 过期的构建版本无法再被安装，但已安装的 App 在过期前仍可使用。记得在过期前上传新版本。

## 6. 收集反馈

### 6.1 崩溃报告

TestFlight 会自动收集测试员的崩溃信息，就像"菜品出了问题自动记录"。

```
App Store Connect
  → TestFlight
  → 崩溃
  → 查看崩溃报告列表
```

崩溃报告查看步骤：

```
1. 进入 TestFlight → 崩溃
2. 选择崩溃类型
3. 查看崩溃堆栈
4. 定位问题代码
```

> 💡 如果上传时勾选了"Upload your app's symbols"，崩溃堆栈会显示具体的代码行号，而不是一堆十六进制地址。这叫 **符号化（Symbolication）**。

崩溃报告示例：

```
Crash Report:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Exception Type: EXC_BAD_ACCESS
Exception Subtype: KERN_INVALID_ADDRESS

Thread 0 Crashed:
0  MyApp                      0x0000000104a3c2a4 NoteViewController.save() + 128
1  MyApp                      0x0000000104a3c1f0 NoteViewController.saveButtonTapped(_:) + 56
2  UIKit                       0x00000001c4a8f3c4 -[UIApplication sendAction:to:from:forEvent:] + 96
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 6.2 截图反馈

测试员可以在 App 中直接截图并标注反馈：

```
测试员操作流程：
1. 在测试 App 中截图（同时按电源键 + 音量上键）
2. 截图预览出现后，点击"分享"按钮
3. 选择 TestFlight Beta Feedback
4. 添加文字描述
5. 提交反馈
```

> 💡 测试员也可以在 TestFlight App 中提交反馈：打开 TestFlight → 选择 App → 点击"发送 Beta 反馈"。

### 6.3 测试员反馈

在 App Store Connect 中查看所有反馈：

```
App Store Connect
  → TestFlight
  → 反馈
  → 查看反馈列表
    ├── 截图反馈
    ├── 崩溃反馈
    └── 文字反馈
```

反馈信息包含：

| 信息 | 说明 |
|------|------|
| 反馈内容 | 测试员写的文字描述 |
| 截图 | 测试员附加的截图 |
| 设备信息 | iPhone 型型、系统版本 |
| App 版本 | 版本号和构建版本号 |
| 时间 | 反馈提交时间 |

### 6.4 在 App 中集成反馈功能

你可以在 App 中添加一个反馈入口，方便测试员直接提交：

```swift
import StoreKit

struct FeedbackView: View {
    @State private var feedbackText = ""

    var body: some View {
        VStack(spacing: 16) {
            Text("提交反馈")
                .font(.headline)

            TextEditor(text: $feedbackText)
                .frame(height: 150)
                .overlay(
                    RoundedRectangle(cornerRadius: 8)
                        .stroke(Color.gray.opacity(0.3), lineWidth: 1)
                )

            Button("提交") {
                submitFeedback()
            }
            .disabled(feedbackText.isEmpty)
        }
        .padding()
    }

    private func submitFeedback() {
        guard let windowScene = UIApplication.shared.connectedScenes.first as? UIWindowScene else { return }
        SKStoreReviewController.requestReview(in: windowScene)
        feedbackText = ""
    }
}
```

> ⚠️ 上述代码使用 `SKStoreReviewController` 仅作演示。TestFlight 环境下，更推荐引导测试员使用 TestFlight 自带的反馈功能，而不是在 App 内自建反馈系统。

## 7. TestFlight 公开链接

### 什么是公开链接？

公开链接就像"试吃券"——你把链接发出去，任何人点击就能参加测试，不需要你逐个添加邮箱。

### 7.1 生成公开链接

```
App Store Connect
  → TestFlight
  → 外部测试
  → 选择测试组
  → 开启"公开链接"
  → 系统自动生成链接
```

生成的链接格式：

```
https://testflight.apple.com/join/XXXXXXXX
```

> 💡 `XXXXXXXX` 是一个唯一的邀请码，每个测试组的链接不同。

### 7.2 公开链接设置

| 设置项 | 说明 |
|--------|------|
| 开启/关闭 | 控制链接是否有效 |
| 人数限制 | 限制通过链接加入的最大人数 |
| 自动接受 | 新加入者是否自动获得测试资格 |

人数限制示例：

```
公开链接设置：
━━━━━━━━━━━━━━━━━━━━
链接状态：✅ 已开启
最大测试员数：500
当前已加入：127
剩余名额：373
━━━━━━━━━━━━━━━━━━━━
```

### 7.3 分享公开链接

公开链接可以通过多种渠道分享：

| 渠道 | 示例 |
|------|------|
| 社交媒体 | 微博、Twitter、小红书 |
| 即时通讯 | 微信群、QQ 群、Slack |
| 官网 | 在你的网站上放置下载按钮 |
| 邮件 | 发送给订阅用户 |

分享文案示例：

```
🎉 MyApp 1.0 公测开始啦！

想第一时间体验新功能吗？
点击链接加入 TestFlight 公测：
https://testflight.apple.com/join/XXXXXXXX

名额有限，先到先得！
```

> ⚠️ 公开链接意味着任何人都可以加入测试，请注意保护 App 的未公开内容。如果发现滥用，可以随时关闭链接。

## 8. 多平台测试

### 8.1 支持的平台

TestFlight 支持在所有苹果平台上测试：

| 平台 | 设备 | TestFlight 支持 |
|------|------|----------------|
| iOS | iPhone | ✅ |
| iPadOS | iPad | ✅ |
| macOS | Mac | ✅ |
| watchOS | Apple Watch | ✅ |
| tvOS | Apple TV | ✅ |
| visionOS | Apple Vision Pro | ✅ |

### 8.2 各平台测试要点

**iPhone 测试：**

```
重点关注：
- 不同屏幕尺寸的适配（SE / 标准 / Plus / Pro Max）
- 横竖屏切换
- 手势操作
- 通知和后台行为
```

**iPad 测试：**

```
重点关注：
- 分屏多任务（Split View / Slide Over）
- 键盘和触控板操作
- iPad 专属界面布局
- Stage Manager 兼容性
```

**Mac 测试（Mac Catalyst / 原生）：**

```
重点关注：
- 窗口大小调整
- 键盘快捷键
- 菜单栏集成
- 触控板手势
```

**Apple Watch 测试：**

```
重点关注：
- 小屏幕上的信息展示
- 抬腕即看
- 通知交互
- 与 iPhone 的配合
```

### 8.3 多平台构建版本上传

如果你的 App 支持多个平台，需要在 Archive 时包含所有平台：

```bash
# Archive 多平台版本
xcodebuild archive \
  -project MyApp.xcodeproj \
  -scheme MyApp \
  -destination "generic/platform=iOS" \
  -archivePath ./build/MyApp-iOS.xcarchive

xcodebuild archive \
  -project MyApp.xcodeproj \
  -scheme MyApp \
  -destination "generic/platform=macOS" \
  -archivePath ./build/MyApp-macOS.xcarchive
```

> 💡 在 Xcode 中，如果你的 App 是通用购买（Universal Purchase），iOS 和 macOS 版本共享同一个 App 记录，测试员可以在对应平台的 TestFlight 中安装。

### 8.4 设备覆盖建议

| 测试优先级 | 设备 | 原因 |

| 🟡 建议测试 | 旧款 iPhone | 验证性能兼容 |

## 9. 最佳实践

### 9.1 制定测试计划

测试不能"随便点点"，需要有计划地进行：

```
测试计划模板：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📋 MyApp 1.0 测试计划

🎯 测试目标：
  - 验证核心功能正常运行
  - 发现并修复关键 Bug
  - 收集用户体验反馈

👥 测试人员：
  - 内部测试：5 名开发团队成员
  - 外部测试：50 名种子用户

📅 测试时间线：
  第 1 周：内部测试，修复关键问题
  第 2 周：小范围外部测试（50人）
  第 3 周：扩大外部测试（200人）
  第 4 周：最终验证，准备上架

✅ 测试重点：
  1. 注册/登录流程
  2. 核心功能 A
  3. 核心功能 B
  4. 支付流程
  5. 不同设备适配

❌ 不在测试范围：
  - 已知的设计细节调整
  - 未上线的功能模块
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 9.2 反馈收集清单

| 反馈类型 | 收集方式 | 处理优先级 |
|---------|---------|-----------|
| 崩溃 | 自动收集 | 🔴 立即修复 |
| 功能异常 | 测试员反馈 | 🔴 优先修复 |
| 体验问题 | 测试员反馈 | 🟡 评估后修复 |
| 建议意见 | 测试员反馈 | 🟢 记录，后续考虑 |

### 9.3 版本迭代流程

```
开发新版本 → 内部测试 → 修复问题 → 外部测试 → 修复问题 → 准备上架
     ↑                                            |
     └──────────── 发现重大问题 ←──────────────────┘
```

每个版本的迭代步骤：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 修复 Bug | 根据反馈修复问题 |
| 2 | 更新版本号 | 递增构建版本号 |
| 3 | Archive & 上传 | 打包新版本上传 |
| 4 | 等待处理 | 5-30 分钟 |
| 5 | 分配测试 | 更新测试组的构建版本 |
| 6 | 收集反馈 | 等待测试员反馈 |
| 7 | 判断是否完成 | 无严重问题则准备上架 |

### 9.4 常见问题与解决方案

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 构建版本不显示 | 还在处理中 | 等待 5-30 分钟 |
| 构建版本无效 | 缺少合规信息 | 填写出口合规信息 |
| 测试员收不到邀请 | 邮件被拦截 | 检查垃圾邮件，或使用公开链接 |
| App 安装后闪退 | 缺少权限描述 | 检查 Info.plist 权限声明 |
| 无法登录 App | 服务器环境问题 | 确认测试环境是否正常 |
| TestFlight 过期 | 90 天有效期 | 上传新版本 |

上架前的最终检查：

```
上架前测试检查清单：

□ 无严重崩溃

□ App 图标和启动屏幕正确
□ 隐私政策链接有效
□ 已修复所有测试员反馈的严重问题
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 小结

| 知识点 | 关键内容 |
|--------|---------|
| TestFlight 简介 | 苹果官方测试平台，上架前必经之路 |
| 上传构建版本 | Xcode Archive → 上传 → 等待处理 |
| 内部测试 | 团队成员，100 人上限，无需审核，即时可用 |
| 外部测试 | 任意用户，10000 人上限，需要审核 |
| 测试流程管理 | 测试组、分阶段发布、版本管理 |
| 收集反馈 | 崩溃报告、截图反馈、测试员反馈 |
| 公开链接 | 生成邀请链接，限制人数，方便分享 |
| 多平台测试 | iPhone / iPad / Mac / Watch 全覆盖 |
| 最佳实践 | 制定计划、收集反馈、迭代版本 |

> 💡 记住：**测试不是可有可无的步骤，而是上架前的必经之路**。一个经过充分测试的 App，才能给用户带来好的体验，才能在 App Store 上获得好的评价。宁可多花一周测试，也不要因为一个低级 Bug 毁掉所有努力。
