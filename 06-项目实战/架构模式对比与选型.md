# 架构模式对比与选型

## 本章目标

- 理解为什么需要架构模式，以及无架构代码的典型痛苦
- 掌握 MVC、MVVM、MVP、VIPER、Clean Architecture、TCA 六种架构模式的核心思想
- 能够为不同规模和复杂度的项目选择合适的架构
- 理解 SwiftUI 时代架构模式的演变趋势
- 通过对比表和决策树快速做出架构选型决策

---

## 1. 为什么需要架构模式

### 1.1 无架构的痛苦

想象你搬进了一间新公寓，刚开始东西随手一放觉得挺方便。但三个月后——衣服堆在沙发上、锅碗瓢盆混在一起、找把钥匙要翻遍整个房间。**代码没有架构，就像没有收纳规划的房间，迟早会变成一团乱麻。**

无架构代码的典型症状：

| 症状 | 表现 | 生活类比 |
|------|------|---------|
| 巨型文件 | 单个 ViewController 超过 1000 行 | 一个抽屉塞满了所有杂物 |
| 职责混乱 | 网络请求写在按钮点击事件里 | 厨房里放着换洗衣物 |
| 难以测试 | 想测业务逻辑必须启动整个 UI | 想试衣服必须先出门走一圈 |
| 改一处崩多处 | 修改 A 功能导致 B 功能异常 | 拔掉一个插头，全屋断电 |
| 新人懵圈 | 接手项目完全不知道从哪看起 | 别人收拾的房间你找不到东西 |

### 1.2 架构的三大目标

所有架构模式都围绕三个核心目标展开：

| 目标 | 含义 | 为什么重要 |
|------|------|-----------|
| **可测试** | 业务逻辑可以脱离 UI 独立测试 | 没有可测试性，重构就是赌博 |
| **可维护** | 代码职责清晰，修改影响范围可控 | 降低长期维护成本 |
| **可扩展** | 新增功能不需要大规模重构 | 适应需求变化，延长项目寿命 |

> 💡 架构模式不是银弹，它是一种**约束和约定**。好的架构让开发者"想写烂代码都难"，坏的架构让开发者"想写好代码都累"。

### 1.3 架构的核心原则

不管选择哪种模式，以下原则是共通的：

- **单一职责原则**：每个类/文件只做一件事
- **依赖倒置**：高层模块不依赖低层模块，都依赖抽象
- **关注点分离**：UI、业务逻辑、数据访问各司其职
- **显式依赖**：依赖关系通过构造函数注入，而非隐式引用

## 2. MVC（Model-View-Controller）

### 2.1 Apple 经典模式

MVC 是 Apple 在 UIKit 时代主推的架构模式，几乎所有的 Xcode 模板都基于 MVC。它的核心思想是将代码分为三层：

| 层 | 职责 | 生活类比 |
|---|------|---------|
| **Model** | 数据和业务规则 | 食材和菜谱 |
| **View** | 界面展示 | 摆盘上桌 |
| **Controller** | 协调 Model 和 View | 厨师，按菜谱把食材变成菜品 |

```swift
struct User: Codable {
    let id: String
    var name: String
    var avatarURL: String?
}

class UserProfileViewController: UIViewController {
    private var user: User?

    @IBOutlet weak var nameLabel: UILabel!
    @IBOutlet weak var avatarImageView: UIImageView!

    override func viewDidLoad() {
        super.viewDidLoad()
        loadUser()
    }

    private func loadUser() {
        URLSession.shared.dataTask(with: url) { [weak self] data, _, _ in
            guard let data, let user = try? JSONDecoder().decode(User.self, from: data) else { return }
            self?.user = user
            DispatchQueue.main.async {
                self?.nameLabel.text = user.name
            }
        }.resume()
    }

    @IBAction func editNameTapped(_ sender: UIButton) {
        let alert = UIAlertController(title: "修改昵称", message: nil, preferredStyle: .alert)
        alert.addTextField { $0.text = user?.name }
        alert.addAction(UIAlertAction(title: "确定", style: .default) { [weak self] _ in
            self?.user?.name = alert.textFields?.first?.text ?? ""
            self?.nameLabel.text = self?.user?.name
            self?.saveUser()
        })
        present(alert, animated: true)
    }

    private func saveUser() {
        guard let data = try? JSONEncoder().encode(user) else { return }
        var request = URLRequest(url: saveURL)
        request.httpMethod = "PUT"
        request.httpBody = data
        URLSession.shared.dataTask(with: request).resume()
    }
}
```

### 2.2 UIViewController 膨胀问题

MVC 在实践中最大的痛点是 **Massive View Controller**（巨型控制器）。因为 Controller 承担了太多职责：

| 职责 | 代码量占比 | 是否属于 Controller 本职 |
|------|-----------|------------------------|
| 视图生命周期管理 | 15% | ✅ 是 |
| UI 布局和更新 | 25% | ❌ 应属于 View |
| 网络请求 | 20% | ❌ 应属于 Service |
| 数据转换 | 15% | ❌ 应属于 ViewModel |
| 导航跳转 | 10% | ❌ 应属于 Coordinator |
| 用户交互响应 | 15% | ✅ 是（但逻辑应抽出） |

> ⚠️ 一个典型的"胖 Controller"往往超过 800 行，其中只有约 30% 是 Controller 真正该做的事。这就是为什么社区戏称 MVC 为 **Massive View Controller**。

### 2.3 SwiftUI 时代 MVC 的演变

SwiftUI 的声明式语法天然将 View 和状态分离，MVC 中的 Controller 职责被大幅削减：

| 方面 | UIKit + MVC | SwiftUI |
|------|-------------|---------|
| 视图更新 | Controller 手动刷新 | 状态驱动自动刷新 |
| 导航 | Controller 控制 | NavigationStack 声明式 |
| 生命周期 | viewDidLoad 等回调 | onAppear 等修饰符 |
| 布局 | Auto Layout 代码 | 声明式布局 DSL |

在 SwiftUI 中，MVC 的 Controller 被拆散：状态管理归 `@State`/`@Observable`，导航归 `NavigationStack`，数据获取归 `.task` 修饰符。**MVC 在 SwiftUI 中自然演变为 MVVM。**

## 3. MVVM（Model-View-ViewModel）

### 3.1 核心思想

MVVM 是目前 iOS 社区最主流的架构模式。它将 MVC 的 Controller 拆分为 ViewModel，实现 UI 与业务逻辑的彻底分离：

| 层 | 职责 | 生活类比 |
|---|------|---------|
| **Model** | 数据模型和业务规则 | 食材 |
| **View** | 界面展示和用户交互 | 菜单和餐桌 |
| **ViewModel** | 状态管理和逻辑处理 | 厨房，把食材加工成可上桌的菜 |

### 3.2 数据绑定机制

MVVM 的关键在于 View 和 ViewModel 之间的数据绑定。在 iOS 中有三种主要方式：

| 绑定方式 | UIKit 适用 | SwiftUI 适用 | 特点 |
|---------|-----------|-------------|------|
| 闭包回调 | ✅ | ❌ | 手动管理，灵活但繁琐 |
| Combine | ✅ | ✅ | 响应式，学习曲线较高 |
| Observation | ❌ | ✅ | 最简洁，Swift 5.9+ 推荐 |

### 3.3 ViewModel 职责边界

ViewModel 应该做什么、不该做什么：

| ✅ 应该做 | ❌ 不应该做 |
|----------|-----------|
| 管理视图状态 | 导入 SwiftUI（不应感知 UI 框架） |
| 调用 Repository/Service | 直接操作 UI 控件 |
| 数据转换和格式化 | 持有 View 的引用 |
| 处理用户交互逻辑 | 执行导航跳转 |
| 错误处理和状态切换 | 包含异步 UI 动画逻辑 |

### 3.4 SwiftUI 天然适配 MVVM

SwiftUI 的 `@Observable` 宏让 MVVM 的实现极其简洁：

```swift
import Observation

@Observable
final class BookListViewModel {
    private(set) var books: [Book] = []
    private(set) var isLoading = false
    private(set) var errorMessage: String?

    private let repository: BookRepositoryProtocol

    init(repository: BookRepositoryProtocol = BookRepository()) {
        self.repository = repository
    }

    @MainActor
    func loadBooks() async {
        isLoading = true
        errorMessage = nil
        do {
            books = try await repository.fetchBooks()
        } catch {
            errorMessage = error.localizedDescription
        }
        isLoading = false
    }

    @MainActor
    func deleteBook(at indexSet: IndexSet) async {
        for index in indexSet {
            let book = books[index]
            do {
                try await repository.deleteBook(book)
                books.remove(at: index)
            } catch {
                errorMessage = error.localizedDescription
            }
        }
    }
}

struct BookListView: View {
    @State private var viewModel = BookListViewModel()

    var body: some View {
        Group {
            if viewModel.isLoading {
                ProgressView("加载中...")
            } else if let error = viewModel.errorMessage {
                ErrorView(message: error) {
                    Task { await viewModel.loadBooks() }
                }
            } else {
                List {
                    ForEach(viewModel.books) { book in
                        BookRowView(book: book)
                    }
                    .onDelete { indexSet in
                        Task { await viewModel.deleteBook(at: indexSet) }
                    }
                }
            }
        }
        .task {
            await viewModel.loadBooks()
        }
    }
}
```

> 💡 注意 ViewModel 使用 `@Observable` 而非 `ObservableObject`。`@Observable` 是 Swift 5.9 引入的更高效观察机制，无需手动标记 `@Published`，性能更好。

### 3.5 完整代码示例：可测试的 MVVM

```swift
protocol BookRepositoryProtocol: Sendable {
    func fetchBooks() async throws -> [Book]
    func deleteBook(_ book: Book) async throws
}

struct Book: Identifiable, Sendable {
    let id: String
    var title: String
    var author: String
    var coverURL: String?
}

final class BookRepository: BookRepositoryProtocol {
    private let apiClient: APIClientProtocol

    init(apiClient: APIClientProtocol = APIClient()) {
        self.apiClient = apiClient
    }

    func fetchBooks() async throws -> [Book] {
        try await apiClient.request(endpoint: .books)
    }

    func deleteBook(_ book: Book) async throws {
        try await apiClient.request(endpoint: .deleteBook(book.id))
    }
}

import Testing
```

## 4. MVP（Model-View-Presenter）

### 4.1 与 MVVM 的区别

MVP 和 MVVM 长得很像，核心区别在于 Presenter 和 ViewModel 的通信方式：

| 对比项 | MVVM | MVP |
|--------|------|-----|
| 通信方式 | 数据绑定（自动同步） | 方法调用（手动同步） |
| View 感知 ViewModel | 不感知（单向依赖） | 感知 Presenter 协议 |
| 测试友好度 | 高（纯状态验证） | 更高（方法调用可 Mock） |
| SwiftUI 适配 | 天然适配 | 不适配（需要额外适配层） |

> 💡 生活类比：MVVM 像自动挡汽车——踩油门就走，不需要手动换挡；MVP 像手动挡——每次换挡都要自己操作，但控制更精确。

### 4.2 Presenter 的同步特性

Presenter 通过协议定义 View 接口，所有 UI 更新都是显式的方法调用：

```swift
protocol UserDetailViewProtocol: AnyObject {
    func showUserName(_ name: String)
    func showUserAvatar(url: URL)
    func showLoading()
    func hideLoading()
    func showError(message: String)
}

final class UserDetailPresenter {
    private weak var view: UserDetailViewProtocol?
    private let userService: UserServiceProtocol

    init(view: UserDetailViewProtocol, userService: UserServiceProtocol) {
        self.view = view
        self.userService = userService
    }

    func loadUser(id: String) {
        view?.showLoading()
        Task { [weak self] in
            do {
                let user = try await self?.userService.fetchUser(id: id)
                self?.view?.showUserName(user?.name ?? "")
                if let url = user?.avatarURL, let avatarURL = URL(string: url) {
                    self?.view?.showUserAvatar(url: avatarURL)
                }
            } catch {
                self?.view?.showError(message: error.localizedDescription)
            }
            self?.view?.hideLoading()
        }
    }
}
```

### 4.3 适用场景

| 场景 | 是否推荐 MVP | 原因 |
|------|-------------|------|
| UIKit 老项目重构 | ✅ 推荐 | 接口明确，迁移成本低 |
| SwiftUI 新项目 | ❌ 不推荐 | 协议驱动与声明式 UI 理念冲突 |
| 需要精确控制 UI 更新时机 | ✅ 推荐 | 显式调用，时机完全可控 |
| 团队对响应式不熟悉 | ✅ 推荐 | 同步调用更直观 |

## 5. VIPER（View-Interactor-Presenter-Entity-Router）

### 5.1 五层架构

VIPER 将职责拆分到极致，每个模块由五个层组成：

| 层 | 职责 | 生活类比 | 文件数 |
|---|------|---------|-------|
| **View** | 展示界面，转发用户操作 | 前台接待员 | 1 |
| **Interactor** | 业务逻辑，数据操作 | 后厨厨师 | 1 |
| **Presenter** | 协调 View 和 Interactor | 传菜员 | 1 |
| **Entity** | 纯数据模型 | 食材 | 1 |
| **Router** | 导航和模块间通信 | 餐厅领位员 | 1 |

一个典型的 VIPER 模块文件结构：

```
Login/
├── LoginView.swift
├── LoginPresenter.swift
├── LoginInteractor.swift
├── LoginEntity.swift
├── LoginRouter.swift
└── Protocols/
    ├── LoginViewProtocol.swift
    ├── LoginPresenterProtocol.swift
    ├── LoginInteractorProtocol.swift
    └── LoginRouterProtocol.swift
```

### 5.2 模块化优势

VIPER 最大的优势是**强模块化**——每个功能模块完全独立，模块间通过协议通信：

```swift
protocol LoginPresenterProtocol: AnyObject {
    var view: LoginViewProtocol? { get set }
    var interactor: LoginInteractorProtocol? { get set }
    var router: LoginRouterProtocol? { get set }

    func viewDidLoad()
    func didTapLogin(username: String, password: String)
}

protocol LoginInteractorProtocol: AnyObject {
    var presenter: LoginInteractorOutputProtocol? { get set }
    func login(username: String, password: String)
}

protocol LoginInteractorOutputProtocol: AnyObject {
    func loginSuccess(user: UserEntity)
    func loginFailure(error: Error)
}

protocol LoginViewProtocol: AnyObject {
    var presenter: LoginPresenterProtocol? { get set }
    func showLoading()
    func hideLoading()
    func showError(message: String)
}

protocol LoginRouterProtocol: AnyObject {
    func navigateToHome(with user: UserEntity)
}
```

### 5.3 复杂度代价

VIPER 的缺点同样明显：

| 代价 | 说明 |
|------|------|
| 文件数量爆炸 | 一个简单登录功能需要 9 个文件 |
| 协议冗余 | 大量只有一两个方法的协议 |
| 学习曲线陡峭 | 新人需要理解五层交互关系 |
| 简单功能过度设计 | 一个设置页面也要五层拆分 |

> ⚠️ VIPER 适合大型团队协作的复杂项目。如果你的项目只有两三个人开发，VIPER 的协议层会让开发速度降低 30% 以上。**不要用大炮打蚊子。**

### 5.4 SwiftUI 中的变体

在 SwiftUI 中，VIPER 的 View 和 Router 可以大幅简化：

| VIPER 层 | UIKit 实现 | SwiftUI 变体 |
|----------|-----------|-------------|
| View | UIViewController | SwiftUI View |
| Router | UINavigationController 包装 | NavigationLink / .navigationDestination |
| Presenter | 协议 + 弱引用 | @Observable 类 |
| Interactor | 协议 + 异步回调 | async/await Service |
| Entity | struct | struct（不变） |

## 6. Clean Architecture（整洁架构）

### 6.1 三层结构

Clean Architecture 由 Robert C. Martin（Uncle Bob）提出，核心思想是**依赖规则**——外层依赖内层，内层完全不知道外层的存在：

| 层 | 职责 | 包含内容 | 生活类比 |
|---|------|---------|---------|
| **领域层（Domain）** | 核心业务规则 | Entity、Use Case | 法律条文 |
| **数据层（Data）** | 数据获取和持久化 | Repository 实现、API、DB | 执法机构 |
| **展示层（Presentation）** | UI 和状态管理 | View、ViewModel | 法庭庭审 |

```
┌─────────────────────────────────┐
│        Presentation Layer       │  ← ViewModel, View
│  ┌───────────────────────────┐  │
│  │        Domain Layer       │  │  ← UseCase, Entity
│  │  ┌─────────────────────┐  │  │
│  │  │     Core Business   │  │  │  ← 最内层，零外部依赖
│  │  └─────────────────────┘  │  │
│  └───────────────────────────┘  │
│  ┌───────────────────────────┐  │
│  │         Data Layer        │  │  ← RepositoryImpl, API, CoreData
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

### 6.2 依赖规则

依赖规则是 Clean Architecture 的灵魂：

```swift
// Domain Layer — 零外部依赖，纯 Swift
protocol BookRepository {
    func fetchBooks() async throws -> [Book]
    func saveBook(_ book: Book) async throws
}

struct Book: Identifiable, Sendable {
    let id: String
    var title: String
    var isRead: Bool
}

struct FetchBooksUseCase: Sendable {
    private let repository: BookRepository

    init(repository: BookRepository) {
        self.repository = repository
    }

    func execute() async throws -> [Book] {
        try await repository.fetchBooks()
    }
}

// Data Layer — 依赖 Domain 层的协议
final class BookRepositoryImpl: BookRepository {
    private let apiClient: APIClient
    private let localStore: LocalStore

    init(apiClient: APIClient, localStore: LocalStore) {
        self.apiClient = apiClient
        self.localStore = localStore
    }

    func fetchBooks() async throws -> [Book] {
        do {
            let books = try await apiClient.fetchBooks()
            try await localStore.saveBooks(books)
            return books
        } catch {
            return try await localStore.loadBooks()
        }
    }

    func saveBook(_ book: Book) async throws {
        try await apiClient.saveBook(book)
        try await localStore.saveBooks([book])
    }
}
```

### 6.3 与 MVVM 的结合

Clean Architecture 通常与 MVVM 结合使用——Domain 层提供 Use Case，Presentation 层用 MVVM 组织：

| 层 | MVVM 对应 | 职责 |
|---|----------|------|
| Domain | — | Use Case + Entity + Repository 协议 |
| Data | — | Repository 实现 + API + 数据库 |
| Presentation | ViewModel | 调用 Use Case，管理 UI 状态 |
| Presentation | View | 绑定 ViewModel，渲染界面 |

> 💡 Clean Architecture + MVVM 是目前中大型 iOS 项目最流行的组合。Domain 层保证业务逻辑的纯粹性，MVVM 保证 UI 层的简洁性，两者互补。

## 7. TCA（The Composable Architecture）

### 7.1 Point-Free 出品

TCA 由 Point-Free 团队开源，是一套为 SwiftUI 设计的状态管理和架构框架。它的核心理念来自 Redux：**单一数据源 + 纯函数 Reducer + 副作用 Effect**。

| 概念 | 职责 | 生活类比 |
|------|------|---------|
| **State** | 模块的完整状态快照 | 银行账户余额 |
| **Action** | 描述发生了什么事 | 取款/存款操作单 |
| **Reducer** | 纯函数，根据 Action 计算新 State | 银行柜员，按操作单更新余额 |
| **Effect** | 副作用（网络请求等） | 银行间转账（需要外部系统） |
| **Store** | 持有 State，分发 Action | 银行系统本身 |

### 7.2 Reducer/Effect/Store

```swift
import ComposableArchitecture

@Reducer
struct BookListFeature {
    @ObservableState
    struct State: Equatable {
        var books: IdentifiedArrayOf<Book> = []
        var isLoading = false
        var errorMessage: String?
    }

    enum Action {
        case onAppear
        case booksLoaded([Book])
        case loadFailed(Error)
        case deleteBook(id: String)
        case bookDeleted(id: String)
    }

    @Dependency(\.bookClient) var bookClient

    var body: some ReducerOf<Self> {
        Reduce { state, action in
            switch action {
            case .onAppear:
                state.isLoading = true
                return .run { send in
                    do {
                        let books = try await bookClient.fetchBooks()
                        await send(.booksLoaded(books))
                    } catch {
                        await send(.loadFailed(error))
                    }
                }

            case let .booksLoaded(books):
                state.isLoading = false
                state.books = IdentifiedArray(uniqueElements: books)
                return .none

            case let .loadFailed(error):
                state.isLoading = false
                state.errorMessage = error.localizedDescription
                return .none

            case let .deleteBook(id):
                return .run { send in
                    try await bookClient.deleteBook(id)
                    await send(.bookDeleted(id: id))
                }

            case let .bookDeleted(id):
                state.books.remove(id: id)
                return .none
            }
        }
    }
}

struct BookClient {
    var fetchBooks: @Sendable () async throws -> [Book]
    var deleteBook: @Sendable (String) async throws -> Void
}

extension BookClient: DependencyKey {
    static let liveValue = BookClient(
        fetchBooks: { try await APIClient.shared.fetchBooks() },
        deleteBook: { id in try await APIClient.shared.deleteBook(id: id) }
    )
    static let testValue = BookClient(
        fetchBooks: { [] },
        deleteBook: { _ in }
    )
}

extension DependencyValues {
    var bookClient: BookClient {
        get { self[BookClient.self] }
        set { self[BookClient.self] = newValue }
    }
}
```

### 7.3 SwiftUI 集成

```swift
struct BookListView: View {

    var body: some View {
        Group {
            if store.isLoading {
                ProgressView("加载中...")

                    }
                }
            }
        }
        .onAppear {
            store.send(.onAppear)
        }
    }
```

### 7.4 适用场景与争议

| ✅ 适合 TCA | ❌ 不适合 TCA |
|------------|-------------|
| 中大型 SwiftUI 项目 | 小型原型项目 |
| 需要严格状态管理 | 团队不熟悉函数式编程 |
| 复杂的副作用链 | 追求极致开发速度 |
| 需要高覆盖率单元测试 | 简单 CRUD 应用 |

| 争议点 | 支持方 | 反对方 |
|--------|--------|--------|
| 模板代码 | "显式优于隐式" | "太多样板代码" |
| 学习曲线 | "一次学习，终身受益" | "新人上手太慢" |
| 性能 | "Reducer 是纯函数，可优化" | "大量值类型拷贝" |
| 框架锁定 | "TCA 是标准，值得锁定" | "被第三方框架绑架" |

> ⚠️ TCA 是一把双刃剑。它为复杂项目提供了强大的状态管理能力，但也引入了显著的学习成本和模板代码。**在决定采用之前，建议团队先用一个小模块试水。**

### 8.2 决策树

根据项目特征快速选择架构：

```
你的项目是什么？
│
├─ SwiftUI 新项目
│   ├─ 项目复杂度低（< 10 个页面）
│   │   └─ → MVVM（简单直接）
│   ├─ 项目复杂度中（10-30 个页面）
│   │   ├─ 团队 < 3 人 → MVVM
│   │   └─ 团队 ≥ 3 人 → Clean + MVVM
│   └─ 项目复杂度高（> 30 个页面）
│       ├─ 需要严格状态管理 → TCA
│       └─ 需要高可测试性 → Clean + MVVM
│
├─ UIKit 老项目
│   ├─ 当前是 MVC，想渐进重构 → MVVM（逐步迁移）
│   ├─ 需要精确控制 UI 更新 → MVP
│   └─ 大型项目模块化改造 → VIPER
│
└─ 混合项目（UIKit + SwiftUI）
    ├─ 以 UIKit 为主 → MVVM + Coordinator
    └─ 以 SwiftUI 为主 → Clean + MVVM
```

### 8.3 常见选型误区

| 误区 | 正确理解 |
|------|---------|
| "架构越复杂越好" | 架构复杂度应匹配项目复杂度，过度设计比没有架构更糟 |
| "一个项目只能用一种架构" | 不同模块可以用不同架构，核心模块用 Clean，简单页面用 MVVM |
| "SwiftUI 必须用 TCA" | MVVM 在大多数 SwiftUI 项目中已经足够 |
| "老项目必须全面重构" | 渐进式迁移优于推翻重来，先从新模块开始 |
| "架构选型是一锤子买卖" | 架构可以演进，从简单开始，随需求升级 |

> 💡 **架构选型的黄金法则**：选择你团队能驾驭的最简架构。一个团队用不好的"完美架构"，不如一个团队能熟练使用的"简单架构"。

## 本章小结

| 架构模式 | 一句话总结 | 最佳场景 | SwiftUI 适配 |
|---------|-----------|---------|-------------|
| MVC | Apple 经典，简单但易膨胀 | 小型 UIKit 项目 | ⭐⭐ |
| MVVM | 当前主流，简洁高效 | 中小型 SwiftUI 项目 | ⭐⭐⭐⭐⭐ |
| MVP | 显式调用，测试友好 | UIKit 项目，需精确控制 | ⭐⭐ |
| VIPER | 极致拆分，强模块化 | 大型团队复杂项目 | ⭐⭐ |
| Clean+MVVM | 分层清晰，业务纯粹 | 中大型项目，高测试要求 | ⭐⭐⭐⭐ |
| TCA | 状态管理严格，可组合 | 复杂 SwiftUI 项目 | ⭐⭐⭐⭐⭐ |

**记住**：没有最好的架构，只有最适合的架构。架构是手段，交付价值才是目的。
