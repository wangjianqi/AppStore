# 日志与可观测性

> 🎯 **本章目标**：理解可观测性在 App 开发中的核心价值，掌握 OSLog 统一日志系统，学会日志分级与过滤，了解远程日志上报与崩溃监控，建立用户行为埋点架构。

---

## 可观测性概述

### 什么是可观测性

可观测性（Observability）是指通过系统外部输出推断其内部状态的能力。在软件工程中，可观测性由三大支柱构成：

- **Logging（日志）**：记录离散事件，回答"发生了什么"
- **Metrics（指标）**：聚合数值数据，回答"发生了多少次、多快、多大"
- **Tracing（追踪）**：串联请求链路，回答"问题出在哪里"

三大支柱各有侧重，协同工作：日志提供细节，指标提供趋势，追踪提供关联。

### 为什么 App 需要可观测性

开发阶段可以通过断点、LLDB 调试来排查问题，但 App 上线后你面对的是：

- **线上问题排查**：用户反馈"App 卡了"，你无法复现，需要日志还原现场
- **性能监控**：启动耗时从 1.2 秒涨到 2.5 秒，需要指标数据发现趋势
- **用户行为分析**：注册转化率只有 30%，需要埋点数据定位流失环节

没有可观测性的 App 就像一个没有仪表盘的汽车——你能开，但不知道油量、速度和发动机状态。

### 生活类比：App 的"黑匣子"

飞机上的黑匣子记录飞行过程中的关键数据，事故发生后可以还原完整经过。可观测性就是 App 的黑匣子：正常运行时默默记录，出问题时帮你还原现场、定位根因。

### 可观测性 vs 调试

| 维度 | 调试（Debugging） | 可观测性（Observability） |
|------|-------------------|--------------------------|
| 时机 | 开发阶段 | 运行全生命周期 |
| 环境 | 本地可控 | 线上不可控 |
| 方式 | 断点、单步执行 | 日志、指标、追踪 |
| 数据 | 实时查看变量 | 事后分析记录 |
| 覆盖 | 单次运行 | 全量用户 |

> 💡 **提示**：可观测性不是调试的替代品，而是调试的延伸。开发阶段用调试，上线后靠可观测性。

## OSLog 统一日志系统

### OSLog 基础

`OSLog` 是 Apple 从 iOS 14 开始推荐的统一日志框架，取代了 `print` 和 `NSLog`。它基于 `Logger` 结构体，支持子系统（subsystem）和分类（category）组织日志。

```swift
import os

let logger = Logger(subsystem: "com.example.myapp", category: "network")
logger.info("请求开始: \(url)")
```

### 五个日志级别详解

| 级别 | 方法 | 用途 | 是否持久化 | 性能影响 |
|------|------|------|-----------|---------|
| Debug | `logger.debug()` | 开发调试信息 | 否（仅内存） | 极低 |
| Info | `logger.info()` | 有用的运行信息 | 是 | 低 |
| Notice（默认） | `logger.notice()` | 默认级别，重要事件 | 是 | 低 |
| Error | `logger.error()` | 功能性错误 | 是 | 中 |
| Fault | `logger.fault()` | 严重系统错误 | 是 | 中 |

```swift
let logger = Logger(subsystem: "com.example.myapp", category: "auth")

logger.debug("Token 刷新中...")
logger.info("用户登录成功, uid: \(uid)")
logger.notice("配置文件已更新")
logger.error("网络请求失败: \(error)")
logger.fault("数据库损坏, 无法读取用户数据")
```

> ⚠️ **警告**：`debug` 级别日志在 Release 构建中不会持久化到磁盘，不要用它记录排查线上问题所需的关键信息。

### 自定义子系统与分类

子系统通常使用反向域名格式，分类按功能模块划分：

```swift
enum LogCategory {
    static let network = "network"
    static let database = "database"
    static let ui = "ui"
    static let auth = "auth"
}

enum AppLog {
    static let subsystem = "com.example.myapp"

    static let network = Logger(subsystem: subsystem, category: LogCategory.network)
    static let database = Logger(subsystem: subsystem, category: LogCategory.database)
    static let ui = Logger(subsystem: subsystem, category: LogCategory.ui)
    static let auth = Logger(subsystem: subsystem, category: LogCategory.auth)
}
```

使用时直接调用：

```swift
AppLog.network.info("请求成功: \(response)")
AppLog.database.error("查询失败: \(error)")
```

### 日志格式化最佳实践

结构化日志让搜索和过滤更高效：

```swift
logger.info("API响应", metadata: [
    "endpoint": "/api/users",
    "statusCode": "\(statusCode)",
    "duration": "\(duration)s"
])
```

OSLog 的字符串插值本身就是结构化的，Apple 建议直接使用插值：

```swift
logger.info("API 请求完成: endpoint=\(endpoint), status=\(statusCode), duration=\(duration)s")
```

### Console.app 查看日志

macOS 自带的 Console.app 是查看 OSLog 的官方工具：

1. 连接 iPhone 到 Mac
2. 打开 Console.app，选择设备
3. 在搜索栏输入 `subsystem:com.example.myapp` 过滤
4. 点击"Start"开始实时查看

也可以用命令行工具：

```bash
log stream --predicate 'subsystem == "com.example.myapp"' --level debug
```

### SwiftUI 中封装日志工具

在 SwiftUI 项目中，可以结合环境值封装日志工具：

```swift
import os

final class LogManager: ObservableObject {
    static let shared = LogManager()

    private let networkLogger = Logger(subsystem: "com.example.myapp", category: "network")
    private let uiLogger = Logger(subsystem: "com.example.myapp", category: "ui")
    private let dataLogger = Logger(subsystem: "com.example.myapp", category: "data")

    func logNetwork(_ message: String) {
        networkLogger.info("\(message)")
    }

    func logUI(_ message: String) {
        uiLogger.debug("\(message)")
    }

    func logData(_ message: String) {
        dataLogger.info("\(message)")
    }

    func logError(_ message: String, category: String = "general") {
        Logger(subsystem: "com.example.myapp", category: category).error("\(message)")
    }
}
```

在 App 入口注入：

```swift
@main
struct MyApp: App {
    @StateObject private var logManager = LogManager.shared

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environmentObject(logManager)
        }
    }
}
```

## 日志分级与过滤

### 开发环境 vs 生产环境的日志策略

不同环境对日志的需求完全不同：

| 维度 | 开发环境 | 生产环境 |
|------|---------|---------|
| 默认级别 | debug | info |
| 输出目标 | Console + Xcode | 磁盘 + 远程 |
| 日志量 | 多 | 少而精 |
| 敏感信息 | 可见 | 必须脱敏 |
| 性能要求 | 宽松 | 严格 |

```swift
enum Environment {
    case debug
    case release
}

struct LogConfig {
    static var minLevel: OSLogEntryLog.Level {
        #if DEBUG
        return .debug
        #else
        return .info
        #endif
    }
}
```

### 动态日志级别调整

OSLog 支持在运行时动态调整日志级别，无需重新编译。通过 `log` 命令行工具或 Console.app 可以修改：

```bash
log config --mode "level:debug" --subsystem com.example.myapp
```

在代码中也可以基于远程配置动态调整：

```swift
final class DynamicLogLevel {
    static func updateLevel(from config: RemoteConfig) {
        let level = config.logLevel
        os_log("日志级别更新为: %{public}@", log: .default, level.rawValue)
    }
}
```

### 日志隐私保护

OSLog 提供了 `private` 和 `public` 标记来控制日志中的隐私信息：

```swift
let logger = Logger(subsystem: "com.example.myapp", category: "auth")

logger.info("用户 \(userId, privacy: .public) 登录成功")
logger.info("密码 \(password, privacy: .private(mask: .hash)) 验证通过")
logger.info("手机号 \(phone, privacy: .private(mask: .none)) 已绑定")
```

隐私标记的行为：

| 标记 | Debug 构建 | Release 构建 |
|------|-----------|-------------|
| `.public` | 原文显示 | 原文显示 |
| `.private` | 原文显示 | 显示 `<private>` |
| `.private(mask: .hash)` | 原文显示 | 显示哈希值 |
| `.private(mask: .none)` | 原文显示 | 完全隐藏 |

> ⚠️ **警告**：默认情况下 OSLog 在 Release 构建中会将插值变量视为 private。如果需要显示，必须显式标记 `.public`。

### 敏感信息脱敏

除了 OSLog 的隐私标记，还需要在日志工具层做脱敏处理：

```swift
enum DataMask {
    static func phone(_ phone: String) -> String {
        guard phone.count >= 11 else { return "***" }
        let start = phone.index(phone.startIndex, offsetBy: 3)
        let end = phone.index(phone.startIndex, offsetBy: 7)
        return phone.replacingCharacters(in: start..<end, with: "****")
    }

    static func email(_ email: String) -> String {
        let parts = email.split(separator: "@")
        guard parts.count == 2 else { return "***" }
        return "***@\(parts[1])"
    }

    static func idCard(_ id: String) -> String {
        guard id.count >= 18 else { return "***" }
        let start = id.index(id.startIndex, offsetBy: 4)
        let end = id.index(id.startIndex, offsetBy: 14)
        return id.replacingCharacters(in: start..<end, with: "**********")
    }
}
```

### 日志性能优化

日志虽好，但滥用会影响性能。以下是优化策略：

```swift
final class PerformanceLogger {
    private let logger = Logger(subsystem: "com.example.myapp", category: "perf")

    func logExpensiveOperation() {
        logger.debug("开始耗时操作")

        let start = CFAbsoluteTimeGetCurrent()
        performExpensiveOperation()
        let duration = CFAbsoluteTimeGetCurrent() - start

        logger.info("耗时操作完成: \(String(format: "%.2f", duration))s")
    }
}
```

关键优化原则：

- 避免在 `debug` 级别日志中做字符串拼接，OSLog 的插值在 Release 下会跳过未持久化的日志
- 不要在日志中序列化大对象
- 批量操作只记录汇总，不逐条记录
- 使用 `os_signpost` 记录性能区间而非手动计时

## 远程日志上报

### 为什么需要远程日志

用户设备上的问题你无法直接查看本地日志。远程日志上报让你能够：

- 收集线上崩溃前的完整日志上下文
- 分析特定用户的问题复现路径
- 监控全量用户的错误率和性能指标

### 日志上报架构设计

一个完整的远程日志上报系统包含以下模块：

```swift
final class RemoteLogReporter {
    private let storage: LogStorage
    private let uploader: LogUploader
    private let compressor: LogCompressor

    struct LogEntry: Codable {
        let timestamp: Date
        let level: String
        let subsystem: String
        let category: String
        let message: String
        let deviceInfo: DeviceInfo
    }

    struct DeviceInfo: Codable {
        let osVersion: String
        let appVersion: String
        let deviceModel: String
    }

    func report(_ entry: LogEntry) {
        storage.append(entry)

        if storage.count >= batchSize {
            flush()
        }
    }

    func flush() {
        let entries = storage.readBatch(count: batchSize)
        guard !entries.isEmpty else { return }

        let compressed = compressor.compress(entries)

        uploader.upload(compressed) { [weak self] success in
            if success {
                self?.storage.removeBatch(count: entries.count)
            }
        }
    }

    private let batchSize = 50
}
```

### 批量上报与压缩

逐条上报会产生大量网络请求，批量上报 + 压缩是标准做法：

```swift
final class LogCompressor {
    func compress(_ entries: [RemoteLogReporter.LogEntry]) -> Data {
        let encoder = JSONEncoder()
        encoder.dateEncodingStrategy = .iso8601
        guard let data = try? encoder.encode(entries) else {
            return Data()
        }
        return (data as NSData).compressed(using: .zlib) as Data
    }
}
```

### 离线日志缓存与重传

网络不可用时，日志需要缓存到本地，网络恢复后重传：

```swift
final class OfflineLogCache {
    private let fileManager = FileManager.default
    private let cacheDirectory: URL

    init() {
        let caches = fileManager.urls(for: .cachesDirectory, in: .userDomainMask)[0]
        cacheDirectory = caches.appendingPathComponent("remote_logs")
        try? fileManager.createDirectory(at: cacheDirectory, withIntermediateDirectories: true)
    }

    func save(_ data: Data) {
        let filename = "\(Int(Date().timeIntervalSince1970)).log"
        let url = cacheDirectory.appendingPathComponent(filename)
        try? data.write(to: url)
    }

    func pendingFiles() -> [URL] {
        let files = try? fileManager.contentsOfDirectory(
            at: cacheDirectory,
            includingPropertiesForKeys: nil
        )
        return (files ?? []).sorted { $0.lastPathComponent < $1.lastPathComponent }
    }

    func remove(_ url: URL) {
        try? fileManager.removeItem(at: url)
    }
}
```

### 隐私合规：日志中不能包含的信息

根据《个人信息保护法》和 App Store 审核要求，日志中严禁包含：

- 用户密码（明文或密文）
- 身份证号完整内容
- 银行卡号完整内容
- 精确地理位置（GPS 坐标）
- 设备唯一标识符（IDFA/IDFV 未经授权）
- 生物识别数据
- 通讯录内容

> ⚠️ **警告**：日志泄露个人信息可能导致 App 被下架，甚至面临法律风险。上线前务必做日志审计。

## 崩溃监控

### Mach 异常 vs Signal vs NSException

iOS 崩溃捕获有三个层次：

| 类型 | 层级 | 典型场景 | 捕获方式 |
|------|------|---------|---------|
| Mach 异常 | 内核层 | 空指针访问、栈溢出 | `mach_exception_handler` |
| Signal | Unix 层 | SIGSEGV、SIGABRT | `signal()` 注册处理函数 |
| NSException | Objective-C 层 | 未捕获异常、数组越界 | `NSUncaughtExceptionHandler` |

```swift
final class CrashHandler {
    static func install() {
        NSSetUncaughtExceptionHandler { exception in
            let crashInfo = """
            名称: \(exception.name.rawValue)
            原因: \(exception.reason ?? "未知")
            堆栈: \(exception.callStackSymbols.joined(separator: "\n"))
            """
            CrashStorage.save(crashInfo)
        }

        signal(SIGABRT) { _ in
            CrashStorage.save("SIGABRT 信号触发")
            exit(SIGABRT.rawValue)
        }

        signal(SIGSEGV) { _ in
            CrashStorage.save("SIGSEGV 信号触发")
            exit(SIGSEGV.rawValue)
        }
    }
}
```

> 💡 **提示**：实际项目中不建议自己写崩溃捕获，优先使用成熟的第三方库（如 PLCrashReporter、Crashlytics），它们处理了大量边界情况。

### 崩溃堆栈符号化

崩溃日志中的地址需要符号化（Symbolication）才能看到函数名和行号：

- **自动符号化**：Firebase Crashlytics 上传 dSYM 后自动完成
- **手动符号化**：使用 `atos` 命令行工具

```bash
atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp -l 0x100000000 0x100003a50
```

确保 dSYM 上传的 Xcode 配置：

1. Build Settings → Debug Information Format 设为 `DWARF with dSYM File`
2. Build Phases 添加 Firebase 的 `upload-symbols` 脚本

```bash
"${PODS_ROOT}/FirebaseCrashlytics/upload-symbols" -gsp "${PROJECT_DIR}/MyApp/GoogleService-Info.plist" -p ios "${DWARF_DSYM_FOLDER_PATH}/${DWARF_DSYM_FILE_NAME}"
```

### crash-free rate 监控

Crash-free rate（无崩溃率）是衡量 App 稳定性的核心指标：

- **≥ 99.5%**：优秀
- **99.0% ~ 99.5%**：良好
- **< 99.0%**：需要紧急修复

```swift
struct CrashFreeRate {
    static func calculate(totalSessions: Int, crashedSessions: Int) -> Double {
        guard totalSessions > 0 else { return 100.0 }
        return (Double(totalSessions - crashedSessions) / Double(totalSessions)) * 100
    }
}
```

Firebase Console 的"Crash-free users"和"Crash-free sessions"面板会自动展示此指标。

### OOM 崩溃检测

OOM（Out of Memory）崩溃不会产生常规崩溃日志，因为系统直接杀死进程。检测方式：

```swift
import MetricKit

final class OOMMonitor: ObservableObject {
    func checkPreviousLaunchOOM() {
        MXMetricManager.shared.subscribe(self)
    }
}

extension OOMMonitor: MXMetricManagerSubscriber {
    func didReceive(_ payloads: [MXDiagnosticPayload]) {
        for payload in payloads {
            if let crashDiagnostics = payload.crashDiagnostics {
                for diagnostic in crashDiagnostics {
                    if diagnostic.exceptionType?.contains("EXC_RESOURCE") == true {
                        handleOOM(diagnostic: diagnostic)
                    }
                }
            }
        }
    }

    private func handleOOM(diagnostic: MXCrashDiagnostic) {
        let memoryUsage = diagnostic.virtualMemoryRegionInfo
        let terminationReason = diagnostic.terminationReasonDescription

        Logger(subsystem: "com.example.myapp", category: "oom")
            .fault("OOM 检测: memory=\(memoryUsage ?? "未知"), reason=\(terminationReason ?? "未知")")
    }
}
```

> 💡 **提示**：MetricKit 最多延迟 24 小时上报诊断数据，不适合实时监控。实时 OOM 检测需要对比 App 启动时上一次退出是否为异常终止。

## 用户行为埋点

### 埋点的价值：数据驱动决策

埋点（Event Tracking）是记录用户行为的关键手段：

- **产品决策**：功能使用率决定优先级
- **转化分析**：注册漏斗每一步的流失率
- **异常发现**：某按钮点击后崩溃率飙升
- **A/B 测试**：两种方案的转化率对比

没有埋点的 App 就像没有监控的网站——你不知道用户在做什么。

### 代码埋点 vs 无埋点

| 维度 | 代码埋点 | 无埋点（全埋点） |
|------|---------|-----------------|
| 原理 | 手动在代码中插入埋点 | SDK 自动采集所有交互事件 |
| 精确度 | 高，事件语义明确 | 低，只有"点击了某个 View" |
| 灵活性 | 高，可自定义属性 | 低，无法添加业务属性 |
| 开发成本 | 高，需要逐个添加 | 低，一次集成 |
| 数据量 | 小 | 大 |
| 适用场景 | 核心业务流程 | 探索性分析 |

> 💡 **提示**：推荐"核心路径代码埋点 + 其他交互无埋点"的混合方案，兼顾精确度和覆盖面。

### 埋点事件设计规范

好的埋点设计需要规范命名和属性：

```swift
enum AnalyticsEvent {
    case pageView(page: String)
    case buttonClick(page: String, button: String)
    case purchase(product: String, amount: Double, method: String)
    case search(keyword: String, resultCount: Int)
    case share(content: String, channel: String)

    var name: String {
        switch self {
        case .pageView: return "page_view"
        case .buttonClick: return "button_click"
        case .purchase: return "purchase"
        case .search: return "search"
        case .share: return "share"
        }
    }

    var parameters: [String: Any] {
        switch self {
        case .pageView(let page):
            return ["page_name": page]
        case .buttonClick(let page, let button):
            return ["page_name": page, "button_name": button]
        case .purchase(let product, let amount, let method):
            return ["product_id": product, "amount": amount, "payment_method": method]
        case .search(let keyword, let count):
            return ["keyword": DataMask.maskKeyword(keyword), "result_count": count]
        case .share(let content, let channel):
            return ["content_type": content, "share_channel": channel]
        }
    }
}
```

命名规范：

- 事件名使用 `snake_case`，如 `user_register_complete`
- 属性名使用 `snake_case`，如 `payment_method`
- 布尔值用 `is_` 前缀，如 `is_premium`
- 数值用 `_count`/`_amount` 后缀

### SwiftUI 中的埋点方案

SwiftUI 的声明式语法让埋点可以优雅地集成：

```swift
struct TrackableModifier: ViewModifier {
    let eventName: String
    let parameters: [String: Any]

    func body(content: Content) -> some View {
        content.onAppear {
            AnalyticsManager.shared.track(eventName, parameters: parameters)
        }
    }
}

extension View {
    func track(_ eventName: String, parameters: [String: Any] = [:]) -> some View {
        modifier(TrackableModifier(eventName: eventName, parameters: parameters))
    }
}
```

使用方式：

```swift
struct ProductDetailView: View {
    let product: Product

    var body: some View {
        VStack {
            ProductImageView(product: product)
            ProductInfoView(product: product)
            Button("购买") {
                AnalyticsManager.shared.track("purchase_tap", parameters: [
                    "product_id": product.id,
                    "product_price": product.price
                ])
                purchase()
            }
        }
        .track("page_view", parameters: ["page_name": "product_detail", "product_id": product.id])
    }
}
```

### 埋点数据上报架构

```swift
final class AnalyticsManager {
    static let shared = AnalyticsManager()

    private var providers: [AnalyticsProvider] = []
    private let queue = DispatchQueue(label: "analytics", qos: .utility)

    func register(_ provider: AnalyticsProvider) {
        providers.append(provider)
    }

    func track(_ event: String, parameters: [String: Any] = [:]) {
        queue.async {
            let enriched = self.enrich(parameters)
            for provider in self.providers {
                provider.track(event, parameters: enriched)
            }
        }
    }

    private func enrich(_ parameters: [String: Any]) -> [String: Any] {
        var result = parameters
        result["timestamp"] = Date().timeIntervalSince1970
        result["app_version"] = Bundle.main.appVersion
        result["os_version"] = UIDevice.current.systemVersion
        result["device_model"] = UIDevice.current.model
        return result
    }
}

protocol AnalyticsProvider {
    func track(_ event: String, parameters: [String: Any])
}
```
