# 78-Spec 驱动：编写完整项目 Spec

> 🎯 **本章目标**：学会用 Spec（规格说明书）驱动开发，掌握 PRD、技术方案、任务拆解和验收标准的编写方法，让你的上架项目从"想到哪写到哪"变成"有章可循"。

---

## 为什么上架项目更需要 Spec

很多人学 SwiftUI 的时候，打开 Xcode 就开始写代码，想到什么功能就加什么功能。这种方式做学习项目没问题，但做上架项目就会遇到大麻烦。

### 学习项目 vs 上架项目对比

| 对比维度 | 学习项目 | 上架项目 |
|---------|---------|---------|
| 功能数量 | 3-5 个 | 20-50 个 |
| 开发周期 | 1-3 天 | 1-3 个月 |
| 返工成本 | 低，重写就行 | 高，改一处动全身 |
| AI 辅助效果 | 随便问也能用 | 没有 Spec，AI 答非所问 |
| 代码质量 | 能跑就行 | 要过审核、要稳定 |

### Spec 带来的四大好处

**1. 帮你理清思路**

写 Spec 的过程就是思考的过程。当你把"这个 App 到底要做什么"写下来，很多模糊的想法会变清晰。

**2. 让 AI 更好地辅助你**

> 💡 **提示**：AI 最大的问题是"不知道你要什么"。一份清晰的 Spec 就像是给 AI 的"需求说明书"，它才能给出精准的代码。

**3. 减少返工**

> ⚠️ **警告**：没有 Spec 就开始写代码，就像没有图纸就盖房子。等你发现方向错了，推倒重来的代价是巨大的。

**4. 方便协作**

即使你是独立开发者，未来的你也是你的"协作者"。三个月后你回头看代码，Spec 能帮你快速回忆"当时为什么这么做"。

## 编写 PRD（产品需求文档）

> 🎯 **本节目标**：学会编写一份完整的 PRD，把"我想做一个 App"变成"这个 App 具体要做什么"。

PRD 是 Product Requirement Document 的缩写，翻译过来就是"产品需求文档"。简单说，它回答了一个问题：**这个 App 到底要做什么？**

### 项目概述

项目概述是 PRD 的"门面"，用最简洁的话说清楚项目是什么。

一个完整的项目概述包含四个要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| 项目名称 | App 的名字 | 「小账本」 |
| 一句话描述 | 用一句话说清楚这个 App 干什么 | 一款极简的个人记账工具，帮你轻松记录每一笔收支 |
| 目标用户 | 谁会用这个 App | 18-35 岁的年轻人，有记账需求但嫌传统记账 App 太复杂 |
| 核心价值 | 用户为什么要用你的 App | 3 秒完成记账，没有多余功能干扰 |

> 💡 **提示**：一句话描述要避免"大而全"，比如"一款全能的生活管理工具"就太模糊了。"极简记账"比"全能管理"更容易打动用户。

### 目标用户

了解你的用户，才能做出他们喜欢的产品。

#### 用户画像

用户画像是你理想用户的"虚拟人物"，包含：

```
姓名：小李
年龄：25 岁
职业：互联网公司产品经理
收入：月薪 12K
记账习惯：偶尔记，经常忘记
常用 App：微信、支付宝、小红书
痛点：记账 App 太复杂，打开就不想记
```

#### 使用场景

想象用户在什么场景下会打开你的 App：

| 场景 | 描述 | 需要的功能 |
|------|------|-----------|
| 买完早餐 | 刚付完钱，想快速记一笔 | 快速记账，3 秒完成 |
| 月底复盘 | 想看看这个月花了多少 | 月度统计、分类汇总 |
| 超预算提醒 | 某个分类花太多了 | 预算设置、超支提醒 |

#### 用户痛点

痛点就是用户的不满，你的 App 要解决这些不满：

- ❌ 传统记账 App 功能太多，学习成本高
- ❌ 记一笔账要填很多字段，太麻烦
- ❌ 统计图表看不懂，没有实际指导意义
- ✅ 我要做的：极简记账，3 秒记一笔，统计一目了然

### 功能需求

功能需求是 PRD 的核心，要按模块组织，并标明优先级。

#### 优先级说明

| 优先级 | 含义 | 说明 |
|--------|------|------|
| P0 | 必须有 | 没有这个功能，App 就没法用 |
| P1 | 应该有 | 有了体验更好，没有也能用 |
| P2 | 可以有 | 锦上添花，后续版本再加 |

#### 功能需求示例（记账 App）

**模块一：记账**

| 功能 | 优先级 | 描述 | 验收标准 |
|------|--------|------|---------|
| 快速记账 | P0 | 输入金额、选择分类、保存 | 从打开到保存 ≤ 3 步操作 |
| 分类选择 | P0 | 预设收支分类，支持自定义 | 至少 10 个预设分类 |
| 记录列表 | P0 | 按日期展示所有记录 | 支持按月查看 |
| 编辑/删除 | P1 | 修改或删除已有记录 | 滑动删除，点击编辑 |
| 搜索记录 | P1 | 按关键词搜索记录 | 支持按金额、分类搜索 |

**模块二：统计**

| 功能 | 优先级 | 描述 | 验收标准 |
|------|--------|------|---------|
| 月度汇总 | P0 | 展示当月收支总额 | 数据实时更新 |
| 分类占比 | P0 | 饼图展示各分类占比 | 点击分类查看明细 |
| 趋势图 | P1 | 折线图展示收支趋势 | 支持按周/月/年查看 |
| 预算管理 | P1 | 设置月度预算，超支提醒 | 超支时推送通知 |

**模块三：设置**

| 功能 | 优先级 | 描述 | 验收标准 |
|------|--------|------|---------|
| 货币设置 | P0 | 选择记账货币 | 支持 CNY/USD/EUR |
| 数据导出 | P1 | 导出 CSV 文件 | 包含所有记录字段 |
| iCloud 同步 | P2 | 多设备数据同步 | 换设备数据不丢失 |

> ⚠️ **警告**：新手常犯的错误是把所有功能都标为 P0。P0 太多意味着你什么都想做，结果什么都做不好。建议 P0 功能不超过 5 个。

### 非功能需求

非功能需求回答的是"App 要做到什么程度"，而不是"App 要做什么"。

| 类别 | 需求 | 具体指标 |
|------|------|---------|
| 性能 | 启动时间 | 冷启动 ≤ 2 秒 |
| 性能 | 页面加载 | 列表滑动无卡顿（60fps） |
| 性能 | 内存使用 | 峰值 ≤ 150MB |
| 兼容性 | iOS 版本 | iOS 16.0 及以上 |
| 兼容性 | 设备 | iPhone SE ~ iPhone 15 Pro Max |
| 兼容性 | 暗黑模式 | 完整支持 |
| 安全 | 数据存储 | 本地加密存储 |
| 安全 | 用户隐私 | 不收集任何个人数据 |

> 💡 **提示**：非功能需求看起来"不紧急"，但 App Store 审核会检查隐私政策、暗黑模式等。提前定义好，避免审核被拒。

### 约束与假设

#### 技术约束

| 约束 | 说明 |
|------|------|
| 开发语言 | Swift + SwiftUI |
| 最低版本 | iOS 16.0 |
| 后端服务 | 无，纯本地存储 |
| 第三方依赖 | 尽量少用，不超过 3 个 |

#### 时间约束

| 阶段 | 时间 | 产出 |
|------|------|------|
| Spec 编写 | 3 天 | PRD + 技术方案 |
| 核心功能开发 | 2 周 | P0 功能完成 |
| 完善功能 | 1 周 | P1 功能完成 |
| 测试与打磨 | 1 周 | Bug 修复、UI 优化 |
| 上架提交 | 3 天 | 截图、描述、提交审核 |

#### 假设条件

- 假设用户设备为 iPhone，暂不考虑 iPad 和 Mac
- 假设用户不需要多币种实时汇率转换
- 假设数据存储在本地，不需要服务端

> ⚠️ **警告**：假设条件要尽量明确。模糊的假设会导致后期需求变更，比如"用户可能需要多设备同步"——如果不确定，就把它列为 P2 功能，而不是假设"不需要"。

### PRD 模板

以下是一份完整的 PRD 模板，以记账 App 为例：

```markdown
# PRD：小账本

## 1. 项目概述
- **项目名称**：小账本
- **一句话描述**：一款极简的个人记账工具，3 秒完成记账

## 2. 目标用户
### 2.1 用户画像
```

## 编写技术方案

> 🎯 **本节目标**：学会编写技术方案，把"App 要做什么"变成"App 怎么实现"。

PRD 回答了"做什么"，技术方案回答"怎么做"。

### 技术选型

技术选型就是选择用什么工具来做。对于 iOS 上架项目，以下是常见选择：

#### 语言与框架

| 选项 | 推荐度 | 理由 |
|------|--------|------|
| Swift + SwiftUI | ⭐⭐⭐⭐⭐ | Apple 主推，开发效率高，适合新项目 |
| Swift + UIKit | ⭐⭐⭐ | 成熟稳定，但代码量大，学习曲线陡 |
| Objective-C | ⭐ | 除非维护老项目，否则不推荐 |
| React Native / Flutter | ⭐⭐ | 可以跨平台，但上架体验不如原生 |

> 💡 **提示**：如果你是新手，强烈推荐 Swift + SwiftUI。SwiftUI 代码量少、预览方便，而且 Apple 每年都在大力改进。

#### 第三方库选择

| 需求 | 推荐库 | 备选 | 说明 |
|------|--------|------|------|
| 图表 | Swift Charts | DGCharts | iOS 16+ 用 Swift Charts（原生） |
| 数据库 | SwiftData | CoreData | iOS 17+ 用 SwiftData（更现代） |
| 网络 | URLSession | Alamofire | 简单需求用 URLSession 就够 |
| 崩溃收集 | 无 | Firebase | 上架初期可不接 |

> ⚠️ **警告**：第三方库越少越好。每个库都是潜在的风险——作者不维护了、和新版 iOS 不兼容了、引入安全漏洞了。能用原生的就用原生的。

### 架构设计

#### MVVM 架构

MVVM 是 iOS 开发最常用的架构，把代码分成三层：

| 层 | 职责 | 类比 |
|----|------|------|
| Model | 数据和业务逻辑 | 蛋糕的配方和原料 |
| View | 界面展示 | 蛋糕的外观 |
| ViewModel | 连接 Model 和 View | 蛋糕师，按配方做蛋糕并摆盘 |

```
┌─────────┐     绑定（自动更新）     ┌────────────┐
│  View    │ ◄──────────────────── │  ViewModel  │
│ (SwiftUI)│                       │             │
│          │ ────── 用户操作 ──────►│             │
└─────────┘                       └──────┬───────┘
                                         │
                                    调用/更新
                                         │
                                         ▼
                                  ┌──────────────┐
                                  │    Model      │
                                  │ (数据+逻辑)   │
                                  └──────────────┘
```

#### 模块划分

以记账 App 为例：

```
小账本 App
├── 记账模块（Record）
│   ├── 快速记账页面
│   ├── 分类选择页面
│   └── 记录列表页面
├── 统计模块（Statistics）
│   ├── 月度汇总页面
│   ├── 分类占比页面
│   └── 趋势图页面
└── 设置模块（Settings）
    ├── 偏好设置页面
    ├── 数据管理页面
    └── 关于页面
```

#### 数据流向图

```
用户点击"保存"
    │
    ▼
View 发送动作给 ViewModel
    │
    ▼
ViewModel 调用 Model 保存数据
    │
    ▼
Model 写入 SwiftData 数据库
    │
    ▼
ViewModel 的 @Published 属性更新
    │
    ▼
SwiftUI 自动刷新 View
```

### 数据模型

数据模型是 App 的"骨架"，定义了你要存储什么数据。

#### 核心模型定义（记账 App）

```swift
import Foundation
import SwiftData

@Model
class Record {
    var id: UUID
    var amount: Double        // 金额
    var type: RecordType      // 收入/支出
    var category: String      // 分类
    var note: String          // 备注
    var date: Date            // 日期
    
    init(amount: Double, type: RecordType, category: String, note: String = "", date: Date = .now) {
        self.id = UUID()
        self.amount = amount
        self.type = type
        self.category = category
        self.note = note
        self.date = date
    }
}

enum RecordType: String, Codable {
    case expense = "支出"
    case income = "收入"
}
```

#### 模型关系

```
Record (记录)          Category (分类)
├── id: UUID          ├── id: UUID
├── amount: Double    ├── name: String
├── type: RecordType  ├── icon: String
├── category: String ─┤── type: RecordType
├── note: String      └── isDefault: Bool
└── date: Date

Budget (预算)
├── id: UUID
├── category: String ──► 关联 Category
├── amount: Double
└── month: Date
```

> 💡 **提示**：先定义核心模型，再定义关联模型。核心模型是 App 必须有的（如 Record），关联模型是锦上添花的（如 Budget）。

### 接口定义

如果你的 App 需要和服务器通信，就要定义 API 接口。纯本地 App 可以跳过这一节。

#### API 接口规范

| 项目 | 规范 |
|------|------|
| 协议 | HTTPS |
| 数据格式 | JSON |
| 认证方式 | Bearer Token |
| 错误格式 | `{ "code": 40001, "message": "参数错误" }` |

#### 示例：获取记录列表

**请求：**

```
GET /api/v1/records?page=1&pageSize=20&type=expense&month=2024-01
Authorization: Bearer xxx
```

**响应：**

```json
{
  "code": 0,
  "data": {
    "total": 156,
    "records": [
      {
        "id": "uuid-1",
        "amount": 35.0,
        "type": "expense",
        "category": "餐饮",
        "note": "午餐",
        "date": "2024-01-15T12:30:00Z"
      }
    ]
  }
}
```

> ⚠️ **警告**：第一个版本建议做纯本地 App，不接后端。后端会增加 10 倍的复杂度——服务器、数据库、接口、鉴权、运维……先把 App 做出来上架，后续再考虑加后端。

### 技术方案模板

```markdown
# 技术方案：小账本

## 1. 技术选型
- **语言**：Swift 5.9+
- **UI 框架**：SwiftUI
- **数据存储**：SwiftData
- **图表**：Swift Charts
- **最低版本**：iOS 17.0
- **第三方依赖**：无

## 2. 架构设计
- **架构模式**：MVVM
- **模块划分**：Record / Statistics / Settings
- **数据流向**：View → ViewModel → Model → ViewModel → View

## 3. 数据模型
- Record：记账记录（金额、分类、日期、备注）
- Category：分类（名称、图标、类型）
- Budget：预算（分类、金额、月份）

## 4. 接口定义
- 纯本地 App，无 API 接口
- 数据通过 SwiftData 本地存储

## 5. 关键技术决策
- 选择 SwiftData 而非 CoreData：API 更简洁，学习成本更低
- 选择 Swift Charts 而非第三方库：原生支持，无额外依赖
- 不做后端：降低复杂度，快速上架
```

## 任务拆解与优先级排序

> 🎯 **本节目标**：学会把 PRD 拆解为可执行的开发任务，并合理安排开发顺序。

### 从 Spec 到 Task

PRD 和技术方案是"要做什么"和"怎么做"，任务拆解是"先做什么后做什么"。

#### 任务拆解示例

以"快速记账"功能为例：

| 任务编号 | 任务描述 | 依赖 | 预估时间 | 验收标准 |
|---------|---------|------|---------|---------|
| T01 | 创建 Record 数据模型 | 无 | 1h | 模型可编译，字段完整 |
| T02 | 创建 Category 数据模型 | 无 | 1h | 预设分类可展示 |
| T03 | 实现记账页面 UI | T01, T02 | 3h | 金额输入、分类选择、保存按钮 |
| T04 | 实现记账 ViewModel | T01 | 2h | 保存记录到 SwiftData |
| T05 | 实现记录列表 UI | T01 | 3h | 按日期分组展示 |
| T06 | 实现编辑/删除功能 | T04, T05 | 2h | 滑动删除，点击编辑 |

### 任务粒度控制

任务太大或太小都不好：

| 粒度 | 示例 | 问题 |
|------|------|------|
| 太大 | "完成记账模块" | 不知道从哪开始，容易拖延 |
| 太小 | "创建 Record.swift 文件" | 任务太多，管理成本高 |
| ✅ 合适 | "实现记账页面 UI" | 1-4 小时可完成，有明确验收标准 |

> 💡 **提示**：判断粒度是否合适的方法——如果你能用一句话说清楚这个任务"做完后能看到什么效果"，粒度就合适了。

### 依赖关系梳理

任务之间有先后顺序，画一个简单的依赖图：

```
T01 (Record 模型) ──┬──► T03 (记账页面 UI) ──► T06 (编辑/删除)
                     │
T02 (Category 模型) ─┘
     │
     └──► T04 (记账 ViewModel) ──► T05 (记录列表 UI)
```

**可以并行的任务：**
- T01 和 T02 可以同时开始（无依赖）
- T03 和 T04 可以同时开始（分别依赖 T01/T02）

**必须串行的任务：**
- T04 必须在 T01 之后
- T06 必须在 T04 和 T05 之后

> ⚠️ **警告**：不要忽略依赖关系。如果先做 T03（UI）但 T01（模型）还没做，你会发现 UI 没有数据可以展示，不得不回头补模型，浪费时间。

## 定义验收标准

> 🎯 **本节目标**：学会为每个功能定义清晰的验收标准，确保"做完"等于"做好"。

### 功能验收

验收标准回答的问题是：**怎么才算这个功能做完了？**

推荐使用 **Given-When-Then** 格式：

| 关键词 | 含义 | 示例 |
|--------|------|------|
| Given | 前提条件 | 用户在记账页面 |
| When | 执行操作 | 用户输入 35 元，选择"餐饮"分类，点击保存 |
| Then | 期望结果 | 记录保存成功，列表中出现这条记录，金额显示 -35.00 |

**示例：快速记账的验收标准**

```
验收标准 1：正常记账
- Given：用户在首页
- When：点击"+"按钮 → 输入金额 35 → 选择"餐饮" → 点击保存
- Then：页面返回首页，列表顶部出现新记录"餐饮 -35.00"

验收标准 2：金额为 0
- Given：用户在记账页面
- When：不输入金额直接点保存
- Then：提示"请输入金额"，不保存

验收标准 3：空分类
- Given：用户在记账页面
- When：输入金额但不选分类就点保存
- Then：默认选择第一个分类并保存
```

### 性能验收

| 指标 | 验收标准 | 测试方法 |
|------|---------|---------|
| 冷启动时间 | ≤ 2 秒 | Xcode Instruments - Time Profiler |
| 记账页面打开 | ≤ 0.5 秒 | 手动计时 |
| 列表滑动 | 60fps 无卡顿 | Xcode Instruments - Core Animation |
| 内存峰值 | ≤ 150MB | Xcode Instruments - Allocations |
| 1000 条记录 | 列表加载 ≤ 1 秒 | 模拟数据测试 |

> 💡 **提示**：性能验收不需要在开发阶段频繁测试，但在提交审核前一定要测一遍。App Store 对性能差的 App 会降权。

### UI 验收

| 验收项 | 标准 | 检查方法 |
|--------|------|---------|
| 设计还原度 | 与设计稿偏差 ≤ 5px | 截图对比 |
| 暗黑模式 | 所有页面正常显示 | 切换暗黑模式逐页检查 |
| iPhone SE | 布局不错乱、文字不截断 | 模拟器测试 |
| iPhone 15 Pro Max | 布局不空洞、间距合理 | 模拟器测试 |
| 动态字体 | 放大 2 倍后布局不错乱 | 设置 → 辅助功能 → 更大字体 |
| 横屏 | 不需要支持横屏，锁定竖屏 | 旋转设备测试 |

> ⚠️ **警告**：暗黑模式和 iPhone SE 适配是 App Store 审核的常见拒绝原因。一定要在提交前测试！

## 用 AI 辅助生成和完善 Spec

> 🎯 **本节目标**：学会用 AI 帮你写 PRD、做技术选型、拆解任务，大幅提升效率。

### 让 AI 帮你写 PRD

**Prompt 模板：**

```
我想开发一款 iOS App，请帮我写一份 PRD。

项目名称：小账本
一句话描述：极简个人记账工具
目标用户：18-35 岁年轻人
核心功能：快速记账、分类统计、预算管理

请按以下格式输出：
1. 项目概述
2. 目标用户（用户画像、使用场景、痛点）
3. 功能需求（按模块组织，标注 P0/P1/P2 优先级）
4. 非功能需求
5. 约束与假设
```

### 让 AI 帮你做技术选型

**Prompt 模板：**

```
我正在开发一款 iOS 记账 App，请帮我做技术选型。

需求：
- 纯本地存储，无后端
- 需要图表展示
- 支持 iOS 16+
- 尽量少用第三方库

请对比以下选项并给出推荐：
1. 数据存储：SwiftData vs CoreData
2. 图表：Swift Charts vs DGCharts
3. 最低版本：iOS 16 vs iOS 17

给出每个选项的优缺点和推荐理由。
```

### 让 AI 帮你拆解任务

**Prompt 模板：**

```
请帮我将以下功能拆解为开发任务，每个任务 1-4 小时可完成。

功能：快速记账
- 输入金额
- 选择分类
- 保存记录
- 查看记录列表

请输出表格，包含：任务编号、任务描述、依赖任务、预估时间、验收标准。
```

### 让 AI 帮你定义验收标准

**Prompt 模板：**

```
请帮我为以下功能定义验收标准，使用 Given-When-Then 格式。

功能：快速记账
- 用户输入金额、选择分类、保存
- 金额为 0 时提示错误
- 不选分类时使用默认分类
- 保存成功后返回列表

请覆盖正常流程和异常流程。
```

> 💡 **提示**：AI 生成的 Spec 不一定完美，但它是很好的起点。你可以在此基础上修改和补充，比从零开始写快 5-10 倍。

> ⚠️ **警告**：不要直接复制粘贴 AI 的输出就当 Spec 用。一定要逐条检查，确保符合你的实际情况。AI 不知道你的时间安排、技术水平和真实需求。

## 小结

本章我们学习了 Spec 驱动开发的完整流程：

| 步骤 | 产出 | 核心要点 |
|------|------|---------|
| 编写 PRD | 产品需求文档 | 说清楚"做什么"，用 P0/P1/P2 排优先级 |
| 编写技术方案 | 技术选型 + 架构设计 | 说清楚"怎么做"，MVVM + SwiftData |
| 任务拆解 | 任务列表 + 依赖关系 | 说清楚"先做什么"，1-4 小时粒度 |
| 定义验收标准 | Given-When-Then | 说清楚"怎么算做完"，覆盖正常+异常流程 |
| AI 辅助 | 快速生成初稿 | 用 Prompt 模板，但一定要人工审核 |

**记住这个核心流程：**

```
想法 → PRD → 技术方案 → 任务拆解 → 编码 → 验收
```

Spec 不是额外的工作，而是帮你省时间的工具。花 3 天写 Spec，可以省 3 周的返工。
