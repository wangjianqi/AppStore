# 68-测试基础

## 本章目标

- 理解为什么需要写测试，以及测试能带来什么好处
- 掌握 XCTest 框架的基本使用方法
- 学会编写单元测试、异步测试和 UI 测试
- 了解 Mock 与 Stub 的概念和使用方式
- 掌握查看测试覆盖率的方法
- 建立良好的测试习惯和最佳实践

## 1. 为什么需要测试

### 1.1 测试就是安全网

想象你在马戏团走钢丝——

| 场景 | 没有安全网 | 有安全网 |
|------|-----------|---------|
| 日常表演 | 小心翼翼，每步都紧张 | 自信从容，专注动作本身 |
| 意外失足 | 直接摔下来 | 被网接住，重新上来 |
| 尝试新动作 | 不敢尝试，怕出错 | 大胆尝试，失败了也不怕 |

**测试就是代码世界的安全网。** 没有测试时，每次改动代码都提心吊胆："我改了这个地方，别的地方会不会出问题？"有了测试，改完代码跑一遍测试，全绿就放心，红了就立刻知道哪里出了问题。

### 1.2 测试的三大好处

| 好处 | 说明 | 生活类比 |
|------|------|---------|
| 减少 Bug | 在代码到达用户之前就发现问题 | 出门前照镜子检查着装 |
| 提升重构信心 | 改代码后跑测试，确认功能没被破坏 | 搬家后对照清单确认东西没丢 |
| 文档作用 | 测试代码本身就是最好的使用文档 | 菜谱就是做菜的"测试用例" |

> 💡 一个常见的误区："写测试太花时间了，项目进度紧，来不及。"实际上，**不写测试省下的时间，会在后期修 Bug 时加倍还回来。** 越是项目进度紧，越需要测试来保证质量。

## 2. XCTest 框架入门

### 2.1 创建测试 Target

在 Xcode 中创建测试 Target 非常简单：

1. 打开你的 Xcode 项目
2. 点击菜单 **File → New → Target...**
3. 选择 **Unit Testing Bundle**（单元测试）或 **UI Testing Bundle**（UI 测试）
4. 命名，通常格式为 `项目名Tests` 或 `项目名UITests`
5. 点击 Finish

> 💡 Xcode 在创建新项目时，会默认勾选 **Include Tests**，这样项目创建完成后就已经自带测试 Target 了。

### 2.2 测试文件结构

创建好测试 Target 后，Xcode 会自动生成一个示例测试文件，结构如下：

```
MyAppTests/
├── MyAppTests.swift        ← 单元测试文件
└── Info.plist

MyAppUITests/
├── MyAppUITests.swift      ← UI 测试文件
├── MyAppUITestsLaunchTests.swift  ← 启动性能测试
└── Info.plist
```

### 2.3 一个最简单的测试文件

```swift
import XCTest
@testable import MyApp

final class MyAppTests: XCTestCase {

    func testExample() throws {
        // 这是 Xcode 自动生成的示例测试
        // 把它改成你自己的测试
    }
}
```

> ⚠️ `@testable import MyApp` 这行很关键！它让你可以访问 `MyApp` 中 `internal` 级别的类型和方法，而不仅仅是 `public` 的。

### 2.4 运行测试的方式

| 方式 | 操作 | 适用场景 |
|------|------|---------|
| 快捷键 | `⌘ + U` | 运行所有测试 |
| 点击菱形按钮 | 点击方法名旁的菱形图标 | 运行单个测试 |
| 测试导航器 | `⌘ + 6` 打开测试导航器 | 查看和运行所有测试 |
| 命令行 | `xcodebuild test` | CI/CD 自动化 |

## 3. 单元测试基础

### 3.1 XCTestCase 生命周期

`XCTestCase` 是所有测试类的基类，它提供了完整的生命周期方法：

```swift
import XCTest
@testable import MyApp

final class CalculatorTests: XCTestCase {

    override func setUpWithError() throws {
        // 每个测试方法执行前调用
        // 用来准备测试数据、初始化对象
    }

    override func tearDownWithError() throws {
        // 每个测试方法执行后调用
        // 用来清理资源、重置状态
    }

    func testAddition() throws {
        // 测试方法：必须以 test 开头
    }

    func testSubtraction() throws {
        // 另一个测试方法
    }
}
```

执行顺序如下：

```
setUpWithError() → testAddition() → tearDownWithError()
setUpWithError() → testSubtraction() → tearDownWithError()
```

> 💡 每个测试方法执行前都会重新调用 `setUp`，执行后都会调用 `tearDown`。这保证了**每个测试方法都在干净的环境中运行**，互不影响。

### 3.2 setUp 与 tearDown 的变体

| 方法 | 调用时机 | 用途 |
|------|---------|------|
| `setUpWithError()` | 每个测试方法前 | 准备测试数据（推荐，可抛出错误） |
| `setUp()` | 每个测试方法前 | 简单初始化 |
| `tearDownWithError()` | 每个测试方法后 | 清理资源（推荐，可抛出错误） |
| `tearDown()` | 每个测试方法后 | 简单清理 |

### 3.3 Assert 系列方法

断言是测试的核心——它判断结果是否符合预期。如果断言失败，测试就标记为失败。

#### 常用断言方法一览

| 断言方法 | 含义 | 示例 |
|---------|------|------|
| `XCTAssertEqual(a, b)` | a 等于 b | `XCTAssertEqual(2 + 3, 5)` |
| `XCTAssertNotEqual(a, b)` | a 不等于 b | `XCTAssertNotEqual(2 + 3, 6)` |
| `XCTAssertTrue(expr)` | 表达式为 true | `XCTAssertTrue(5 > 3)` |
| `XCTAssertFalse(expr)` | 表达式为 false | `XCTAssertFalse(5 < 3)` |
| `XCTAssertNil(a)` | a 为 nil | `XCTAssertNil(optionalValue)` |
| `XCTAssertNotNil(a)` | a 不为 nil | `XCTAssertNotNil(result)` |
| `XCTAssertGreaterThan(a, b)` | a > b | `XCTAssertGreaterThan(10, 5)` |
| `XCTAssertLessThan(a, b)` | a < b | `XCTAssertLessThan(3, 5)` |
| `XCTAssertThrowsError(expr)` | 表达式抛出错误 | 验证错误处理逻辑 |
| `XCTAssertNoThrow(expr)` | 表达式不抛出错误 | 验证正常路径 |

#### 完整示例：测试一个计算器类

先写被测试的代码：

```swift
struct Calculator {
    func add(_ a: Int, _ b: Int) -> Int {
        a + b
    }

    func divide(_ a: Int, _ b: Int) throws -> Int {
        guard b != 0 else {
            throw CalculatorError.divisionByZero
        }
        return a / b
    }
}

enum CalculatorError: Error {
    case divisionByZero
}
```

然后写测试：

```swift
final class CalculatorTests: XCTestCase {

    var calculator: Calculator!

    override func setUpWithError() throws {
        calculator = Calculator()
    }

    override func tearDownWithError() throws {
        calculator = nil
    }

    func testAddTwoPositiveNumbers() {
        let result = calculator.add(3, 5)
        XCTAssertEqual(result, 8, "3 + 5 应该等于 8")
    }

    func testAddNegativeNumbers() {
        let result = calculator.add(-3, -5)
        XCTAssertEqual(result, -8, "-3 + -5 应该等于 -8")
    }

    func testDivideNormalCase() throws {
        let result = try calculator.divide(10, 2)
        XCTAssertEqual(result, 5, "10 / 2 应该等于 5")
    }

    func testDivideByZeroThrowsError() {
        XCTAssertThrowsError(try calculator.divide(10, 0)) { error in
            XCTAssertEqual(error as? CalculatorError, .divisionByZero)
        }
    }
}
```

> 💡 断言方法的最后一个参数是可选的**失败消息**，当测试失败时会显示这条消息，帮助你快速定位问题。养成写失败消息的好习惯！

## 4. 测试 SwiftUI 视图

SwiftUI 视图的测试和普通逻辑测试不同——视图是声明式的，不容易直接"断言 UI 长什么样"。这里介绍两种常用方式。

### 4.1 方式一：Accessibility 测试（推荐入门）

通过给视图添加 accessibility 标识，然后在测试中查找和验证：

```swift
// 被测试的视图
struct GreetingView: View {
    let name: String

    var body: some View {
        Text("你好, \(name)!")
            .accessibilityIdentifier("greetingText")
    }
}
```

```swift
// 测试
final class GreetingViewTests: XCTestCase {

    func testGreetingMessage() {
        let view = GreetingView(name: "小明")
        let hostingController = UIHostingController(rootView: view)

        let text = hostingController.view
            .accessibilityElement(with: .identifier("greetingText"))

        XCTAssertNotNil(text)
    }
}
```

### 4.2 方式二：测试视图依赖的 ViewModel

更实用的做法是**不直接测试视图，而是测试视图背后的 ViewModel**：

```swift
class CounterViewModel: ObservableObject {
    @Published var count = 0

    func increment() {
        count += 1
    }

    func decrement() {
        count -= 1
    }
}
```

```swift
final class CounterViewModelTests: XCTestCase {

    var viewModel: CounterViewModel!

    override func setUpWithError() throws {
        viewModel = CounterViewModel()
    }

    func testIncrement() {
        viewModel.increment()
        XCTAssertEqual(viewModel.count, 1)

        viewModel.increment()
        XCTAssertEqual(viewModel.count, 2)
    }

    func testDecrement() {
        viewModel.decrement()
        XCTAssertEqual(viewModel.count, -1)
    }
}
```

> 💡 **测试 ViewModel 而不是 View** 是 SwiftUI 项目中最实用的测试策略。视图只是 ViewModel 的"展示层"，只要 ViewModel 的逻辑正确，视图大概率也是对的。

### 4.3 方式三：ViewInspector（第三方库）

[ViewInspector](https://github.com/nalexn/ViewInspector) 是一个专门用来检查 SwiftUI 视图层级结构的库，可以更深入地测试视图：

```swift
import ViewInspector
@testable import MyApp

final class ContentViewTests: XCTestCase {

    func testContentViewDisplaysGreeting() throws {
        let view = ContentView(name: "小红")

        let text = try view.inspect().find(text: "你好, 小红!")
        XCTAssertNotNil(text)
    }
}
```

> ⚠️ ViewInspector 是第三方库，需要通过 SPM 添加依赖。对于初学者，建议先掌握前两种方式，等有需要再引入 ViewInspector。

## 5. 异步代码测试

真实项目中大量使用异步操作：网络请求、定时器、动画完成回调等。测试异步代码需要特殊处理。

### 5.1 问题：异步代码测试为什么会失败？

```swift
// ❌ 这样写测试一定会通过，因为断言在回调之前就执行了！
func testFetchDataWrong() {
    var result: String?

    fetchData { data in
        result = data
    }

    XCTAssertEqual(result, "hello")  // 此时 result 还是 nil！
}
```

这就像你点了外卖，还没送到就检查餐盒——当然什么都没有。

### 5.2 XCTestExpectation：等待异步完成

`XCTestExpectation` 让测试"暂停"，等异步操作完成后才继续：

```swift
func testFetchDataWithExpectation() {
    let expectation = XCTestExpectation(description: "数据加载完成")

    var result: String?

    fetchData { data in
        result = data
        expectation.fulfill()  // 通知：异步操作完成了！
    }

    wait(for: [expectation], timeout: 5.0)  // 最多等 5 秒

    XCTAssertEqual(result, "hello")
}
```

| 步骤 | 说明 | 类比 |
|------|------|------|
| 创建 Expectation | 声明"我在等某件事" | 取餐时拿个号码牌 |
| fulfill() | 通知"事情做完了" | 叫号了，餐好了 |
| wait(for:timeout:) | 等待，超时则失败 | 最多等 10 分钟，超时就投诉 |

### 5.3 async/await 测试

Swift 5.5 引入的 async/await 让异步测试变得和同步一样简单：

```swift
func testFetchDataAsync() async throws {
    let result = try await fetchDataAsync()
    XCTAssertEqual(result, "hello")
}
```

被测试的代码：

```swift
func fetchDataAsync() async throws -> String {
    try await Task.sleep(for: .seconds(1))
    return "hello"
}
```

> 💡 Xcode 13.3+ 支持在测试方法上直接标记 `async throws`，不需要手动写 `XCTestExpectation`，代码更简洁。

### 5.4 多个异步操作

```swift
func testMultipleAsyncOperations() {
    let expectation1 = XCTestExpectation(description: "用户数据加载")
    let expectation2 = XCTestExpectation(description: "配置数据加载")

    fetchUser { _ in expectation1.fulfill() }
    fetchConfig { _ in expectation2.fulfill() }

    wait(for: [expectation1, expectation2], timeout: 10.0)
}
```

> ⚠️ `timeout` 不要设太短（容易因网络波动而失败），也不要设太长（拖慢测试速度）。一般 3~5 秒比较合适。

## 6. Mock 与 Stub

### 6.1 什么是 Mock 和 Stub？

| 概念 | 含义 | 生活类比 |
|------|------|---------|
| **Stub（桩）** | 返回预设的固定数据 | 餐厅的试吃样品——不是真做一道菜，而是给你尝一口 |
| **Mock（模拟）** | 模拟真实对象的行为，可以验证交互 | 模拟面试——不是真面试，但流程一样 |

### 6.2 为什么需要 Mock？

测试中直接调用真实网络请求会有这些问题：

| 问题 | 说明 |
|------|------|
| 速度慢 | 网络请求可能要几秒 |
| 不稳定 | 网络断了测试就失败 |
| 不可控 | 服务器返回什么数据你说了不算 |
| 有副作用 | 可能真的修改了数据库 |

**解决方案：用 Mock 替代真实的网络服务。**

### 6.3 通过协议注入实现 Mock

第一步：定义协议

```swift
protocol UserServiceProtocol {
    func fetchUser(id: String) async throws -> User
}
```

第二步：真实实现

```swift
class UserService: UserServiceProtocol {
    private let baseURL = "https://api.example.com"

    func fetchUser(id: String) async throws -> User {
        let url = URL(string: "\(baseURL)/users/\(id)")!
        let (data, _) = try await URLSession.shared.data(from: url)
        return try JSONDecoder().decode(User.self, from: data)
    }
}
```

第三步：Mock 实现

```swift
class MockUserService: UserServiceProtocol {
    var mockUser: User?
    var shouldThrowError = false

    func fetchUser(id: String) async throws -> User {
        if shouldThrowError {
            throw UserServiceError.notFound
        }
        return mockUser ?? User(id: id, name: "测试用户")
    }
}
```

第四步：在 ViewModel 中通过协议注入

```swift
class UserViewModel: ObservableObject {
    @Published var user: User?
    @Published var errorMessage: String?

    private let userService: UserServiceProtocol

    init(userService: UserServiceProtocol = UserService()) {
        self.userService = userService
    }

    func loadUser(id: String) async {
        do {
            user = try await userService.fetchUser(id: id)
        } catch {
            errorMessage = error.localizedDescription
        }
    }
}
```

第五步：写测试

```swift
final class UserViewModelTests: XCTestCase {

    var mockService: MockUserService!
    var viewModel: UserViewModel!

    override func setUpWithError() throws {
        mockService = MockUserService()
        viewModel = UserViewModel(userService: mockService)
    }

    func testLoadUserSuccess() async {
        mockService.mockUser = User(id: "1", name: "小明")

        await viewModel.loadUser(id: "1")

        XCTAssertEqual(viewModel.user?.name, "小明")
        XCTAssertNil(viewModel.errorMessage)
    }

    func testLoadUserFailure() async {
        mockService.shouldThrowError = true

        await viewModel.loadUser(id: "999")

        XCTAssertNil(viewModel.user)
        XCTAssertNotNil(viewModel.errorMessage)
    }
}
```

> 💡 这种"通过协议注入依赖"的模式叫做**依赖注入（Dependency Injection, DI）**。它不仅让代码更容易测试，也让代码更松耦合、更灵活。

### 6.4 Stub 示例：模拟网络返回数据

```swift
class StubWeatherService: WeatherServiceProtocol {
    func fetchWeather(city: String) -> Weather {
        return Weather(
            city: city,
            temperature: 25,
            condition: .sunny
        )
    }
}
```

Stub 的特点是：**不管输入什么，都返回固定的数据。** 适合用来测试"拿到数据后，界面怎么展示"。

## 7. UI 测试入门

### 7.1 单元测试 vs UI 测试

| 对比项 | 单元测试 | UI 测试 |
|--------|---------|--------|
| 测试对象 | 函数、方法、类 | 用户界面和交互 |
| 速度 | 快（毫秒级） | 慢（秒级） |
| 稳定性 | 高 | 较低（受 UI 布局影响） |
| 数量建议 | 多 | 少（只测关键路径） |

### 7.2 创建 UI 测试

UI 测试需要使用 **XCUITest** 框架，测试文件结构如下：

```swift
import XCTest

final class MyAppUITests: XCTestCase {

    override func setUpWithError() throws {
        continueAfterFailure = false
    }

    func testLaunchPerformance() throws {
        let app = XCUIApplication()
        app.launch()
    }
}
```

### 7.3 UI 测试三步走

| 步骤 | 方法 | 说明 |
|------|------|------|
| 1. 启动应用 | `XCUIApplication().launch()` | 打开 App |
| 2. 查找元素 | `app.buttons["登录"]` | 找到要操作的控件 |
| 3. 交互与验证 | `.tap()` + `XCTAssertEqual` | 操作并检查结果 |

### 7.4 完整示例：测试登录流程

```swift
final class LoginUITests: XCTestCase {

    var app: XCUIApplication!

    override func setUpWithError() throws {
        continueAfterFailure = false
        app = XCUIApplication()
        app.launch()
    }

    func testLoginWithValidCredentials() {
        // 1. 找到输入框并输入
        let usernameField = app.textFields["用户名"]
        usernameField.tap()
        usernameField.typeText("testuser")

        let passwordField = app.secureTextFields["密码"]
        passwordField.tap()
        passwordField.typeText("password123")

        // 2. 点击登录按钮
        let loginButton = app.buttons["登录"]
        loginButton.tap()

        // 3. 验证是否跳转到主页
        let homeLabel = app.staticTexts["欢迎回来"]
        XCTAssertTrue(homeLabel.waitForExistence(timeout: 5))
    }

    func testLoginWithEmptyFields() {
        let loginButton = app.buttons["登录"]
        loginButton.tap()

        let errorLabel = app.staticTexts["请输入用户名和密码"]
        XCTAssertTrue(errorLabel.exists)
    }
}
```

### 7.5 元素查找方式

| 查找方式 | 示例 | 说明 |
|---------|------|------|
| Accessibility Identifier | `app.buttons["loginButton"]` | 最推荐，稳定可靠 |
| Accessibility Label | `app.buttons["登录"]` | 使用用户可见文本 |
| 类型查找 | `app.textFields.element` | 找第一个匹配的元素 |

> 💡 给 SwiftUI 视图添加 Accessibility Identifier：

```swift
Button("登录") {
    performLogin()
}
.accessibilityIdentifier("loginButton")
```

### 7.6 常用交互方法

| 方法 | 说明 | 示例 |
|------|------|------|
| `.tap()` | 点击 | `button.tap()` |
| `.typeText()` | 输入文字 | `field.typeText("hello")` |
| `.swipeUp()` | 向上滑动 | `scrollViews.first.swipeUp()` |
| `.swipeLeft()` | 向左滑动 | `element.swipeLeft()` |
| `.doubleTap()` | 双击 | `element.doubleTap()` |

### 7.7 录制 UI 测试

Xcode 提供了录制功能，可以自动生成 UI 测试代码：

1. 打开 UI 测试文件
2. 将光标放在测试方法内
3. 点击编辑区域底部的 **红色录制按钮**
4. 在模拟器上操作 App
5. Xcode 自动生成对应的测试代码
6. 点击停止录制

> ⚠️ 录制生成的代码通常需要手动调整和优化，比如添加断言、修改查找方式为 Accessibility Identifier 等。

## 8. 测试覆盖率

### 8.1 什么是测试覆盖率

测试覆盖率告诉你：**你的代码有多少行被执行了测试。**

| 覆盖率 | 含义 |
|--------|------|
| 0% | 完全没有测试 |
| 50% | 一半代码被测试覆盖 |
| 100% | 所有代码都被测试覆盖 |

> ⚠️ 100% 覆盖率 ≠ 没有Bug！覆盖率只告诉你"代码被执行了"，不保证"所有情况都被测试了"。

### 8.2 如何查看覆盖率

1. 打开 Xcode 菜单：**Product → Scheme → Edit Scheme...**
2. 选择 **Test** → **Options**
3. 勾选 **Code Coverage**
4. 运行测试（`⌘ + U`）
5. 在 **Report Navigator**（`⌘ + 9`）中查看覆盖率报告

覆盖率报告会显示每个文件、每个函数的覆盖情况：

| 文件 | 覆盖率 | 未覆盖行数 |
|------|--------|-----------|
| Calculator.swift | 100% | 0 |
| UserService.swift | 75% | 12 |
| LoginView.swift | 40% | 35 |

点击具体文件，Xcode 会在代码编辑器中用颜色标注：

- **绿色**：被测试覆盖的代码行
- **红色**：未被测试覆盖的代码行

### 8.3 覆盖率目标建议

| 项目阶段 | 建议覆盖率 | 说明 |
|---------|-----------|------|
| 个人练手项目 | 30%~50% | 核心逻辑测试即可 |
| 正式项目 | 60%~80% | 重点覆盖业务逻辑 |
| 金融/医疗等高要求 | 80%~95% | 尽可能全面覆盖 |
| 追求 100% | 不建议 | 收益递减，性价比低 |

> 💡 不要为了覆盖率数字而写测试。**重点覆盖核心业务逻辑和容易出错的代码**，比追求高覆盖率更有价值。

## 9. 测试最佳实践

### 9.1 AAA 模式

每个测试方法都应该遵循 **Arrange-Act-Assert** 三步模式：

```swift
func testAddition() {
    // Arrange（准备）：设置测试数据
    let calculator = Calculator()

    // Act（执行）：调用被测试的方法
    let result = calculator.add(3, 5)

    // Assert（断言）：验证结果
    XCTAssertEqual(result, 8)
}
```

| 步骤 | 英文 | 含义 | 生活类比 |
|------|------|------|---------|
| 准备 | Arrange | 准备测试所需的一切 | 准备食材和厨具 |
| 执行 | Act | 调用被测试的方法 | 按菜谱做菜 |
| 断言 | Assert | 验证结果是否符合预期 | 尝一口看味道对不对 |

### 9.2 测试命名规范

好的测试名应该像一句话，读起来就能理解测试意图：

```swift
// ❌ 不好：看不出测试什么
func test1() { ... }
func testCalculator() { ... }

// ✅ 好：一目了然
func testAdd_TwoPositiveNumbers_ReturnsCorrectSum() { ... }
func testDivide_ByZero_ThrowsError() { ... }
func testLogin_WithEmptyPassword_ShowsErrorMessage() { ... }
```

常用命名格式：

| 格式 | 示例 |
|------|------|
| `test_方法名_场景_预期结果` | `test_divide_byZero_throwsError` |
| `test方法名 When场景 Then预期` | `testLoginWhenPasswordEmptyThenShowError` |
| `test方法名 场景 预期` | `testFetchData NetworkError ReturnsNil` |

> 💡 选一种格式，在整个项目中保持一致即可。团队协作时统一命名规范比选哪种规范更重要。

### 9.3 测试金字塔

测试金字塔是测试策略的经典模型：

```
          /  \
         / UI  \          ← 少量 UI 测试
        / 测试    \          （慢、脆弱、昂贵）
       /----------\
      /  集成测试    \      ← 适量集成测试
     /    (Mock等)     \      （中等速度）
    /------------------\
   /     单元测试        \   ← 大量单元测试
  /    (快速、稳定)        \    （快、稳定、便宜）
 /--------------------------\
```

| 层级 | 数量 | 速度 | 成本 | 覆盖范围 |
|------|------|------|------|---------|
| 单元测试 | 多（70%） | 快 | 低 | 单个函数/类 |
| 集成测试 | 适中（20%） | 中 | 中 | 多个模块协作 |
| UI 测试 | 少（10%） | 慢 | 高 | 完整用户流程 |

### 9.4 其他最佳实践

| 实践 | 说明 | 反面教材 |
|------|------|---------|
| 一个测试只测一件事 | 每个测试方法只验证一个行为 | 一个测试里验证了 5 个功能 |
| 测试之间互不依赖 | 任何测试单独运行都能通过 | 测试 B 依赖测试 A 先运行 |
| 不要测试私有方法 | 只测试公开接口 | 用技巧去调用 private 方法 |
| 测试行为，不是实现 | 关注"做了什么"，不是"怎么做的" | 断言内部调用了某个方法几次 |
| 及时维护测试代码 | 测试代码和业务代码一样需要维护 | 测试坏了就注释掉 |

### 9.5 TDD 简介（选读）

**测试驱动开发（Test-Driven Development）** 是一种"先写测试，再写代码"的开发方式：

```
🔴 Red    → 先写一个会失败的测试
🟢 Green  → 写最少的代码让测试通过
🔵 Refactor → 重构代码，保持测试通过
```

```swift
// 🔴 Red：先写测试
func testGreeting() {
    let greeter = Greeter()
    XCTAssertEqual(greeter.greet(name: "小明"), "你好, 小明!")
}

// 此时 Greeter 类还不存在，编译失败 ✗

// 🟢 Green：写最少的代码让测试通过
struct Greeter {
    func greet(name: String) -> String {
        "你好, \(name)!"
    }
}

// 测试通过 ✓

// 🔵 Refactor：优化代码（如果需要）
// 比如添加对空名字的处理等
```

> 💡 TDD 是一种很好的实践，但初学者不必强求。**先养成写测试的习惯**，等熟练了再尝试 TDD 流程。

## 小结

本章我们学习了 iOS 开发中测试的基础知识：

| 主题 | 核心要点 |
|------|---------|
| 为什么需要测试 | 测试是安全网，减少 Bug，提升重构信心 |
| XCTest 入门 | 创建测试 Target、测试文件结构、运行测试 |
| 单元测试基础 | XCTestCase 生命周期、setUp/tearDown、assert 断言 |
| 测试 SwiftUI 视图 | 优先测试 ViewModel、Accessibility 测试、ViewInspector |
| 异步代码测试 | XCTestExpectation 等待回调、async/await 简化测试 |
| Mock 与 Stub | 协议注入实现依赖替换、模拟成功和失败场景 |
| UI 测试入门 | XCUITest 三步走、元素查找、录制测试 |
| 测试覆盖率 | 查看报告、合理设定目标、不为数字而测试 |
| 最佳实践 | AAA 模式、命名规范、测试金字塔 |

> 💡 记住：**写测试就像买保险——你不会每天都用到它，但当你需要的时候，你会庆幸自己有它。** 从小处开始，给最核心的代码写测试，逐步扩大覆盖范围。不需要一步到位，但一定要开始行动！
