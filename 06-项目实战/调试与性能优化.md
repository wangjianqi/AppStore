## 1. Xcode 调试基础

### 1.1 断点类型全览

想象你是一位侦探，断点就是你在犯罪现场设置的"监控摄像头"——不同类型的摄像头，捕捉不同类型的线索。

| 断点类型 | 用途 | 生活类比 |
|---------|------|---------|
| 普通 Breakpoint | 在某一行暂停执行 | 在路口设卡检查 |
| 条件 Breakpoint | 满足条件时才暂停 | 只拦超速的车辆 |
| 异常 Breakpoint | 抛出异常时自动暂停 | 火灾报警器一响就行动 |
| Symbolic Breakpoint | 在指定函数/方法处暂停 | 在特定门口蹲守 |
| Error Breakpoint | Swift Error 抛出时暂停 | 医院急诊分诊台 |

**普通断点**：点击代码行号左侧即可添加，最基础也最常用。

**条件断点**：右键断点 → Edit Breakpoint → 添加 Condition：

```
// 只在 index == 5 时暂停
index == 5

// 只在字符串匹配时暂停
name.contains("error")
```

**异常断点**：Cmd+8 打开断点导航器 → 左下角 + → Exception Breakpoint。这是 iOS 开发中**必须添加**的断点，否则 crash 时往往只停在 `main` 函数，看不到具体出错位置。

**Symbolic 断点**：在系统或第三方库的方法处暂停，即使你没有源码：

```
// 在 UIViewController.viewDidLoad 时暂停
Symbol: UIViewController.viewDidLoad

// 在 malloc 处暂停（排查内存问题）
Symbol: malloc
```

> 💡 善用断点的 **Action** 功能：可以在断点触发时自动执行 LLDB 命令、播放声音、打印日志，甚至选择"Automatically continue"实现无侵入式日志。

### 1.2 LLDB 常用命令

LLDB 是 Xcode 内置的调试器，就像医生的听诊器——虽然界面简洁，但能精准诊断问题。

```swift
// 打印变量值
po user.name
po viewModel.items.count

// 打印对象地址和类型
p frame
p count

// 调用表达式
expr let temp = items.filter { $0.isActive }
po temp

// 修改变量值（调试时动态修改）
expr name = "测试用户"
expr isLoaded = true

// 打印调用栈
bt

// 打印所有线程调用栈
bt all

// 继续执行
continue (或 c)

// 单步执行（不进入函数）
next (或 n)

// 单步执行（进入函数）
step (或 s)

// 跳出当前函数
finish
```

> ⚠️ `po`（print object）会调用对象的 `debugDescription`，对于复杂对象可能触发大量计算。如果只需要看基本类型值，用 `p` 更快。

### 1.3 LLDB 实战技巧

```swift
// 设置断点命令：在断点处自动打印并继续
breakpoint set -n "viewDidLoad" -C "po self" -G true

// 查看视图层级（命令行版 View Debugger）
po recursiveDescription

// 查看指定视图的约束
po self.view.constraints

// 查看内存中的所有 UIViewController 实例
objc[0] : UIViewController
```

## 2. View Debugger

### 2.1 视图层级调试

View Debugger 就像 X 光机——让你看透 UI 表面之下各层的排列关系。

**启动方式**：运行 App 时点击 Xcode 底部工具栏的 📐 图标，或菜单 **Debug → View Debugging → Capture View Hierarchy**。

| 功能 | 说明 |
|------|------|
| 3D 旋转 | 拖动可旋转查看视图层级深度 |
| 层级树 | 左侧显示视图层级关系 |
| 属性面板 | 右侧显示选中视图的属性 |
| 过滤 | 按类名、约束等过滤视图 |

常见排查场景：

```swift
// 视图不显示？检查这些属性
po hiddenView.isHidden    // 是否隐藏
po hiddenView.alpha       // 透明度是否为 0
po hiddenView.frame       // frame 是否在屏幕外
po hiddenView.superview   // 是否已添加到父视图

// 视图被遮挡？用 View Debugger 的 "Show Clipped Views"
// 快速找到被裁剪或被其他视图盖住的视图
```

### 2.2 约束冲突排查

约束冲突就像两个人同时指挥交通——信号矛盾，系统不知道听谁的。

**典型冲突日志**：

```
Unable to simultaneously satisfy constraints.
    Probably at least one of the constraints in the following list is one you don't want...
```

**排查步骤**：

1. 在冲突日志中找到你自己的约束（非系统约束）
2. 给关键约束设置 `identifier`，方便定位：

```swift
titleConstraint.identifier = "titleLabel-leading"
subtitleConstraint.identifier = "subtitleLabel-top"

// 冲突日志中会显示 identifier，一目了然
```

3. 使用 Symbolic Breakpoint 在 `UIViewAlertForUnsatisfiableConstraints` 处暂停：

```
Symbol: UIViewAlertForUnsatisfiableConstraints
Action: expr (void)[[UIApplication sharedApplication] setExclusiveTouch:YES]
// 或者在断点处 po 调用栈，定位冲突来源
```

> 💡 优先使用 `priority` 降低约束优先级来解决冲突，而不是删除约束。这样在特殊布局下仍能提供回退方案。

## 3. Memory Graph

### 3.1 内存泄漏检测

Memory Graph 就像房屋的管道检测仪——帮你找到暗处漏水的地方，那些看不见但一直在浪费资源的问题。

**启动方式**：运行 App 时点击 Xcode 底部工具栏的 🐉 图标，或菜单 **Debug → Memory Graph**。

| 检测项 | 说明 |
|--------|------|
| 紫色 ⚠️ 标记 | 疑似循环引用 |
| 泄漏对象 | 蓝色标记，无任何引用指向但未释放 |
| 强引用关系 | 箭头显示对象间的引用关系 |
| 引用计数 | 侧边栏显示对象的 retainCount |

### 3.2 循环引用排查

循环引用（Retain Cycle）就像两个人互相拽着对方的手——谁都不肯先松开，结果谁也走不了。

```swift
// ❌ 典型循环引用：闭包强引用 self
class ProfileViewController: UIViewController {
    var profile: Profile?

    func loadData() {
        API.fetchProfile { result in
            // 闭包强引用 self，self 强引用闭包（通过属性或任务）
            self.profile = result.value
            self.updateUI()
        }
    }
}

// ✅ 使用 [weak self] 打破循环
func loadData() {
    API.fetchProfile { [weak self] result in
        guard let self else { return }
        self.profile = result.value
        self.updateUI()
    }
}
```

### 3.3 常见循环引用场景

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| 闭包捕获 self | 闭包强引用 self | `[weak self]` 或 `[unowned self]` |
| Timer | target 强引用 | 使用 `weak` 封装或 block-based Timer |
| Delegate | 强引用 delegate | 声明为 `weak` |
| NotificationCenter | 闭包强引用 self | 使用 `[weak self]` 并及时 removeObserver |

```swift
// ❌ Timer 循环引用
class HeartbeatManager {
    var timer: Timer?

    func start() {
        timer = Timer.scheduledTimer(
            timeInterval: 1.0,
            target: self,       // Timer 强引用 target
            selector: #selector(tick),
            userInfo: nil,
            repeats: true
        )
    }
}

// ✅ 使用 block-based Timer
func start() {
    timer = Timer.scheduledTimer(withTimeInterval: 1.0, repeats: true) { [weak self] _ in
        self?.tick()
    }
}
```

> ⚠️ `unowned` 和 `weak` 的区别：`weak` 是可选型（可能为 nil），`unowned` 是非可选型（假设对象一定存在）。如果闭包在对象释放后仍可能执行，**必须用 `weak`**，否则会 crash。

## 4. Instruments 工具全览

Instruments 就像一家设备齐全的体检中心——不同的仪器检查不同的健康指标。

### 4.1 Instruments 工具对比

| 工具 | 检测内容 | 适用场景 | 生活类比 |
|------|---------|---------|---------|
| Time Profiler | CPU 耗时分布 | 卡顿、慢操作 | 心电图——看哪里跳得慢 |
| Allocations | 内存分配与增长 | 内存持续增长 | 水表——看哪里在漏水 |
| Leaks | 内存泄漏 | 对象未释放 | 漏水检测器 |
| Network | 网络请求与流量 | 请求过多、数据量大 | 流量计 |
| Core Animation | GPU 渲染性能 | 滚动卡顿、绘制问题 | 帧率检测仪 |

### 4.2 Time Profiler 实战

Time Profiler 是排查卡顿的首选工具：

1. **Product → Profile**（Cmd+I）→ 选择 Time Profiler
2. 操作 App 触发卡顿场景
3. 查看调用栈中耗时最长的函数

```
关键操作：
- 按 ⌥+点击 聚焦到你的代码（隐藏系统调用）
- 勾选 "Invert Call Tree" 从叶子节点看起
- 勾选 "Hide System Libraries" 只看自己的代码
- 关注 "Self Time" 而非 "Total Time"
```

### 4.4 Core Animation 性能调试

| 指标 | 含义 | 目标值 |
|------|------|--------|
| FPS | 每秒帧数 | ≥ 60（ProMotion 设备 ≥ 120） |
| GPU Time | GPU 每帧耗时 | < 16ms（60fps） |
| Tiling | 图层分块渲染 | 减少大图层 |
| Blended Layers | 混合图层 | 越少越好 |

> 💡 在模拟器中开启 **Debug → Color Blended Layers**，红色区域表示需要混合渲染的图层。设置 `layer.shouldRasterize = true` 或给视图设置不透明背景色可减少混合。

## 5. SwiftUI 性能分析

### 5.1 视图重绘优化

SwiftUI 的视图重绘就像画布重绘——如果整幅画只改了一角，却把整块画布擦掉重画，那太浪费了。

```swift
// ❌ 整个列表因一个状态变化而重绘
struct ItemListView: View {
    @State var items: [Item] = []
    @State var selectedID: UUID?   // 选中状态变化 → 整个 View 重绘

    var body: some View {
        List(items) { item in
            ItemRow(item: item, isSelected: item.id == selectedID)
        }
    }
}

// ✅ 将选中状态下沉到子视图
struct ItemListView: View {
    @State var items: [Item] = []

    var body: some View {
        List(items) { item in
            ItemRow(item: item)  // 选中状态由 ItemRow 自己管理
        }
    }
}
```

### 5.2 @State vs @Observable 粒度控制

| 属性包装器 | 观察粒度 | 适用场景 | 重绘范围 |
|-----------|---------|---------|---------|
| @State | 值变化即重绘 | 简单局部状态 | 所在视图 |
| @Observable | 属性级观察 | 复杂模型 | 仅访问变化属性的视图 |
| @ObservedObject | 对象级观察 | 外部传入的模型 | 引用该对象的所有视图 |
| @Environment | 环境级观察 | 全局共享状态 | 所有读取该值的视图 |

```swift
// ✅ 使用 @Observable 实现属性级精准更新
@Observable
class AppState {
    var userName: String = ""
    var unreadCount: Int = 0
    var isDarkMode: Bool = false
}

struct HeaderView: View {
    @State var appState = AppState()

    var body: some View {
        // 只访问 userName → 只有 userName 变化时才重绘
        Text("Hello, \(appState.userName)")
    }
}

struct BadgeView: View {
    @State var appState = AppState()

    var body: some View {
        // 只访问 unreadCount → 只有 unreadCount 变化时才重绘
        Text("\(appState.unreadCount)")
    }
}
```

### 5.3 Lazy 容器使用

```swift
// ❌ 一次性创建所有子视图
ScrollView {
    VStack {
        ForEach(0..<1000) { i in
            HeavyRow(index: i)  // 1000 个全部创建
        }
    }
}

// ✅ 使用 Lazy 容器按需创建
List {
    ForEach(0..<1000) { i in
        HeavyRow(index: i)  // 只创建可见的约 10 个
    }
}

// ✅ LazyVStack/LazyHStack 也可以
ScrollView {
    LazyVStack {
        ForEach(0..<1000) { i in
            HeavyRow(index: i)
        }
    }
}
```

> ⚠️ `LazyVStack` 和 `List` 的区别：`List` 会自动复用单元格（类似 UIKit 的 cell 复用），`LazyVStack` 只延迟加载但不复用。对于超长列表，优先使用 `List`。

## 6. 网络性能优化

### 6.1 请求合并

网络请求就像快递——一个一个寄当然可以，但把多个包裹打包一起寄更高效。

```swift
// ❌ 逐个请求
func loadDashboard() async {
    let user = await fetchUser()       // 等待完成
    let feed = await fetchFeed()       // 再等待
    let notifications = await fetchNotifications()  // 再等待
    // 总耗时 = 请求1 + 请求2 + 请求3
}

// ✅ 并发请求
func loadDashboard() async {
    async let user = fetchUser()
    async let feed = fetchFeed()
    async let notifications = fetchNotifications()

    let (userResult, feedResult, notifResult) = try await (user, feed, notifications)
    // 总耗时 ≈ max(请求1, 请求2, 请求3)
}
```

### 6.2 缓存策略

| 缓存层级 | 技术 | 生命周期 | 适用数据 |
|---------|------|---------|---------|
| 内存缓存 | NSCache / 字典 | App 运行期间 | 频繁访问的小数据 |
| 磁盘缓存 | URLCache / 文件 | 持久化 | 图片、API 响应 |
| HTTP 缓存 | ETag / Last-Modified | 服务端控制 | 标准 API 请求 |

```swift
// 配置 URLSession 缓存
let cache = URLCache(
    memoryCapacity: 50 * 1024 * 1024,   // 50MB 内存
    diskCapacity: 200 * 1024 * 1024      // 200MB 磁盘
)

let config = URLSessionConfiguration.default
config.urlCache = cache
config.requestCachePolicy = .returnCacheDataElseLoad

let session = URLSession(configuration: config)
```

### 6.3 图片加载优化

```swift
// 使用 AsyncImage + 缩略图策略
struct AvatarView: View {
    let url: URL

    var body: some View {
        AsyncImage(url: url) { phase in
            switch phase {
            case .success(let image):
                image
                    .resizable()
                    .aspectRatio(contentMode: .fill)
            case .failure:
                Image(systemName: "person.circle.fill")
            default:
                ProgressView()
            }
        }
        .frame(width: 48, height: 48)
        .clipShape(Circle())
    }
}
```

> 💡 图片优化关键策略：服务端提供多种尺寸（缩略图/中图/原图），列表用缩略图，详情用原图。使用 WebP/HEIC 格式可减少 30-50% 体积。

## 7. 启动优化

### 7.1 冷启动与热启动

启动优化就像餐厅开门迎客——冷启动是早上从零开始准备一切，热启动是午休后继续营业。

| 阶段 | 冷启动 | 热启动 |
|------|--------|--------|
| 定义 | App 进程不存在，从零启动 | App 在后台，切回前台 |
| 耗时 | 较长（通常 400ms-2s） | 很短（通常 < 100ms） |
| 优化重点 | pre-main + post-main | 恢复状态 |

### 7.2 pre-main 阶段优化

pre-main 是 `main()` 函数执行之前的阶段，系统要加载动态库、初始化运行时等：

```
pre-main 阶段：
1. dyld 加载可执行文件
2. 加载依赖的动态库
3. Rebase & Bind（地址修正）
4. ObjC 运行时初始化
5. +load 方法执行
6. C++ 静态初始化
```

**测量 pre-main 耗时**：

```bash
# 在环境变量中添加
DYLD_PRINT_STATISTICS = 1
DYLD_PRINT_STATISTICS_DETAILS = 1
```

**优化手段**：

| 优化项 | 方法 | 预期收益 |
|--------|------|---------|
| 减少动态库 | 合并动态库，静态库优先 | 每减少一个库省 10-30ms |
| 减少 +load | 用 +initialize 替代 | 每个 +load 约 1-5ms |
| 减少类/方法数 | 清理无用代码 | 减少 Rebase/Bind 时间 |
| 二进制重排 | Instrument 生成 order file | 减少 Page Fault |

### 7.3 延迟初始化

```swift
// ❌ 在 AppDelegate 中初始化所有服务
func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: ...) -> Bool {
    AnalyticsManager.shared.initialize()
    PushManager.shared.setup()
    DatabaseManager.shared.open()
    CacheManager.shared.warmUp()
    FeatureFlagManager.shared.fetch()
    // ... 启动时间被拖长
    return true
}

// ✅ 延迟到需要时再初始化
func application(_ application: UIApplication, didFinishLaunchingWithOptions launchOptions: ...) -> Bool {
    // 只做必须的初始化
    setupCrashReporting()   // 崩溃监控必须早初始化
    setupAppearance()       // UI 样式必须早设置
    return true
}

// 其他服务按需初始化
class AnalyticsManager {
    static let shared = AnalyticsManager()

    private var isInitialized = false

    func track(event: String) {
        if !isInitialized {
            initialize()
            isInitialized = true
        }
        // 发送事件
    }
}
```

> ⚠️ 不要把所有初始化都改成 lazy——崩溃监控、日志系统等基础服务必须尽早初始化，否则可能丢失关键信息。

## 8. 包体积优化

### 8.1 优化手段对比

包体积就像行李箱——出发前仔细整理，该扔的扔，该压缩的压缩。

| 优化手段 | 原理 | 预期收益 |
|---------|------|---------|
| Asset Catalog 压缩 | Xcode 自动压缩 PNG | 10-30% 图片体积减少 |
| 无用资源清理 | 删除未引用的图片/文件 | 视项目而定 |
| 代码瘦身 | 移除无用类/方法/框架 | 5-15% 代码体积减少 |
| Swift ABI 稳定性 | iOS 12+ 不再内嵌 Swift stdlib | 减少 5-15MB |
| App Thinning | 按设备分发所需资源 | 用户下载量减少 30-60% |

### 8.4 Swift ABI 稳定性

```swift
// Build Settings 中设置：
// SWIFT_OPTIMIZATION_LEVEL = -O
// ALWAYS_EMBED_SWIFT_STANDARD_LIBRARIES = NO（对动态库）
// DEAD_CODE_STRIPPING = YES

// App Thinning 自动生效：
// 1. Slicing：按设备架构分发（arm64 only）
// 2. On-Demand Resources：按需下载资源
// 3. Bitcode：App Store 自动优化（已废弃）
```

> 💡 在 Xcode Organizer 中查看 App Thinning 报告：**Window → Organizer → 选择版本 → Download App Thinning Size Report**。

## 9. 性能优化实战 Checklist

### 9.1 全链路优化清单

性能优化就像体检报告——逐项检查，每项都达标才算健康。

| 阶段 | 优化项 | 目标 | 检查方法 |
|------|--------|------|---------|
| 启动 | 冷启动时间 | < 400ms | Instruments Time Profiler |
| 启动 | pre-main 耗时 | < 100ms | DYLD_PRINT_STATISTICS |

| 内存 | 基线内存 | < 50MB | Allocations |
| 内存 | 内存泄漏 | 0 个 | Memory Graph + Leaks |
| 内存 | 峰值内存 | < 200MB | Allocations |
| 滚动 | FPS | ≥ 58fps | Core Animation |
| 滚动 | 卡顿帧 | < 1% | Instruments Time Profiler |
| 网络 | 首屏数据加载 | < 1s | Network Instrument |

| 体积 | 下载大小 | < 50MB | App Thinning Report |
| 体积 | 安装大小 | < 100MB | App Thinning Report |

### 9.2 优化优先级

```
高优先级（用户体验直接感知）：
├── 启动速度
├── 滚动流畅度
└── 内存泄漏

中优先级（影响留存和转化）：
├── 网络请求速度
├── 内存峰值
└── 包体积

低优先级（长期维护）：
├── 代码体积
├── 无用资源
└── 编译速度
```

### 9.3 持续监控方案

```swift
// 在 App 中埋点监控关键指标
final class PerformanceMonitor {
    static func trackLaunchTime() {
        let start = ProcessInfo.processInfo.systemUptime
        DispatchQueue.main.asyncAfter(deadline: .now() + 0.1) {
            let elapsed = ProcessInfo.processInfo.systemUptime - start
            Analytics.track(event: "app_launch", properties: [
                "duration_ms": Int(elapsed * 1000),
                "is_cold_launch": !UIApplication.shared.applicationState.contains(.background)
            ])
        }
    }

    static func trackFrameDrop() {
        let link = CADisplayLink(target: self, selector: #selector(tick))
        link.add(to: .main, forMode: .common)
    }

    @objc private func tick(link: CADisplayLink) {
        let duration = link.targetTimestamp - link.timestamp
        let fps = 1.0 / duration
        if fps < 55 {
            Analytics.track(event: "frame_drop", properties: ["fps": fps])
        }
    }
}
```

## 10. AI 辅助调试

### 10.1 用 AI 分析崩溃日志

AI 就像一位经验丰富的老医生——你把症状（崩溃日志）描述给它，它能快速定位病因。

**典型崩溃日志分析流程**：

```
1. 获取崩溃日志：
   - Xcode Organizer → Crashes
   - App Store Connect → Metrics → Crashes
   - 第三方：Firebase Crashlytics / Sentry

2. 符号化（Symbolication）：
   - 确保有对应版本的 dSYM 文件
   - 使用 atos 或 symbolicatecrash 工具

3. AI 分析提示词模板：
```

```
请分析以下 iOS 崩溃日志，帮我定位问题：

崩溃类型：SIGABRT
崩溃线程：
Thread 0 Crashed:
0  libsystem_kernel.dylib  __pthread_kill + 8
1  libsystem_pthread.dylib pthread_kill + 256
2  libsystem_c.dylib       abort + 120
3  MyApp                   specialized closure #1 in APIManager.fetchData() + 328
4  MyApp                   thunk for @escaping @callee_guaranteed (@guaranteed Result<Data, Error>) -> () + 20

请分析：
1. 崩溃的根本原因是什么？
2. 可能的修复方案？

```

### 10.3 AI 辅助调试的最佳实践

| 场景 | AI 提示词要点 | 注意事项 |
|------|-------------|---------|
| 崩溃分析 | 提供完整崩溃栈、设备信息、系统版本 | AI 无法访问你的代码，需附上关键代码片段 |
| 内存泄漏 | 提供对象引用关系、类定义 | 用 Memory Graph 导出的关系描述 |
| 性能瓶颈 | 提供 Time Profiler 数据 | Self Weight 高的才是真正瓶颈 |
| 约束冲突 | 提供完整冲突日志 | 附上相关约束代码 |

> ⚠️ AI 辅助调试的局限性：AI 无法运行你的代码，无法看到实时内存状态，分析结果需要你自行验证。把 AI 当作"快速缩小排查范围"的工具，而非"自动修复"的银弹。

## 本章小结

| 主题 | 核心要点 | 关键工具/技术 |
|------|---------|-------------|
