## 项目目录结构

> 🎯 **本节目标**：学会创建清晰的项目目录结构，让代码"各归其位"，方便查找和维护。

### 推荐目录结构

一个规范的 iOS 项目目录长这样：

```
MyApp/
├── App/                        # App 入口和生命周期
│   ├── MyAppApp.swift          # @main 入口
│   └── AppDelegate.swift       # (可选) 生命周期事件
├── Models/                     # 数据模型
│   ├── Record.swift
│   ├── Category.swift
│   └── Budget.swift
├── ViewModels/                 # 视图模型
│   ├── RecordViewModel.swift
│   ├── StatisticsViewModel.swift
│   └── SettingsViewModel.swift
├── Views/                      # 视图
│   ├── Features/               # 按功能模块分
│   │   ├── Record/             # 记账模块
│   │   │   ├── RecordListView.swift
│   │   │   ├── RecordAddView.swift
│   │   │   └── RecordEditView.swift
│   │   ├── Statistics/         # 统计模块
│   │   │   ├── StatisticsView.swift
│   │   │   └── CategoryPieChartView.swift
│   │   └── Settings/           # 设置模块
│   │       └── SettingsView.swift
│   └── Components/             # 可复用组件
│       ├── AmountInputView.swift
│       ├── CategoryPickerView.swift
│       └── EmptyStateView.swift
├── Services/                   # 服务层
│   ├── DatabaseService.swift   # 数据库操作
│   ├── ExportService.swift     # 数据导出
│   └── NotificationService.swift
├── Utilities/                  # 工具类
│   ├── Constants.swift         # 常量定义
│   ├── Extensions/             # 扩展方法
│   │   ├── Color+Ext.swift
│   │   ├── Date+Ext.swift
│   │   └── String+Ext.swift
│   └── Helpers/                # 辅助函数
│       └── Formatter.swift
└── Resources/                  # 资源文件
    ├── Assets.xcassets/        # 图片和颜色
    ├── Localizable.strings     # 多语言
    └── Info.plist              # 配置信息
```

#### 各目录职责一览

| 目录 | 放什么 | 不放什么 |
|------|--------|---------|
| App/ | 入口文件、生命周期 | 业务逻辑 |
| Models/ | 数据模型定义 | UI 代码、网络请求 |
| ViewModels/ | 业务逻辑、状态管理 | SwiftUI 视图代码 |
| Views/ | 页面和组件 | 数据库操作、网络请求 |
| Services/ | 数据库、网络、通知等服务 | UI 代码 |
| Utilities/ | 常量、扩展、工具函数 | 业务逻辑 |
| Resources/ | 图片、配置、多语言文件 | Swift 代码 |

> 💡 **提示**：如果你不确定一个文件该放哪，问自己："这个文件是关于什么的？"如果是数据，放 Models；如果是界面，放 Views；如果是逻辑，放 ViewModels。

### 文件命名规范

#### 基本规则

| 规则 | 说明 | 正确示例 | 错误示例 |
|------|------|---------|---------|
| 大驼峰命名 | 每个单词首字母大写 | `RecordListView` | `recordlistview` |
| 文件名与类型名一致 | 类名是什么，文件名就是什么 | `Record.swift` 里定义 `Record` 类 | `RecordModel.swift` 里定义 `Record` 类 |
| 功能后缀 | 用后缀区分类型 | `RecordListView` / `RecordViewModel` | `ViewForRecordList` / `VMForRecord` |

#### 常见后缀约定

| 后缀 | 含义 | 示例 |
|------|------|------|
| View | SwiftUI 视图 | `RecordListView` |
| ViewModel | 视图模型 | `RecordViewModel` |
| Service | 服务类 | `DatabaseService` |
| Ext / +Ext | 扩展文件 | `Date+Ext.swift` |
| Helper | 辅助工具 | `Formatter` |

> ⚠️ **警告**：命名一定要一致！如果 A 模块叫 `RecordListView`，B 模块叫 `StatsView`，风格不统一会让项目看起来很乱。选定一种风格，全项目统一。

## MVVM 架构入门

> 🎯 **本节目标**：理解 MVVM 架构的三层职责和数据流向，学会用 MVVM 组织代码。

MVVM 是 **Model-View-ViewModel** 的缩写，是 iOS 开发中最主流的架构模式。它的核心思想是：**让每一层只做自己的事，互不干涉**。

### Model 层

Model 是"数据层"，负责定义数据结构和业务规则。

#### Model 做什么

| 职责 | 说明 | 示例 |
|------|------|------|
| 定义数据结构 | 数据有哪些字段 | Record 有 amount、category、date |
| 数据校验 | 数据是否合法 | 金额不能为负数 |
| 业务规则 | 业务逻辑判断 | 本月支出是否超预算 |

#### Model 不做什么

- ❌ 不关心数据怎么展示（那是 View 的事）
- ❌ 不关心用户点了什么按钮（那是 ViewModel 的事）
- ❌ 不包含 UI 代码

#### 示例：Record 模型

```swift
import Foundation
import SwiftData

@Model
class Record {
    var id: UUID
    var amount: Double
    var type: RecordType
    var category: String
    var note: String
    var date: Date

    init(amount: Double, type: RecordType, category: String, note: String = "", date: Date = .now) {
        self.id = UUID()
        self.amount = amount
        self.type = type
        self.category = category
        self.note = note
        self.date = date
    }

    var isValid: Bool {
        amount > 0 && !category.isEmpty
    }

    var displayAmount: String {
        let prefix = type == .expense ? "-" : "+"
        return "\(prefix)\(String(format: "%.2f", amount))"
    }
}

enum RecordType: String, Codable, CaseIterable {
    case expense = "支出"
    case income = "收入"
}
```

> 💡 **提示**：Model 里可以放一些简单的计算属性（如 `displayAmount`），只要它不涉及 UI 展示逻辑。判断标准：这个计算在命令行环境也能用吗？如果能，就放 Model。

### View 层

View 是"展示层"，负责把数据渲染成用户看到的界面。

#### View 做什么

| 职责 | 说明 | 示例 |
|------|------|------|
| 展示数据 | 把 ViewModel 的数据显示出来 | 显示金额、分类名称 |
| 响应用户操作 | 把用户操作转发给 ViewModel | 点击保存按钮 |
| 布局排版 | 控制元素的位置和样式 | VStack、HStack、padding |

#### View 不做什么

- ❌ 不直接操作数据库
- ❌ 不包含业务逻辑（如计算月度总额）
- ❌ 不自己管理状态（状态由 ViewModel 管理）

#### 示例：记账列表 View

```swift
import SwiftUI

struct RecordListView: View {
    @StateObject private var viewModel = RecordViewModel()

    var body: some View {
        NavigationStack {
            Group {
                if viewModel.records.isEmpty {
                    EmptyStateView(message: "还没有记录，点击 + 添加")
                } else {
                    List {
                        ForEach(viewModel.groupedRecords) { group in
                            Section(group.dateString) {
                                ForEach(group.records) { record in
                                    RecordRowView(record: record)
                                }
                                .onDelete { indexSet in
                                    viewModel.deleteRecord(in: group, at: indexSet)
                                }
                            }
                        }
                    }
                }
            }
            .navigationTitle("账本")
            .toolbar {
                ToolbarItem(placement: .navigationBarTrailing) {
                    NavigationLink(destination: RecordAddView(viewModel: viewModel)) {
                        Image(systemName: "plus")
                    }
                }
            }
            .task {
                viewModel.fetchRecords()
            }
        }
    }
}
```

> 💡 **提示**：View 的代码应该尽量"薄"。如果你发现 View 里有大量 `if-else` 或计算逻辑，说明这些逻辑应该搬到 ViewModel。

### ViewModel 层

ViewModel 是"逻辑层"，是 Model 和 View 之间的桥梁。

#### ViewModel 做什么

| 职责 | 说明 | 示例 |
|------|------|------|
| 管理状态 | 持有 View 需要的数据 | `@Published var records: [Record]` |
| 处理用户操作 | 响应 View 发来的动作 | `addRecord()` / `deleteRecord()` |
| 调用 Model | 读写数据 | 保存记录到 SwiftData |
| 数据转换 | 把 Model 数据转成 View 方便用的格式 | 按日期分组、格式化金额 |

#### ViewModel 不做什么

- ❌ 不包含 UI 代码（不 import SwiftUI，不用 `Color`、`Image` 等）
- ❌ 不直接操作 View（不控制导航、不显示 Alert——这些由 View 响应状态变化来完成）

#### 示例：RecordViewModel

```swift
import Foundation
import SwiftData

@Observable
class RecordViewModel {
    var records: [Record] = []
    var groupedRecords: [RecordGroup] = []

    private var modelContext: ModelContext?

    func setup(modelContext: ModelContext) {
        self.modelContext = modelContext
        fetchRecords()
    }

    func fetchRecords() {
        guard let modelContext else { return }
        let descriptor = FetchDescriptor<Record>(sortBy: [SortDescriptor(\.date, order: .reverse)])
        records = (try? modelContext.fetch(descriptor)) ?? []
        groupedRecords = groupRecordsByDate(records)
    }

    func addRecord(amount: Double, type: RecordType, category: String, note: String) {
        guard let modelContext else { return }
        let record = Record(amount: amount, type: type, category: category, note: note)
        modelContext.insert(record)
        try? modelContext.save()
        fetchRecords()
    }

    func deleteRecord(in group: RecordGroup, at offsets: IndexSet) {
        guard let modelContext else { return }
        for index in offsets {
            let record = group.records[index]
            modelContext.delete(record)
        }
        try? modelContext.save()
        fetchRecords()
    }

    private func groupRecordsByDate(_ records: [Record]) -> [RecordGroup] {
        let calendar = Calendar.current
        let grouped = Dictionary(grouping: records) { record in
            calendar.startOfDay(for: record.date)
        }
        return grouped.map { RecordGroup(date: $0.key, records: $0.value) }
            .sorted { $0.date > $1.date }
    }
}

struct RecordGroup: Identifiable {
    let id = UUID()
    let date: Date
    let records: [Record]

    var dateString: String {
        date.formatted(date: .abbreviated, time: .omitted)
    }
}
```

> ⚠️ **警告**：ViewModel 里不要 `import SwiftUI`。如果你发现自己在 ViewModel 里用了 `Color.red`、`Image(systemName:)` 等 UI 类型，说明你的架构出了问题——UI 相关的东西应该放在 View 层。

### 数据流向

MVVM 的数据流向是单向的，像一条流水线：

```
┌──────────────────────────────────────────────────────────┐
│                      用户操作                              │
│  （点击按钮、输入文字、滑动列表...）                          │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────┐      用户动作      ┌──────────────┐
│   View   │ ────────────────► │  ViewModel   │
│ (SwiftUI)│                   │              │
│          │ ◄──────────────── │              │
│          │   @Published 变化  │              │
└──────────┘                   └──────┬───────┘
       ▲                              │
       │                         调用/更新
       │                              │
       │                              ▼
       │                       ┌──────────────┐
       │                       │    Model     │
       │                       │  (数据+逻辑)  │
       │                       └──────────────┘
       │                              │
       └──────── 数据变化通知 ─────────┘
```

#### 具体流程（以"添加记录"为例）

| 步骤 | 发生了什么 | 代码位置 |
|------|-----------|---------|
| 1 | 用户在 View 点击"保存"按钮 | `RecordAddView.swift` |
| 2 | View 调用 ViewModel 的 `addRecord()` | `viewModel.addRecord(...)` |
| 3 | ViewModel 创建 Record 模型并保存 | `RecordViewModel.swift` |
| 4 | Model 写入 SwiftData 数据库 | `modelContext.insert(record)` |
| 5 | ViewModel 刷新数据，`@Published` 属性更新 | `fetchRecords()` |
| 6 | SwiftUI 检测到数据变化，自动刷新 View | 自动完成 |

> 💡 **提示**：SwiftUI 的数据绑定是自动的。只要 ViewModel 的属性标记了 `@Published`（或使用 `@Observable`），数据变了 View 就会自动更新，你不需要手动刷新。

## 代码组织与模块化

> 🎯 **本节目标**：学会三种代码组织方式，并选择最适合你的方式。

### 按功能模块组织

每个功能一个文件夹，文件夹内包含该功能的 Model、View、ViewModel：

```
MyApp/
├── Record/                     # 记账模块
│   ├── Record.swift            # Model
│   ├── RecordViewModel.swift   # ViewModel
│   ├── RecordListView.swift    # View
│   └── RecordAddView.swift     # View
├── Statistics/                 # 统计模块
│   ├── StatisticsViewModel.swift
│   ├── StatisticsView.swift
│   └── CategoryPieChartView.swift
└── Settings/                   # 设置模块
    ├── SettingsViewModel.swift
    └── SettingsView.swift
```

| 优点 | 缺点 |
|------|------|
| 功能内聚，改一个功能只动一个文件夹 | 同类型的文件分散在不同文件夹 |
| 适合多人协作，每人负责一个模块 | 跨模块复用组件需要额外管理 |

### 按层级组织

所有 Model 放一起，所有 View 放一起，所有 ViewModel 放一起：

```
MyApp/
├── Models/
│   ├── Record.swift
│   ├── Category.swift
│   └── Budget.swift
├── ViewModels/
│   ├── RecordViewModel.swift
│   ├── StatisticsViewModel.swift
│   └── SettingsViewModel.swift
├── Views/
│   ├── RecordListView.swift
│   ├── RecordAddView.swift
│   ├── StatisticsView.swift
│   └── SettingsView.swift
└── Services/
    └── DatabaseService.swift
```

| 优点 | 缺点 |
|------|------|
| 同类型文件集中，找 Model 去 Models 就行 | 改一个功能要跨多个文件夹 |
| 结构清晰，适合新手理解 | 功能多了文件也多，不好管理 |

### 混合组织方式（推荐）

**按功能模块为主，按层级为辅**——这是最推荐的方式：

```
MyApp/
├── App/
│   └── MyAppApp.swift
├── Features/                   # 按功能模块组织
│   ├── Record/
│   │   ├── Views/
│   │   │   ├── RecordListView.swift
│   │   │   └── RecordAddView.swift
│   │   ├── RecordViewModel.swift
│   │   └── Record.swift
│   ├── Statistics/
│   │   ├── Views/
│   │   │   └── StatisticsView.swift
│   │   ├── StatisticsViewModel.swift
│   │   └── RecordGroup.swift
│   └── Settings/
│       ├── Views/
│       │   └── SettingsView.swift
│       └── SettingsViewModel.swift
├── Shared/                     # 跨模块共享
│   ├── Models/
│   │   └── Category.swift
│   ├── Components/
│   │   ├── AmountInputView.swift
│   │   └── EmptyStateView.swift
│   └── Services/
│       └── DatabaseService.swift
└── Utilities/
    ├── Constants.swift
    └── Extensions/
        ├── Date+Ext.swift
        └── Color+Ext.swift
```

| 优点 | 缺点 |
|------|------|
| 功能内聚，改一个功能只动一个文件夹 | 目录层级稍深 |
| 共享代码单独管理，避免重复 | 需要判断文件放 Features 还是 Shared |
| 扩展方便，加功能就加文件夹 | — |

> 💡 **提示**：判断一个文件放 Features 还是 Shared 的方法——问自己"这个文件只被一个模块用，还是多个模块都用？"只被一个模块用就放 Features 下，多个模块都用就放 Shared 下。

## Git 版本管理与分支策略

> 🎯 **本节目标**：学会用 Git 管理代码版本，掌握分支策略和提交信息规范。

### Git 基础操作

Git 是代码的"时光机"，可以帮你记录每一次修改，随时回到之前的版本。

#### 核心命令

| 命令 | 作用 | 示例 |
|------|------|------|
| `git init` | 初始化仓库 | 在项目根目录执行一次 |
| `git add .` | 暂存所有修改 | 每次提交前执行 |
| `git commit -m "消息"` | 提交修改 | 记录这次改了什么 |
| `git push` | 推送到远程仓库 | 把本地代码推到 GitHub |
| `git pull` | 拉取远程更新 | 把 GitHub 上的代码拉到本地 |
| `git status` | 查看当前状态 | 看看哪些文件改了 |
| `git log` | 查看提交历史 | 看看之前都改了什么 |

#### 典型工作流

```bash
# 第一次：初始化项目
cd MyApp
git init
git add .
git commit -m "feat: 初始化项目"

# 日常开发：改了代码后
git status                        # 看看改了什么
git add .                         # 暂存修改
git commit -m "feat: 添加记账页面"  # 提交
git push                          # 推送到远程

# 换了一台电脑：拉取最新代码
git pull                          # 拉取远程更新
```

> 💡 **提示**：养成"小步提交"的习惯——每完成一个小功能就 commit 一次，而不是一天结束后才 commit。小步提交的好处是：出问题容易定位，回滚代价小。

### 分支策略（Git Flow）

分支是 Git 最强大的功能之一，让你可以同时进行多项工作互不干扰。

#### 五种分支

| 分支类型 | 命名 | 用途 | 生命周期 |
|---------|------|------|---------|
| main | `main` | 线上版本，永远可发布 | 永久 |
| develop | `develop` | 开发主线，最新开发代码 | 永久 |
| feature | `feature/记账页面` | 开发新功能 | 合并后删除 |
| release | `release/1.0.0` | 准备发布版本 | 合并后删除 |
| hotfix | `hotfix/修复崩溃` | 紧急修复线上 Bug | 合并后删除 |

#### 示例工作流

```bash
# 1. 从 develop 创建功能分支
git checkout develop
git checkout -b feature/record-list

# 2. 在功能分支上开发
# ... 写代码 ...
git add .
git commit -m "feat: 实现记录列表页面"

# ... 继续写代码 ...
git add .
git commit -m "feat: 添加滑动删除功能"

# 3. 功能完成，合并回 develop
git checkout develop
git merge feature/record-list

# 4. 删除功能分支
git branch -d feature/record-list

# 5. 准备发布
git checkout -b release/1.0.0
# ... 修复 Bug、调整版本号 ...
git checkout main
git merge release/1.0.0
git tag v1.0.0

# 6. 同时合并回 develop
git checkout develop
git merge release/1.0.0
git branch -d release/1.0.0
```

#### 分支流程图

```
main:      ──────────────────────────────────●───────── v1.0.0
                                           /
develop:   ─────────────────●──────────────/────●──────
                         /                      \
feature:   ──●──●──●──●─/                        \
              开发记账页面                         release/1.0.0
```

> ⚠️ **警告**：对于独立开发者，不需要严格遵循 Git Flow。推荐简化版：只用 `main` + `feature` 两个分支就够了。每次开发新功能从 `main` 拉分支，完成后合并回 `main`。

### 提交信息规范

规范的提交信息让项目历史一目了然。

#### Conventional Commits 格式

```
<类型>(<范围>): <描述>

[可选的正文]

[可选的脚注]
```

#### 常用类型

| 类型 | 用途 | 示例 |
|------|------|------|
| feat | 新功能 | `feat(record): 添加快速记账页面` |
| fix | 修复 Bug | `fix(record): 修复金额为负数的崩溃` |
| docs | 文档修改 | `docs: 更新 README` |
| style | 代码格式（不影响逻辑） | `style: 统一缩进为 4 空格` |
| refactor | 重构（不是新功能也不是修 Bug） | `refactor(record): 提取公共组件` |
| perf | 性能优化 | `perf(list): 优化列表滑动性能` |
| test | 添加测试 | `test(record): 添加 ViewModel 单元测试` |
| chore | 构建/工具变更 | `chore: 升级 Xcode 到 15.2` |

#### 好的 vs 差的提交信息

| 差 ❌ | 好 ✅ | 为什么 |
|-------|-------|--------|
| `修改了代码` | `feat(record): 添加分类选择功能` | 好的提交信息说明了改了什么、在哪个模块 |
| `fix bug` | `fix(record): 修复金额为 0 时崩溃的问题` | 好的提交信息说明了修了什么 Bug |
| `update` | `refactor(statistics): 提取日期分组逻辑到 ViewModel` | 好的提交信息说明了为什么改 |

> 💡 **提示**：写提交信息时，想象三个月后的自己看到这条记录，能不能一眼看出改了什么。如果看不出来，就写得更具体一点。

## 配置 .cursorrules / CLAUDE.md

> 🎯 **本节目标**：学会编写 AI 规则文件，让 Cursor / Claude 等 AI 工具更好地理解你的项目，生成更符合你项目规范的代码。

### .cursorrules 编写

`.cursorrules` 是 Cursor 编辑器的项目规则文件，放在项目根目录下，Cursor 每次对话都会自动读取。

#### 完整模板

````
# 项目信息
项目名称：小账本
项目描述：极简个人记账 iOS App
技术栈：Swift 5.9 + SwiftUI + SwiftData
最低版本：iOS 17.0
架构模式：MVVM

# 代码规范
## 命名规范
- 类型名使用大驼峰：RecordViewModel
- 变量名使用小驼峰：recordList
- 常量使用大驼峰 + k 前缀：kDefaultCurrency
- 文件名与主类型名一致：RecordViewModel.swift
- SwiftUI View 以 View 结尾：RecordListView
- ViewModel 以 ViewModel 结尾：RecordViewModel

## 代码风格
- 缩进使用 4 个空格
- 每个文件末尾保留一个空行
- 函数体超过 20 行时考虑拆分
- 优先使用 Swift 并发（async/await）而非闭包回调
- 使用 #if DEBUG 而非条件编译以外的调试代码

## SwiftUI 规范
- View 代码不超过 100 行，超过则拆分子 View
- 使用 @State 管理本地状态，@Bindable/@Environment 绑定外部状态
- 颜色使用 Asset Catalog 中定义的颜色，不硬编码
- 字体使用系统字体，通过 .font() 修饰符调整

## SwiftData 规范
- Model 类使用 @Model 宏
- 查询使用 @Query 或 FetchDescriptor
- 数据变更后调用 modelContext.save()

## 架构规范
- 严格遵循 MVVM：View 不直接操作 Model，ViewModel 不包含 UI 代码
- ViewModel 不 import SwiftUI
- Service 层负责数据库操作，ViewModel 通过 Service 访问数据
- 可复用组件放在 Views/Components/ 目录

## 注释规范
- 不写冗余注释，代码本身应足够清晰
- 公共接口使用 /// 文档注释
- 复杂逻辑使用 // MARK: - 分区

# 项目结构
MyApp/
├── App/
├── Features/
│   ├── Record/
│   ├── Statistics/
│   └── Settings/
├── Shared/
│   ├── Models/
│   ├── Components/
│   └── Services/
└── Utilities/

# 第三方依赖
无第三方依赖，全部使用原生框架

# 注意事项
- 所有文本使用中文
- 金额显示保留两位小数
- 日期格式使用中文习惯（2024年1月15日）
- 支持暗黑模式，所有颜色使用语义化命名
````

#### 每个部分说明

| 部分 | 作用 | 为什么重要 |
|------|------|-----------|
| 项目信息 | 告诉 AI 项目的基本情况 | AI 知道技术栈才能给出正确的代码 |
| 代码规范 | 定义命名、风格等规则 | AI 生成的代码风格和你保持一致 |
| SwiftUI 规范 | SwiftUI 特定的约定 | 避免 AI 生成 UIKit 风格的代码 |
| SwiftData 规范 | 数据层约定 | 避免 AI 混用 CoreData 和 SwiftData |
| 架构规范 | MVVM 分层约定 | 避免 AI 把逻辑写在 View 里 |
| 项目结构 | 目录组织方式 | AI 创建新文件时放到正确的位置 |
| 注意事项 | 项目特有的约定 | 避免细节问题（如金额格式、日期格式） |

### CLAUDE.md 编写

`CLAUDE.md` 是 Claude Code 的项目规则文件，格式和作用与 `.cursorrules` 类似。

#### 完整模板

````
# CLAUDE.md - 小账本项目规则

## 项目概述
- 名称：小账本
- 类型：iOS App（纯本地，无后端）
- 技术栈：Swift + SwiftUI + SwiftData
- 最低版本：iOS 17.0
- 架构：MVVM

## 开发规范

### 命名
- 大驼峰：类型名、文件名
- 小驼峰：变量名、函数名
- View 后缀：SwiftUI 视图
- ViewModel 后缀：视图模型
- Service 后缀：服务类

### 架构规则
- View：只负责展示，不含业务逻辑
- ViewModel：业务逻辑，不 import SwiftUI
- Model：数据定义，使用 @Model 宏
- Service：数据库操作，被 ViewModel 调用

### 代码风格
- 4 空格缩进
- View 不超过 100 行
- 函数不超过 20 行
- 优先 async/await 而非闭包

### SwiftUI 约定
- 本地状态用 @State
- 绑定用 @Bindable
- 环境依赖用 @Environment
- 颜色用 Asset Catalog，不硬编码
- 支持暗黑模式

### SwiftData 约定
- Model 用 @Model 宏
- 查询用 @Query 或 FetchDescriptor
- 变更后调用 save()

## 项目结构
```
MyApp/
├── App/
├── Features/Record/Statistics/Settings/
├── Shared/Models/Components/Services/
└── Utilities/
```

## 特殊约定
- 界面文本使用中文
- 金额保留两位小数，支出显示负号
- 日期格式：2024年1月15日
- 无第三方依赖
````

#### 每个部分说明

| 部分 | 作用 | 与 .cursorrules 的区别 |
|------|------|----------------------|
| 项目概述 | 快速了解项目 | 更简洁，侧重关键信息 |
| 开发规范 | 代码规则 | 格式更紧凑，按类别分组 |
| 特殊约定 | 项目特有规则 | 强调中文、格式等本地化要求 |

### 让 AI 理解你的项目

#### AI 如何利用这些文件

| 场景 | 没有 AI 规则文件 | 有 AI 规则文件 |
|------|----------------|---------------|
| 创建新 View | AI 可能用 UIKit 风格 | AI 自动用 SwiftUI + MVVM |
| 保存数据 | AI 可能用 CoreData | AI 自动用 SwiftData |
| 命名文件 | AI 可能用 `record_view.swift` | AI 自动用 `RecordListView.swift` |
| 放置文件 | AI 可能放根目录 | AI 自动放到 `Features/Record/Views/` |
| 格式化金额 | AI 可能用 `$35.00` | AI 自动用 `-35.00` |

#### 最佳实践

1. **项目一开始就创建** AI 规则文件，不要等项目做了一半才加
2. **规则要具体**，不要写"代码要规范"，要写"View 不超过 100 行"
3. **随项目演进更新**，比如加了新模块就更新项目结构
4. **两个文件都创建**，`.cursorrules` 和 `CLAUDE.md` 内容可以基本一致
5. **规则不要太多**，10-20 条核心规则就够了，太多 AI 反而会忽略

> ⚠️ **警告**：AI 规则文件不是万能的。即使你写了"ViewModel 不 import SwiftUI"，AI 偶尔还是会犯错。每次生成代码后都要检查，特别是 import 语句和架构分层。

## 小结

本章我们学习了项目搭建与架构的核心知识：

| 主题 | 核心要点 | 一句话总结 |
|------|---------|-----------|
| 项目目录结构 | 按功能模块 + 按层级混合组织 | 功能内聚，共享独立 |
| MVVM 架构 | Model/View/ViewModel 三层分离 | View 只展示，ViewModel 只逻辑，Model 只数据 |
| 代码组织 | 混合方式（Features + Shared） | 按功能分文件夹，共享代码单独管理 |
| Git 版本管理 | main + feature 分支，Conventional Commits | 小步提交，规范消息 |
| AI 规则文件 | .cursorrules + CLAUDE.md | 让 AI 懂你的项目规范 |

**记住这三个核心原则：**

1. **分层清晰**：View 不写逻辑，ViewModel 不写 UI，Model 不写界面
2. **命名一致**：全项目统一命名风格，文件名和类型名一致
3. **规则先行**：先建目录、先配 AI 规则、先定 Git 规范，再写业务代码
