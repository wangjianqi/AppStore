# 73-依赖管理与开源库

## 本章目标

- 理解依赖管理的必要性，掌握 SPM、CocoaPods、Carthage 三种方式的优劣
- 熟练编写 Package.swift，掌握版本规则与本地包开发流程
- 掌握 SPM 进阶用法：binary target、资源文件、条件编译、平台指定
- 能独立配置 CocoaPods 并处理与 SPM 共存的场景
- 了解各领域常用开源库，能根据项目需求做出合理选型
- 建立开源库选型评估体系，避免引入"僵尸库"
- 掌握依赖冲突的诊断与解决策略
- 理解许可证合规、供应链安全和隐私清单的实践要求

## 1. 依赖管理概述

### 1.1 为什么需要依赖管理

想象你搬进新家——如果每件家具都要自己从原木开始打造，你可能一辈子都住不进去。依赖管理就像宜家商城：别人已经设计好、测试过的家具（开源库），你只需要挑选、下单、组装（声明依赖、集成、调用）。

没有依赖管理的项目会面临这些问题：

| 问题 | 描述 |
|------|------|
| 手动拷贝 | 源码直接拖入项目，更新时需重新下载替换 |
| 版本失控 | 不知道当前用的是哪个版本，无法回溯 |
| 传递依赖 | A 依赖 B，B 依赖 C，手动管理极易遗漏 |
| 冲突频发 | 两个库依赖同一库的不同版本 |
| 团队协作 | 每个成员的依赖版本可能不一致 |

### 1.2 三大依赖管理工具对比

| 特性 | SPM | CocoaPods | Carthage |
|------|-----|-----------|----------|
| 发布年份 | 2019 | 2011 | 2014 |
| 官方支持 | ✅ Apple 官方 | ❌ 社区维护 | ❌ 社区维护 |
| 集成方式 | 自动修改项目 | 自动修改项目 | 手动嵌入 framework |
| 构建方式 | 随项目一起编译 | 预编译或随项目编译 | 预编译 framework |
| 配置文件 | Package.swift | Podfile | Cartfile |
| 中心仓库 | 无（直连 Git） | CocoaPods Specs | 无（直连 Git） |
| 学习成本 | 低 | 中 | 中 |
| 构建速度 | 中（全量编译） | 慢（首次 pod install） | 快（增量编译） |
| 生态成熟度 | 快速增长 | 最丰富 | 逐渐减少 |
| 推荐场景 | 新项目首选 | 大量历史 Pod 依赖 | 需要最小侵入时 |

> 💡 2024 年起，Apple 在 Xcode 中深度集成 SPM，CocoaPods 官方也宣布进入维护模式。**新项目应优先选择 SPM**。

## 2. Swift Package Manager 详解

### 2.1 Package.swift 结构

Package.swift 是 SPM 的核心配置文件，就像一份"购物清单"——告诉 SPM 你的项目叫什么、包含什么、需要什么。

```swift
// swift-tools-version:5.9
import PackageDescription

let package = Package(
    name: "MyAppKit",
    platforms: [
        .iOS(.v15),
        .macOS(.v12)
    ],
    products: [
        .library(
            name: "MyAppKit",
            targets: ["MyAppKit"]
        )
    ],
    dependencies: [
        .package(url: "https://github.com/Alamofire/Alamofire.git", from: "5.8.0"),
        .package(url: "https://github.com/SwiftyJSON/SwiftyJSON.git", from: "5.0.0")
    ],
    targets: [
        .target(
            name: "MyAppKit",
            dependencies: [
                .product(name: "Alamofire", package: "Alamofire"),
                .product(name: "SwiftyJSON", package: "SwiftyJSON")
            ]
        ),
        .testTarget(
            name: "MyAppKitTests",
            dependencies: ["MyAppKit"]
        )
    ]
)
```

关键字段解读：

| 字段 | 作用 | 生活类比 |
|------|------|---------|
| `name` | 包的名称 | 商品名称 |
| `platforms` | 支持的最低平台版本 | 配送范围 |
| `products` | 对外暴露的库 | 上架商品 |
| `dependencies` | 外部依赖声明 | 进货清单 |
| `targets` | 编译目标（源码/测试） | 仓库分区 |

### 2.2 添加依赖的步骤

在 Xcode 中添加 SPM 依赖只需三步：

1. **File → Add Package Dependencies...**
2. **输入仓库 URL**，点击 Add Package
3. **选择需要的 Product**，点击 Add

也可以在项目设置的 Package Dependencies 标签页中管理。

### 2.3 版本规则详解

版本规则决定了"你愿意接受哪些版本的更新"，就像你告诉快递员"只接受 2 楼以上的包裹"。

```swift
// 从 5.8.0 起，允许 5.x.x 的更新（不升主版本）
.package(url: "...", from: "5.8.0")

// 精确指定版本
.package(url: "...", .exact("5.8.1"))

// 指定版本范围
.package(url: "...", "5.8.0"..<"6.0.0")

// 指定分支（开发阶段使用）
.package(url: "...", branch: "main")

// 指定 commit（最精确，但不推荐长期使用）
.package(url: "...", revision: "a1b2c3d")
```

| 规则 | 匹配范围 | 风险 | 推荐场景 |
|------|---------|------|---------|
| `from: "x.y.z"` | ≥ x.y.z，< (x+1).0.0 | 低 | **日常首选** |
| `.exact()` | 仅指定版本 | 无更新 | 严格管控环境 |
| 范围 `"a"..<"b"` | [a, b) | 中 | 需要上限控制 |
| `branch:` | 分支最新提交 | 高 | 开发调试 |
| `revision:` | 特定 commit | 高 | 临时修复 |

> ⚠️ `from` 规则遵循语义化版本（SemVer）：主版本号变更意味着不兼容的 API 变化。所以 `from: "5.8.0"` 不会自动升级到 6.0.0。

### 2.4 本地包开发

当项目逐渐变大，把模块拆分为本地包是最佳实践——就像把一个大衣柜分成多个抽屉，每个抽屉独立整理。

目录结构：

```
MyApp/
├── App/                    # 主应用
│   └── MyApp.xcodeproj
├── Packages/
│   ├── CoreKit/           # 核心模块
│   │   ├── Package.swift
│   │   └── Sources/
│   ├── NetworkKit/        # 网络模块
│   │   ├── Package.swift
│   │   └── Sources/
│   └── UIComponents/      # UI 组件
│       ├── Package.swift
│       └── Sources/
└── MyApp.xcworkspace
```

在主项目的 Package.swift 或 Xcode 中添加本地包：

```swift
dependencies: [
    .package(path: "../Packages/CoreKit"),
    .package(path: "../Packages/NetworkKit")
]
```

本地包的优势：

- 编译速度更快（增量编译）
- 模块边界清晰，防止循环依赖
- 团队成员可以独立开发各模块
- 未来可轻松抽取为独立仓库

## 3. SPM 进阶

### 3.1 Binary Target

并非所有库都提供源码——有些只提供编译好的 `.xcframework`，就像买现成的家电，你不需要知道内部电路，插电即用。

```swift
targets: [
    .binaryTarget(
        name: "FirebaseAnalytics",
        url: "https://github.com/firebase/firebase-ios-sdk/releases/download/10.12.0/FirebaseAnalytics.xcframework.zip",
        checksum: "a1b2c3d4e5f6..."
    )
]
```

> ⚠️ `checksum` 是 zip 文件的校验和，SPM 会验证下载文件的完整性。如果校验失败，构建会中断。可通过 `swift package compute-checksum FirebaseAnalytics.xcframework.zip` 计算。

也可以使用本地 xcframework：

```swift
.binaryTarget(
    name: "PaidSDK",
    path: "Frameworks/PaidSDK.xcframework"
)
```

### 3.2 资源文件处理

SPM 从 5.3 开始支持资源文件。默认情况下，SPM 会根据文件扩展名自动处理：

```swift
.target(
    name: "UIComponents",
    dependencies: [],
    resources: [
        .process("Images"),           // 自动处理，优化分发
        .copy("Config.json"),         // 原样拷贝，保留目录结构
        .process("Localization")      // 本地化资源自动处理
    ]
)
```

在代码中访问资源：

```swift
import Foundation

if let url = Bundle.module.url(forResource: "Config", withExtension: "json") {
    let data = try Data(contentsOf: url)
}

if let image = UIImage(named: "logo", in: .module, compatibleWith: nil) {
    imageView.image = image
}
```

| 处理方式 | `.process()` | `.copy()` |
|---------|-------------|-----------|
| 行为 | SPM 自动优化（如 Asset Catalog 编译） | 原样拷贝到 bundle |
| 适用 | 图片、本地化、Asset Catalog | JSON、配置文件、数据文件 |
| 访问 | `Bundle.module` | `Bundle.module` |

> 💡 始终使用 `Bundle.module` 而非 `Bundle.main` 访问包内资源。SPM 会为每个 target 生成独立的 resource bundle。

### 3.3 条件编译

不同平台可能需要不同的依赖或源码，就像同一款衣服分冬装和夏装——面料不同，但款式一致。

```swift
dependencies: [
    .package(url: "https://github.com/Alamofire/Alamofire.git", from: "5.8.0"),
    .package(url: "https://github.com/apple/swift-nio.git", from: "2.0.0", condition: .when(platforms: [.macOS]))
]
```

在源码中使用编译条件：

```swift
#if canImport(UIKit)
import UIKit
public typealias PlatformColor = UIColor
#elseif canImport(AppKit)
import AppKit
public typealias PlatformColor = NSColor
#endif

public struct Theme {
    public static let primary = PlatformColor(red: 0.2, green: 0.5, blue: 0.9, alpha: 1.0)
}
```

### 3.4 平台指定

明确声明最低支持平台，就像餐厅标注"最低消费"——不达要求就不接待。

```swift
platforms: [
    .iOS(.v15),
    .macOS(.v12),
    .tvOS(.v15),
    .watchOS(.v8),
    .visionOS(.v1)
]
```

> ⚠️ 如果不指定 `platforms`，SPM 会使用各平台的最低默认版本（如 iOS 9.0），这可能导致你使用了新 API 却没有编译警告。**务必显式指定平台版本。**

## 4. CocoaPods 使用

### 4.1 Podfile 配置

虽然 SPM 是未来方向，但大量历史项目和第三方库仍使用 CocoaPods。掌握它就像学会开手动挡——自动挡是趋势，但路上还有很多手动挡的车。

```ruby
platform :ios, '15.0'
use_frameworks!

target 'MyApp' do
  pod 'Alamofire', '~> 5.8'
  pod 'Kingfisher', '~> 7.0'
  pod 'SnapKit', '~> 5.6'

  target 'MyAppTests' do
    inherit! :search_paths
    pod 'Quick', '~> 7.0'
    pod 'Nimble', '~> 13.0'
  end
end

post_install do |installer|
  installer.pods_project.targets.each do |target|
    target.build_configurations.each do |config|
      config.build_settings['IPHONEOS_DEPLOYMENT_TARGET'] = '15.0'
    end
  end
end
```

Podfile 版本操作符：

| 操作符 | 含义 | 示例 | 匹配版本 |
|--------|------|------|---------|
| `~> x.y` | 兼容更新 | `~> 5.8` | ≥ 5.8, < 6.0 |
| `~> x.y.z` | 补丁更新 | `~> 5.8.0` | ≥ 5.8.0, < 5.9.0 |
| `>= x.y` | 大于等于 | `>= 5.0` | ≥ 5.0 |
| `= x.y.z` | 精确版本 | `= 5.8.1` | 仅 5.8.1 |

### 4.2 常用命令

| 命令 | 用途 | 使用场景 |
|------|------|---------|
| `pod install` | 安装/更新 Pod | 每次修改 Podfile 后 |
| `pod update` | 更新所有 Pod 到最新兼容版本 | 想获取最新版本时 |
| `pod update Alamofire` | 仅更新指定 Pod | 只想更新某个库 |
| `pod repo update` | 更新本地 Specs 仓库 | `pod install` 找不到新版本时 |
| `pod deintegrate` | 移除 CocoaPods 集成 | 迁移到 SPM 时 |
| `pod cache clean --all` | 清除缓存 | 下载损坏或版本异常时 |

> 💡 `pod install` vs `pod update`：`install` 会尊重 Podfile.lock 中的版本，只处理新增/删除的依赖；`update` 会忽略 lock 文件，拉取最新兼容版本。**日常开发应使用 `pod install`**。

### 4.3 与 SPM 共存

迁移期间，CocoaPods 和 SPM 可以共存，就像新旧两套家具可以暂时放在同一个房间里。

**方式一：CocoaPods 项目中引入 SPM 包**

在 Xcode 中直接 File → Add Package Dependencies...，Xcode 会自动处理。Pod 项目和 SPM 包互不干扰。

**方式二：逐步迁移策略**

```
阶段 1: 新依赖优先使用 SPM
阶段 2: 将有 SPM 版本的 Pod 逐个迁移
阶段 3: 仅剩无 SPM 版本的 Pod
阶段 4: 完全移除 CocoaPods
```

迁移单个库的步骤：

1. 从 Podfile 中删除该库
2. 运行 `pod install`
3. 在 Xcode 中通过 SPM 添加该库
4. 编译验证，修复可能的 API 变更
5. 提交变更

> ⚠️ 迁移时注意：同一个库不能同时通过 SPM 和 CocoaPods 引入，否则会产生重复符号冲突。

## 6. 开源库选型原则

选开源库就像选队友——能力再强，如果不靠谱，也会拖垮整个团队。

### 6.1 评估维度

| 维度 | 检查方法 | 红线指标 |
|------|---------|---------|
| 活跃度 | 最近 commit 时间、issue 响应速度 | 超过 1 年无更新需警惕 |
| Star 数 | GitHub Stars | 低于 500 需谨慎评估 |
| 维护者 | 核心贡献者数量 | 仅 1 人维护风险较高 |
| 许可证 | LICENSE 文件 | 无许可证 = 不可用 |
| 包大小 | 编译后体积增量 | 超过 5MB 需评估必要性 |
| 依赖链 | 依赖的其他库数量 | 传递依赖过多增加风险 |
| 文档质量 | README、API Doc、示例 | 无文档 = 上手成本极高 |
| Swift 版本 | 是否支持最新 Swift | 不支持 Swift 6 需关注 |

### 6.2 选型决策流程

```
1. 原生 API 能否满足？ ──是──→ 使用原生方案
       │否
2. 是否有多个候选库？ ──否──→ 评估唯一候选
       │是
3. 对比活跃度与 Star ──淘汰低活跃库
       │
4. 检查许可证兼容性 ──淘汰不兼容库
       │
5. 评估包大小与依赖链 ──淘汰过重库
       │
6. 试运行 Demo/Example ──验证易用性
       │
7. 锁定版本，引入项目
```

### 6.3 许可证速查

| 许可证 | 商用 | 修改 | 需开源 | 推荐度 |
|--------|------|------|--------|--------|
| MIT | ✅ | ✅ | ❌ | ⭐⭐⭐⭐⭐ |
| Apache 2.0 | ✅ | ✅ | ❌ | ⭐⭐⭐⭐⭐ |
| BSD | ✅ | ✅ | ❌ | ⭐⭐⭐⭐⭐ |
| LGPL | ✅ | ✅ | 部分 | ⭐⭐⭐ |
| GPL | ❌ | ✅ | ✅ | ⭐ |
| 无许可证 | ❌ | ❌ | - | 🚫 |

> ⚠️ GPL 许可证具有"传染性"——如果你的项目链接了 GPL 库，整个项目可能需要开源。App Store 上架的 App 使用 GPL 库存在法律争议，**强烈建议避免**。

## 7. 依赖冲突解决

### 7.1 版本冲突

当两个依赖要求同一个库的不同版本时，就会产生冲突——就像两个人抢同一把椅子，谁都不肯让步。

典型场景：

```
MyApp
├── LibraryA → requires Alamofire ~> 5.8  (5.8.0 ~ 5.x.x)
└── LibraryB → requires Alamofire ~> 5.6  (5.6.0 ~ 5.x.x)
```

SPM 的解决策略：取两个范围的**交集**，即 `5.8.0 ~ 5.x.x`。

但如果冲突无法调和：

```
MyApp
├── LibraryA → requires Alamofire ~> 5.0
└── LibraryB → requires Alamofire ~> 6.0
```

SPM 会报错：`package 'Alamofire' is required using two different versioning strategies`。

**解决方法：**

1. **升级/降级某个依赖**，使其兼容同一大版本
2. **联系库作者**请求更新依赖版本
3. **Fork 并自行修改**依赖版本后指向自己的仓库

```swift
// 使用 fork 替代原始仓库
.package(url: "https://github.com/your-org/Alamofire.git", .upToNextMinor(from: "5.8.0"))
```

### 7.2 不同源混用冲突

SPM 和 CocoaPods 同时引入同一个库时，会出现重复符号错误：

```
duplicate symbol '_$s9Alamofire...' in:
    - MyApp(Alamofire.o)
    - Pods_Alamofire(Alamofire.o)
```

**解决方法：**

1. 统一使用一种方式引入该库
2. 如果 Pod 有 SPM 版本，迁移到 SPM
3. 如果 Pod 没有 SPM 版本，在 SPM 中用 binaryTarget 引入 Pod 编译的 xcframework

### 7.3 Resolution 策略

SPM 使用 `Package.resolved` 文件锁定依赖版本（类似 Podfile.lock），确保团队成员和 CI 环境使用一致的版本。

```bash
# 查看当前依赖树
swift package show-dependencies

# 强制重新解析依赖
swift package resolve

# 重置所有缓存（终极手段）
swift package reset
```

在 Xcode 中：File → Packages → Reset Package Caches 可以清除缓存重新拉取。

> 💡 将 `Package.resolved` 提交到版本控制中，确保团队和 CI 使用完全相同的依赖版本。如果希望获取最新兼容版本，使用 File → Packages → Update to Latest Package Versions。

## 8. 安全与合规

### 8.1 许可证合规检查

App 上架前必须确保所有依赖的许可证合规，就像餐厅开业前必须拿到所有食材的合格证。

**自动化检查工具：**

```bash
# 使用 swift-license-check 检查 SPM 依赖许可证
swift run swift-license-check

# 使用 LicensePlist 生成许可证清单（CocoaPods + SPM）
brew install licenseplist
license-plist --output-path ./Settings.bundle
```

LicensePlist 会自动生成一个 Settings.bundle，在 App 的设置页面展示所有第三方库的许可证信息——这是 App Store 审核的常见要求。

### 8.2 供应链安全

开源供应链攻击日益增多——有人给流行的库投毒，就像有人在食品供应链中掺假。

**防护措施：**

| 措施 | 说明 | 实践 |
|------|------|------|
| 校验完整性 | SPM 的 checksum 机制 | binaryTarget 必须指定 checksum |
| 锁定版本 | 使用 resolved 文件 | 提交 Package.resolved 到 Git |
| 审查依赖 | 定期检查依赖树 | `swift package show-dependencies` |
| 最小依赖 | 只引入必要的库 | 避免"全家桶"式引入 |
| 私有 Mirror | 企业内部镜像 | 使用 Artifactory / Nexus |
| SAST 扫描 | 静态安全扫描 | 集成到 CI 流程 |

> ⚠️ 2023 年发生的 XcodeGhost 事件和多个 npm 投毒事件警示我们：**不要盲目信任任何第三方代码**。对关键依赖，应定期审计源码。

### 8.3 隐私清单兼容

从 2024 年春季起，App Store 要求所有 App 和第三方 SDK 声明隐私清单（Privacy Manifest）。这就像食品包装上的"营养成分表"——必须如实标注。

**隐私清单文件：** `PrivacyInfo.xcprivacy`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>NSPrivacyTracking</key>
    <false/>
    <key>NSPrivacyTrackingDomains</key>
    <array/>
    <key>NSPrivacyCollectedDataTypes</key>
    <array>
        <dict>
            <key>NSPrivacyCollectedDataType</key>
            <string>NSPrivacyCollectedDataTypeEmailAddress</string>
            <key>NSPrivacyCollectedDataTypeLinked</key>
            <true/>
            <key>NSPrivacyCollectedDataTypeTracking</key>
            <false/>
            <key>NSPrivacyCollectedDataTypePurposes</key>
            <array>
                <string>NSPrivacyCollectedDataTypePurposeAppFunctionality</string>
            </array>
        </dict>
    </array>
    <key>NSPrivacyAccessedAPITypes</key>
    <array>
        <dict>
            <key>NSPrivacyAccessedAPIType</key>
            <string>NSPrivacyAccessedAPITypeFileTimestamp</string>
            <key>NSPrivacyAccessedAPITypeReasons</key>
            <array>
                <string>C617.1</string>
            </array>
        </dict>
    </array>
</dict>
</plist>
```

在 SPM 中包含隐私清单：

```swift
.target(
    name: "MyAppKit",
    dependencies: [],
    resources: [
        .copy("PrivacyInfo.xcprivacy")
    ]
)
```

**需要声明的常见 API：**

| API 类别 | 说明 | 常见原因代码 |
|---------|------|------------|
| File Timestamp | 文件时间戳访问 | C617.1 |
| System Boot Time | 系统启动时间 | 35F9.1 |
| Disk Space | 磁盘空间查询 | E174.1 |
| Active Keyboards | 活跃键盘列表 | 3B52.1 |
| User Defaults | UserDefaults 访问 | CA92.1 |

> ⚠️ 如果你的 App 或依赖使用了上述 API 但未声明隐私清单，Apple 可能会拒绝上架或发送警告邮件。选择第三方库时，应优先选择已适配隐私清单的库。
