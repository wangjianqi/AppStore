# 代码评审流程

> 🎯 **本章目标**：理解代码评审的核心价值，掌握评审流程的建立方法，学会编写高质量 PR 与评审意见，建立人机协作的评审工作流。

---

## 为什么需要代码评审

### 代码评审的四大价值

代码评审（Code Review）是现代软件开发中不可或缺的环节。它不仅仅是"找 Bug"，更是一种团队协作与知识传递的机制。

**质量保障**：评审是最有效的缺陷预防手段之一。研究表明，代码评审能发现 60%–90% 的缺陷，远高于测试 alone 的检出率。评审者以旁观者视角审视代码，往往能发现作者因思维定式而忽略的问题。

**知识共享**：每一次评审都是一次隐性的知识传递。评审者了解业务逻辑的实现方式，作者从评审意见中学习更好的编码技巧。这种双向交流打破了"只有某个人懂某段代码"的知识孤岛。

**团队标准**：评审过程天然地推动团队编码风格的一致性。当多人反复指出同一类风格问题时，团队会自发形成共识，进而沉淀为规范文档或 Lint 规则。

**持续改进**：评审不仅改进当前代码，更推动团队工程实践的演进。从评审中发现的共性问题，可以转化为自动化检查、架构决策或最佳实践文档，形成正向循环。

### 没有评审的痛点

缺乏代码评审的团队，往往会遇到以下问题：

- **Bug 上线**：逻辑错误、边界条件遗漏、线程安全问题等在开发阶段未被捕获，直接进入生产环境
- **风格混乱**：不同开发者使用不同的命名风格、架构模式和代码组织方式，项目逐渐变得难以维护
- **知识孤岛**：核心逻辑只有作者本人理解，一旦人员变动，代码变成"无人敢动"的黑盒
- **技术债务累积**：为了赶进度而写的临时方案、硬编码、缺少错误处理的代码不断堆积

### 代码评审 vs AI 代码审查

| 维度 | 代码评审（人工） | AI 代码审查 |
|------|------------------|-------------|
| 速度 | 较慢，依赖人工时间 | 极快，秒级返回结果 |
| 深度 | 能理解业务逻辑与上下文 | 擅长语法与模式识别 |
| 一致性 | 受评审者状态影响 | 规则一致，不受情绪影响 |
| 创造性 | 能提出架构级改进建议 | 主要识别已知模式的问题 |
| 知识传递 | 双向交流，隐性知识共享 | 单向输出，无社交属性 |
| 成本 | 占用团队时间 | API 调用成本 |
| 最佳策略 | — | AI 先审 + 人工复审 |

> 💡 **提示**：AI 代码审查不是要取代人工评审，而是作为前置环节过滤掉低级问题，让人工评审聚焦于架构与业务逻辑层面。

## 评审流程建立

### PR 驱动的评审流程

现代 iOS 开发团队普遍采用 Pull Request（PR）驱动的评审流程。核心步骤如下：

1. **开发者创建分支**：从 `main` 或 `develop` 拉取功能分支
2. **编写代码并提交**：在功能分支上完成开发，确保本地通过编译与测试
3. **创建 PR**：推送分支到远程仓库，创建 Pull Request
4. **自动检查**：CI 流水线运行编译、测试、Lint 检查
5. **人工评审**：至少一位评审者审查代码
6. **修改与迭代**：根据评审意见修改代码
7. **批准与合并**：评审通过后合并到目标分支

### PR 大小控制：小 PR 原则

小 PR 是高效评审的基础。一个 PR 的变更量应控制在 200–400 行以内（不含自动生成代码）。超过 400 行的 PR 会显著降低评审质量——评审者要么草草了事，要么需要花费过多时间。

**拆分策略**：

- 按功能拆分：一个大功能拆为数据层、业务层、UI 层多个 PR
- 按阶段拆分：先提交基础架构，再提交具体实现
- 按文件类型拆分：先提交 Model 定义，再提交业务逻辑

### PR 描述模板

一个清晰的 PR 描述应包含以下要素：

```markdown
## 变更说明
简要描述本次变更的目的和内容。

## 关联 Issue
Closes #123

## 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 性能优化

## 测试方式
描述如何验证本次变更。

## 截图/录屏
（如涉及 UI 变更，附上截图或录屏）

## Checklist
- [ ] 自测通过
- [ ] 单元测试已补充
- [ ] 无 SwiftLint 警告
- [ ] 无硬编码字符串
```

### 评审角色与职责

| 角色 | 职责 |
|------|------|
| PR 作者 | 编写高质量代码、完善 PR 描述、自审后再提交、及时响应评审意见 |
| 评审者 | 仔细审查代码、提供建设性意见、在约定时间内完成评审 |
| 项目负责人 | 确保评审流程执行、处理争议、维护评审规范 |

### 评审节奏：何时评审、多久完成

评审的时效性直接影响团队效率。推荐的节奏如下：

- **何时评审**：收到评审请求后，在当前任务的一个自然中断点（如完成手头一个任务后）开始评审
- **多久完成**：小型 PR（200 行以内）应在 4 小时内完成评审；中型 PR（200–400 行）应在 1 个工作日内完成
- **避免堆积**：每天至少留出 30 分钟专门处理评审任务

### 流程图示

```
创建分支 → 编写代码 → 自审 → 创建 PR → CI 自动检查
                                              ↓
                                         检查通过？
                                        ↙        ↘
                                      是           否
                                      ↓            ↓
                                  人工评审    修复后重新提交
                                      ↓
                                  评审通过？
                                 ↙        ↘
                               是           否
                               ↓            ↓
                            合并代码    修改后重新评审
```

## 编写高质量 PR

### PR 标题与描述规范

PR 标题应简洁明确，使用 Conventional Commits 风格：

```
feat: 添加用户登录功能
fix: 修复购物车数量计算错误
refactor: 重构网络层为 async/await
```

描述部分要回答三个核心问题：**为什么改**、**改了什么**、**怎么验证**。

### 关联 Issue 与 Spec

每个 PR 都应关联对应的 Issue 或 Spec 文档。这样做的好处：

- 评审者可以快速了解需求背景
- 合并后自动关闭对应 Issue
- 形成从需求到代码的完整追溯链

在 PR 描述中使用关键字关联：

```markdown
Closes #42
Spec: docs/specs/user-login.md
```

### 代码变更的自说明

好的 PR 应该让评审者仅通过代码和描述就能理解变更意图，而不需要反复追问作者。以下是一些实践：

- 变量与函数命名应准确表达意图
- 复杂逻辑添加必要的说明
- 对非显而易见的设计决策在 PR 描述中解释原因

```swift
struct UserSession {
    let userID: String
    let accessToken: String
    let refreshToken: String
    let expirationDate: Date

    var isExpired: Bool {
        expirationDate < Date()
    }

    var needsRefresh: Bool {
        expirationDate < Date().addingTimeInterval(300)
    }
}
```

在上述代码中，`needsRefresh` 在过期前 5 分钟返回 `true`，这个"5 分钟"的设计决策应在 PR 描述中说明原因。

### 截图与录屏辅助

涉及 UI 变更的 PR，必须附带截图或录屏。这是评审者判断 UI 实现是否符合设计稿的最直接方式。

推荐做法：

- **截图**：附上变更前后的对比截图
- **录屏**：涉及交互动画时，录制短视频展示效果
- **多设备**：如涉及布局适配，提供不同屏幕尺寸的截图

### PR 模板示例

```markdown
## 变更说明
实现用户登录功能，支持手机号+验证码登录方式。

## 关联
Closes #42
```

## 评审最佳实践

### 评审关注点分层

评审时应按层次关注不同维度，避免将精力平均分配：

| 层次 | 关注点 | 示例问题 |
|------|--------|----------|
| 架构层 | 设计是否合理、职责是否清晰 | 这个 ViewModel 是否承担了过多职责？ |
| 逻辑层 | 业务逻辑是否正确、边界条件是否覆盖 | 用户未登录时的行为是否处理？ |
| 实现层 | 代码是否高效、是否有更好的 API | 是否可以用 `async let` 替代嵌套回调？ |
| 风格层 | 命名是否规范、格式是否一致 | 变量名是否符合 Swift 命名规范？ |

> 💡 **提示**：风格层的问题应优先交给 SwiftLint 等工具自动检查，评审者应将精力集中在架构层和逻辑层。

### 评审意见的写法

好的评审意见应具备三个特征：**建设性**、**具体**、**可操作**。

**建设性**：不只指出问题，还提供改进方向。

```swift
// ❌ 不好的评审意见
"这段代码写得不好。"

// ✅ 好的评审意见
"这里使用强制解包可能导致崩溃，建议使用 guard let 安全解包：
 guard let user = user else { return }
"
```

**具体**：明确指出代码位置和问题所在。

```swift
// ❌ 不好的评审意见
"有些地方缺少错误处理。"

// ✅ 好的评审意见
"第 47 行的 networkManager.fetch() 缺少错误处理，
如果网络请求失败，这里会直接 crash。建议添加 do-catch 或
在 async 函数中处理可能的错误。"
```

**可操作**：评审意见应让作者知道下一步该怎么做。

```swift
// ❌ 不好的评审意见
"性能有问题。"

// ✅ 好的评审意见
"这个方法在 cellForRow 中每次都创建新的 DateFormatter，
建议将 formatter 提取为 static 属性复用：
static let formatter: DateFormatter = { ... }()
"
```

### 评审常见反模式

| 反模式 | 描述 | 改进方式 |
|--------|------|----------|
| 橡皮图章评审 | 只看一眼就 Approve，未认真审查 | 至少花 10 分钟仔细阅读代码 |
| 吹毛求疵 | 只关注格式和命名，忽略架构问题 | 将格式问题交给 Lint，聚焦逻辑 |
| 评审阻塞 | 长时间不评审，阻塞他人进度 | 设定评审 SLA，优先处理评审请求 |
| 争论式评审 | 在 PR 中反复争论，无法达成共识 | 争议问题线下讨论，记录结论 |
| 大包评审 | 一次性评审上千行代码 | 要求拆分为小 PR |
| 只批不赞 | 只指出问题，从不肯定好的写法 | 对优秀的代码设计给予正面反馈 |

### 评审与讨论的平衡

评审是讨论代码的场所，但不是所有讨论都适合在 PR 中进行。以下原则有助于保持平衡：

- **代码相关**的讨论留在 PR 中，形成知识记录
- **架构方向**的争议移到 Issue 或会议中讨论
- **个人偏好**的分歧遵循团队规范，规范未覆盖的由 Tech Lead 裁决
- **紧急修复**可以简化评审流程，但事后必须补审

### 评审 Checklist

以下是一份通用的 iOS 代码评审 Checklist：

- [ ] 代码是否正确实现了需求？
- [ ] 是否有明显的逻辑错误或边界条件遗漏？
- [ ] 错误处理是否完善（网络失败、数据为空、权限拒绝等）？
- [ ] 是否存在内存泄漏风险（闭包循环引用、未释放的资源）？
- [ ] 线程安全：是否有并发访问共享状态的问题？
- [ ] API 设计是否合理，命名是否清晰？
- [ ] 是否有硬编码的字符串、颜色、尺寸？
- [ ] 是否有可以复用的代码被重复实现？
- [ ] 测试覆盖是否充分？
- [ ] 是否引入了不必要的依赖？

## 人机协作评审工作流

### AI 先审 + 人工复审

将 AI 代码审查作为人工评审的前置环节，可以显著提升评审效率。推荐的工作流：

1. **开发者提交 PR**
2. **AI 自动审查**：检查语法问题、潜在 Bug、风格违规、安全风险
3. **开发者根据 AI 意见修改**：处理低级问题
4. **人工评审**：聚焦架构设计、业务逻辑、用户体验
5. **合并代码**

这种模式的优势在于：AI 过滤掉大量低级问题，人工评审者不再需要为命名不规范、缺少空行等琐事分心，可以集中精力在真正需要人类判断的维度上。

### SwiftLint 自动检查作为评审前置条件

SwiftLint 应作为 PR 合并的必要条件。在 CI 流水线中配置：

```yaml
# GitHub Actions 示例
steps:
  - name: SwiftLint
    run: |
      swiftlint lint --reporter github-actions-logging
```

当 SwiftLint 检查未通过时，PR 应被阻止合并。这确保了风格层的问题不会进入人工评审环节。

在 Xcode 中也可以配置 Build Phase 自动运行 SwiftLint：

```swift
if which swiftlint >/dev/null; then
    swiftlint
else
    echo "warning: SwiftLint not installed"
fi
```

### AI 生成评审摘要

AI 可以在评审前自动生成变更摘要，帮助评审者快速理解 PR 的整体情况。例如：

```markdown
## AI 评审摘要

本次 PR 新增了用户登录功能，主要变更：
- 新增 `UserSession` 模型（+25 行）
- 新增 `LoginViewController` 及 ViewModel（+180 行）
- 修改 `NetworkManager` 支持 token 刷新（+30 行）
- 新增 3 个单元测试文件（+120 行）

潜在关注点：
- `LoginViewModel.verifyCode()` 中存在强制解包
- `KeychainHelper` 缺少 unit test
- `accessToken` 存储未使用 `kSecAttrAccessible` 属性
```

这种摘要让评审者在阅读代码前就建立了整体认知，大大缩短了理解 PR 的时间。

### 评审效率提升策略

| 策略 | 描述 | 效果 |
|------|------|------|
| PR 体积控制 | 每个 PR 不超过 400 行 | 评审质量提升 30%+ |
| AI 前置审查 | AI 先过滤低级问题 | 人工评审时间减少 40% |
| SwiftLint 门禁 | Lint 不通过禁止合并 | 风格问题不再占用评审时间 |
| 评审摘要 | AI 生成变更概览 | 评审者上手时间减少 50% |
| 评审时间块 | 每天固定 30 分钟处理评审 | 评审响应时间缩短 |
| 评审配对 | 复杂 PR 两人同时评审 | 关键代码评审质量提升 |
| 评审轮换 | 不同人评审不同模块 | 促进跨模块知识共享 |

> ⚠️ **警告**：AI 审查不能替代人工评审。AI 无法理解业务上下文、产品意图和用户体验，这些维度必须由人类评审者把关。

## 小结

代码评审是 iOS 开发团队保障代码质量、促进知识共享的核心实践。通过建立清晰的评审流程、编写高质量的 PR、遵循评审最佳实践，并善用 AI 工具辅助，团队可以显著提升评审效率和代码质量。

| 要点 | 说明 |
|------|------|
| 评审价值 | 质量保障、知识共享、团队标准、持续改进 |
| 流程核心 | PR 驱动、小 PR 原则、明确角色与节奏 |
| PR 质量 | 规范标题描述、关联 Issue、自说明代码、截图辅助 |
| 评审实践 | 分层关注、建设性意见、避免反模式、使用 Checklist |
| 人机协作 | AI 先审 + 人工复审、SwiftLint 门禁、AI 评审摘要 |

> 💡 **提示**：评审文化的建立是一个渐进过程。从最基础的流程开始，逐步引入工具和规范，让团队在实践中不断优化。
