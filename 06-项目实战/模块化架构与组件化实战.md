# 模块化架构与组件化实战

> 🎯 **本章目标**：理解模块化与组件化的核心思想，掌握基于 SPM 的多模块拆分策略，学会 Feature/Domain/Data 三层分层架构，能够实现模块间通信与解耦，掌握渐进式模块化改造的方法。

---

## 1. 为什么需要模块化

### 1.1 单体架构的痛点

当你刚启动一个 iOS 项目时，所有代码放在一个 Target 里，编译飞快、跳转方便，一切看起来都很美好。但随着业务增长，问题会像滚雪球一样越来越大：

| 痛点 | 具体表现 | 影响 |
|------|---------|------|
| 编译缓慢 | 改一行代码要等 3~5 分钟全量编译 | 开发效率断崖式下降 |
| 冲突频繁 | 多人修改同一个文件，Git 冲突不断 | 团队协作成本飙升 |
| 职责不清 | 网络请求、UI 逻辑、数据存储混在一起 | 代码像意大利面条一样纠缠 |
| 难以测试 | 想测一个业务逻辑必须启动整个 App | 测试覆盖率上不去 |
| 复用困难 | 想把登录功能用到另一个 App，发现到处是耦合 | 只能复制粘贴再改 |
| 新人迷茫 | 几百个文件没有清晰的边界和归属 | 上手周期极长 |

### 1.2 生活类比：宜家家具的模块化设计

模块化就像宜家家具的设计理念——一个书架不是一整块木头雕出来的，而是由侧板、层板、背板、螺丝等多个独立部件组成。每个部件可以独立生产、独立质检、独立包装。你想要三层书架就买三层，想扩展到五层就再加两块层板。

代码模块化也是同样的道理：把 App 拆成多个独立模块，每个模块独立开发、独立测试、按需组合。登录模块、支付模块、分享模块就像书架的层板，想用哪个加哪个。

### 1.3 何时需要模块化

模块化不是万能药，也不是所有项目都需要。过早模块化反而会增加不必要的复杂度。以下判断标准帮你做出决策：

| 项目规模 | 特征 | 建议 |
|---------|------|------|
| 小型（1~3 人，< 50 个文件） | 功能简单、迭代慢、团队小 | 单模块即可，保持简单 |
| 中型（3~5 人，50~200 个文件） | 功能增多、开始出现职责混乱 | 开始规划模块化，先拆基础层 |
| 大型（5~10 人，200~500 个文件） | 多业务线、编译慢、冲突多 | 必须模块化，Feature 级别拆分 |
| 超大型（10+ 人，500+ 个文件） | 多团队协作、CI 时间超长 | 深度组件化 + 仓库拆分 + Tuist |

> 💡 **提示**：当你发现"改一个功能要编译整个项目"或"两个人同时改同一个文件"频繁发生时，就是模块化的最佳时机。

### 1.4 模块化 vs 组件化的区别

很多人把模块化和组件化混为一谈，但它们侧重点不同：

| 维度 | 模块化 | 组件化 |
|------|--------|--------|
| 核心思想 | 按职责拆分代码，降低耦合 | 按功能封装独立单元，即插即用 |
| 粒度 | 可以很大（整个业务模块） | 通常较小（一个 UI 控件、一个功能单元） |
| 复用性 | 不强调跨项目复用 | 强调跨项目复用 |
| 独立性 | 模块间有依赖关系 | 组件尽量独立，通过协议通信 |
| 典型例子 | FeatureAuth、FeatureOrder | LoginKit、ShareKit、PaymentKit |

简单说：**模块化是拆，组件化是封**。模块化关注"怎么把大项目拆小"，组件化关注"怎么把小功能封好"。在实际项目中，两者往往结合使用——先模块化拆分，再对独立模块做组件化封装。

## 2. 模块化基础：SPM 多模块项目

### 2.1 SPM Local Package 的创建与配置

Swift Package Manager（SPM）是 Apple 官方的依赖管理工具，从 Xcode 11 开始深度集成。用 SPM 做多模块拆分，不需要额外的工具，开箱即用。

创建 Local Package 的步骤：

1. 在 Xcode 中选择 File → New → Package
2. 选择存放位置（通常在项目根目录的 `Packages/` 文件夹下）
3. 命名 Package（如 `FeatureAuth`）
4. Xcode 自动生成标准目录结构

也可以用命令行创建：

```bash
mkdir -p Packages/FeatureAuth
cd Packages/FeatureAuth
swift package init --name FeatureAuth --type library
```

### 2.2 Package.swift 的依赖声明

Package.swift 是 SPM 的核心配置文件，它定义了模块的名称、依赖、目标和产品：

```swift
import PackageDescription

let package = Package(
    name: "FeatureAuth",
    platforms: [.iOS(.v15)],
    products: [
        .library(name: "FeatureAuth", targets: ["FeatureAuth"])
    ],
    dependencies: [
        .package(path: "../Domain"),
        .package(path: "../DesignKit")
    ],
    targets: [
        .target(
            name: "FeatureAuth",
            dependencies: [
                "Domain",
                "DesignKit"
            ]
        ),
        .testTarget(
            name: "FeatureAuthTests",
            dependencies: ["FeatureAuth"]
        )
    ]
)
```

关键配置说明：

| 字段 | 作用 | 说明 |
|------|------|------|
| `platforms` | 最低支持平台版本 | 建议统一设置，避免各模块不一致 |
| `products` | 对外暴露的库 | 其他模块只能引用这里声明的产品 |
| `dependencies` | 外部依赖 | 支持本地路径、Git 仓库、Registry |
| `targets` | 编译目标 | 每个 Target 对应一个编译产物 |

### 2.3 多 Target 配置

一个 Package 可以包含多个 Target，适合把相关功能组织在一起：

```swift
targets: [
    .target(name: "NetworkCore", dependencies: []),
    .target(name: "NetworkOAuth", dependencies: ["NetworkCore"]),
    .testTarget(name: "NetworkCoreTests", dependencies: ["NetworkCore"]),
    .testTarget(name: "NetworkOAuthTests", dependencies: ["NetworkOAuth"])
]
```

### 2.4 项目目录结构规划

一个典型的多模块项目目录结构：

```
MyApp/
├── MyApp/                    # 主 App Target（壳工程）
│   ├── AppDelegate.swift
│   ├── SceneDelegate.swift
│   └── Resources/
├── Packages/
│   ├── FeatureAuth/          # 登录注册模块
│   │   ├── Package.swift
│   │   └── Sources/
│   ├── FeatureHome/          # 首页模块
│   │   ├── Package.swift
│   │   └── Sources/
│   ├── FeatureProfile/       # 个人中心模块
│   │   ├── Package.swift
│   │   └── Sources/
│   ├── Domain/               # 业务领域层
│   │   ├── Package.swift
│   │   └── Sources/
│   ├── Data/                 # 数据层
│   │   ├── Package.swift
│   │   └── Sources/
│   └── DesignKit/            # UI 基础组件
│       ├── Package.swift
│       └── Sources/
├── MyApp.xcodeproj
└── MyApp.xcworkspace
```

> 💡 **提示**：把所有 Local Package 放在 `Packages/` 目录下，而不是散落在项目各处，这样结构清晰、便于管理。

### 2.5 完整示例：从单模块到多模块的拆分步骤

假设你有一个单模块项目，登录功能写在 `LoginViewController.swift` 里。拆分步骤如下：

**第一步：创建 FeatureAuth Package**

```bash
mkdir -p Packages/FeatureAuth/Sources/FeatureAuth
cd Packages/FeatureAuth
swift package init --name FeatureAuth --type library
```

**第二步：迁移代码**

将 `LoginViewController.swift`、`LoginViewModel.swift` 等文件从主 Target 移动到 `Packages/FeatureAuth/Sources/FeatureAuth/` 下。

**第三步：配置 Package.swift**

```swift
import PackageDescription

let package = Package(
    name: "FeatureAuth",
    platforms: [.iOS(.v15)],
    products: [
        .library(name: "FeatureAuth", targets: ["FeatureAuth"])
    ],
    dependencies: [],
    targets: [
        .target(name: "FeatureAuth", dependencies: []),
        .testTarget(name: "FeatureAuthTests", dependencies: ["FeatureAuth"])
    ]
)
```

**第四步：在主 App 中添加依赖**

在 Xcode 中将 `Packages/FeatureAuth` 拖入项目，或在主 App Target 的 Frameworks 中添加 `FeatureAuth`。

**第五步：编译验证**

```bash
xcodebuild build \
    -scheme MyApp \
    -destination 'platform=iOS Simulator,name=iPhone 15'
```

> ⚠️ **警告**：迁移代码时一定要注意 `import` 语句。移入 Package 的文件需要 `import UIKit`，主 App 中使用该模块需要 `import FeatureAuth`。遗漏 import 是最常见的编译错误。

## 3. 分层架构：Feature / Domain / Data

### 3.1 三层架构的核心思想

Feature / Domain / Data 三层架构源自 Clean Architecture，是 iOS 项目中最实用的分层方案。它的核心原则是**依赖规则**：外层可以依赖内层，内层绝对不能依赖外层。

```
┌─────────────────────────────────┐
│         Feature 层              │  ← UI、ViewController、ViewModel
│    ┌─────────────────────┐      │
│    │     Domain 层       │      │  ← 业务规则、实体、用例
│    │  ┌─────────────┐    │      │
│    │  │  Data 层    │    │      │  ← 网络、数据库、缓存
│    │  └─────────────┘    │      │
│    └─────────────────────┘      │
└─────────────────────────────────┘

依赖方向：Feature → Domain ← Data
```

| 层 | 职责 | 包含内容 | 依赖 |
|---|------|---------|------|
| Feature | UI 展示与交互 | ViewController、ViewModel、View | Domain |
| Domain | 业务规则与实体 | Entity、UseCase、Repository 协议 | 无（最内层） |
| Data | 数据获取与持久化 | NetworkService、Repository 实现、CoreData | Domain |

> 💡 **提示**：Domain 层是整个架构的核心，它不依赖任何外层，因此可以被独立测试。Repository 的协议定义在 Domain 层，实现在 Data 层——这就是**依赖倒置**。

### 3.2 Feature 层：UI 与交互逻辑

Feature 层负责所有的 UI 展示和用户交互。每个 Feature 对应一个独立的 SPM Package：

```swift
import UIKit
import Domain

public class LoginViewController: UIViewController {
    private let loginUseCase: LoginUseCaseProtocol
    private var viewModel: LoginViewModel!

    public init(loginUseCase: LoginUseCaseProtocol) {
        self.loginUseCase = loginUseCase
        super.init(nibName: nil, bundle: nil)
    }

    required init?(coder: NSCoder) {
        fatalError("init(coder:) has not been implemented")
    }

    public override func viewDidLoad() {
        super.viewDidLoad()
        setupUI()
        bindViewModel()
    }

    private func setupUI() {
        view.backgroundColor = .systemBackground
    }

    private func bindViewModel() {
        viewModel = LoginViewModel(loginUseCase: loginUseCase)
    }

    @objc private func loginTapped() {
        Task {
            do {
                let user = try await viewModel.login(
                    email: "test@example.com",
                    password: "password"
                )
                print("Login success: \(user.name)")
            } catch {
                print("Login failed: \(error)")
            }
        }
    }
}
```

### 3.3 Domain 层：业务规则与实体

Domain 层是纯 Swift 代码，不依赖 UIKit，不依赖任何外部框架：

```swift
public struct User: Sendable {
    public let id: String
    public let name: String
    public let email: String

    public init(id: String, name: String, email: String) {
        self.id = id
        self.name = name
        self.email = email
    }
}

public struct LoginRequest: Sendable {
    public let email: String
    public let password: String

    public init(email: String, password: String) {
        self.email = email
        self.password = password
    }
}

public protocol AuthRepositoryProtocol: Sendable {
    func login(request: LoginRequest) async throws -> User
}

public protocol LoginUseCaseProtocol: Sendable {
    func execute(email: String, password: String) async throws -> User
}

public final class LoginUseCase: LoginUseCaseProtocol, Sendable {
    private let repository: AuthRepositoryProtocol

    public init(repository: AuthRepositoryProtocol) {
        self.repository = repository
    }

    public func execute(email: String, password: String) async throws -> User {
        guard !email.isEmpty else {
            throw DomainError.invalidEmail
        }
        guard password.count >= 6 else {
            throw DomainError.weakPassword
        }
        let request = LoginRequest(email: email, password: password)
        return try await repository.login(request: request)
    }
}

public enum DomainError: Error, LocalizedError {
    case invalidEmail
    case weakPassword
    case userNotFound
    case unauthorized

    public var errorDescription: String? {
        switch self {
        case .invalidEmail: return "邮箱格式不正确"
        case .weakPassword: return "密码长度不能少于6位"
        case .userNotFound: return "用户不存在"
        case .unauthorized: return "认证失败"
        }
    }
}
```

Domain 层的 Package.swift 非常简洁，没有任何外部依赖：

```swift
import PackageDescription

let package = Package(
    name: "Domain",
    platforms: [.iOS(.v15)],
    products: [
        .library(name: "Domain", targets: ["Domain"])
    ],
    dependencies: [],
    targets: [
        .target(name: "Domain", dependencies: []),
        .testTarget(name: "DomainTests", dependencies: ["Domain"])
    ]
)
```

### 3.4 Data 层：网络请求与数据持久化

Data 层负责实现 Domain 层定义的 Repository 协议，并处理具体的数据获取逻辑：

```swift
import Foundation
import Domain

public final class AuthRepositoryImpl: AuthRepositoryProtocol {
    private let networkService: NetworkServiceProtocol

    public init(networkService: NetworkServiceProtocol) {
        self.networkService = networkService
    }

    public func login(request: LoginRequest) async throws -> User {
        let endpoint = AuthEndpoint.login(email: request.email, password: request.password)
        let response: LoginResponseDTO = try await networkService.request(endpoint)
        return response.toDomain()
    }
}

public struct LoginResponseDTO: Codable, Sendable {
    let userId: String
    let userName: String
    let userEmail: String

    func toDomain() -> User {
        User(id: userId, name: userName, email: userEmail)
    }
}

public enum AuthEndpoint {
    case login(email: String, password: String)
}

extension AuthEndpoint: Endpoint {
    public var path: String {
        switch self {
        case .login: return "/auth/login"
        }
    }

    public var method: HTTPMethod {
        switch self {
        case .login: return .post
        }
    }

    public var body: Data? {
        switch self {
        case .login(let email, let password):
            let dict = ["email": email, "password": password]
            return try? JSONEncoder().encode(dict)
        }
    }
}

public protocol NetworkServiceProtocol: Sendable {
    func request<T: Decodable>(_ endpoint: Endpoint) async throws -> T
}

public protocol Endpoint {
    var path: String { get }
    var method: HTTPMethod { get }
    var body: Data? { get }
}

public enum HTTPMethod: String, Sendable {
    case get = "GET"
    case post = "POST"
    case put = "PUT"
    case delete = "DELETE"
}
```

Data 层的 Package.swift 依赖 Domain：

```swift
import PackageDescription

let package = Package(
    name: "Data",
    platforms: [.iOS(.v15)],
    products: [
        .library(name: "Data", targets: ["Data"])
    ],
    dependencies: [
        .package(path: "../Domain")
    ],
    targets: [
        .target(name: "Data", dependencies: ["Domain"]),
        .testTarget(name: "DataTests", dependencies: ["Data"])
    ]
)
```

### 3.5 依赖规则总结

| 规则 | 说明 | 违反示例 |
|------|------|---------|
| Feature → Domain | Feature 可以调用 Domain 的 UseCase | ✅ 正确 |
| Data → Domain | Data 实现 Domain 的 Repository 协议 | ✅ 正确 |
| Feature → Data | Feature 不应直接依赖 Data | ❌ ViewController 直接调用 NetworkService |
| Domain → Feature | Domain 不能知道 UI 的存在 | ❌ Entity 里 import UIKit |
| Domain → Data | Domain 不能依赖具体实现 | ❌ UseCase 直接创建 RepositoryImpl |

> ⚠️ **警告**：最常见的架构违规是在 Domain 层引入具体实现依赖。如果 Domain 层的 `import` 出现了 Data 层或 Feature 层的模块名，说明依赖方向反了。

## 4. 模块间通信与解耦

### 4.1 直接依赖 vs 协议解耦

模块间通信最简单的方式是直接依赖，但这种方式会导致强耦合：

| 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 直接依赖 | 简单直接、编译期检查 | 强耦合、改一处动多处 | 模块间有明确的上下级关系 |
| 协议解耦 | 松耦合、可替换、可测试 | 需要额外定义协议和注册 | 模块间平级通信、需要灵活替换 |

### 4.2 Router 协议设计：基于 URL 的路由方案

Router 是 iOS 中最常用的模块间解耦方案。核心思想是：模块不直接引用彼此，而是通过 URL 进行通信：

```swift
public protocol RouterProtocol: AnyObject {
    func register(path: String, handler: @escaping ([String: Any]) -> Any?)
    func route(to path: String, parameters: [String: Any]) -> Any?
}

public final class Router: RouterProtocol {
    public static let shared = Router()

    private var handlers: [String: ([String: Any]) -> Any?] = [:]

    private init() {}

    public func register(path: String, handler: @escaping ([String: Any]) -> Any?) {
        handlers[path] = handler
    }

    public func route(to path: String, parameters: [String: Any] = [:]) -> Any? {
        guard let handler = handlers[path] else {
            print("Route not found: \(path)")
            return nil
        }
        return handler(parameters)
    }
}
```

各模块在启动时注册自己的路由：

```swift
import FeatureAuth
import Router

public final class AuthModuleSetup {
    public static func registerRoutes() {
        Router.shared.register(path: "myapp://auth/login") { parameters in
            let loginVC = LoginViewController()
            if let animated = parameters["animated"] as? Bool {
                loginVC.modalTransitionStyle = animated ? .coverVertical : .crossDissolve
            }
            return loginVC
        }

        Router.shared.register(path: "myapp://auth/profile") { parameters in
            guard let userId = parameters["userId"] as? String else { return nil }
            return ProfileViewController(userId: userId)
        }
    }
}
```

使用路由跳转：

```swift
Router.shared.route(to: "myapp://auth/login", parameters: ["animated": true])
Router.shared.route(to: "myapp://auth/profile", parameters: ["userId": "123"])
```

### 4.3 依赖注入容器

依赖注入容器负责管理所有模块的依赖关系，在 App 启动时完成组装：

```swift
public protocol DIContainerProtocol {
    func register<T>(_ type: T.Type, factory: @escaping () -> T)
    func resolve<T>(_ type: T.Type) -> T
}

public final class DIContainer: DIContainerProtocol {
    public static let shared = DIContainer()

    private var factories: [String: Any] = [:]

    private init() {}

    public func register<T>(_ type: T.Type, factory: @escaping () -> T) {
        let key = String(describing: type)
        factories[key] = factory
    }

    public func resolve<T>(_ type: T.Type) -> T {
        let key = String(describing: type)
        guard let factory = factories[key] as? () -> T else {
            fatalError("No registration for \(key)")
        }
        return factory()
    }
}
```

在 App 启动时组装依赖：

```swift
import Domain
import Data

func setupDependencies() {
    DIContainer.shared.register(NetworkServiceProtocol.self) {
        NetworkService()
    }
    DIContainer.shared.register(AuthRepositoryProtocol.self) {
        AuthRepositoryImpl(
            networkService: DIContainer.shared.resolve(NetworkServiceProtocol.self)
        )
    }
    DIContainer.shared.register(LoginUseCaseProtocol.self) {
        LoginUseCase(
            repository: DIContainer.shared.resolve(AuthRepositoryProtocol.self)
        )
    }
}
```

### 4.4 EventBus / Callback 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Router | URL 路由表映射 | 解耦彻底、支持 DeepLink | 类型不安全、参数传递受限 |
| DI Container | 注册/解析依赖 | 类型安全、便于测试 | 需要手动注册、启动时组装 |
| EventBus | 发布/订阅事件 | 完全解耦、一对多通信 | 调试困难、生命周期难管理 |
| Callback | 闭包回调 | 简单直接 | 容易造成循环引用 |

EventBus 的简单实现：

```swift
public final class EventBus {
    public static let shared = EventBus()

    private var subscribers: [String: [(Any) -> Void]] = [:]

    private init() {}

    public func subscribe<T>(_ eventType: T.Type, handler: @escaping (T) -> Void) {
        let key = String(describing: eventType)
        if subscribers[key] == nil {
            subscribers[key] = []
        }
        subscribers[key]?.append { anyValue in
            if let value = anyValue as? T {
                handler(value)
            }
        }
    }

    public func publish<T>(_ event: T) {
        let key = String(describing: T.self)
        subscribers[key]?.forEach { handler in
            handler(event)
        }
    }
}
```

### 4.5 DeepLink 与模块路由的统一

DeepLink 是从外部（通知、Safari、其他 App）打开 App 内特定页面的机制。将 DeepLink 与 Router 统一，可以实现一套路由系统同时服务内部跳转和外部调起：

```swift
import UIKit

public final class DeepLinkHandler {
    private let router: RouterProtocol

    public init(router: RouterProtocol) {
        self.router = router
    }

    public func handle(url: URL) -> Bool {
        guard let host = url.host else { return false }
        let path = "myapp://\(host)\(url.path)"
        var parameters: [String: Any] = [:]
        if let components = URLComponents(url: url, resolvingAgainstBaseURL: false),
           let queryItems = components.queryItems {
            for item in queryItems {
                parameters[item.name] = item.value
            }
        }
        return router.route(to: path, parameters: parameters) != nil
    }
}
```

在 AppDelegate 中处理 DeepLink：

```swift
func application(_ app: UIApplication, open url: URL, options: [UIApplication.OpenURLOptionsKey: Any] = [:]) -> Bool {
    return DeepLinkHandler(router: Router.shared).handle(url: url)
}
```

## 5. 组件化实践

### 5.1 基础组件

基础组件是跨项目通用的底层库，不包含任何业务逻辑：

| 组件类型 | 示例 | 职责 |
|---------|------|------|
| UI Kit | DesignKit | 统一颜色、字体、按钮样式、间距常量 |
| 网络库 | NetworkKit | 封装 URLSession、请求/响应模型、错误处理 |
| 工具类 | UtilsKit | 日期格式化、字符串处理、设备信息 |
| 存储库 | StorageKit | UserDefaults 封装、Keychain 封装、文件管理 |
| 日志库 | LoggerKit | 统一日志输出、日志级别控制 |

DesignKit 示例：

```swift
import UIKit

public enum AppColor {
    public static let primary = UIColor(hex: "#1A73E8")
    public static let secondary = UIColor(hex: "#5F6368")
    public static let background = UIColor(hex: "#FFFFFF")
    public static let error = UIColor(hex: "#D93025")
}

public enum AppFont {
    public static let title = UIFont.systemFont(ofSize: 24, weight: .bold)
    public static let headline = UIFont.systemFont(ofSize: 18, weight: .semibold)
    public static let body = UIFont.systemFont(ofSize: 16, weight: .regular)
    public static let caption = UIFont.systemFont(ofSize: 12, weight: .regular)
}

public enum AppSpacing {
    public static let xs: CGFloat = 4
    public static let sm: CGFloat = 8
    public static let md: CGFloat = 16
    public static let lg: CGFloat = 24
    public static let xl: CGFloat = 32
}

extension UIColor {
    convenience init(hex: String) {
        var hexSanitized = hex.trimmingCharacters(in: .whitespacesAndNewlines)
        hexSanitized = hexSanitized.replacingOccurrences(of: "#", with: "")
        var rgb: UInt64 = 0
        Scanner(string: hexSanitized).scanHexInt64(&rgb)
        self.init(
            red: CGFloat((rgb & 0xFF0000) >> 16) / 255.0,
            green: CGFloat((rgb & 0x00FF00) >> 8) / 255.0,
            blue: CGFloat(rgb & 0x0000FF) / 255.0,
            alpha: 1.0
        )
    }
}
```

### 5.2 业务组件

业务组件是包含完整业务功能的独立模块，可以被不同 App 复用：

| 业务组件 | 包含内容 | 对外接口 |
|---------|---------|---------|
| 登录模块 | 登录/注册/忘记密码 UI + 逻辑 | `AuthModule.showLogin()` |
| 支付模块 | 支付方式选择、支付流程、结果回调 | `PaymentModule.pay(order:)` |
| 分享模块 | 分享面板、各平台 SDK 封装 | `ShareModule.share(content:)` |
| 推送模块 | 注册、权限、消息处理 | `PushModule.register()` |

业务组件的标准结构：

```
FeatureAuth/
├── Package.swift
├── Sources/
│   └── FeatureAuth/
│       ├── Public/              # 对外暴露的接口
│       │   └── AuthModule.swift
│       ├── Views/               # UI 组件
│       │   ├── LoginView.swift
│       │   └── RegisterView.swift
│       ├── ViewModels/          # 视图模型
│       │   └── LoginViewModel.swift
│       └── Resources/           # 资源文件
│           └── Assets.xcassets
└── Tests/
    └── FeatureAuthTests/
```

对外接口封装：

```swift
import UIKit
```

### 5.4 组件的资源管理

SPM 从 5.3 开始支持资源文件管理。在 Package.swift 中声明资源：

```swift
.target(
    name: "DesignKit",
    dependencies: [],
    resources: [
        .process("Resources/Assets.xcassets"),
        .process("Resources/Colors.xcassets"),
        .copy("Resources/Fonts")
    ]
)
```

在代码中访问资源：

```swift
let bannerImage = UIImage(named: "LoginBanner", in: .module, compatibleWith: nil)
let accentColor = UIColor(named: "AccentColor", in: .module, compatibleWith: nil)
```

| 资源类型 | 声明方式 | 访问方式 |
|---------|---------|---------|
| Asset Catalog | `.process()` | `UIImage(named:in:compatibleWith:)` |
| 颜色 | `.process()` | `UIColor(named:in:compatibleWith:)` |
| 字体 | `.copy()` | 自定义字体注册后使用 |
| JSON/Plist | `.process()` | `Bundle.module.path(forResource:ofType:)` |

> ⚠️ **警告**：`.process()` 会对资源进行优化处理（如 Asset Catalog 的编译），`.copy()` 则原样复制。字体文件必须用 `.copy()`，否则可能无法正确注册。

### 5.5 组件版本管理与发布

对于需要跨项目共享的组件，建议使用语义化版本（SemVer）管理：

```
主版本号.次版本号.修订号
 1      .0       .0
 │       │        │
 │       │        └── 修复 Bug，向后兼容
 │       └────────── 新增功能，向后兼容
 └────────────────── 破坏性变更，不兼容
```

在 Package.swift 中声明版本：

```swift
dependencies: [
    .package(url: "https://github.com/your-org/DesignKit.git", from: "1.2.0"),
    .package(url: "https://github.com/your-org/NetworkKit.git", .upToNextMinor(from: "2.1.0"))
]
```

发布流程：

```bash
git tag 1.2.0
git push origin 1.2.0
```

## 6. 渐进式模块化改造

### 6.1 评估现有项目的模块化程度

在动手改造之前，先评估项目的现状。以下评分表帮助你量化模块化程度：

| 评估项 | 满分 | 评分标准 |
|--------|------|---------|
| 代码分层 | 20 | UI/逻辑/数据是否分离 |
| 模块独立性 | 20 | 模块间是否可以独立编译 |
| 依赖方向 | 20 | 是否遵循单向依赖 |
| 可测试性 | 20 | 核心逻辑是否可脱离 UI 测试 |
| 资源管理 | 10 | 资源是否按模块组织 |
| 构建速度 | 10 | 增量编译是否生效 |

| 总分 | 等级 | 建议 |
|------|------|------|
| 80~100 | 优秀 | 继续优化细节 |
| 60~79 | 良好 | 针对薄弱项改进 |
| 40~59 | 一般 | 需要系统性改造 |
| 0~39 | 较差 | 建议尽快启动模块化 |

### 6.2 制定改造计划：从最独立的模块开始

改造的黄金法则是：**从最独立的模块开始，逐步向外扩展**。就像拆房子——先搬走家具，再拆墙壁，最后处理地基。

选择改造顺序的优先级：

1. **工具类 / 基础组件**（最独立，零业务依赖）→ NetworkKit、UtilsKit
2. **数据层**（依赖最少，接口明确）→ Repository 实现
3. **Domain 层**（纯逻辑，无 UI 依赖）→ Entity、UseCase
4. **独立业务模块**（低耦合的功能）→ 设置页、关于页
5. **核心业务模块**（高耦合的功能）→ 首页、订单
6. **主 App 壳工程**（最后处理）

### 6.3 改造步骤：提取 → 隔离 → 验证 → 合并

每个模块的改造遵循四步法：

**第一步：提取**

将相关文件从主 Target 移动到新的 SPM Package 中。此时先不处理依赖，允许编译错误存在。

**第二步：隔离**

处理模块对主 Target 的依赖。常见依赖类型及处理方式：

| 依赖类型 | 处理方式 |
|---------|---------|
| 直接引用其他模块的类 | 通过协议抽象，用 DI 注入 |
| 使用全局常量/单例 | 将常量移入共享模块，单例改为注入 |
| 访问 AppDelegate | 通过协议抽象 App 级服务 |
| 使用 Storyboard/XIB | 改为纯代码布局或迁移资源文件 |

**第三步：验证**

```bash
xcodebuild build \
    -scheme FeatureAuth \
    -destination 'platform=iOS Simulator,name=iPhone 15'
```

确保模块可以独立编译，测试全部通过。

**第四步：合并**

将改造好的模块集成回主 App，验证整体功能正常：

```bash
xcodebuild test \
    -scheme MyApp \
    -destination 'platform=iOS Simulator,name=iPhone 15'
```

### 6.4 常见改造陷阱与解决方案

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| 循环依赖 | A 依赖 B，B 又依赖 A | 提取共享部分到 C，A→C←B |
| 过度拆分 | 一个类一个模块，模块数量爆炸 | 按功能域聚合，保持合理粒度 |
| 接口膨胀 | 协议定义了过多方法 | 按职责拆分协议，遵循接口隔离原则 |
| 迁移不彻底 | 模块内仍 import 主 Target | 逐步清理，每次 CI 检查非法依赖 |
| 资源遗漏 | 图片/字符串留在主 Target | 使用 `Bundle.module` 统一管理 |

### 6.5 改造过程中的 CI/CD 适配

模块化改造期间，CI/CD 需要做相应调整：

**编译策略优化**：利用 SPM 的增量编译特性，只编译变更的模块：

```yaml
steps:
  - name: Detect changed packages
    run: |
      CHANGED=$(git diff --name-only origin/main...HEAD | grep "^Packages/" | cut -d'/' -f2 | sort -u)
      echo "Changed packages: $CHANGED"

  - name: Build changed packages
    run: |
      for pkg in $CHANGED; do
        xcodebuild build-for-testing \
          -scheme "$pkg" \
          -destination 'platform=iOS Simulator,name=iPhone 15'
      done
```

**模块依赖检查**：在 CI 中添加脚本，确保依赖方向正确：

```bash
#!/bin/bash
for dir in Packages/*/; do
    pkg_name=$(basename "$dir")
    swift_file=$(find "$dir" -name "*.swift" -type f)
    if echo "$swift_file" | xargs grep -l "import MyApp"; then
        echo "ERROR: $pkg_name imports MyApp (main target)"
        exit 1
    fi
done
echo "All dependencies are valid"
```

## 7. Tuist 大型项目模板化（选读）

### 7.1 Tuist 是什么

Tuist 是一个 Xcode 项目生成工具。它不使用 `.xcodeproj` 和 `.xcworkspace` 文件，而是通过 Swift 代码描述项目结构，然后生成 Xcode 项目。这就像用代码来描述项目结构，然后生成 Xcode 项目文件。

> 💡 **提示**：当你的项目超过 10 个 SPM Local Package 时，Xcode 的打开速度和索引速度会明显变慢。Tuist 可以通过按需生成项目来解决这个问题。

### 7.2 为什么大型项目需要 Tuist

| 痛点 | Tuist 的解决方案 |
|------|----------------|
| `.xcodeproj` 文件冲突频繁 | 项目文件由代码生成，不需要手动编辑 |
| Xcode 打开超大项目极慢 | 按需生成只包含所需模块的子项目 |
| 重复的 Target 配置 | 模板化配置，一套配置复用多个 Target |
| 新增模块步骤繁琐 | 一个命令生成模块脚手架 |

### 7.3 基本配置与项目生成

Tuist 使用 Swift 代码（`Project.swift`）描述项目：

```swift
import ProjectDescription

let project = Project(
    name: "MyApp",
    targets: [
        Target(
            name: "MyApp",
            platform: .iOS,
            product: .app,
            bundleId: "com.example.myapp",
            deploymentTarget: .iOS(targetVersion: "15.0", devices: .iphone),
            infoPlist: .extendingDefault(with: [:]),
            sources: ["MyApp/Sources/**"],
            resources: ["MyApp/Resources/**"],
            dependencies: [
                .project(target: "FeatureAuth", path: .relativeToManifest("Packages/FeatureAuth")),
                .project(target: "FeatureHome", path: .relativeToManifest("Packages/FeatureHome")),
                .project(target: "Domain", path: .relativeToManifest("Packages/Domain")),
                .project(target: "Data", path: .relativeToManifest("Packages/Data")),
                .project(target: "DesignKit", path: .relativeToManifest("Packages/DesignKit"))
            ]
        )
    ]
)
```

生成并打开项目：

```bash
tuist generate
open MyApp.xcworkspace
```

### 7.4 与 SPM 的配合使用

Tuist 和 SPM 不是互斥的，而是互补的。推荐的使用方式：

| 场景 | 使用工具 | 原因 |
|------|---------|------|
| 内部业务模块 | Tuist Project | 更灵活的配置、更快的生成速度 |
| 开源第三方依赖 | SPM | 生态兼容、版本管理方便 |
| 基础组件 | SPM Package | 便于跨项目复用和开源 |
| App 壳工程 | Tuist Target | 统一管理多 Target 配置 |

Tuist 可以直接引用 SPM Package 作为依赖：

```swift
dependencies: [
    .external(name: "SnapKit", condition: .none),
    .external(name: "Kingfisher", condition: .none)
]
```

在 `Package.swift` 或 `Dependencies.swift` 中声明外部依赖：

```swift
import ProjectDescription

let dependencies = Dependencies(
    swiftPackageManager: [
        .remote(url: "https://github.com/SnapKit/SnapKit.git", requirement: .upToNextMinor(from: "5.0.0")),
        .remote(url: "https://github.com/onevcat/Kingfisher.git", requirement: .upToNextMinor(from: "7.0.0"))
    ],
    platforms: [.iOS]
)
```

> ⚠️ **警告**：Tuist 生成的项目文件不应该提交到 Git。将 `*.xcodeproj` 和 `*.xcworkspace` 加入 `.gitignore`，团队成员通过 `tuist generate` 各自生成。

## 小结

本章从单体架构的痛点出发，系统讲解了 iOS 项目的模块化与组件化实战方法。以下是核心知识点总结：

| 知识点 | 核心内容 | 关键要点 |
|--------|---------|---------|
| 模块化动机 | 解决编译慢、冲突多、职责不清 | 中大型项目必须模块化 |
| 模块化 vs 组件化 | 模块化是拆，组件化是封 | 两者结合使用效果最佳 |
| SPM 多模块 | Local Package + Package.swift | Xcode 原生支持，零额外工具 |
| 三层架构 | Feature → Domain ← Data | Domain 层零外部依赖 |
| 依赖规则 | 外层依赖内层，内层不依赖外层 | 依赖倒置是核心原则 |
| 模块间通信 | Router / DI / EventBus | Router 适合页面跳转，DI 适合服务注入 |
| DeepLink 统一 | 外部调起与内部路由共用一套 | 一处注册，多处使用 |
| 基础组件 | DesignKit / NetworkKit / UtilsKit | 不含业务逻辑，跨项目复用 |
| 业务组件 | 登录 / 支付 / 分享 | 对外暴露简洁接口 |
| 独立调试 | Demo App Target | 每个组件可独立运行 |
| 资源管理 | `.process()` / `.copy()` | 字体必须用 `.copy()` |
| 版本管理 | SemVer 语义化版本 | 主版本号变更表示不兼容 |
| 渐进式改造 | 提取→隔离→验证→合并 | 从最独立的模块开始 |
| 改造陷阱 | 循环依赖、过度拆分、接口膨胀 | 每步验证，小步前进 |
| CI/CD 适配 | 增量编译、依赖检查 | 模块化后 CI 速度反而更快 |
| Tuist | Xcode 项目生成工具 | 超大型项目推荐使用 |

> 💡 **提示**：模块化不是一蹴而就的，而是一个持续演进的过程。先搭好分层骨架，再逐步拆分模块，最后做组件化封装。每一步都要确保编译通过、测试通过，再进行下一步。
