## 1. A/B 测试是什么

### 1.1 一个生活类比

想象你开了一家奶茶店，菜单上有两种新杯型设计，你不确定哪种更能吸引顾客：

| 做法 | 问题 |
|------|------|
| 凭感觉选一个 | 可能选错，白白损失收入 |
| 问朋友意见 | 样本太小，不代表真实顾客 |
| **让一半顾客看 A 设计，另一半看 B 设计，然后比较谁买得多** | ✅ 这就是 A/B 测试！ |

**A/B 测试**，也叫对照实验（Controlled Experiment），就是：

> 把用户随机分成两组（或多组），给不同组展示不同版本，然后用数据来判断哪个版本更好。

### 1.2 为什么需要 A/B 测试

| 直觉驱动 | 数据驱动 |
|----------|----------|
| "我觉得蓝色按钮更好看" | "蓝色按钮的点击率比绿色高 23%" |
| "老板说这样改" | "实验数据显示这样改会降低转化率" |
| "竞品都这么做" | "我们的用户群体不同，实验证明不适用" |

> 💡 **核心思想**：不要猜，要测。让数据替你做决定。

### 1.3 A/B 测试的基本术语

| 术语 | 含义 | 类比 |
|------|------|------|
| 对照组（Control） | 展示当前版本的组 | 奶茶店原来的杯子 |
| 实验组（Variant） | 展示新版本的组 | 奶茶店新设计的杯子 |
| 指标（Metric） | 用来衡量效果的数据 | 买奶茶的人数 |
| 样本（Sample） | 参与实验的用户 | 来奶茶店的顾客 |
| 显著性（Significance） | 结果不是碰巧的概率 | 不是运气好才卖得多 |

## 2. A/B 测试流程

A/B 测试不是"改一改然后看看"，而是一个严谨的五步流程：

```
假设 → 设计 → 实施 → 分析 → 决策
```

### 2.1 第一步：提出假设

假设必须具体、可验证：

| ❌ 糟糕的假设 | ✅ 好的假设 |
|---------------|-------------|
| "改一下按钮" | "将购买按钮从绿色改为橙色，预计点击率提升 15%" |
| "优化页面" | "将付费页面从单列布局改为双列布局，预计转化率提升 10%" |
| "让用户更喜欢" | "添加每日推荐功能，预计 7 日留存率提升 5%" |

**假设模板**：

> 如果我们 **[做什么改变]**，那么 **[哪个指标]** 会 **[提升/降低多少]**，因为 **[原因]**。

### 2.2 第二步：设计实验

设计时需要确定：

| 设计要素 | 要回答的问题 |
|----------|--------------|
| 实验变量 | 改什么？只改一个变量 |
| 分组方案 | 几个组？每组多少人？ |
| 指标定义 | 主指标是什么？辅助指标呢？ |
| 实验时长 | 跑多久？至少覆盖一个完整周期 |
| 停止条件 | 什么时候可以下结论？ |

> ⚠️ **每次只改一个变量**：如果同时改了按钮颜色和按钮文字，你永远不知道是哪个改动起了作用。

### 2.3 第三步：实施实验

将设计转化为代码，主要工作包括：

1. 集成 A/B 测试 SDK（如 Firebase Remote Config）
2. 实现实验分组逻辑
3. 埋点追踪关键指标
4. 设置功能开关

### 2.4 第四步：分析数据

收集数据后，对比各组指标：

| 指标 | 对照组（A） | 实验组（B） | 变化 |
|------|------------|------------|------|
| 点击率 | 3.2% | 3.9% | +21.9% |
| 转化率 | 1.5% | 1.8% | +20.0% |
| 人均收入 | ¥2.3 | ¥2.7 | +17.4% |

### 2.5 第五步：做出决策

| 结果 | 决策 |
|------|------|
| 实验组显著优于对照组 | 全量上线新版本 |
| 实验组显著劣于对照组 | 放弃新版本，保留原版 |
| 无显著差异 | 考虑是否需要更多样本，或放弃实验 |

## 3. Firebase Remote Config 集成

Firebase Remote Config 是实现 A/B 测试的核心工具，它让你可以**远程控制 App 的行为**，无需发版。

### 3.1 生活类比

Remote Config 就像一个**远程遥控器**：

- 你在 Firebase 控制台按下按钮（修改参数值）
- App 里的功能立即响应（读取新值并生效）
- 不需要用户更新 App

### 3.2 安装 Firebase SDK

**第一步：添加 Firebase 到项目**

在 `Package.swift` 中添加依赖：

```swift
dependencies: [
    .package(
        url: "https://github.com/firebase/firebase-ios-sdk",
        from: "10.0.0"
    )
],
targets: [
    .target(
        name: "YourApp",
        dependencies: [
            .product(name: "FirebaseRemoteConfig", package: "firebase-ios-sdk"),
            .product(name: "FirebaseAnalytics", package: "firebase-ios-sdk"),
            .product(name: "FirebaseABTesting", package: "firebase-ios-sdk")
        ]
    )
]
```

如果使用 CocoaPods，则在 `Podfile` 中：

```ruby
pod 'Firebase/RemoteConfig'
pod 'Firebase/Analytics'
pod 'Firebase/ABTesting'
```

**第二步：配置 Firebase**

1. 在 [Firebase Console](https://console.firebase.google.com/) 创建项目
2. 添加 iOS App，下载 `GoogleService-Info.plist`
3. 将 `GoogleService-Info.plist` 拖入 Xcode 项目

**第三步：初始化**

```swift
import Firebase

@main
struct YourApp: App {
    init() {
        FirebaseApp.configure()
    }

    var body: some Scene {
        WindowGroup {
            ContentView()
        }
    }
}
```

### 3.3 配置 Remote Config

创建一个专门的配置管理类：

```swift
import FirebaseRemoteConfig

final class RemoteConfigManager: ObservableObject {
    static let shared = RemoteConfigManager()

    @Published var showNewPaywall = false
    @Published var paywallVariant = "control"
    @Published var featureXTipEnabled = true

    private let remoteConfig = RemoteConfig.remoteConfig()

    private init() {
        let settings = RemoteConfigSettings()
        settings.minimumFetchInterval = 0
        remoteConfig.configSettings = settings

        setDefaults()
    }

    private func setDefaults() {
        let defaults: [String: Any] = [
            "show_new_paywall": false,
            "paywall_variant": "control",
            "feature_x_tip_enabled": true
        ]
        remoteConfig.setDefaults(defaults as [String: NSObject])
    }

    func fetchConfig() async {
        do {
            let status = try await remoteConfig.fetch()
            let activated = try await remoteConfig.activate()
            print("Fetch status: \(status.rawValue), activated: \(activated)")
            applyConfig()
        } catch {
            print("Remote Config fetch error: \(error)")
            applyConfig()
        }
    }

    private func applyConfig() {
        DispatchQueue.main.async {
            self.showNewPaywall = self.remoteConfig["show_new_paywall"].boolValue
            self.paywallVariant = self.remoteConfig["paywall_variant"].stringValue ?? "control"
            self.featureXTipEnabled = self.remoteConfig["feature_x_tip_enabled"].boolValue
        }
    }
}
```

> 💡 **`minimumFetchInterval = 0`** 仅用于开发阶段，方便实时调试。生产环境建议设为 3600（1 小时）或更长，减少不必要的网络请求。

### 3.4 在 App 启动时获取配置

```swift
@main
struct YourApp: App {
    @StateObject private var remoteConfig = RemoteConfigManager.shared

    init() {
        FirebaseApp.configure()
    }

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environmentObject(remoteConfig)
                .task {
                    await remoteConfig.fetchConfig()
                }
        }
    }
}
```

## 4. 实现功能开关

功能开关（Feature Flag）是 A/B 测试的基础设施，让你可以远程控制功能的展示与隐藏。

### 4.1 为什么需要功能开关

| 场景 | 没有功能开关 | 有功能开关 |
|------|-------------|-----------|
| 新功能有 Bug | 需要紧急发版修复 | 远程关闭，0 秒生效 |
| 想先给 10% 用户试用 | 无法做到 | 设置参数为 10% |
| 节日活动到期 | 需要发版下线 | 远程关闭即可 |
| A/B 测试 | 无法实现 | 核心基础能力 |

### 4.2 实现一个简单的功能开关

```swift
struct FeatureFlag {
    let key: String
    let defaultValue: Bool

    var isEnabled: Bool {
        RemoteConfig.remoteConfig()[key].boolValue
    }
}

enum Feature {
    static let newPaywall = FeatureFlag(key: "show_new_paywall", defaultValue: false)
    static let socialSharing = FeatureFlag(key: "social_sharing_enabled", defaultValue: false)
    static let dailyTip = FeatureFlag(key: "daily_tip_enabled", defaultValue: true)
    static let onboardingV2 = FeatureFlag(key: "onboarding_v2", defaultValue: false)
}
```

使用方式：

```swift
struct PaywallView: View {
    var body: some View {
        if Feature.newPaywall.isEnabled {
            NewPaywallView()
        } else {
            OriginalPaywallView()
        }
    }
}
```

### 4.3 更灵活的功能开关：支持百分比灰度

在 Firebase 控制台设置参数时，可以使用条件值实现百分比灰度：

| 参数名 | 条件 | 值 |
|--------|------|-----|
| `show_new_paywall` | 默认 | `false` |
| `show_new_paywall` | 用户随机百分位 ≤ 10 | `true` |

这样只有 10% 的用户会看到新功能，其余 90% 看到旧版本。

> 💡 **灰度发布策略**：1% → 5% → 10% → 50% → 100%，逐步扩大范围，降低风险。

## 5. 实验分组

### 5.1 用户分桶

"分桶"就是把用户分到不同组的形象说法——想象把球扔进不同的桶里。

```
所有用户
  ├── 桶 A（对照组）：看到当前版本
  ├── 桶 B（实验组 1）：看到新版本 1
  └── 桶 C（实验组 2）：看到新版本 2
```

### 5.2 随机分配

随机分配确保各组用户特征相似，避免偏差。Firebase A/B Testing 自动处理随机分配。

**手动实现随机分配**（了解原理）：

```swift
struct ABTestAssignment {
    enum Group: String {
        case control = "A"
        case variant1 = "B"
        case variant2 = "C"
    }

    static func assign(userId: String, experimentId: String) -> Group {
        let hashInput = "\(userId)_\(experimentId)"
        let hash = abs(hashInput.hashValue)
        let bucket = hash % 100

        switch bucket {
        case 0..<50:
            return .control
        case 50..<75:
            return .variant1
        default:
            return .variant2
        }
    }
}
```

> ⚠️ **关键原则**：同一用户每次打开 App，必须分到同一组。用 `userId + experimentId` 的哈希值来保证一致性。

### 5.3 分层实验

当同时运行多个实验时，需要"分层"来避免实验之间互相干扰：

| 分层 | 实验 | 互不影响 |
|------|------|---------|
| UI 层 | 按钮颜色实验 | ↕️ 互不影响 |
| 定价层 | 折扣力度实验 | ↕️ 互不影响 |
| 功能层 | 新功能开关实验 | ↕️ 互不影响 |

```
用户 → UI 层随机分组 → 定价层随机分组 → 功能层随机分组
         ↓                  ↓                  ↓
     按钮颜色 A/B       折扣 8 折/9 折      功能 开/关
```

> 💡 **Firebase A/B Testing** 自动处理分层，你只需在控制台创建实验即可。

## 6. 指标追踪

### 6.1 定义指标

| 指标类型 | 示例 | 说明 |
|----------|------|------|
| 主指标（OEC） | 付费转化率 | 实验的核心评判标准 |
| 辅助指标 | 点击率、页面停留时间 | 帮助理解主指标变化的原因 |
| 护栏指标 | 崩溃率、卸载率 | 确保实验没有负面影响 |

> ⚠️ **OEC（Overall Evaluation Criterion）**：每个实验必须有一个明确的主指标，不要"什么都想看"。

### 6.2 埋点追踪

使用 Firebase Analytics 追踪实验相关事件：

```swift
import FirebaseAnalytics

struct ExperimentTracker {
    static func logExperimentExposure(experimentId: String, variant: String) {
        Analytics.logEvent("ab_test_exposure", parameters: [
            "experiment_id": experimentId,
            "variant": variant
        ])
    }

    static func logPaywallShown(variant: String) {
        Analytics.logEvent("paywall_shown", parameters: [
            "variant": variant
        ])
    }

    static func logPaywallAction(variant: String, action: String) {
        Analytics.logEvent("paywall_action", parameters: [
            "variant": variant,
            "action": action
        ])
    }

    static func logPurchase(variant: String, productId: String, price: Double) {
        Analytics.logEvent("purchase", parameters: [
            "variant": variant,
            "product_id": productId,
            "price": price
        ])
    }
}
```

### 6.3 实验组 vs 对照组指标对比

假设我们运行了一个付费页面实验，收集到以下数据：

| 指标 | 对照组（A） | 实验组（B） | 变化 | 显著？ |
|------|------------|------------|------|--------|
| 曝光人数 | 5,000 | 5,000 | — | — |
| 点击人数 | 160 | 215 | +34.4% | ✅ |
| 点击率 | 3.2% | 4.3% | +34.4% | ✅ |
| 付费人数 | 75 | 90 | +20.0% | ⚠️ 待验证 |
| 付费转化率 | 1.5% | 1.8% | +20.0% | ⚠️ 待验证 |
| 崩溃率 | 0.1% | 0.1% | 0% | ✅ 无影响 |

> 💡 点击率显著提升，但付费转化率需要进一步验证统计显著性（见下一节）。

## 7. 统计显著性

### 7.1 为什么需要统计显著性

想象抛硬币：连续 3 次都是正面，能说明硬币有问题吗？不能，因为可能只是运气。

同理，A/B 测试中实验组表现更好，也可能只是随机波动。**统计显著性**告诉你：这个结果有多大概率不是碰巧的。

### 7.2 核心概念

| 概念 | 含义 | 类比 |
|------|------|------|
| p 值 | 结果由随机造成的概率 | 硬币连续正面的概率 |
| 置信度 | 1 - p 值 | 结果可信的程度 |
| 置信区间 | 真实值可能所在的范围 | "转化率在 1.5%~2.1% 之间" |
| 统计功效 | 检测到真实效果的概率 | 如果确实有差异，能发现的概率 |

**判断标准**：

| p 值 | 置信度 | 结论 |
|------|--------|------|
| < 0.05 | > 95% | ✅ 统计显著，结果可信 |
| 0.05 ~ 0.10 | 90%~95% | ⚠️ 边缘显著，需更多数据 |
| > 0.10 | < 90% | ❌ 不显著，无法下结论 |

### 7.3 样本量计算

实验前必须估算需要多少用户，否则可能跑了几个月也得不到显著结果。

**简化公式**（两个比例的比较）：

```
每组所需样本量 ≈ 16 × p × (1 - p) / δ²

其中：
- p = 基准转化率（对照组预期的转化率）
- δ = 最小可检测效应（MDE，你关心的最小变化幅度）
```

**速查表**（置信度 95%，功效 80%）：

| 基准转化率 | 最小可检测效应 | 每组所需样本 |
|-----------|---------------|-------------|
| 2% | +0.5 个百分点（2%→2.5%） | ~25,000 |
| 2% | +1.0 个百分点（2%→3%） | ~6,400 |
| 5% | +0.5 个百分点（5%→5.5%） | ~62,000 |
| 5% | +1.0 个百分点（5%→6%） | ~15,700 |
| 10% | +1.0 个百分点（10%→11%） | ~14,300 |
| 10% | +2.0 个百分点（10%→12%） | ~3,700 |

> ⚠️ **小 App 的现实**：如果你的日活只有 1000 人，而实验需要每组 25000 人，那需要跑 50 天才能达到足够样本量。考虑提高 MDE 或延长实验周期。

### 7.4 何时停止实验

| ❌ 错误做法 | ✅ 正确做法 |
|------------|-----------|
| 看到第 3 天数据很好就停 | 达到预设样本量后再分析 |
| 每天看 p 值，显著了就停 | 预先确定实验时长，到期后一次性分析 |
| 觉得差不多了就停 | 同时满足样本量和时长要求 |

**为什么不能"看到显著就停"**？

这就像反复抛硬币，只要等得够久，总会连续出现几次正面。每天偷看数据会增加"假阳性"的概率——看起来显著，实际是巧合。

> 💡 **最佳实践**：实验至少运行 1~2 个完整周期（如完整的 7 天或 14 天），覆盖工作日和周末的用户行为差异。

## 8. 实战示例：测试两种付费页面设计

### 8.1 实验背景

假设你的 App 有一个付费页面，当前设计是**单列大卡片**（版本 A），你想测试**双列小卡片**（版本 B）是否能提升转化率。

### 8.2 实验设计

| 要素 | 内容 |
|------|------|
| 假设 | 双列小卡片布局能提升付费转化率 20% |
| 主指标 | 付费转化率 |
| 辅助指标 | 页面停留时间、套餐选择分布 |
| 护栏指标 | 崩溃率、页面加载时间 |
| 分组 | 50% 对照组 / 50% 实验组 |
| 时长 | 14 天 |
| 所需样本 | 每组约 15,000（基准转化率 5%，MDE 1%） |

### 8.3 Firebase 控制台配置

**第一步：创建 Remote Config 参数**

在 Firebase Console → Remote Config 中添加参数：

| 参数键 | 默认值 | 说明 |
|--------|--------|------|
| `paywall_variant` | `control` | 付费页面版本 |

**第二步：创建 A/B Testing 实验**

在 Firebase Console → A/B Testing 中：

1. 点击"创建实验" → "Remote Config"
2. 设置实验名称：`Paywall Layout Test`
3. 设置目标用户：所有用户
4. 设置分组和变量值：

| 分组 | 比例 | 参数值 |
|------|------|--------|
| 对照组（Control） | 50% | `control` |
| 实验组（Variant B） | 50% | `double_column` |

5. 设置目标指标：`purchase` 事件

### 8.4 代码实现

**付费页面视图**：

```swift
struct PaywallView: View {
    @EnvironmentObject var remoteConfig: RemoteConfigManager
    @State private var selectedPlan: Plan?

    var body: some View {
        Group {
            switch remoteConfig.paywallVariant {
            case "double_column":
                DoubleColumnPaywallView(selectedPlan: $selectedPlan)
            default:
                SingleColumnPaywallView(selectedPlan: $selectedPlan)
            }
        }
        .onAppear {
            ExperimentTracker.logPaywallShown(variant: remoteConfig.paywallVariant)
        }
    }
}
```

**单列布局（对照组）**：

```swift
struct SingleColumnPaywallView: View {
    @Binding var selectedPlan: Plan?
    let plans = Plan.allPlans

    var body: some View {
        ScrollView {
            VStack(spacing: 16) {
                Text("升级到 Pro")
                    .font(.largeTitle)
                    .bold()

                ForEach(plans) { plan in
                    PlanCard(plan: plan, isSelected: selectedPlan?.id == plan.id)
                        .onTapGesture {
                            selectedPlan = plan
                        }
                }

                Button("立即订阅") {
                    if let plan = selectedPlan {
                        purchase(plan: plan)
                    }
                }
                .buttonStyle(.borderedProminent)
                .disabled(selectedPlan == nil)
            }
            .padding()
        }
    }

    private func purchase(plan: Plan) {
        ExperimentTracker.logPaywallAction(
            variant: "control",
            action: "purchase_tap"
        )
    }
}
```

**双列布局（实验组）**：

```swift

    @Binding var selectedPlan: Plan?
```

## 9. 常见陷阱

### 9.1 样本偏差

**问题**：实验组和对照组的用户特征不一致，导致结果失真。

| 偏差类型 | 例子 | 后果 |
|----------|------|------|
| 新用户偏差 | 实验组中新用户占比更高 | 新用户行为不同，干扰结果 |
| 地区偏差 | 实验组中某地区用户更多 | 地区消费力差异影响付费数据 |
| 设备偏差 | 实验组中 iPhone 用户更多 | 设备差异影响体验 |

**解决方案**：使用随机分配，确保各组用户特征分布相似。Firebase A/B Testing 自动处理。

### 9.2 多重比较

**问题**：同时看很多指标，总有一个会"显著"。

类比：抛 20 次硬币，至少有一次连续 3 个正面的概率很高，但这不代表硬币有问题。

| 看的指标数 | 至少一个假阳性的概率 |
|-----------|---------------------|
| 1 | 5% |
| 5 | 23% |
| 10 | 40% |
| 20 | 64% |

**解决方案**：

1. 预先确定主指标，只对主指标做显著性检验
2. 使用 Bonferroni 校正：将显著性阈值除以指标数（如 0.05 / 5 = 0.01）
3. 辅助指标只做参考，不做决策依据

### 9.3 过早停止

**问题**：实验前几天数据看起来很好，就提前结束。

```
第 1 天：实验组 +50%  ← 看起来很棒！
第 3 天：实验组 +30%  ← 还不错
第 7 天：实验组 +15%  ← 在下降...
第 14 天：实验组 +5%  ← 不显著了
```

这就是**回归均值**现象——极端的早期数据往往会回归到正常水平。

**解决方案**：坚持到预设的实验时长，不要提前停止。

### 9.4 新奇效应

**问题**：新设计仅仅因为"新鲜"而短期表现好，长期效果消退。

| 时间 | 实验组表现 | 原因 |
|------|-----------|------|
| 第 1 周 | 很好 ✅ | 用户好奇，多看了几眼 |
| 第 2 周 | 一般 ⚠️ | 新鲜感消退 |
| 第 3 周 | 和对照组差不多 ❌ | 完全回归 |

**解决方案**：实验至少运行 2 周，观察指标趋势是否稳定。

### 9.5 辛普森悖

**问题**：分组数据看 A 更好，合并数据看 B 更好。

| 分组 | 对照组转化率 | 实验组转化率 |
|------|-------------|-------------|
| iOS 用户 | 10% (100/1000) | 12% (60/500) |
| Android 用户 | 2% (20/1000) | 3% (30/1000) |
| **合并** | **6%** (120/2000) | **6%** (90/1500) |

各组都是实验组更好，但合并后看起来一样——因为实验组中 Android 用户（低转化群体）占比更高。

**解决方案**：分层分析，检查各子群体的结果是否一致。

## 10. 增长实验文化

### 10.1 从直觉驱动到数据驱动

| 阶段 | 特征 | 决策方式 |
|------|------|---------|
| 直觉驱动 | "我觉得应该这样" | 老板/产品经理拍脑袋 |
| 数据辅助 | "数据看起来支持这样做" | 有数据参考，但直觉仍占主导 |
| 数据驱动 | "实验证明这样做更好" | 所有重大决策都经过实验验证 |
| 数据文化 | "不实验，不决策" | 实验成为习惯，人人参与 |

### 10.2 建立实验节奏

| 频率 | 活动 | 参与者 |
|------|------|--------|
| 每周 | 提出实验假设，评审实验设计 | 产品 + 开发 + 设计 |
| 每两周 | 回顾实验结果，做出决策 | 全团队 |
| 每月 | 总结实验洞察，更新产品路线图 | 全团队 |
| 每季度 | 评估实验体系，优化流程 | 管理层 |

### 10.3 实验优先级框架

不是所有想法都值得测试，用 ICE 框架排序：

| 维度 | 含义 | 评分（1-10） |
|------|------|-------------|
| Impact | 影响有多大？ | 10 = 巨大影响 |
| Confidence | 你有多确定会有效？ | 10 = 非常确定 |
| Ease | 实施有多容易？ | 10 = 非常容易 |

**ICE 分数 = Impact × Confidence × Ease**

| 实验想法 | I | C | E | ICE 分数 | 优先级 |
|----------|---|---|---|---------|--------|
| 改购买按钮颜色 | 3 | 5 | 9 | 135 | 🥇 |
| 重新设计付费页面 | 8 | 4 | 3 | 96 | 🥈 |
| 添加社交分享功能 | 5 | 3 | 5 | 75 | 🥉 |
| 重写整个 App | 10 | 1 | 1 | 10 | ❌ |

### 10.4 失败的实验也有价值

| 实验结果 | 价值 |
|----------|------|
| 实验组胜出 | ✅ 直接收益：上线新版本 |
| 对照组胜出 | ✅ 避免损失：没有上线差的版本 |
| 无显著差异 | ✅ 节省时间：不用纠结，把精力放在别处 |
| 意外发现 | ✅ 新洞察：发现了之前没想到的用户行为 |

> 💡 **记住**：实验的目的是学习，而不仅仅是赢。每一次实验都在帮你更好地理解用户。

### 10.5 实验清单模板

每次启动实验前，用这个清单检查：

```
□ 假设是否具体、可验证？
□ 主指标是否明确？
□ 样本量是否足够？
□ 实验时长是否覆盖完整周期？
□ 是否只改变了一个变量？
□ 护栏指标是否定义？
□ 停止条件是否预设？
□ 埋点是否正确？
□ 分组是否随机且一致？
□ 是否有人负责监控和决策？
```

## 小结

| 主题 | 核心要点 |
|------|---------|
| A/B 测试概念 | 随机分组、对照比较、数据决策 |
| 实验流程 | 假设 → 设计 → 实施 → 分析 → 决策 |
| Remote Config | 远程控制 App 行为，无需发版 |
| 功能开关 | 远程控制功能展示/隐藏，支持灰度发布 |
| 实验分组 | 随机分配、一致性哈希、分层实验 |
| 指标追踪 | 主指标 + 辅助指标 + 护栏指标 |
| 统计显著性 | p < 0.05、预设样本量、不要提前停止 |
| 实战示例 | Firebase A/B Testing 测试付费页面 |
| 常见陷阱 | 样本偏差、多重比较、过早停止、新奇效应 |
| 增长文化 | 从直觉到数据、建立实验节奏、ICE 优先级 |

> 💡 **一句话总结**：A/B 测试的本质是让数据替你做决定——不要猜，要测；不要急，要等；不要只看结果，要理解原因。
