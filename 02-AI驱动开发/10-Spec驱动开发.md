# 10-Spec 驱动开发：AI 时代的最佳实践

> 🎯 **本章目标**：理解 Spec 驱动开发的概念和核心价值，掌握 PRD、技术方案、任务拆解三大文档的编写方法，学会从 Spec 到代码的完整工作流，能够用 Spec 驱动方式让 AI 高效、可靠地帮你开发功能。

---

## 什么是 Spec 驱动开发？

**Spec** 是 **Specification** 的缩写，中文叫"规格说明书"。Spec 驱动开发，就是**先把"要做什么"写清楚，再动手写代码**。

听起来很直觉对吧？但现实中，很多人拿到一个想法就迫不及待地让 AI 写代码，结果写出来的东西和想要的完全不一样——这就是缺少 Spec 的后果。

### 一个生活中的类比

```
❌ 没有 Spec 的开发：
  你：帮我建一栋房子
  工人：好的！（开始施工）
  结果：你想要别墅，工人建了个公厕

✅ 有 Spec 的开发：
  你：帮我建一栋 3 层别墅，面积 300㎡，现代简约风格，4 室 2 厅 3 卫...
  工人：好的！按照图纸施工
  结果：和你的期望基本一致
```

💡 **一句话理解**：Spec 就是建房子前的"图纸"。没有图纸就施工，建出来的东西大概率不是你想要的。

### Spec 驱动开发的核心流程

```
编写 Spec（想清楚要什么）
    ↓
拆解任务（把大目标拆成小步骤）
    ↓
AI 逐任务开发（每次只让 AI 做一件小事）
    ↓
验收与迭代（检查结果，不满意就调整）
```

⚠️ **关键认知**：Spec 驱动开发不是让你写完所有文档再写代码，而是**先想清楚再动手**。Spec 可以很简短，但必须清晰。

## 为什么 Spec 是 AI 开发的核心

### AI 的局限性

AI 很强大，但它远没有你想象的那么"聪明"。如果不给它足够的约束，它会犯各种离谱的错误：

| 局限性 | 说明 | 真实案例 |
|--------|------|---------|
| **不理解业务背景** | AI 不知道你的项目是给谁用的、有什么特殊规则 | 你做电商 App，AI 却按社交 App 的逻辑写代码 |
| **会"幻觉"** | AI 会编造不存在的 API、库、函数 | AI 调用了 `user.login()`，但你的项目根本没有这个方法 |
| **上下文有限** | AI 一次只能处理有限的代码量，无法同时理解整个项目 | 你让 AI 改登录逻辑，它不知道注册逻辑和它有关联 |
| **无法判断优先级** | AI 不知道哪些功能最重要，哪些可以延后 | 你想要核心功能，AI 却花大量代码写日志系统 |
| **风格不统一** | 每次 AI 生成的代码风格可能不同 | 同一个项目里，有的用 `const`，有的用 `let`，命名风格混乱 |

💡 **类比**：AI 就像一个能力很强但完全不了解你公司的新员工。如果你不给他明确的工作指引，他要么做错事，要么做无关的事。

### Spec 如何弥补 AI 的不足

| AI 的问题 | Spec 如何解决 | 效果 |
|-----------|-------------|------|
| 不理解业务背景 | PRD 提供完整的业务上下文 | AI 知道项目是做什么的、给谁用的 |
| 会"幻觉" | 技术方案明确指定用哪些 API 和库 | AI 不会编造不存在的东西 |
| 上下文有限 | 任务拆解让每次只做一件小事 | AI 可以专注处理，不会遗漏 |
| 无法判断优先级 | PRD 标注 P0/P1/P2 优先级 | AI 知道先做什么后做什么 |
| 风格不统一 | 技术方案定义编码规范 | AI 生成的代码风格一致 |

### Spec 驱动 vs 瀑布模型 vs 敏捷开发

很多人觉得 Spec 驱动开发就是瀑布模型（先写完所有文档再开发），其实完全不同：

| 对比维度 | 瀑布模型 | 敏捷开发 | Spec 驱动开发 |
|---------|---------|---------|-------------|
| **核心理念** | 一次性规划，按序执行 | 快速迭代，拥抱变化 | 先定义清楚，再让 AI 执行 |
| **文档量** | 极多，写完才开始 | 极少，边做边写 | 适量，够用就行 |
| **Spec 粒度** | 非常细，几百页 | 几乎没有 | 精简但清晰，几页纸 |
| **变更成本** | 极高，改需求要改一堆文档 | 低，随时调整 | 低，改 Spec 再让 AI 重新生成 |
| **适合团队** | 大型传统项目 | 人工开发团队 | AI 辅助开发 |
| **迭代方式** | 不迭代 | 人工迭代 | AI 快速迭代 |
| **开发主体** | 人 | 人 | 人 + AI |

💡 **关键区别**：Spec 驱动开发不是瀑布模型！它的 Spec 是**轻量的、可变的**。你随时可以修改 Spec，然后让 AI 重新生成代码——改 Spec 的成本远低于改代码。

⚠️ **注意**：Spec 驱动开发是**AI 时代的敏捷**。传统敏捷是"人快速迭代"，Spec 驱动是"人写 Spec，AI 快速实现，人快速验收"——迭代速度比传统敏捷快 10 倍以上。

## PRD（产品需求文档）编写

PRD（Product Requirements Document）是 Spec 的第一步，它回答的问题是：**我们要做什么？为什么做？做成什么样？**

### PRD 模板

以下是一个适合个人开发者和小团队的精简 PRD 模板：

```markdown
# PRD：[项目/功能名称]

## 1. 项目概述
- 一句话描述这个项目/功能是什么
- 为什么要做这个项目/功能

## 2. 目标用户
- 谁会使用这个产品？
- 他们的核心痛点是什么？

## 3. 功能需求

### P0（必须有，没有就不能上线）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 功能A | ... | ... |

### P1（重要，但可以第一版不做）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 功能B | ... | ... |

### P2（锦上添花，后续迭代）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 功能C | ... | ... |

## 4. 非功能需求
- 性能要求：页面加载 < 2秒
- 安全要求：密码加密存储
- 兼容性：支持 iOS 15+ 和 Android 12+

## 5. 约束与假设
- 约束：必须在 2 周内完成
- 假设：用户已有账号体系
```

💡 **提示**：PRD 不需要写得很长！对于个人项目，1-2 页就足够。关键是**把"做什么"和"不做什做"写清楚**，而不是写一堆废话。

### 功能描述规范

#### 用用户故事描述功能

用户故事是描述功能的标准方式，格式为：

```
作为 [角色]，我想要 [功能]，以便 [价值/目的]
```

| 描述方式 | 示例 | 评价 |
|---------|------|------|
| ❌ 差的描述 | "做一个登录页面" | 没说给谁用、为什么做 |
| ❌ 差的描述 | "用户可以登录" | 太笼统，不知道具体怎么登录 |
| ✅ 好的描述 | "作为注册用户，我想要用邮箱和密码登录，以便访问我的个人数据" | 角色 + 功能 + 价值，清晰完整 |
| ✅ 好的描述 | "作为忘记密码的用户，我想要通过邮箱重置密码，以便重新获得账号访问权" | 场景明确，价值清晰 |

#### 用验收标准定义"做完"

验收标准用 **Given-When-Then** 格式编写：

```
Given（给定）：前置条件
When（当）：用户操作
Then（那么）：预期结果
```

**示例——"用户登录"功能的验收标准**：

```
验收标准 1：正常登录
  Given 用户已注册账号且未登录
  When 用户输入正确的邮箱和密码，点击"登录"
  Then 跳转到首页，显示用户昵称

验收标准 2：密码错误
  Given 用户已注册账号且未登录
  When 用户输入正确的邮箱和错误的密码，点击"登录"
  Then 显示错误提示"邮箱或密码不正确"，密码输入框清空

验收标准 3：账号不存在
  Given 用户未注册过账号
  When 用户输入未注册的邮箱和任意密码，点击"登录"
  Then 显示错误提示"该邮箱未注册"，并显示"去注册"链接
```

### 验收标准定义

#### 什么是验收标准

验收标准就是**"怎样才算做完了"**的判断依据。没有验收标准，你和 AI 都不知道什么时候该停下来。

#### 好的 vs 差的验收标准

| 维度 | 差的验收标准 | 好的验收标准 |
|------|------------|------------|
| **模糊 vs 具体** | "登录功能正常" | "输入正确邮箱密码后跳转首页" |
| **主观 vs 客观** | "界面要好看" | "登录按钮宽度 100%，高度 48px，圆角 8px" |
| **不可测 vs 可测** | "速度要快" | "登录请求响应时间 < 1秒" |
| **遗漏 vs 完整** | 只写了成功的情况 | 成功、失败、边界情况都覆盖 |
| **笼统 vs 精确** | "要有错误提示" | "密码错误时显示红色提示文字'邮箱或密码不正确'" |

💡 **编写验收标准的技巧**：想象你是一个测试人员，你需要精确地知道要点哪个按钮、输入什么内容、期望看到什么结果。如果你无法根据验收标准执行测试，那说明它还不够具体。

⚠️ **警告**：不要跳过验收标准！很多人觉得"功能描述已经够清楚了，不需要验收标准"。但当你让 AI 开发时，没有验收标准，AI 就不知道边界在哪里——它可能过度实现（加了不需要的功能），也可能实现不足（漏掉了错误处理）。

## 技术方案文档编写

PRD 回答了"做什么"，技术方案回答"怎么做"。技术方案是给 AI 的"施工图纸"。

### 技术选型

#### 为什么需要技术选型文档

你可能会想："技术选型我自己心里清楚就行了，为什么要写下来？"

因为**写下来才能让 AI 知道你的选择**。如果你不告诉 AI 用什么技术栈，它可能会：
- 用你项目里根本没装的库
- 用过时的方案
- 用和你项目风格不一致的写法

#### 选型维度

| 维度 | 说明 | 示例问题 |
|------|------|---------|
| **性能** | 能否满足性能要求？ | 这个状态管理库在大数据量下会卡吗？ |
| **生态** | 社区是否活跃？文档是否完善？ | 这个库的 GitHub star 多吗？最近有更新吗？ |
| **学习成本** | 上手难度如何？ | 需要学多少新概念才能用？ |
| **维护性** | 长期维护是否有保障？ | 是大公司维护的还是个人项目？ |
| **兼容性** | 和现有项目是否兼容？ | 能不能和已有的技术栈无缝集成？ |

#### 技术选型示例

```markdown
## 技术选型：状态管理方案

| 方案 | 性能 | 生态 | 学习成本 | 维护性 | 总评 |
|------|------|------|---------|--------|------|
| Redux | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐⭐ | 适合大型项目 |
| MobX | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | 适合中小项目 |
| Zustand | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | 适合轻量项目 |

**最终选择：Zustand**
- 理由：本项目为轻量级应用，Zustand 学习成本低、性能好、API 简洁
- 风险：社区规模不如 Redux，遇到问题可能需要自己解决
```

### 架构设计

架构设计不需要画复杂的 UML 图，用清晰的文字描述即可。关键是让 AI 理解你的项目结构。

#### 架构描述示例

```markdown
## 架构设计

### 整体架构
本项目采用前后端分离架构：
- 前端：React + TypeScript + Zustand
- 后端：Node.js + Express + PostgreSQL
- 通信：RESTful API

### 模块划分
├── frontend/           # 前端项目
│   ├── src/
│   │   ├── components/ # 通用 UI 组件
│   │   ├── pages/      # 页面组件
│   │   ├── stores/     # Zustand 状态管理
│   │   ├── services/   # API 请求封装
│   │   ├── utils/      # 工具函数
│   │   └── types/      # TypeScript 类型定义
│   └── package.json
├── backend/            # 后端项目
│   ├── src/
│   │   ├── routes/     # 路由定义
│   │   ├── controllers/# 控制器
│   │   ├── services/   # 业务逻辑
│   │   ├── models/     # 数据模型
│   │   ├── middlewares/ # 中间件
│   │   └── utils/      # 工具函数
│   └── package.json
└── docs/               # 项目文档
```

#### 数据流向

```markdown
### 数据流向

用户操作 → 页面组件 → 调用 Store 方法 → Store 调用 Service → Service 发起 API 请求
                                                                    ↓
页面更新 ← Store 更新状态 ← Service 返回数据 ← 后端返回 JSON ← 后端处理请求
```

💡 **提示**：架构设计的核心是**让 AI 知道代码应该放在哪里**。如果 AI 不知道项目结构，它可能会把所有代码写在一个文件里，或者把组件放到错误的目录。

### 接口定义

接口定义是技术方案中最关键的部分之一。明确的接口定义可以避免 AI 编造不存在的 API。

#### API 接口规范

```markdown
## API 接口定义

### 用户登录

**请求**
- 方法：POST
- 路径：/api/auth/login
- Content-Type：application/json

**请求体**
```json
{
  "email": "user@example.com",
  "password": "string"
}
```

**成功响应（200）**
```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "jwt_token_string",
    "user": {
      "id": 1,
      "email": "user@example.com",
      "nickname": "小明"
    }
  }
}
```

**失败响应（401）**
```json
{
  "code": 40101,
  "message": "邮箱或密码不正确",
  "data": null
}
```

**账号不存在响应（404）**
```json
{
  "code": 40401,
  "message": "该邮箱未注册",
  "data": null
}
```
```

#### 数据模型定义

```markdown
## 数据模型

### User 用户表
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | integer | 是 | 主键，自增 |
| email | string | 是 | 邮箱，唯一索引 |
| password_hash | string | 是 | 密码哈希值（bcrypt） |
| nickname | string | 是 | 昵称，2-20字符 |
| avatar_url | string | 否 | 头像 URL |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 更新时间 |
```

#### 错误码定义

```markdown
## 错误码规范

| 错误码 | HTTP 状态码 | 说明 |
|--------|-----------|------|
| 0 | 200 | 成功 |
| 40001 | 400 | 请求参数错误 |
| 40101 | 401 | 邮箱或密码不正确 |
| 40102 | 401 | Token 已过期 |
| 40301 | 403 | 无权限访问 |
| 40401 | 404 | 资源不存在 |
| 40901 | 409 | 邮箱已被注册 |
| 50001 | 500 | 服务器内部错误 |
```

⚠️ **注意**：接口定义越详细，AI 生成的代码越准确。特别是错误码和错误响应格式——如果你不定义，AI 就会按自己的理解来写，很可能和你的其他接口不一致。

## 任务拆解与 Checklist

### 从 Spec 到 Task

有了 PRD 和技术方案，下一步是把它们拆成一个个**可执行的小任务**。这是 Spec 驱动开发中最关键的步骤之一。

#### 为什么要拆解任务？

```
❌ 不拆解，直接让 AI 做"用户登录功能"：
  AI 可能会：
  - 一次生成几百行代码，你无法审查
  - 遗漏某些验收标准
  - 前后代码风格不一致
  - 出了 bug 不知道问题在哪

✅ 拆解后，逐任务让 AI 做：
  任务1：创建 User 数据模型 → 审查 → ✅ 通过
  任务2：实现注册 API → 审查 → ✅ 通过
  任务3：实现登录 API → 审查 → 发现问题，修改 → ✅ 通过
  任务4：创建登录页面 UI → 审查 → ✅ 通过
  任务5：前后端联调 → 测试 → ✅ 通过
```

💡 **核心原则**：每个任务应该**1-2 小时内可完成**。太大了无法审查，太小了效率太低。

#### 任务模板

```markdown
## 任务：[任务名称]

**所属功能**：[来自 PRD 的哪个功能]
**优先级**：P0 / P1 / P2
**预估时间**：[1-2小时]

### 任务描述
[具体要做什么，越具体越好]

### 验收标准
- [ ] 标准1
- [ ] 标准2
- [ ] 标准3

### 相关 Spec
[引用 PRD 或技术方案中的相关部分]

### 技术要点
[实现时需要注意的技术细节]
```

### 任务粒度控制

| 粒度 | 示例 | 问题 |
|------|------|------|
| **太大** | "实现用户模块"（包含注册、登录、个人信息、修改密码...） | 一次生成代码太多，无法审查，出错概率高 |
| **太小** | "创建 User 类型定义文件" | 任务太琐碎，AI 来回切换上下文，效率低 |
| **合适** | "实现用户注册 API，包含参数验证和错误处理" | 大小适中，可以完整审查，出错容易定位 |

💡 **判断标准**：如果一个任务的代码量超过 **200 行**，说明太大了，需要继续拆分。如果一个任务只需要改 **10 行以内**的代码，说明太小了，可以和相邻任务合并。

### 优先级排序

#### MoSCoW 方法

| 优先级 | 含义 | 说明 | 示例 |
|--------|------|------|------|
| **M**ust have | 必须有 | 没有这个功能，产品不能发布 | 用户注册、登录 |
| **S**hould have | 应该有 | 重要但不是第一版必须的 | 找回密码、记住登录 |
| **C**ould have | 可以有 | 锦上添花的功能 | 第三方登录 |
| **W**on't have | 不做 | 明确排除的功能 | 人脸识别登录 |

#### P0/P1/P2 标注法

| 优先级 | 含义 | 开发顺序 | 示例 |
|--------|------|---------|------|
| **P0** | 核心功能，必须完成 | 第一批 | 注册、登录、首页 |
| **P1** | 重要功能，尽快完成 | 第二批 | 个人信息编辑、设置 |
| **P2** | 优化功能，后续迭代 | 第三批 | 暗黑模式、多语言 |

💡 **建议**：对于个人开发者，P0/P1/P2 标注法更直观好用。先把所有 P0 任务做完，再做 P1，最后做 P2。不要同时做不同优先级的任务。

## 从 Spec 到代码的完整工作流

### Step 1: 编写 PRD

把"要做什么"写清楚。不需要很长，但必须回答以下问题：

```
✅ PRD 必须回答的问题：
1. 这个项目/功能是什么？
2. 给谁用的？
3. 有哪些功能？优先级是什么？
4. 每个功能的验收标准是什么？
5. 有什么约束和假设？
```

💡 **提示**：PRD 可以用 Markdown 写，也可以用 Notion、飞书文档等工具。格式不重要，内容清晰才重要。对于小功能，甚至可以只写几行文字——但必须写下来。

### Step 2: 编写技术方案

把"怎么做"想清楚。技术方案需要回答：

```
✅ 技术方案必须回答的问题：
1. 用什么技术栈？
2. 代码怎么组织（目录结构）？
3. 数据怎么存储（数据模型）？
4. 前后端怎么通信（API 接口）？
5. 有什么技术风险？
```

⚠️ **注意**：技术方案不需要完美！先写一个 70 分的方案，开发过程中可以随时调整。关键是让 AI 有一个明确的"施工图纸"，而不是让它自己瞎猜。

### Step 3: 拆解任务

把 PRD 和技术方案拆成一个个小任务：

```
PRD 功能列表          技术方案              拆解后的任务
┌──────────┐     ┌──────────┐     ┌─────────────────────┐
│ 用户注册   │ ──→ │ 数据模型   │ ──→ │ 任务1: 创建 User 模型  │
│          │     │ API 接口   │ ──→ │ 任务2: 实现注册 API    │
│          │     │ 页面 UI   │ ──→ │ 任务3: 创建注册页面    │
├──────────┤     ├──────────┤     ├─────────────────────┤
│ 用户登录   │ ──→ │ API 接口   │ ──→ │ 任务4: 实现登录 API    │
│          │     │ 页面 UI   │ ──→ │ 任务5: 创建登录页面    │
│          │     │ 状态管理   │ ──→ │ 任务6: 实现登录状态管理 │
└──────────┘     └──────────┘     └─────────────────────┘
```

### Step 4: AI 辅助逐任务开发

这是最关键的一步。**每次只给 AI 一个任务**，而不是把所有需求一股脑丢给它。

#### 正确的做法

```
你给 AI 的信息：
1. 项目背景（简短介绍项目是什么）
2. 技术方案（相关的部分）
3. 当前任务描述
4. 验收标准
5. 相关代码（已有的、需要参考的文件）

AI 返回：
1. 实现代码
2. 需要修改的文件列表
3. 实现说明

你做的：
1. 审查 AI 生成的代码
2. 运行测试
3. 对照验收标准检查
4. 通过后进入下一个任务
```

#### 错误的做法

```
❌ 把整个 PRD 丢给 AI：
  "帮我做一个用户系统，包含注册、登录、修改密码、个人信息管理..."
  结果：AI 一次生成几千行代码，你无法审查，大概率有 bug

❌ 不给 AI 上下文：
  "帮我写一个登录 API"
  结果：AI 不知道你的项目用什么框架、什么数据库、什么命名规范

❌ 不检查就接受：
  AI 生成了代码，你直接接受
  结果：可能有安全漏洞、性能问题、逻辑错误
```

💡 **核心原则**：**一次一个任务，给够上下文，审查再接受**。

### Step 5: 验收与迭代

每个任务完成后，对照验收标准检查：

```
验收检查清单：
□ 功能是否满足验收标准？
□ 代码是否符合项目编码规范？
□ 是否有明显的安全漏洞？
□ 是否有明显的性能问题？
□ 是否处理了错误情况？
□ 是否和已有代码风格一致？
```

如果不满足验收标准，把问题反馈给 AI，让它修改。**不要自己默默改**——把问题告诉 AI，让它理解哪里做错了，这样下次它才能做得更好。

## 实战：用 Spec 驱动开发一个功能模块

让我们以"用户登录功能"为例，完整演示 Spec 驱动开发的全流程。

### Step 1: 编写 PRD

```markdown
# PRD：用户登录功能

## 1. 项目概述
为 App 添加用户登录功能，让已注册用户可以通过邮箱和密码登录，访问个人数据。

## 2. 目标用户
- 已通过注册页面创建账号的用户
- 需要重新登录的用户（Token 过期后）

## 3. 功能需求

### P0（必须有）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 邮箱密码登录 | 用户输入邮箱和密码登录 | Given 已注册用户，When 输入正确邮箱密码，Then 跳转首页 |
| 登录错误提示 | 登录失败时显示错误信息 | Given 密码错误，When 点击登录，Then 显示"邮箱或密码不正确" |
| Token 管理 | 登录成功后保存 Token | Given 登录成功，When 跳转首页，Then 本地存储有效 Token |

### P1（重要）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 记住登录状态 | 关闭 App 后不需要重新登录 | Given 已登录，When 重新打开 App，Then 自动登录 |
| 退出登录 | 用户主动退出登录 | Given 已登录，When 点击退出，Then 清除 Token，跳转登录页 |

### P2（后续迭代）
| 功能 | 描述 | 验收标准 |
|------|------|---------|
| 第三方登录 | 支持微信/Apple 登录 | 暂不实现 |

## 4. 非功能需求
- 登录请求响应时间 < 1秒
- 密码在传输和存储时必须加密
- 连续 5 次登录失败后锁定账号 15 分钟

## 5. 约束与假设
- 假设用户已通过注册页面创建了账号
- 假设后端 API 已就绪
- 约束：只实现 P0 功能，P1/P2 后续迭代
```

### Step 2: 编写技术方案

```markdown
# 技术方案：用户登录功能

## 1. 技术选型
- 前端框架：React Native + TypeScript
- 状态管理：Zustand
- 网络请求：axios
- 本地存储：AsyncStorage
- 路由：React Navigation

## 2. 目录结构
src/
├── pages/
│   └── LoginPage.tsx        # 登录页面
├── services/
│   └── authService.ts       # 认证相关 API 请求
├── stores/
│   └── authStore.ts         # 认证状态管理
├── types/
│   └── auth.ts              # 认证相关类型定义
└── utils/
    └── token.ts             # Token 管理工具

## 3. API 接口

### POST /api/auth/login
请求体：{ email: string, password: string }
成功响应：{ code: 0, data: { token: string, user: UserInfo } }
失败响应：{ code: 40101, message: "邮箱或密码不正确" }

## 4. 数据模型

### UserInfo
{
  id: number;
  email: string;
  nickname: string;
  avatar_url: string | null;
}

## 5. 状态管理

### authStore
{
  token: string | null;
  user: UserInfo | null;
  isLoading: boolean;
  login: (email: string, password: string) => Promise<void>;
  logout: () => void;
}
```

### Step 3: 拆解任务

```markdown
## 任务清单

### 任务 1：创建认证类型定义
- 文件：src/types/auth.ts
- 内容：定义 UserInfo、LoginRequest、LoginResponse 类型
- 预估时间：15 分钟

### 任务 2：创建 Token 管理工具
- 文件：src/utils/token.ts
- 内容：实现 saveToken、getToken、removeToken 方法
- 预估时间：30 分钟

### 任务 3：创建认证 API 服务
- 文件：src/services/authService.ts
- 内容：实现 login API 请求函数
- 预估时间：30 分钟

### 任务 4：创建认证状态管理
- 文件：src/stores/authStore.ts
- 内容：实现 login、logout 方法，管理 token 和 user 状态
- 预估时间：45 分钟

### 任务 5：创建登录页面 UI
- 文件：src/pages/LoginPage.tsx
- 内容：邮箱输入框、密码输入框、登录按钮、错误提示、加载状态
- 预估时间：1 小时

### 任务 6：联调与测试
- 内容：前后端联调，验证所有验收标准
- 预估时间：1 小时
```

### Step 4: AI 辅助逐任务开发

以**任务 3：创建认证 API 服务**为例，演示如何给 AI 发 Prompt：

```
你是一个 React Native 开发者。请帮我实现认证 API 服务。

【项目背景】
这是一个 React Native + TypeScript 项目，使用 axios 进行网络请求。

【技术方案】
- API 基础地址：https://api.example.com
- 所有请求需要设置 Content-Type: application/json
- 错误统一处理：网络错误抛出 Error，业务错误返回错误信息

【类型定义】（已有文件 src/types/auth.ts）
interface LoginRequest {
  email: string;
  password: string;
}

interface LoginResponse {
  code: number;
  message: string;
  data: {
    token: string;
    user: UserInfo;
  };
}

【当前任务】
创建 src/services/authService.ts，实现 login 函数：
- 接收 email 和 password 参数
- 调用 POST /api/auth/login
- 成功时返回 LoginResponse
- 失败时抛出包含错误信息的 Error

【验收标准】
- login 函数类型正确，参数和返回值都有类型定义
- 请求错误时有统一的错误处理
- 代码风格和项目其他 service 文件一致
```

AI 可能返回的代码：

```typescript
import axios from 'axios';
import type { LoginRequest, LoginResponse } from '../types/auth';

const BASE_URL = 'https://api.example.com';

const api = axios.create({
  baseURL: BASE_URL,
  headers: {
    'Content-Type': 'application/json',
  },
});

export const authService = {
  async login(data: LoginRequest): Promise<LoginResponse> {
    try {
      const response = await api.post<LoginResponse>('/api/auth/login', data);
      return response.data;
    } catch (error) {
      if (axios.isAxiosError(error) && error.response) {
        const message = error.response.data?.message || '登录失败，请稍后重试';
        throw new Error(message);
      }
      throw new Error('网络错误，请检查网络连接');
    }
  },
};
```

### Step 5: 验收

对照验收标准逐项检查：

| 验收标准 | 结果 | 说明 |
|---------|------|------|
| login 函数类型正确 | ✅ | 参数 LoginRequest，返回 Promise\<LoginResponse\> |
| 请求错误时有统一错误处理 | ✅ | 区分业务错误和网络错误 |
| 代码风格一致 | ✅ | 使用 axios、async/await、命名规范一致 |

✅ 任务 3 通过验收，进入任务 4。

## 小结

本章我们学习了 Spec 驱动开发——AI 时代最有效的开发方法论：

1. **Spec 驱动开发 = 先想清楚再动手**——就像建房子先画图纸，写代码前先写清楚要做什么、怎么做
2. **Spec 弥补了 AI 的不足**——AI 不理解业务、会幻觉、上下文有限，Spec 提供了完整的上下文和约束
3. **PRD 回答"做什么"**——用用户故事描述功能，用 Given-When-Then 定义验收标准
4. **技术方案回答"怎么做"**——技术选型、架构设计、接口定义，给 AI 一张清晰的"施工图纸"
5. **任务拆解是关键**——把大需求拆成 1-2 小时可完成的小任务，逐个让 AI 实现
6. **一次一个任务，给够上下文，审查再接受**——这是 AI 辅助开发的黄金法则

⚠️ **最重要的提醒**：Spec 不需要完美！先写一个 70 分的 Spec，开始开发，在开发过程中迭代完善。不要陷入"过度设计"的陷阱——Spec 的目的是让 AI 更好地工作，而不是写一堆没人看的文档。
