## Prompt Engineering 编程技巧

Prompt（提示词）是你给 AI 的指令。写好 Prompt，就像给一个新员工写清楚工作说明——说明越清楚，结果越靠谱。

### 如何描述需求让 AI 理解

#### 5 要素法：角色 + 背景 + 任务 + 约束 + 示例

| 要素 | 说明 | 为什么重要 |
|------|------|-----------|
| **角色** | 告诉 AI 它是谁 | 不同角色有不同的思维方式和专业深度 |
| **背景** | 项目上下文信息 | AI 需要了解你的项目才能给出合适的方案 |
| **任务** | 具体要做什么 | 明确的任务让 AI 不偏离方向 |
| **约束** | 限制条件和要求 | 约束让 AI 不乱来，输出更可控 |
| **示例** | 期望的输出格式或参考 | 示例让 AI 知道你要什么样的结果 |

#### 好的 Prompt vs 差的 Prompt

**差的 Prompt**：

```
帮我写一个登录功能
```

❌ 问题：没有角色、没有背景、没有约束、没有示例，AI 只能猜你要什么。

**好的 Prompt**：

```
你是一个 React Native 高级开发工程师。

【背景】
我正在开发一个电商 App，使用 React Native + TypeScript + Zustand 技术栈。
项目使用 axios 做网络请求，AsyncStorage 做本地存储。

【任务】
实现用户登录功能，包含：
1. 登录页面 UI（邮箱输入框 + 密码输入框 + 登录按钮 + 错误提示）
2. 登录 API 调用（POST /api/auth/login）
3. 登录状态管理（Zustand store）

【约束】
- 使用 TypeScript，所有变量和函数都要有类型定义
- 密码输入框需要支持显示/隐藏密码
- 登录按钮在请求期间显示 loading 状态，防止重复点击
- 错误提示使用红色文字，显示在表单下方
- 代码风格：使用函数式组件 + hooks，不使用 class 组件

【示例】
登录 API 的请求和响应格式：
请求：{ email: "user@example.com", password: "123456" }
成功：{ code: 0, data: { token: "xxx", user: { id: 1, nickname: "小明" } } }
失败：{ code: 40101, message: "邮箱或密码不正确" }
```

✅ 优点：角色明确、背景充分、任务具体、约束清晰、有示例参考。

💡 **提示**：写 Prompt 就像写 Spec——越具体，AI 的输出越接近你的期望。花 5 分钟写好 Prompt，可以省下 30 分钟的修改时间。

### 上下文管理

#### 给 AI 足够的上下文

AI 不了解你的项目，它只看到你给它的信息。上下文不足是 AI 输出质量差的第一大原因。

| 上下文类型 | 说明 | 什么时候给 |
|-----------|------|-----------|
| **项目技术栈** | 用了什么框架、库、工具 | 第一次对话时 |
| **目录结构** | 代码文件的组织方式 | 涉及创建新文件时 |
| **相关代码** | 需要参考或修改的已有代码 | 涉及修改现有功能时 |
| **编码规范** | 命名风格、代码格式等 | 第一次对话时 |
| **业务规则** | 特定的业务逻辑和约束 | 涉及业务逻辑时 |

#### 不要一次性给太多

虽然上下文很重要，但**一次性塞太多信息**也会出问题：

```
❌ 一次性给太多：
  把整个项目的 50 个文件都贴给 AI
  → AI 上下文溢出，抓不住重点
  → 响应变慢，质量下降

✅ 分步骤递进：
  第1轮：给项目背景 + 技术栈 + 目录结构
  第2轮：给当前任务 + 相关代码
  第3轮：给具体约束 + 示例
  → AI 每轮都聚焦，输出质量高
```

💡 **原则**：**给 AI 刚好够用的上下文**。就像你给同事布置任务——不需要把公司所有文档都给他，只需要给他和这个任务相关的信息。

#### 分步骤递进示例

```
第1轮对话 — 建立项目认知：
  "这是一个 React Native 电商 App，使用 TypeScript + Zustand + axios。
   目录结构：src/{pages, services, stores, types, utils}
   编码规范：函数式组件、camelCase 命名、所有函数有类型定义。"

第2轮对话 — 给出具体任务：
  "请帮我实现登录页面。需要邮箱输入框、密码输入框、登录按钮。
   密码框支持显示/隐藏。登录按钮点击后调用 API。"

第3轮对话 — 细化和修正：
  "登录按钮需要加 loading 状态，防止重复点击。
   错误提示显示在表单下方，用红色文字。
   请参考 src/pages/SignupPage.tsx 的风格。"
```

### 迭代式对话

#### 不要期望一次得到完美结果

AI 不是"许愿机"——你提一个需求，它就完美实现。现实中的 AI 协作是**迭代式**的：

```
第1轮：你提需求 → AI 生成初版代码
第2轮：你指出问题 → AI 修改
第3轮：你补充细节 → AI 完善
第4轮：你验收通过 ✅
```

#### 逐步细化和修正

| 迭代轮次 | 你做什么 | AI 做什么 |
|---------|---------|----------|
| 第1轮 | 描述核心需求 | 生成基础代码框架 |
| 第2轮 | 指出遗漏和问题 | 修复 bug、补充逻辑 |
| 第3轮 | 补充边界情况和细节 | 添加错误处理、优化体验 |
| 第4轮 | 审查和验收 | 最终调整 |

#### 迭代对话示例

```
第1轮 — 生成基础代码：
  你："帮我写一个登录页面"
  AI：生成一个基础登录页面

第2轮 — 修正问题：
  你："密码输入框没有显示/隐藏功能，请加上"
  AI：添加密码显示/隐藏切换

第3轮 — 补充细节：
  你："登录按钮在请求期间要显示 loading，防止重复点击。
       还有，邮箱输入框需要验证格式，不合法时提示用户。"
  AI：添加 loading 状态和邮箱格式验证

第4轮 — 优化体验：
  你："错误提示的样式和注册页不一致，请参考 SignupPage 的样式。
       另外，按回车键也应该触发登录。"
  AI：统一样式，添加回车登录支持
```

💡 **技巧**：每次迭代只提 1-2 个修改点，不要一次提太多。这样 AI 可以集中处理，修改更准确。

#### 重构注意事项

| 注意事项 | 说明 | 原因 |
|---------|------|------|
| **先测试再重构** | 重构前确保有测试用例 | 防止重构引入新 bug |

## AI 生成代码的质量把控

### 代码验证清单（10 项检查表）

每次接受 AI 生成的代码前，请逐项检查：

| # | 检查项 | 说明 | 如何检查 |
|---|--------|------|---------|
| 1 | **功能正确性** | 代码是否实现了需求？ | 对照验收标准逐项验证 |
| 2 | **类型安全** | TypeScript 类型是否正确？ | 运行 `tsc --noEmit` 检查 |
| 3 | **错误处理** | 是否处理了所有错误情况？ | 检查 try-catch、空值判断 |
| 4 | **安全性** | 是否有安全漏洞？ | 检查输入验证、敏感数据处理 |
| 5 | **性能** | 是否有明显的性能问题？ | 检查循环、渲染、内存使用 |
| 6 | **命名规范** | 变量/函数命名是否合理？ | 对照项目编码规范 |
| 7 | **代码风格** | 是否和项目风格一致？ | 运行 ESLint/Prettier 检查 |
| 8 | **边界情况** | 是否处理了空值、极端输入？ | 思考各种可能的输入 |
| 9 | **依赖检查** | 是否引入了不需要的依赖？ | 检查 import 语句 |
| 10 | **可维护性** | 代码是否容易理解和修改？ | 6 个月后你还能看懂吗？ |

💡 **建议**：把这张清单打印出来贴在显示器旁边，或者保存为书签。每次审查 AI 代码时，逐项打勾——**不要跳过任何一项**。

### 安全性检查

#### 常见 AI 生成的安全问题

| 安全问题 | 说明 | AI 常犯的错误 |
|---------|------|-------------|
| **SQL 注入** | 恶意输入被拼接到 SQL 语句中 | AI 可能直接拼接字符串而不是使用参数化查询 |
| **XSS 攻击** | 恶意脚本被注入到页面中 | AI 可能使用 `dangerouslySetInnerHTML` 或 `innerHTML` |
| **敏感信息泄露** | 密码、Token 等暴露在前端代码中 | AI 可能把密钥硬编码在代码里 |
| **未验证输入** | 用户输入未经验证直接使用 | AI 可能省略输入验证以简化代码 |
| **不安全的存储** | 敏感数据存储在不安全的位置 | AI 可能用 localStorage 存 Token 而不是 httpOnly Cookie |

#### 检查方法

```typescript
// ❌ AI 可能生成的危险代码
const query = `SELECT * FROM users WHERE email = '${email}'`;
document.getElementById('content').innerHTML = userInput;
const API_KEY = 'sk-xxxxxxxxxxxxx';
localStorage.setItem('token', token);

// ✅ 安全的写法
const query = 'SELECT * FROM users WHERE email = ?';
db.query(query, [email]);
element.textContent = userInput;
const API_KEY = process.env.API_KEY;
SecureStore.setItemAsync('token', token);
```

⚠️ **警告**：**永远不要把 API Key、密码、Token 等敏感信息硬编码在代码中**。AI 经常犯这个错误——它不知道这些信息不应该出现在代码里。你必须在审查时特别留意。

### 性能考量

#### AI 可能生成的性能问题

| 性能问题 | 说明 | AI 常犯的错误 |
|---------|------|-------------|
| **不必要的重渲染** | 组件频繁重新渲染 | AI 可能没有使用 `useMemo`、`useCallback` |
| **循环中发请求** | 在循环里逐个发 API 请求 | AI 可能用 `for` 循环逐个请求而不是批量请求 |
| **大列表不虚拟化** | 一次性渲染大量列表项 | AI 可能直接 `map` 渲染所有数据 |
| **内存泄漏** | 未清理定时器、事件监听器 | AI 可能忘记在 `useEffect` 的 cleanup 中清理 |
| **过度获取数据** | 请求了不需要的数据 | AI 可能用 `SELECT *` 而不是只查需要的字段 |

#### 检查方法

```typescript
// ❌ AI 可能生成的低效代码
function UserList({ users }) {
  return users.map(user => <UserCard user={user} />); // 大列表不虚拟化
}

useEffect(() => {
  const timer = setInterval(() => { /* ... */ }, 1000);
  // 忘记返回 cleanup 函数，导致内存泄漏
}, []);

for (const id of ids) {
  await fetch(`/api/user/${id}`); // 循环中逐个请求
}

// ✅ 高效的写法
import { FlatList } from 'react-native';
function UserList({ users }) {
  return <FlatList data={users} renderItem={({ item }) => <UserCard user={item} />} />;
}

useEffect(() => {
  const timer = setInterval(() => { /* ... */ }, 1000);
  return () => clearInterval(timer); // 清理定时器
}, []);

const users = await fetch('/api/users', { method: 'POST', body: JSON.stringify({ ids }) }); // 批量请求
```

💡 **提示**：性能问题通常不会导致功能错误，所以很容易被忽略。但当你上线后用户量增长，这些问题就会暴露出来。**在审查 AI 代码时，特别关注循环、列表渲染和定时器**。

## 常见 AI 陷阱

### 幻觉问题

#### 什么是 AI 幻觉

AI 幻觉是指 AI **编造了不存在的信息**，但说得很自信，让你以为是真的。

| 幻觉类型 | 说明 | 示例 |
|---------|------|------|
| **编造 API** | 调用了不存在的函数或方法 | AI 使用了 `user.login()`，但库的 API 是 `auth.signIn()` |
| **编造库** | 引用了不存在的第三方库 | AI `import { MagicButton } from 'react-magic-ui'`，这个库根本不存在 |
| **编造参数** | 使用了不存在的参数 | AI 传了 `scrollEnabled={false}`，但该组件没有这个 prop |
| **编造文档** | 引用了不存在的文档或链接 | AI 说"参考 React 官方文档 xxx 页"，但这个页面不存在 |

#### 如何识别

```
识别 AI 幻觉的信号：
1. AI 使用的函数/方法你从未见过 → 可能是幻觉
2. AI 引用的库你从未听说过 → 可能是幻觉
3. AI 给出的代码看起来"太完美" → 可能是幻觉
4. AI 给出的链接打不开 → 可能是幻觉
5. AI 说的和你查到的官方文档不一致 → 可能是幻觉
```

#### 如何避免

| 方法 | 说明 | 操作 |
|------|------|------|
| **验证 API** | 检查 AI 使用的 API 是否真实存在 | 查阅官方文档 |
| **验证库** | 检查 AI 引用的库是否真实存在 | 在 npm/GitHub 上搜索 |
| **运行代码** | 实际运行 AI 生成的代码 | 看是否报错 |
| **提供文档** | 在 Prompt 中提供正确的 API 文档 | 让 AI 基于真实文档生成代码 |
| **指定版本** | 告诉 AI 你使用的库版本 | 防止 AI 使用新版本才有的 API |

💡 **核心原则**：**永远不要盲目信任 AI 生成的代码**。至少要运行一次、验证一次。

### 过时代码

#### AI 可能使用已废弃的 API

AI 的训练数据有时间截止点，它可能不知道某些 API 已经被废弃：

| 废弃情况 | AI 可能使用的 | 正确的替代方案 |
|---------|-------------|--------------|
| React 类组件 | `class MyComponent extends Component` | 函数式组件 + Hooks |
| React 旧生命周期 | `componentWillMount` | `useEffect` |
| React Router v5 | `<Switch>` | `<Routes>`（v6+） |
| Node.js 回调风格 | `fs.readFile(path, callback)` | `fs.promises.readFile(path)` |
| 旧版 Zustand | `create(() => ({}))` | `create(() => ({}))` + 新版中间件 |

#### 如何验证

```
验证 AI 代码是否过时的方法：
1. 查看官方文档的最新版本
2. 在代码编辑器中看是否有废弃警告（删除线）
3. 运行代码看控制台是否有 deprecation warning
4. 在 Prompt 中明确指定库的版本号
```

💡 **建议**：在 Prompt 中写明你使用的库版本，比如"React 18 + React Router v6"，这样 AI 就不会生成旧版本的代码。

### 安全漏洞

#### 常见安全漏洞类型

| 漏洞类型 | 危害 | AI 常犯的错误 |
|---------|------|-------------|
| **硬编码密钥** | 密钥泄露，被恶意使用 | 把 API Key 直接写在代码里 |
| **SQL 注入** | 数据库被攻击 | 拼接 SQL 字符串而不是参数化查询 |
| **XSS** | 用户数据被窃取 | 直接插入用户输入到 HTML |
| **不安全的认证** | 账号被盗 | Token 存在 localStorage、密码明文传输 |
| **未授权访问** | 数据泄露 | 缺少权限检查 |

#### 防范方法

```typescript
// 1. 敏感信息用环境变量
const API_KEY = process.env.EXPO_PUBLIC_API_KEY;

// 2. 使用参数化查询
db.query('SELECT * FROM users WHERE id = ?', [userId]);

// 3. 转义用户输入
import sanitizeHtml from 'sanitize-html';
const safeContent = sanitizeHtml(userInput);

// 4. 安全存储 Token
import * as SecureStore from 'expo-secure-store';
await SecureStore.setItemAsync('token', token);

// 5. 始终验证权限
if (!currentUser.canEdit(projectId)) {
  throw new ForbiddenError('无权限操作');
}
```

⚠️ **警告**：安全漏洞是 AI 生成代码中**最危险**的问题。功能错了可以改，安全漏洞可能让你损失用户数据甚至面临法律风险。**每次审查 AI 代码时，安全检查必须放在第一位**。

### 过度依赖

#### 过度依赖 AI 的危害

| 危害 | 说明 | 后果 |
|------|------|------|
| **能力退化** | 不再自己思考，完全依赖 AI | 离开 AI 就不会写代码 |
| **无法判断对错** | 不理解 AI 生成的代码，无法判断质量 | 引入 bug 和安全漏洞而不自知 |
| **被 AI 误导** | AI 幻觉时你也不知道 | 采用了错误的方案 |
| **失去创造力** | 所有方案都让 AI 想象 | 代码千篇一律，没有个人风格 |
| **无法调试** | 出了问题不知道怎么排查 | 只能反复问 AI，效率极低 |

#### 保持独立思考

```
健康的 AI 协作方式：
1. 先自己思考方案，再让 AI 补充
2. 理解 AI 生成的每一行代码，不理解就问
3. 不要让 AI 替你做架构决策
4. 定期脱离 AI 手写代码，保持手感
5. 把 AI 当"助手"而不是"老板"
```

💡 **类比**：AI 就像计算器。计算器帮你算得更快，但你必须知道什么时候该用加法、什么时候该用乘法。如果你连加减乘除都不会，计算器也帮不了你。

## 如何逐步构建 AI 友好的项目结构

AI 友好的项目结构，就是让 AI **更容易理解你的项目**，从而生成更准确的代码。

### 清晰的目录结构

```
❌ AI 不友好的结构：
  src/
  ├── App.tsx
  ├── components.tsx      # 所有组件塞在一个文件
  ├── utils.js            # 所有工具函数塞在一个文件
  ├── api.ts              # 所有 API 请求塞在一个文件
  └── styles.css          # 所有样式塞在一个文件

✅ AI 友好的结构：
  src/
  ├── pages/
  │   ├── LoginPage.tsx
  │   ├── HomePage.tsx
  │   └── ProfilePage.tsx
  ├── components/
  │   ├── Button/
  │   │   ├── Button.tsx
  │   │   └── Button.styles.ts
  │   └── Input/
  │       ├── Input.tsx
  │       └── Input.styles.ts
  ├── services/
  │   ├── authService.ts
  │   └── userService.ts
  ├── stores/
  │   ├── authStore.ts
  │   └── userStore.ts
  ├── types/
  │   ├── auth.ts
  │   └── user.ts
  └── utils/
      ├── format.ts
      └── validate.ts
```

| 原则 | 说明 | 好处 |
|------|------|------|
| **按功能分目录** | pages、components、services 等各归其位 | AI 知道新代码该放哪里 |
| **一个文件一个职责** | 每个文件只做一件事 | AI 不会把无关代码混在一起 |
| **命名即文档** | 文件名和函数名能说明用途 | AI 不需要额外解释就能理解 |
| **扁平不过深** | 目录层级不超过 3 层 | AI 不会在深层目录中迷失 |

### 完善的注释和文档

```typescript
// ❌ AI 不友好的注释
// 处理数据
function process(d: any) { ... }

// ✅ AI 友好的注释
/**
 * 将用户提交的表单数据转换为 API 请求格式
 * @param formData - 表单数据对象
 * @returns 符合 POST /api/user 接口要求的请求体
 */
function formatUserFormData(formData: UserFormData): CreateUserRequest { ... }
```

💡 **原则**：注释应该解释**为什么**，而不是**做什么**。代码本身已经说明了"做什么"，注释应该补充代码无法表达的信息——比如业务背景、设计决策、注意事项。

### 一致的编码风格

| 风格维度 | 不一致的表现 | 一致的做法 |
|---------|------------|-----------|
| **命名** | 有的 `camelCase`，有的 `snake_case` | 统一用 `camelCase` |
| **组件风格** | 有的函数式，有的类式 | 统一用函数式组件 |
| **导出方式** | 有的 `export default`，有的命名导出 | 统一用命名导出 |
| **状态管理** | 有的用 Zustand，有的用 Context | 统一用 Zustand |
| **错误处理** | 有的 try-catch，有的 `.catch()` | 统一用 try-catch |

⚠️ **注意**：AI 每次生成代码时，风格可能不一致。你需要在 Prompt 中明确指定编码风格，或者使用 ESLint + Prettier 自动格式化。

### 模块化设计

```
模块化的好处：
1. AI 每次只需要理解一个模块，不需要理解整个项目
2. 修改一个模块不会影响其他模块
3. 可以让 AI 逐模块开发，降低出错概率
4. 测试可以按模块编写，更容易覆盖

模块化原则：
- 高内聚：一个模块只做一件事
- 低耦合：模块之间依赖越少越好
- 单一职责：每个文件/函数只负责一个功能
- 接口清晰：模块之间的交互通过明确的接口
```

## .cursorrules / CLAUDE.md 等项目规范文件编写

项目规范文件是**让 AI 自动理解你项目规则**的最佳方式。它们就像项目的"员工手册"——AI 每次开始工作时，先读这个文件，就知道该怎么做。

### .cursorrules 模板

`.cursorrules` 是 Cursor AI IDE 的项目规范文件，放在项目根目录下：

```
# 项目规范

## 项目概述
这是一个 [项目名称]，使用 [技术栈] 开发。
目标用户是 [目标用户]，核心功能是 [核心功能]。

## 技术栈
- 前端：React Native + TypeScript
- 状态管理：Zustand
- 网络请求：axios
- 路由：React Navigation v6
- 本地存储：AsyncStorage / expo-secure-store
- 样式：StyleSheet（React Native 内置）

## 目录结构
src/
├── pages/        # 页面组件，每个页面一个文件
├── components/   # 通用 UI 组件，每个组件一个目录
├── services/     # API 请求封装，按业务模块分文件
├── stores/       # Zustand 状态管理，按业务模块分文件
├── types/        # TypeScript 类型定义，按业务模块分文件
├── utils/        # 工具函数，按功能分文件
└── constants/    # 常量定义

## 编码规范
- 使用函数式组件 + Hooks，不使用 class 组件
- 使用 TypeScript，所有变量和函数都要有类型定义
- 使用命名导出（named export），不使用默认导出
- 变量和函数使用 camelCase，组件和类型使用 PascalCase
- 常量使用 UPPER_SNAKE_CASE
- 每个函数不超过 30 行，超过就拆分
- 错误处理统一使用 try-catch
- 异步操作统一使用 async/await，不使用 .then()

## API 规范
- API 基础地址：从环境变量读取
- 所有请求通过 services/ 目录下的函数发起
- 请求统一设置 Content-Type: application/json
- 响应格式：{ code: number, message: string, data: T | null }
- 错误处理：业务错误抛出 Error(message)，网络错误抛出 Error('网络错误')

## 状态管理规范
- 使用 Zustand，每个业务模块一个 store
- Store 文件放在 stores/ 目录下
- Store 命名：use[模块名]Store，如 useAuthStore
- 异步操作放在 store 的 action 中

## 组件规范
- 组件文件名使用 PascalCase，如 LoginPage.tsx
- 组件 props 使用 interface 定义，命名为 [组件名]Props
- 样式使用 StyleSheet.create()，放在组件文件底部
- 列表组件使用 FlatList，不使用 map 渲染长列表

## 禁止事项
- 不要使用 any 类型
- 不要使用 @ts-ignore
- 不要使用 dangerouslySetInnerHTML
- 不要在代码中硬编码 API Key 或密钥
- 不要使用 var 声明变量
- 不要在循环中发起 API 请求
```

#### 每个部分的说明

| 部分 | 作用 | 为什么重要 |
|------|------|-----------|
| **项目概述** | 让 AI 快速了解项目 | AI 知道项目是做什么的，不会偏离方向 |
| **技术栈** | 明确使用的技术 | AI 不会使用项目未安装的库 |
| **目录结构** | 告诉 AI 代码放哪里 | AI 生成的文件会放到正确的位置 |
| **编码规范** | 统一代码风格 | AI 生成的代码风格和项目一致 |
| **API 规范** | 统一接口调用方式 | AI 不会编造不存在的 API |
| **状态管理规范** | 统一状态管理方式 | AI 不会混用多种状态管理方案 |
| **组件规范** | 统一组件写法 | AI 生成的组件风格一致 |
| **禁止事项** | 明确不能做的事 | AI 不会生成不安全的代码 |

### CLAUDE.md 模板

`CLAUDE.md` 是 Claude Code 的项目规范文件，同样放在项目根目录下：

```
# CLAUDE.md — 项目规范

## 项目信息
- 项目名称：[项目名称]
- 项目类型：React Native 移动应用
- 主要语言：TypeScript
- 包管理器：npm / yarn / pnpm

## 常用命令
- 启动开发服务器：`npx expo start`
- 运行 iOS：`npx expo run:ios`
- 运行 Android：`npx expo run:android`
- 运行测试：`npm test`
- 类型检查：`npx tsc --noEmit`
- 代码检查：`npx eslint src/`
- 代码格式化：`npx prettier --write src/`

## 技术栈
- React Native + Expo SDK 50+
- TypeScript 5+
- Zustand（状态管理）
- axios（网络请求）
- React Navigation v6（路由）
- expo-secure-store（安全存储）

## 项目结构
src/
├── pages/        # 页面组件
├── components/   # 通用组件
├── services/     # API 服务
├── stores/       # Zustand stores
├── types/        # 类型定义
├── utils/        # 工具函数
└── constants/    # 常量

## 编码风格
- 函数式组件 + Hooks
- TypeScript 严格模式
- 命名导出，不用默认导出
- camelCase 变量/函数，PascalCase 组件/类型
- async/await 代替 .then()
- try-catch 处理错误

## 开发规范
- 新建文件前先确认目录结构是否正确
- 修改代码前先运行类型检查
- 每次修改后运行相关测试
- 不要修改不相关的文件
- 提交前运行 lint 和格式化

## 注意事项
- iOS 和 Android 的样式可能有差异，注意兼容
- 使用 expo-secure-store 存储 Token，不要用 AsyncStorage
- 图片资源放在 assets/ 目录下
- 环境变量以 EXPO_PUBLIC_ 开头
```

#### 每个部分的说明

| 部分 | 作用 | 为什么重要 |
|------|------|-----------|
| **项目信息** | 快速了解项目基本信息 | Claude 知道项目类型和语言 |
| **常用命令** | 知道如何运行和测试项目 | Claude 可以自动运行命令验证代码 |
| **技术栈** | 明确技术选型 | Claude 不会使用不兼容的库 |
| **项目结构** | 知道代码组织方式 | Claude 生成的文件放到正确位置 |
| **编码风格** | 统一代码风格 | Claude 生成的代码风格一致 |
| **开发规范** | 开发流程规范 | Claude 不会跳过必要的检查步骤 |
| **注意事项** | 平台特定的注意点 | Claude 不会犯平台相关的错误 |

### 最佳实践

#### 保持更新

```
项目规范文件不是"写一次就不管了"。以下情况需要更新：

1. 引入新技术/库时 → 更新技术栈和编码规范
2. 目录结构调整时 → 更新项目结构
3. 发现 AI 反复犯同一个错误时 → 添加到禁止事项
4. 团队编码规范变更时 → 更新编码风格
5. 新增常用命令时 → 更新常用命令
```

💡 **建议**：每完成一个功能模块，花 2 分钟回顾一下项目规范文件，看看是否需要更新。这 2 分钟的投资，可以节省后续数小时的 AI 沟通成本。

#### 随项目演进

```
项目规范文件应该随项目一起成长：

项目初期（1-2 周）：
  → 规范文件可以很简短，只有基本信息

项目中期（1-2 月）：
  → 逐步补充编码规范、API 规范、组件规范

项目后期（3 月+）：
  → 规范文件比较完善，AI 几乎不需要额外说明
```

#### 团队统一

| 场景 | 做法 | 原因 |
|------|------|------|
| **个人项目** | 自己维护一份规范文件 | 让 AI 了解你的偏好 |
| **小团队** | 规范文件纳入 Git 版本控制 | 所有人和 AI 使用同一套规范 |
| **大团队** | 规范文件 + Code Review 双重保障 | AI 规范 + 人工审查，质量更可靠 |

⚠️ **注意**：项目规范文件应该**纳入 Git 版本控制**，和代码一起管理。这样团队成员和 AI 都能使用最新版本的规范。

## 小结

本章我们学习了 AI 辅助开发的最佳实践：

1. **写好 Prompt 是 AI 协作的基础**——用 5 要素法（角色 + 背景 + 任务 + 约束 + 示例）构建清晰的 Prompt，给 AI 足够但不冗余的上下文，通过迭代式对话逐步完善结果
2. **AI 是强大的代码审查助手**——让 AI 从安全、性能、可读性、最佳实践、边界情况五个维度审查代码，帮你发现容易忽略的问题
3. **质量把控不可省略**——每次接受 AI 代码前，用 10 项检查表逐项验证，特别关注安全性和性能
4. **警惕 AI 陷阱**——幻觉、过时代码、安全漏洞、过度依赖，四大陷阱需要时刻防范
5. **AI 友好的项目结构让协作更高效**——清晰的目录、一致的编码风格、模块化设计，让 AI 更容易理解你的项目
6. **项目规范文件是 AI 的"员工手册"**——`.cursorrules` 和 `CLAUDE.md` 让 AI 自动理解项目规则，减少重复沟通

💡 **最重要的原则**：**AI 是工具，不是替代品**。你的判断力和创造力是 AI 无法替代的。用 AI 提升效率，但永远保持独立思考和对代码质量的把控。
