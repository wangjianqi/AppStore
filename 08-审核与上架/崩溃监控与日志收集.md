## 1. 为什么需要崩溃监控

### 1.1 用户不会主动报告崩溃

想象一下：你开了一家餐厅，客人吃到不新鲜的菜，绝大多数人不会找经理投诉——他们只是默默离开，再也不来了。App 崩溃也是一样：

| 场景 | 用户行为 | 开发者感知 |
|------|----------|-----------|
| 偶发崩溃 | "可能是我手机问题"，忽略 | 完全不知道 |
| 频繁崩溃 | 直接卸载，给一星差评 | 看到差评才知道 |
| 关键路径崩溃 | 气愤地写差评 | 差评滞后数天 |

> 💡 业界统计：只有不到 1% 的用户会主动反馈崩溃问题。如果你等用户投诉才发现 Bug，说明 99% 的崩溃你根本不知道。

### 1.2 App Store 崩溃数据延迟严重

Apple 确实在 App Store Connect 中提供了崩溃报告，但它有几个致命问题：

| 问题 | 说明 |
|------|------|
| 延迟长 | 崩溃数据通常延迟 1-3 天才能看到，紧急问题无法实时响应 |
| 依赖用户设置 | 用户需在"设置 → 隐私与安全性 → 分析与改进"中开启"与开发者共享"，默认关闭 |
| 信息有限 | 只有堆栈，没有自定义日志、用户操作路径等上下文 |
| 无法告警 | 没有崩溃率飙升时的自动通知机制 |
| 无非致命异常 | 只记录崩溃，不记录卡顿、ANR 等非致命问题 |

### 1.3 自建监控的必要性

就像医院不能只靠病人自己上门才知道有传染病爆发——你需要一套"疫情监测系统"。自建崩溃监控的核心价值：

- **实时感知**：崩溃发生后秒级上报，分钟级看到数据
- **丰富上下文**：记录用户操作路径、设备状态、自定义日志
- **主动告警**：崩溃率超过阈值时自动通知团队
- **趋势分析**：按版本、设备、系统追踪崩溃率变化
- **非致命异常**：捕获卡顿、OOM 等不产生崩溃日志的问题

> ⚠️ 自建监控不等于自己从零写一个崩溃捕获框架。推荐使用成熟的开源或商业方案（Crashlytics / Sentry），再配合自建日志系统形成完整体系。

## 2. iOS 崩溃类型全览

### 2.1 崩溃类型总表

iOS 上的崩溃就像人体的不同疾病——症状不同，病因不同，诊断方法也不同：

| 崩溃类型 | 触发层 | 典型场景 | 能否捕获 |
|----------|--------|----------|----------|
| Mach 异常 | 内核层 | 空指针访问、栈溢出 | ✅ Mach 端口 |
| Signal 异常 | Unix 层 | SIGABRT、SIGSEGV、SIGBUS | ✅ Signal Handler |
| NSException | Objective-C 层 | 未识别的选择器、KVO 异常 | ✅ UncaughtExceptionHandler |
| Swift Error | Swift 层 | try! 强制解包失败、fatalError | ✅ 映射为 Signal |
| OOM / Watchdog 强杀 | 系统层 | 内存超限、主线程卡死 | ❌ 无法捕获进程内 |

### 2.2 Mach 异常

Mach 是 macOS/iOS 的微内核，最底层的异常由 Mach 产生。就像人体的"基因层面"问题，是最根本的：

- **EXC_BAD_ACCESS**：访问了无效内存地址（野指针、已释放对象）
- **EXC_ARITHMETIC**：除以零
- **EXC_BREAKPOINT**：触发了断点指令（Swift 的 precondition 失败）

### 2.3 Signal 异常

Mach 异常会被转换为 Unix Signal，在进程层面暴露。这是大多数崩溃监控工具的捕获入口：

| Signal | 含义 | 常见原因 |
|--------|------|----------|
| SIGABRT | 程序主动中止 | assert 失败、Objective-C 异常未捕获 |
| SIGSEGV | 段错误 | 访问未映射内存 |
| SIGBUS | 总线错误 | 内存对齐问题 |
| SIGFPE | 浮点异常 | 整数除以零 |
| SIGILL | 非法指令 | 执行了无效的机器指令 |
| SIGTERM | 终止信号 | 系统强制终止 |

### 2.4 NSException

Objective-C 层的异常，通常伴随可读的错误信息：

```swift
// 典型触发场景
let array = NSMutableArray()
array.addObject("hello")  // 在 Swift 中不常见，但桥接 OC 代码时可能遇到

// 更常见：未识别的选择器
// [NSObject performSelector:@selector(nonexistentMethod)]
// → NSInvalidArgumentException: unrecognized selector sent to instance
```

### 2.5 Swift Error

Swift 的错误处理更安全，但仍有"强制"路径会导致崩溃：

```swift
// 1. 强制解包 nil
let name: String? = nil
let length = name!.count  // 💥 EXC_BAD_INSTRUCTION

// 2. fatalError
func mustImplement() {
    fatalError("子类必须实现此方法")  // 💥 SIGABRT
}

// 3. try!
let data = try! JSONDecoder().decode(MyModel.self, from: badData)  // 💥

// 4. precondition 失败
precondition(index >= 0, "索引不能为负数")  // 💥
```

### 2.6 OOM 与 Watchdog 强杀

这两种"崩溃"进程自身无法捕获，因为系统直接把进程杀了——就像一个人无法记录自己被闪电击中的瞬间：

| 类型 | 触发条件 | 特征 |
|------|----------|------|
| FOOM（Foreground OOM） | 前台内存超限 | 系统日志中有 `per-process-limit` 标记 |
| BOOM（Background OOM） | 后台内存超限 | 常见于后台播放、定位 |
| Watchdog 强杀 | 主线程卡死超时 | 系统日志中有 `0x8badf00d`（eat bad food） |

> 💡 OOM 和 Watchdog 强杀虽然无法在进程内捕获，但可以通过监控内存水位、主线程卡顿来提前预警，也可以通过 MetricKit 获取系统诊断数据。

## 3. 崩溃捕获原理

### 3.1 捕获层次架构

崩溃捕获就像在医院建立分诊系统——不同级别的病症由不同科室处理：

```
┌─────────────────────────────────────────┐
│            应用层（最晚介入）              │
│  NSSetUncaughtExceptionHandler          │
│  捕获：NSException                      │
├─────────────────────────────────────────┤
│            Signal 层                     │
│  signal() / sigaction()                 │
│  捕获：SIGABRT、SIGSEGV 等              │
├─────────────────────────────────────────┤
│            Mach 层（最早介入）            │
│  task_set_exception_ports()             │
│  捕获：EXC_BAD_ACCESS 等                │
├─────────────────────────────────────────┤
│            内核                          │
│  最底层，无法在用户态捕获                  │
└─────────────────────────────────────────┘
```

### 3.2 NSSetUncaughtExceptionHandler

捕获 Objective-C 层未处理异常，是最简单的捕获方式：

```swift
// 在 AppDelegate 中注册
func application(
    _ application: UIApplication,
    didFinishLaunchingWithOptions launchOptions: [UIApplication.LaunchOptionsKey: Any]?
) -> Bool {
    NSSetUncaughtExceptionHandler { exception in
        print("🔥 未捕获的 NSException:")
        print("  名称: \(exception.name.rawValue)")
        print("  原因: \(exception.reason ?? "未知")")
        print("  堆栈:\n\(exception.callStackSymbols.joined(separator: "\n"))")

        // 保存到本地文件，下次启动时上传
        CrashStore.save(
            name: exception.name.rawValue,
            reason: exception.reason ?? "",
            stack: exception.callStackSymbols
        )
    }
    return true
}
```

> ⚠️ 多个第三方 SDK 可能都注册了 UncaughtExceptionHandler，后注册的会覆盖先注册的。如果你的 App 同时用了多个监控 SDK，要注意注册顺序，或者保存前一个 handler 并在回调中链式调用。

### 3.3 Signal Handler

捕获 Unix Signal，处理更底层的崩溃：

```swift
// 保存原始 handler
private var previousHandlers: [Int32: (@convention(c) (Int32) -> Void)?] = [:]

func registerSignalHandlers() {
    let signals: [Int32] = [SIGABRT, SIGSEGV, SIGBUS, SIGFPE, SIGILL, SIGTERM]

    for sig in signals {
        var oldAction = sigaction()
        sigaction(sig, nil, &oldAction)

        signal(sig) { sigNum in
            print("🔥 收到 Signal: \(sigNum)")

            let stack = Thread.callStackSymbols
            CrashStore.save(
                name: "Signal",
                reason: "Signal \(sigNum)",
                stack: stack
            )

            // 恢复默认处理，让系统正常崩溃
            signal(sig, SIG_DFL)
            raise(sig)
        }
    }
}
```

> ⚠️ Signal Handler 中只能调用"异步安全"（async-signal-safe）的函数。不能调用 malloc、NSLog、Objective-C 方法等。实际项目中建议只做最少的操作（写文件），复杂逻辑留给下次启动处理。

### 3.4 Mach 异常端口

最底层的捕获方式，PLCrashReporter 和 Crashlytics 都使用此方式：

```swift

            ptr.withMemoryRebound(to: exception_mask_array_t?.self, capacity: 1) { maskPtr in
                // 获取旧端口（简化示意，实际需要更完整的实现）
            }
        }

        // 3. 设置新的异常端口
        task_set_exception_ports(
            mach_task_self_,
            EXC_MASK_BAD_ACCESS | EXC_MASK_BAD_INSTRUCTION | EXC_MASK_ARITHMETIC | EXC_MASK_BREAKPOINT,
            serverPort,
            EXCEPTION_DEFAULT,
            THREAD_STATE_NONE

        Thread {
            self.listenForExceptions()
        }.start()

}
```

> 💡 Mach 异常端口方式的优势：可以在异常抛出但还未转为 Signal 之前捕获，此时线程状态更完整，堆栈信息更准确。但实现复杂，不建议自己手写，推荐使用 PLCrashReporter 等成熟库。

## 6. 自建轻量崩溃收集

### 6.1 PLCrashReporter 集成

PLCrashReporter 是开源的崩溃捕获库，Crashlytics 底层也基于它：

```swift
// Package.swift
dependencies: [
    .package(url: "https://github.com/microsoft/plcrashreporter", from: "1.11.0")
]

import CrashReporter

class CrashMonitor {
    private var crashReporter: PLCrashReporter?

    func start() {
        let config = PLCrashReporterConfig(
            signalHandlerType: .BSD,
            symbolicationStrategy: .all
        )
        crashReporter = PLCrashReporter(configuration: config)

        do {
            try crashReporter?.enableAndReturnError()

            // 检查上次崩溃报告
            if let reporter = crashReporter,
               reporter.hasPendingCrashReport() {
                processPendingCrashReport(reporter)
            }
        } catch {
            print("崩溃监控启动失败: \(error)")
        }
    }

    private func processPendingCrashReport(_ reporter: PLCrashReporter) {
        do {
            let data = try reporter.loadPendingCrashReportDataAndReturnError()
            let report = try PLCrashReport(data: data)

            // 提取崩溃信息
            if let thread = report.crashedThread {
                let frames = thread.stackFrames.map { frame in
                    "\(frame.instructionAddress ?? 0)"
                }
                let crashInfo = """
                崩溃时间: \(report.systemInfo.timestamp ?? Date())
                异常类型: \(report.exceptionInfo?.exceptionName ?? "未知")
                异常原因: \(report.exceptionInfo?.exceptionReason ?? "未知")
                堆栈:
                \(frames.joined(separator: "\n"))
                """
                saveCrashReport(crashInfo)
            }

            // 处理完毕后清除
            reporter.purgePendingCrashReport()
        } catch {
            print("处理崩溃报告失败: \(error)")
        }
    }

    private func saveCrashReport(_ report: String) {
        let url = FileManager.default
            .urls(for: .cachesDirectory, in: .userDomainMask)[0]
            .appendingPathComponent("crash_reports")
            .appendingPathComponent("crash_\(Int(Date().timeIntervalSince1970)).log")
        try? report.write(to: url, atomically: true, encoding: .utf8)
    }
}
```

### 6.2 崩溃日志符号化

PLCrashReporter 捕获的是内存地址，需要符号化才能看到方法名。这就像拿到了一封密码信，需要密钥（dSYM）才能解读：

```bash
# 使用 atos 命令符号化
# 格式：atos -arch <架构> -o <dSYM路径> -l <加载地址> <崩溃地址>

# 示例
atos -arch arm64 \
     -o YourApp.app.dSYM/Contents/Resources/DWARF/YourApp \
     -l 0x100000000 \
     0x100003a5c

# 输出示例：
# -[ViewController viewDidLoad] (in YourApp) (ViewController.m:23)
```

### 6.3 批量符号化脚本

```bash
#!/bin/bash
# symbolicate.sh - 批量符号化崩溃日志

DSYM_PATH="$1"
CRASH_FILE="$2"
ARCH="arm64"

if [ -z "$DSYM_PATH" ] || [ -z "$CRASH_FILE" ]; then
    echo "用法: ./symbolicate.sh <dSYM路径> <崩溃日志路径>"
    exit 1
fi

echo "=== 符号化崩溃日志 ==="
echo "dSYM: $DSYM_PATH"
echo "崩溃日志: $CRASH_FILE"
echo ""

# 提取二进制加载地址和崩溃地址
while IFS= read -r line; do
    if [[ "$line" =~ ^[9]+ ]]; then
        addr=$(echo "$line" | awk '{print $NF}')
        load_addr=$(echo "$line" | awk '{print $(NF-1)}')
        result=$(atos -arch "$ARCH" -o "$DSYM_PATH" -l "$load_addr" "$addr" 2>/dev/null)
        if [ -n "$result" ]; then
            echo "原始: $line"
            echo "符号: $result"
            echo "---"
        fi
    fi
done < "$CRASH_FILE"
```

> 💡 Xcode Organizer 也可以自动符号化：Window → Organizer → Crashes。前提是已上传对应版本的 dSYM 到 App Store Connect。

## 7. 日志系统设计

### 7.1 OSLog / Logger 框架

iOS 14+ 推出的 `Logger` 框架是 Apple 官方推荐的日志方案。它就像医院的病历系统——不同级别的病情记录在不同的日志本上：

```swift
import os

// 创建 Logger（按子系统和方法分类）
let networkLogger = Logger(subsystem: "com.yourapp.network", category: "API")
let uiLogger = Logger(subsystem: "com.yourapp.ui", category: "Navigation")
let dataLogger = Logger(subsystem: "com.yourapp.data", category: "Database")

// 不同级别日志
networkLogger.debug("请求参数: page=1, size=20")       // 调试信息
networkLogger.info("成功获取用户列表，共 20 条")         // 常规信息
networkLogger.warning("请求超时，正在重试 (2/3)")        // 警告
networkLogger.error("支付接口返回错误: \(400)")          // 错误
networkLogger.critical("数据库损坏，需要重建!")           // 严重错误
```

### 7.2 日志级别对比

| 级别 | Logger 方法 | OSLog 类型 | 保存时长 | 使用场景 |
|------|------------|-----------|----------|----------|
| Debug | `.debug` | `.debug` | 内存中，不持久化 | 开发调试、临时变量 |
| Info | `.info` | `.info` | 内存中，最多数小时 | 关键业务流程节点 |
| Warning | `.warning` | `.default` | 磁盘，约数天 | 可恢复的异常情况 |
| Error | `.error` | `.error` | 磁盘，约数周 | 功能失败、需要关注 |
| Fault | `.critical` | `.fault` | 磁盘，长期保留 | 严重错误、数据损坏 |

### 7.3 封装日志管理器

```swift
import os
import Foundation

final class AppLogger {
    static let shared = AppLogger()

    private let networkLogger = Logger(subsystem: "com.yourapp", category: "network")
    private let uiLogger = Logger(subsystem: "com.yourapp", category: "ui")
    private let dataLogger = Logger(subsystem: "com.yourapp", category: "data")

    private let fileLogger: FileLogger

    private init() {
        fileLogger = FileLogger()
    }

    func network(_ message: String, level: LogLevel = .info) {
        log(message, logger: networkLogger, level: level)
    }

    func ui(_ message: String, level: LogLevel = .info) {
        log(message, logger: uiLogger, level: level)
    }

    func data(_ message: String, level: LogLevel = .info) {
        log(message, logger: dataLogger, level: level)
    }

    private func log(_ message: String, logger: Logger, level: LogLevel) {
        switch level {
        case .debug: logger.debug("\(message, privacy: .private)")
        case .info: logger.info("\(message, privacy: .private)")
        case .warning: logger.warning("\(message, privacy: .private)")
        case .error: logger.error("\(message, privacy: .private)")
        case .critical: logger.critical("\(message, privacy: .private)")
        }

        if level >= .warning {
            fileLogger.append(message, level: level)
        }
    }
}

enum LogLevel: Int, Comparable {
    case debug = 0
    case info = 1
    case warning = 2
    case error = 3
    case critical = 4

    static func < (lhs: LogLevel, rhs: LogLevel) -> Bool {
        lhs.rawValue < rhs.rawValue
    }
}
```

### 7.4 持久化与上传策略

```swift
final class FileLogger {
    private let logDirectory: URL
    private let maxFileSize: Int = 5 * 1024 * 1024   // 单文件最大 5MB
    private let maxFileCount: Int = 5                  // 最多保留 5 个文件
    private let uploadThreshold: Int = 2 * 1024 * 1024 // 累积 2MB 后上传

    init() {
        logDirectory = FileManager.default
            .urls(for: .cachesDirectory, in: .userDomainMask)[0]
            .appendingPathComponent("logs")
        try? FileManager.default.createDirectory(
            at: logDirectory, withIntermediateDirectories: true
        )
    }

    func append(_ message: String, level: LogLevel) {
        let timestamp = ISO8601DateFormatter().string(from: Date())
        let line = "[\(timestamp)] [\(level)] \(message)\n"
        let currentFile = currentLogFile()

        if let data = line.data(using: .utf8) {
            if FileManager.default.fileExists(atPath: currentFile.path) {
                if let handle = try? FileHandle(forWritingTo: currentFile) {
                    handle.seekToEndOfFile()
                    handle.write(data)
                    handle.closeFile()
                }
            } else {
                try? data.write(to: currentFile)
            }
        }

        rotateIfNeeded()
        uploadIfNeeded()
    }

    private func currentLogFile() -> URL {
        let formatter = DateFormatter()
        formatter.dateFormat = "yyyy-MM-dd"
        let fileName = "log_\(formatter.string(from: Date())).txt"
        return logDirectory.appendingPathComponent(fileName)
    }

    private func rotateIfNeeded() {
        guard let files = try? FileManager.default
            .contentsOfDirectory(at: logDirectory, includingPropertiesForKeys: [.fileSizeKey])
            .sorted(by: { $0.lastPathComponent > $1.lastPathComponent })
        else { return }

        for (index, file) in files.enumerated() {
            if index >= maxFileCount {
                try? FileManager.default.removeItem(at: file)
            }
        }
    }

    private func uploadIfNeeded() {
        let totalSize = logDirectory.totalFileSize ?? 0
        guard totalSize >= uploadThreshold else { return }

        let files = (try? FileManager.default
            .contentsOfDirectory(at: logDirectory, includingPropertiesForKeys: nil))
            ?? []

        for file in files where file != currentLogFile() {
            LogUploader.upload(file: file) { success in
                if success {
                    try? FileManager.default.removeItem(at: file)
                }
            }
        }
    }
}
```

> 💡 日志上传策略建议：WiFi 环境下自动上传、蜂窝网络下仅上传 error 及以上级别、无网络时本地缓存等待下次上传。遵守"最小必要"原则，不要上传用户隐私数据。

## 8. 崩溃日志分析实战

### 8.1 读懂崩溃堆栈

一份典型的崩溃日志包含以下部分：

```

CrashReporter Key:   abc123                    ← 设备标识
Hardware Model:      iPhone15,2                ← 设备型号
Process:             YourApp [12345]           ← 进程名和 PID
Path:                /var/containers/.../YourApp
Identifier:          com.yourapp
Version:             2.1.0 (42)               ← 版本号
Code Type:           ARM-64
OS Version:          iPhone OS 17.2

Exception Type:  EXC_BAD_ACCESS (SIGSEGV)     ← 崩溃类型
Exception Subtype: KERN_INVALID_ADDRESS at 0x00000000  ← 具体原因
Termination Signal: Signal 11 (SIGSEGV)

Thread 0 Crashed:                              ← 崩溃线程
0  YourApp    0x100003a5c 0x100000000 + 14940  ← 崩溃地址
1  YourApp    0x100004b20 0x100000000 + 19232
2  UIKitCore  0x1a2b3c4d0 0x1a2000000 + 7538576
3  UIKitCore  0x1a2b3e8f0 0x1a2000000 + 7547376

Thread 1:                                       ← 其他线程
0  libsystem_kernel.dylib  0x1b2c3d4e0 mach_msg_trap
1  libsystem_kernel.dylib  0x1b2c3d5a0 mach_msg
```

### 8.2 常见崩溃模式

| 崩溃模式 | 堆栈特征 | 典型原因 | 修复思路 |
|----------|----------|----------|----------|
| 野指针 | EXC_BAD_ACCESS + objc_msgSend | 访问已释放的对象 | 开启 Zombie 诊断、用 weak 引用 |
| 数组越界 | NSRangeException + objectAtIndex | index 超出数组范围 | 添加边界检查 |
| 强制解包 | EXC_BAD_INSTRUCTION + Swift runtime | nil 强制解包 | 使用 if let / guard let |
| 主线程死锁 | 多个线程互相等待 | 同步派发到自身队列 | 避免嵌套 sync、用 async |
| 后台任务超时 | 0x8badf00d | 后台执行时间过长 | 缩短后台任务、使用 BGTaskScheduler |
| 内存泄漏 | 内存持续增长后 OOM | 循环引用、未释放资源 | Instruments Leaks 检测 |

### 8.3 dSYM 符号化完整流程

dSYM（Debug Symbol File）是编译时生成的调试符号文件，它和 App 二进制一一对应，就像锁和钥匙的关系：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  崩溃日志     │     │   dSYM 文件   │     │  符号化结果   │
│  (内存地址)   │ ──→ │  (地址→方法名) │ ──→ │  (方法名+行号) │
│  0x100003a5c │     │  UUID 匹配    │     │  viewDidLoad │
└──────────────┘     └──────────────┘     └──────────────┘
```

**步骤一：确认 dSYM UUID 匹配**

```bash
# 查看 dSYM 的 UUID
dwarfdump --uuid YourApp.app.dSYM

# 查看崩溃日志中的 UUID
# 在 Binary Images 行中查找
# 0x100000000 - 0x1000FFFFF YourApp arm64 <8A2B3C4D5E6F7G8H>
```

**步骤二：使用 atos 符号化**

```bash
atos -arch arm64 \
     -o YourApp.app.dSYM/Contents/Resources/DWARF/YourApp \
     -l 0x100000000 \
     0x100003a5c 0x100004b20
```

**步骤三：批量符号化（使用 symbolicatecrash）**

```bash
# Xcode 自带的符号化工具
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
/Applications/Xcode.app/Contents/SharedFrameworks/DVTFoundation.framework/Versions/A/Resources/symbolicatecrash \
    crash_log.crash \
    YourApp.app.dSYM \
    > symbolicated_crash.log
```

> ⚠️ 每次构建都会生成不同的 dSYM，必须保留与发布版本对应的 dSYM 文件。建议在 CI/CD 流程中自动上传 dSYM 到 Crashlytics 或 Sentry，同时归档到安全存储。

## 9. 上架后监控最佳实践

### 9.1 崩溃率目标

崩溃率就像医院的"感染率"——越低越好，但不可能为零。业界通常的目标：

| 崩溃率 | 评级 | 说明 |
|--------|------|------|
| < 0.1% | 🟢 优秀 | 顶级 App 水平，用户几乎无感知 |
| 0.1% - 0.5% | 🟡 良好 | 可接受范围，持续优化 |
| 0.5% - 1% | 🟠 需关注 | 部分用户体验受损，需优先修复 |
| 1% - 2% | 🔴 严重 | 大量用户受影响，需紧急修复 |
| > 2% | ⚫ 灾难 | 应立即发布热修复版本 |

> 💡 崩溃率 = 崩溃用户数 / 活跃用户数。注意区分"崩溃率"和"崩溃次数"——一个用户崩溃 10 次只算 1 个崩溃用户。

### 9.2 告警机制

```swift
// 崩溃率告警规则示例
struct CrashAlertRule {
    let metric: Metric
    let threshold: Double
    let window: TimeInterval

    enum Metric {
        case crashRate           // 崩溃率

    CrashAlertRule(metric: .crashRate, threshold: 1.0, window: 1800, severity: .critical),
    CrashAlertRule(metric: .newIssueCount, threshold: 3, window: 3600, severity: .warning),
    CrashAlertRule(metric: .affectedUserCount, threshold: 100, window: 1800, severity: .critical),
```

### 9.3 热修复思路

iOS 不支持像 Android 那样的热更新（JSPatch 等方案已被 Apple 明确禁止），但可以采用以下策略：

| 策略 | 说明 | Apple 合规性 |
|------|------|-------------|
| 服务端配置开关 | 预埋功能开关，服务端远程关闭问题功能 | ✅ 完全合规 |
| 降级策略 | 检测到异常时自动降级到安全路径 | ✅ 完全合规 |
| 数据修正 | 服务端修复错误数据，客户端重新拉取 | ✅ 完全合规 |
| WebView 热修 | 用 WebView 替换有问题的原生页面 | ✅ 合规（前提是不动态执行原生代码） |
| JSPatch / Rollout | 动态下发 JavaScript 补丁修改原生行为 | ❌ 违反审核指南 2.5.2 |

```swift
// 合规的热修复示例：功能开关
struct FeatureFlag: Codable {
    let feature: String
    let enabled: Bool
    let maxVersion: String?
}

class FeatureFlagManager {
    static let shared = FeatureFlagManager()
    private var flags: [String: FeatureFlag] = [:]

    func fetchFlags() async {
        let url = URL(string: "https://api.yourapp.com/feature-flags")!
        do {
            let (data, _) = try await URLSession.shared.data(from: url)
            let decoded = try JSONDecoder().decode([FeatureFlag].self, from: data)
            for flag in decoded {
                flags[flag.feature] = flag
            }
        } catch {
            print("获取功能开关失败: \(error)")
        }
    }

    func isEnabled(_ feature: String) -> Bool {
        guard let flag = flags[feature] else { return true }
        if let maxVersion = flag.maxVersion {
            return Bundle.main.appVersion <= maxVersion && flag.enabled
        }
        return flag.enabled
    }
}

// 使用：在问题功能入口检查
if FeatureFlagManager.shared.isEnabled("advanced_filter") {
    showAdvancedFilter()
} else {
    showSimpleFilter()
}
```
