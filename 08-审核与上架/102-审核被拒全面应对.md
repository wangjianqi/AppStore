## Apple 审核指南核心条款解读

> 🎯 **本节目标**：了解 Apple 审核指南的整体结构和五大板块，逐条理解最重要的核心条款，知道 Apple 审核的底线在哪里。

### 审核指南结构

Apple 审核指南（App Store Review Guidelines）是所有 iOS 开发者必须遵守的"宪法"。它分为 5 大板块，每个板块覆盖不同领域：

| 板块 | 编号 | 核心关注 | 一句话概括 |
|------|:----:|----------|-----------|
| 安全性 | 1.x | 内容安全、用户保护 | 不要做伤害用户的事 |
| 性能 | 2.x | App 质量、元数据准确性 | App 要好用、信息要真实 |
| 商业 | 3.x | 支付、广告、订阅 | 赚钱要走 Apple 的规则 |
| 设计 | 4.x | 功能完整性、原创性 | App 要有灵魂、不是凑数的 |
| 法律 | 5.x | 隐私、数据、知识产权 | 合法合规是底线 |

💡 **提示**：审核指南会不定期更新，建议收藏官方页面 [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)，每次提交审核前快速浏览最新变动。Apple 通常会在 WWDC 前后进行较大更新。

### 核心条款解读

以下是审核中最常触发的核心条款，每条包含原文要点、通俗解读、常见问题和应对方法。

---

**1.1 令人反感的内容（Objectionable Content）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | App 不得包含或宣扬令人反感、歧视性、暴力或非法的内容 |
| 通俗解读 | 你的 App 里不能有色情、暴力、仇恨言论、赌博、毒品等敏感内容 |
| 常见问题 | 用户生成内容（UGC）中出现了违规内容；App 内有暗示性内容 |
| 应对方法 | ① 所有 UGC 必须有内容审核机制和举报功能 ② 上架前预置内容过滤 ③ 在审核备注中说明内容审核措施 |

---

**2.1 性能 — App 崩溃/Bug（Performance — Software Crashes / Bugs）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | App 不应包含已知 Bug，不应在正常使用中崩溃 |
| 通俗解读 | 审核员测试时 App 不能崩溃、不能有明显 Bug |
| 常见问题 | 审核员使用特定设备或系统版本时崩溃；网络请求失败导致白屏 |
| 应对方法 | ① 提交前在多种设备和系统版本上测试 ② 做好网络异常处理 ③ 使用崩溃监控工具 ④ 在审核备注中说明特殊操作步骤 |

---

**3.1 支付 — 虚拟商品必须用 IAP（Payments — In-App Purchase）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | 在 App 内解锁功能或购买虚拟商品/服务，必须使用 Apple 内购（IAP） |
| 通俗解读 | 只要是 App 内的"虚拟东西"，必须走 Apple 支付，Apple 要抽 30%（小开发者 15%） |
| 常见问题 | 使用微信/支付宝购买虚拟商品；引导用户去网页购买以绕过 IAP |
| 应对方法 | ① 虚拟商品必须接入 IAP ② 实物商品可以用第三方支付 ③ 详见本章节 3.1 小节 |

---

**4.2 最小功能 — 网页打包/功能太少（Design — Minimum Functionality）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | App 应提供足够的原生功能和价值，不能只是网站打包 |
| 通俗解读 | 你的 App 不能只是把一个网页套个壳就上架，要有原生功能 |
| 常见问题 | App 只是 WebView 加载网页；功能太简单，只做了一件事 |
| 应对方法 | ① 添加原生交互功能（推送、离线缓存、相机等） ② 使用原生 UI 而非纯网页 ③ 详见本章节 4.2 小节 |

---

**4.8 登录 — 第三方登录要求（Design — Sign in with Apple）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | 如果 App 支持第三方社交登录，则必须同时提供"通过 Apple 登录" |
| 通俗解读 | 你有微信登录、QQ 登录，就必须也有 Apple 登录 |
| 常见问题 | 只提供微信/QQ 登录但没有 Apple 登录；Apple 登录后功能不完整 |
| 应对方法 | ① 只要用了第三方登录就必须加 Apple 登录 ② Apple 登录体验要和其他登录方式一致 ③ 详见本章节 4.8 小节 |

---

**5.1 隐私 — 数据收集与隐私政策（Legal — Privacy — Data Collection and Storage）**

| 项目 | 内容 |
|------|------|
| 条款原文要点 | App 收集用户数据必须征得同意，必须提供隐私政策，数据收集必须透明 |
| 通俗解读 | 收集什么数据、怎么用，必须告诉用户，而且要用户同意 |
| 常见问题 | 没有隐私政策；收集了数据但没声明；隐私政策 URL 无法访问 |
| 应对方法 | ① 提供有效的隐私政策 URL ② 在 App Store Connect 中如实填写数据收集声明 ③ App 内首次使用时请求权限 ④ 详见本章节 5.1 小节 |

---

💡 **提示**：以上只是最核心的条款。完整的审核指南有上百条，建议至少通读一遍，做到心中有数。你不需要背下来，但要知道哪些红线不能碰。

## 常见被拒原因 Top 20 详解

> 🎯 **本节目标**：逐一了解最常见的 20 种被拒原因，掌握每种原因的预防方法和应对策略，做到"知道会被拒，所以不会犯"。

### 2.1 性能问题 — App 崩溃/Bug

这是最"冤"的被拒原因——你的 App 在自己手机上好好的，审核员一测就崩了。

**原因分析：**

| 原因 | 说明 |
|------|------|
| 设备兼容性 | 你只在 iPhone 15 Pro 测试过，审核员用的是 iPhone 12 |
| 系统版本差异 | 你在 iOS 17 开发，审核员用 iOS 16 测试 |
| 网络环境 | 你的测试环境网络良好，审核员网络可能较慢 |
| 数据状态 | 你的测试账号有数据，审核员的账号是空的 |
| 内存不足 | 审核员设备内存紧张，你的 App 没做好内存管理 |

**预防方法：**

| 方法 | 操作 |
|------|------|
| 多设备测试 | 至少在 3 种不同型号的设备上测试 |
| 多系统版本测试 | 支持的最低版本和最新版本都要测 |
| 模拟弱网 | 用 Network Link Conditioner 模拟弱网环境 |
| 空数据测试 | 用全新账号登录，检查空状态页面 |
| 崩溃监控 | 集成 Crashlytics 或 Bugly，提前发现崩溃 |

**应对策略：**

```
1. 仔细阅读被拒邮件中的崩溃描述和附件截图
2. 根据描述复现崩溃场景
3. 修复 Bug 并充分测试
4. 在审核备注中说明修复内容
5. 重新提交审核
```

💡 **提示**：Apple 有时会在被拒邮件中附带崩溃日志。如果附带的是 .ips 文件，可以用 Xcode 的 Devices and Simulators 窗口导入查看，或者用 `symbolicatecrash` 工具符号化后分析。

### 2.3 元数据问题 — 描述与截图不符

App 的文字描述、截图、功能必须一致，不能"挂羊头卖狗肉"。

**原因分析：**

| 原因 | 说明 |
|------|------|
| 截图展示了描述中没提到的功能 | 截图里有功能 A，但描述里没写 |
| 描述中承诺的功能 App 里没有 | 描述写了"支持暗黑模式"，但 App 实际不支持 |
| 截图与实际界面不一致 | 截图是设计稿，实际界面长不一样 |
| 关键词堆砌 | 关键词里写了一堆和 App 无关的热词 |

**预防方法：**

| 方法 | 操作 |
|------|------|
| 截图用真实界面 | 用真机截图，不要用设计稿 |
| 描述与功能对齐 | 每次更新后检查描述是否还准确 |
| 关键词相关 | 只写和 App 功能相关的关键词 |
| 更新后检查 | 版本更新后，检查截图和描述是否需要同步更新 |

**应对策略：**

```
1. 修改描述，使其与 App 实际功能一致
2. 替换不准确的截图
3. 清理不相关的关键词
4. 重新提交审核（元数据被拒通常不需要新构建版本）
```

⚠️ **警告**：元数据被拒（Metadata Rejected）不需要重新上传构建版本，只需修改信息后重新提交即可。但如果你同时修改了代码，则需要上传新构建版本。

### 2.5 元数据问题 — 截图问题

截图是用户对 App 的第一印象，也是审核员重点检查的项目。

**原因分析：**

| 原因 | 说明 |
|------|------|
| 截图尺寸不对 | 没有提供必需设备尺寸的截图 |
| 截图包含模拟器边框 | Apple 不允许截图中出现模拟器界面 |
| 截图有占位内容 | "Lorem ipsum" 等占位文字出现在截图中 |
| 截图与 App 无关 | 截图内容不是 App 的真实界面 |
| 截图包含竞品信息 | 截图中出现了其他 App 的名称或 Logo |

**预防方法：**

| 方法 | 操作 |
|------|------|
| 使用正确尺寸 | 至少提供 6.7 寸 iPhone 截图（必需） |
| 真机截图 | 用真机或模拟器截图，不要用设计稿 |
| 检查内容 | 确保截图中没有占位文字和无关信息 |
| 多尺寸覆盖 | 建议同时提供 6.7 寸和 iPad 截图 |

**各设备截图尺寸要求：**

| 设备类型 | 分辨率（像素） | 是否必需 |
|----------|---------------|:--------:|
| 6.9 寸 iPhone | 1320 × 2868 | 选填 |
| 6.7 寸 iPhone | 1290 × 2796 | ✅ 必需 |
| 6.5 寸 iPhone | 1284 × 2778 | 选填 |
| 5.5 寸 iPhone | 1242 × 2208 | 选填 |
| 12.9 寸 iPad | 2048 × 2732 | 支持 iPad 时必需 |

**应对策略：**

```
1. 按要求尺寸重新截图
2. 确保截图内容真实、无占位符
3. 在 App Store Connect 中替换截图
4. 重新提交审核
```

💡 **提示**：可以使用 `sips` 命令行工具或第三方工具（如 Fastlane Snapshot）批量生成不同尺寸的截图，省去手动操作的麻烦。

### 3.1 支付问题 — 虚拟商品必须用 IAP

这是**最常见的被拒原因之一**，也是让很多开发者最头疼的问题。Apple 对虚拟商品支付的控制非常严格。

**什么是虚拟商品？**

虚拟商品是指在 App 内部消费的数字内容或服务，没有实体形态。

| 类型 | 示例 | 是否虚拟商品 |
|------|------|:----------:|
| 数字内容 | 电子书章节、视频课程、音乐 | ✅ 是 |
| 虚拟道具 | 游戏金币、皮肤、装备 | ✅ 是 |
| 会员/订阅 | VIP 会员、去广告、云存储 | ✅ 是 |
| 功能解锁 | 专业版功能、高级编辑工具 | ✅ 是 |
| 实物商品 | 外卖、服装、电子产品 | ❌ 否 |
| 实体服务 | 打车、外卖配送、家政服务 | ❌ 否 |

**必须用 IAP 的场景：**

| 场景 | 说明 | IAP 类型 |
|------|------|----------|
| 购买虚拟道具 | 游戏金币、表情包、滤镜 | 消耗型 |
| 解锁功能 | 专业版、高级功能 | 非消耗型 |
| 订阅服务 | 会员、云存储、去广告 | 自动续期订阅 |
| 购买数字内容 | 电子书、课程、音乐 | 非消耗型/消耗型 |

**可以用其他支付的场景：**

| 场景 | 说明 | 可用支付方式 |
|------|------|-------------|
| 购买实物商品 | 电商购物 | 微信支付、支付宝等 |
| 购买实体服务 | 打车、外卖 | 微信支付、支付宝等 |
| 跨平台服务 | 在网页端购买，App 端只是使用 | 网页支付（但 App 内不能有购买入口） |

**应对策略：**

```
场景1：你的 App 确实卖虚拟商品
→ 必须接入 IAP，没有商量余地
→ 参考 Apple 官方 In-App Purchase 文档接入

场景2：你的 App 卖的是实物/实体服务
→ 可以使用第三方支付
→ 在审核备注中明确说明：本 App 销售的是实物商品/实体服务，
  不涉及虚拟商品，因此使用第三方支付符合审核指南 3.1 条款

场景3：你的 App 同时有虚拟和实物商品
→ 虚拟商品用 IAP，实物用第三方支付
→ 在 App 中明确区分两种支付场景
```

⚠️ **警告**：绝对不要试图绕过 IAP！以下做法都会被拒：
- 在 App 内提示"去网页购买"
- 虚拟商品用微信/支付宝支付
- 价格显示但跳转到外部浏览器购买
- 限制 IAP 购买渠道，只允许网页购买

### 3.2 支付问题 — 订阅相关问题

自动续期订阅（Auto-Renewable Subscriptions）是另一个高频被拒点。

**常见问题：**

| 问题 | 说明 |
|------|------|
| 订阅说明不清晰 | 用户不知道订阅了什么、多久扣费一次 |
| 缺少订阅管理入口 | 用户无法在 App 内查看/取消订阅 |
| 订阅价格不合理 | 订阅价格与提供的价值不匹配 |
| 免费试用未说明 | 免费试用期结束后自动扣费，但没有明确告知 |
| 多个订阅层级混乱 | 多个订阅方案之间的关系不清楚 |

**预防方法：**

| 方法 | 操作 |
|------|------|
| 清晰的订阅说明 | 在购买页面明确显示：价格、周期、内容、自动续费说明 |
| 提供订阅管理入口 | 在 App 设置中添加"管理订阅"链接 |
| 免费试用声明 | 明确告知试用期长度和到期后自动扣费 |
| 合理定价 | 订阅价格应与提供的服务价值匹配 |
| 展示订阅条款 | 在购买前展示订阅条款和隐私政策 |

**订阅说明必须包含的信息：**

```
✅ 订阅名称
✅ 订阅价格和周期（如：¥18/月）
✅ 订阅包含的具体内容/服务
✅ 免费试用期的长度（如有）
✅ 试用期结束后自动扣费的明确提示
✅ 取消订阅的方式和链接
✅ 隐私政策和服务条款链接
```

**应对策略：**

```
1. 在 App 内补充完整的订阅说明
2. 添加"管理订阅"入口（链接到 Apple 的订阅管理页面）
3. 在审核备注中附上订阅说明页面的截图
4. 说明已按照审核指南 3.1.2 条款提供完整信息
5. 重新提交审核
```

💡 **提示**：Apple 要求在 App 内提供订阅管理入口。最简单的做法是添加一个按钮，链接到 `https://apps.apple.com/account/subscriptions`，用户点击后可以在 App Store 中管理订阅。

### 4.1 模仿问题 — 抄袭已有 App

Apple 非常重视知识产权保护，抄袭别人的 App 会被直接拒绝。

**什么算模仿？**

| 行为 | 是否算模仿 | 说明 |
|------|:----------:|------|
| 界面设计高度相似 | ✅ 是 | 和已有 App 长得几乎一样 |
| 抄袭代码 | ✅ 是 | 直接复制别人的代码 |
| 使用别人的品牌/Logo | ✅ 是 | 侵犯商标权 |
| 功能类似但设计不同 | ❌ 否 | 同类竞品是允许的 |
| 使用开源代码 | ❌ 否 | 遵守开源协议即可 |

**如何避免：**

| 方法 | 操作 |
|------|------|
| 原创设计 | 使用自己的 UI 设计，不要照搬竞品 |
| 独特功能 | 添加竞品没有的特色功能 |
| 不用他人品牌 | 不要在 App 名称、图标、截图中使用他人品牌 |
| 遵守开源协议 | 使用开源代码时遵守对应协议 |

**应对策略：**

```
1. 如果确实存在模仿，必须重新设计界面和功能
2. 如果是误判（功能类似但设计原创），准备设计过程证据
3. 在申诉中说明你的 App 与被指模仿的 App 的区别
4. 提供设计稿、开发记录等证明原创性
```

⚠️ **警告**：如果你收到了 DMCA 投诉（数字千年版权法），情况会比较严重。Apple 会给你一个回复期限，如果不回复或败诉，App 会被下架。建议认真对待，必要时咨询律师。

### 4.2 最小功能 — 网页打包/功能太少

Apple 不希望 App Store 里充斥着低质量的"网页打包"App。

**什么算最小功能？**

| 情况 | 是否会被拒 | 说明 |
|------|:----------:|------|
| 纯 WebView 加载网站 | ✅ 大概率被拒 | 没有原生功能，用户不如用浏览器 |
| 功能极其简单 | ✅ 可能被拒 | 只有一个计算器、一个倒计时 |
| 有原生交互的混合 App | ❌ 一般不会 | 虽然有 WebView，但也有原生功能 |
| 功能丰富的原生 App | ❌ 不会 | 有完整的原生功能体系 |

**如何避免：**

| 方法 | 操作 |
|------|------|
| 添加原生功能 | 推送通知、离线缓存、相机、定位等 |
| 使用原生 UI | 至少核心页面使用原生控件 |
| 提供完整体验 | 不要让用户感觉"不如用网页" |
| 添加特色功能 | 做一些网页做不到的事（如 Widget、Siri 集成） |

**WebView App 如何增加原生功能：**

| 原生功能 | 说明 | 实现难度 |
|----------|------|:--------:|
| 推送通知 | 接收远程推送消息 | ⭐⭐ |
| 离线缓存 | 无网络时也能查看部分内容 | ⭐⭐ |
| 下拉刷新 | 原生下拉刷新体验 | ⭐ |
| 分享功能 | 调用系统分享面板 | ⭐ |
| 生物识别 | Face ID / Touch ID 登录 | ⭐⭐ |
| Widget | 桌面小组件 | ⭐⭐⭐ |
| Siri 快捷指令 | 语音操作 | ⭐⭐⭐ |

**应对策略：**

```
1. 评估当前 App 的原生功能数量
2. 添加 2-3 个原生功能（推送、离线缓存、Widget 等）
3. 在审核备注中详细说明 App 提供的原生功能
4. 强调 App 不是简单的网页打包，而是提供了网页无法实现的体验
5. 重新提交审核
```

💡 **提示**：如果你的 App 确实需要大量使用 WebView（比如内容型应用），建议至少做到：原生导航栏 + 原生登录页 + 推送通知 + 离线缓存。这样审核员能看出你做了原生开发工作，不是简单套壳。

### 4.3 垃圾 App — 重复提交

Apple 对"垃圾 App"（Spam）的定义很广，重复提交是其中最常见的情况。

**什么算垃圾 App？**

| 行为 | 是否算垃圾 App | 说明 |
|------|:--------------:|------|
| 同一功能创建多个 App | ✅ 是 | 比如做 10 个不同城市名的天气 App |
| 换皮 App | ✅ 是 | 同一个 App 换个图标和名字就提交 |
| 批量生成 App | ✅ 是 | 用模板批量生成功能相似的 App |
| 同一开发者多个相似 App | ✅ 是 | 功能高度重叠的多个 App |
| 一个 App 多个版本 | ❌ 否 | 正常的版本迭代不算 |

**如何避免：**

| 方法 | 操作 |
|------|------|
| 一个功能一个 App | 不要把一个 App 拆成多个 |
| 合并相似 App | 如果已有相似 App，在新版本中添加功能而不是创建新 App |
| 差异化 | 如果确实需要多个 App，确保功能有明显差异 |
| 不要换皮 | 每个 App 都要有独特的价值 |

**应对策略：**

```
1. 如果确实有多个相似 App，考虑合并为一个
2. 在申诉中说明每个 App 的差异化功能
3. 如果被要求合并，将功能整合到一个 App 中
4. 删除多余的相似 App
```

⚠️ **警告**：Apple 可能会一次性审查你账号下所有 App。如果发现大量垃圾 App，不仅相关 App 会被拒，你的开发者账号也可能被标记，影响后续所有提交。

### 4.8 登录问题 — 第三方登录要求

自 2019 年起，Apple 强制要求：如果你的 App 支持第三方社交登录，就必须同时提供"通过 Apple 登录"（Sign in with Apple）。

**Apple 登录要求：**

| 场景 | 是否需要 Apple 登录 | 说明 |
|------|:-------------------:|------|
| 有微信/QQ/微博登录 | ✅ 必须 | 只要有第三方社交登录就必须加 |
| 只有手机号/邮箱登录 | ❌ 不需要 | 这些不算第三方社交登录 |
| 只有企业账号登录 | ❌ 不需要 | 企业内部登录不算第三方社交登录 |
| 有 Apple 登录 + 第三方登录 | ✅ 已满足 | 已经有了就行 |
| 完全不需要登录 | ❌ 不需要 | 没有登录功能就不需要 |

**第三方登录规范：**

| 规范 | 说明 |
|------|------|
| Apple 登录不能是唯一登录方式 | 如果有其他登录方式，Apple 登录只是其中之一 |
| Apple 登录按钮要醒目 | 不能把 Apple 登录藏在角落里 |
| Apple 登录后功能要完整 | 不能登录后功能比其他登录方式少 |
| 不能要求填写额外信息 | Apple 登录已经提供了必要信息，不能强制补充 |

**接入 Sign in with Apple 的步骤：**

```
1. 在 Apple Developer 网站为 App ID 开启 "Sign in with Apple" 能力
2. 在 Xcode 中添加 Sign in with Apple Capability
3. 使用 AuthenticationServices 框架实现登录
4. 处理用户凭证和身份令牌
5. 测试登录流程
```

**应对策略：**

```
1. 添加 Sign in with Apple 功能
2. 确保 Apple 登录按钮与其他第三方登录按钮同样醒目
3. 确保 Apple 登录后能正常使用所有功能
4. 在审核备注中说明已添加 Apple 登录
5. 重新提交审核
```

💡 **提示**：如果你不想接入第三方登录，最简单的办法是只提供手机号/邮箱登录。这样就不需要加 Apple 登录，也能满足审核要求。

### 5.1 隐私问题 — 数据收集未说明

隐私问题是近年来 Apple 审核的重点关注领域，审核越来越严格。

**隐私政策要求：**

| 要求 | 说明 |
|------|------|
| 必须提供隐私政策 URL | 在 App Store Connect 中填写，且链接必须可访问 |
| 隐私政策必须完整 | 包含数据收集、使用、存储、分享的完整说明 |
| 隐私政策必须准确 | 实际收集的数据必须与声明一致 |
| 隐私政策必须可理解 | 用用户能看懂的语言编写 |
| App 内也要可访问 | 在 App 内提供隐私政策的入口 |

**数据收集声明：**

在 App Store Connect 中，你必须如实声明 App 收集了哪些数据：

| 数据类型 | 是否收集 | 声明要求 |
|----------|:--------:|----------|
| 联系信息（邮箱、电话） | 按实际情况 | 必须声明 |
| 健康/健身数据 | 按实际情况 | 必须声明 |
| 财务信息 | 按实际情况 | 必须声明 |
| 位置信息 | 按实际情况 | 必须声明 |
| 浏览历史 | 按实际情况 | 必须声明 |
| 搜索历史 | 按实际情况 | 必须声明 |
| 用户内容（照片、视频） | 按实际情况 | 必须声明 |
| 标识符（设备 ID、广告 ID） | 按实际情况 | 必须声明 |
| 使用数据（点击、浏览时长） | 按实际情况 | 必须声明 |
| 诊断数据（崩溃日志） | 按实际情况 | 必须声明 |

**应对策略：**

```
1. 编写完整的隐私政策（可使用在线模板生成器）
2. 确保隐私政策 URL 可正常访问
3. 在 App Store Connect 中如实填写数据收集声明
4. 在 App 内添加隐私政策入口（通常在"设置"或"关于"页面）
5. 确保实际数据收集行为与声明一致
6. 重新提交审核
```

💡 **提示**：推荐使用 [Termly](https://termly.io/) 或 [GetTerms.io](https://getterms.io/) 等工具快速生成隐私政策。但生成后一定要根据你的 App 实际情况修改，不能直接用模板。

### 5.2 隐私问题 — 权限滥用

Apple 要求 App 只能请求和使用与功能直接相关的权限。

**什么算权限滥用？**

| 行为 | 是否算滥用 | 说明 |
|------|:----------:|------|
| 请求了但没使用定位权限 | ✅ 是 | App 不需要定位却请求了定位 |
| 请求了相机权限但只用来扫码 | ❌ 一般不算 | 扫码是相机的合理用途 |
| 后台持续获取位置 | ✅ 可能是 | 没有充分理由不需要后台定位 |
| 请求通讯录权限来邀请好友 | ✅ 可能是 | 应该用系统自带的分享面板 |
| 请求所有权限"以防万一" | ✅ 是 | 只请求需要的权限 |

**如何正确使用权限：**

| 原则 | 说明 |
|------|------|
| 按需请求 | 只请求功能必需的权限 |
| 延迟请求 | 在用户使用相关功能时才请求，不要一启动就全请求 |
| 说明用途 | 在 Info.plist 中填写权限用途描述（必须） |
| 提供降级方案 | 用户拒绝权限后，App 仍应可用（功能受限但不崩溃） |

**Info.plist 权限描述示例：**

```xml
<key>NSLocationWhenInUseUsageDescription</key>
<string>我们需要您的位置来显示附近天气信息</string>

<key>NSCameraUsageDescription</key>
<string>我们需要使用相机来扫描二维码</string>

<key>NSPhotoLibraryUsageDescription</key>
<string>我们需要访问相册以便您选择头像</string>

<key>NSMicrophoneUsageDescription</key>
<string>我们需要使用麦克风来录制语音消息</string>
```

**应对策略：**

```
1. 检查 App 请求了哪些权限
2. 移除不需要的权限请求
3. 确保 Info.plist 中每个权限都有清晰的用途描述
4. 实现权限被拒绝后的降级方案
5. 在审核备注中说明每个权限的用途
6. 重新提交审核
```

⚠️ **警告**：权限用途描述不能留空，也不能写得太笼统（如"用于提供更好的服务"）。Apple 要求描述必须具体说明权限的用途，否则会被拒。

### 5.3 隐私问题 — 后台定位

后台定位是权限滥用中最常见的一种，Apple 对此审核非常严格。

**后台定位要求：**

| 要求 | 说明 |
|------|------|
| 必须有充分理由 | 不是所有需要定位的 App 都需要后台定位 |
| 必须在 Info.plist 中声明 | 同时需要 `NSLocationAlwaysAndWhenInUseUsageDescription` |
| 必须在 App 中说明 | 在 App 内告诉用户为什么需要后台定位 |
| 不能偷偷定位 | 不能在没有用户知情的情况下持续获取位置 |

**哪些 App 合理需要后台定位：**

| App 类型 | 是否合理需要 | 说明 |
|----------|:----------:|------|
| 导航类 | ✅ 合理 | 导航需要持续定位 |
| 跑步/运动类 | ✅ 合理 | 记录运动轨迹 |
| 外卖/打车类 | ✅ 合理 | 配送/行程追踪 |
| 天气类 | ❌ 不合理 | 只需要前台获取一次位置 |
| 新闻类 | ❌ 不合理 | 不需要持续定位 |
| 社交类 | ❌ 不合理 | 不需要后台持续定位 |

**如何正确使用后台定位：**

```
1. 只在确实需要时请求"始终允许"定位权限
2. 在 Info.plist 中填写详细的后台定位用途描述
3. 在 App 内提供说明页面，解释为什么需要后台定位
4. 使用显著位置变化（significant-change）代替持续定位（如果精度要求不高）
5. 允许用户在 App 设置中关闭后台定位
```

**Info.plist 后台定位配置：**

```xml
<key>NSLocationAlwaysAndWhenInUseUsageDescription</key>
<string>我们需要在后台持续获取您的位置，以便在您跑步时记录运动轨迹</string>

<key>NSLocationWhenInUseUsageDescription</key>
<string>我们需要您的位置来显示附近的跑步路线</string>

<key>UIBackgroundModes</key>
<array>
    <string>location</string>
</array>
```

**应对策略：**

```
1. 评估 App 是否真的需要后台定位
2. 如果不需要，移除后台定位权限，只保留"使用期间"定位
3. 如果需要，确保用途描述充分、App 内有说明页面
4. 在审核备注中详细解释为什么需要后台定位
5. 重新提交审核
```

### 其他常见被拒原因

| 条款 | 名称 | 常见问题 | 应对方法 |
|------|------|----------|----------|
| 1.1 | 令人反感的内容 | UGC 中出现违规内容 | 添加内容审核和举报机制 |
| 1.5 | 开发者行为 | 开发者有违规记录 | 遵守开发者协议，保持良好记录 |
| 2.2 | 软件要求 | App 不符合 iOS 技术标准 | 遵循 Apple 的技术规范和 Human Interface Guidelines |
| 3.2.2 | 广告相关 | 广告过多影响体验、误导点击 | 控制广告频率，广告要有明确标识 |
| 5.6 | 数据安全 | 数据传输未加密、存储不安全 | 使用 HTTPS、Keychain 存储敏感信息 |

**1.1 令人反感的内容 — 详细说明：**

如果你的 App 包含用户生成内容（UGC），必须具备以下功能：

```
✅ 内容过滤机制（关键词过滤 + 人工审核）
✅ 用户举报功能
✅ 违规内容删除机制
✅ 违规用户封禁机制
✅ 在审核备注中说明以上机制
```

**3.2.2 广告相关 — 详细说明：**

| 规则 | 说明 |
|------|------|
| 广告要有标识 | 用户要能区分广告和内容 |
| 不能误导点击 | 广告按钮不能伪装成系统弹窗 |
| 不能过多 | 广告不能严重影响用户体验 |
| 不能有成人广告 | 不能展示色情、暴力等广告 |

**5.6 数据安全 — 详细说明：**

| 要求 | 实现方法 |
|------|----------|
| 网络传输加密 | 所有网络请求使用 HTTPS |
| 敏感数据安全存储 | 使用 Keychain 存储密码、Token 等 |
| 不明文存储密码 | 密码必须加密或哈希后存储 |
| App Transport Security | 默认启用 ATS，不要随意添加例外域名 |

## 被拒后的申诉流程

> 🎯 **本节目标**：了解三种申诉渠道的适用场景，掌握完整的申诉流程和时间线，知道被拒后应该做什么、怎么做。

### 申诉渠道

| 渠道 | 适用场景 | 响应速度 | 效果 |
|------|----------|----------|------|
| App Store Connect Resolution Center | 首次被拒、常规沟通 | 1-2 天 | 解决大部分问题 |
| 电话沟通 | 多次被拒、需要详细解释 | 即时 | 直接沟通效率高 |
| 上诉委员会（App Review Board） | 对审核结果有异议 | 1-3 天 | 最终裁定权 |

💡 **提示**：90% 的被拒问题通过 Resolution Center 就能解决。建议先通过 Resolution Center 沟通，如果效果不好再升级。

### 申诉流程

**完整申诉流程：**

```
收到被拒通知
    ↓
仔细阅读被拒原因（逐字阅读！）
    ↓
分析被拒原因，确定问题所在
    ↓
┌─────────────────────────────────┐
│  问题明确且可以修复？              │
│  ├── 是 → 修复问题，重新提交审核   │
│  └── 否 → 准备申诉材料            │
│           ↓                      │
│      在 Resolution Center 回复    │
│           ↓                      │
│      等待审核团队回复（1-2 天）     │
│           ↓                      │
│      问题解决？                    │
│      ├── 是 → 重新提交审核        │
│      └── 否 → 考虑电话沟通        │
│               ↓                  │
│          仍无法解决？              │
│          └── 是 → 请求上诉委员会   │
└─────────────────────────────────┘
```

**准备申诉材料：**

| 材料 | 说明 |
|------|------|
| 被拒邮件原文 | 保留完整的被拒通知 |
| 截图/视频证据 | 证明你的 App 符合要求的截图或录屏 |
| 审核指南引用 | 引用支持你观点的审核指南条款 |
| 技术说明 | 如果是技术问题，提供详细的技术解释 |
| 用户数据 | 如果涉及用户影响，提供相关数据 |

### 申诉时间线

| 阶段 | 时间参考 | 说明 |
|------|----------|------|
| 收到被拒通知 | 提交审核后 1-3 天 | Apple 会发邮件通知 |
| 分析和准备材料 | 0.5-1 天 | 仔细阅读原因，准备申诉材料 |
| Resolution Center 回复 | 1-2 天 | 审核团队回复你的申诉 |
| 修复并重新提交 | 0.5-2 天 | 根据反馈修复问题 |
| 重新审核 | 1-2 天 | 重新提交后的审核时间 |
| 电话沟通 | 当天 | 预约后通常当天或次日通话 |
| 上诉委员会 | 1-3 天 | 提交上诉后的回复时间 |

💡 **提示**：被拒后不要急于回复，先花时间充分理解被拒原因。仓促回复往往效果不好，反而可能让审核员觉得你没有认真对待问题。

## 如何写申诉信

> 🎯 **本节目标**：掌握申诉信的结构和写法，学会使用模板快速编写申诉信，了解沟通话术和技巧。

### 申诉信结构

一封好的申诉信应该结构清晰、有理有据：

| 部分 | 内容 | 占比 |
|------|------|:----:|
| 开头 | 确认收到审核反馈，表示感谢 | 10% |
| 中间 | 逐条回应被拒原因，提供证据 | 80% |
| 结尾 | 请求重新审核，表达合作意愿 | 10% |

**写作原则：**

| 原则 | 说明 | ❌ 错误做法 | ✅ 正确做法 |
|------|------|-----------|-----------|
| 礼貌专业 | 保持尊重和客观 | "你们审核标准不一致" | "感谢审核反馈，我们已做如下调整" |
| 有理有据 | 用事实和条款说话 | "我们的 App 没问题" | "根据审核指南 3.1 条款，我们的 App 属于..." |
| 逐条回应 | 不遗漏任何被拒原因 | 笼统回复 | "关于问题1：...；关于问题2：..." |
| 提供证据 | 截图、录屏、文档 | 空口无凭 | 附上截图和操作视频链接 |
| 简明扼要 | 不要长篇大论 | 写了 3000 字 | 控制在 500 字以内 |

### 申诉信案例

**案例1：3.1 支付问题申诉成功**

> 被拒原因：App 内使用微信支付购买会员，违反 3.1 条款。

```
Dear App Review Team,

Thank you for your feedback regarding Guideline 3.1.

We would like to clarify that our app sells physical goods
(food delivery), not virtual goods. Users purchase actual meals
from restaurants, which are delivered to their location.

Per Guideline 3.1.3(a), apps may use payment methods other than
IAP for physical goods and services. Our app falls under this
category.

We have attached screenshots showing:
1. The food delivery ordering process
2. Physical goods being delivered
3. Our business license for food delivery service

We kindly request a re-review of our app.

Best regards,
Development Team
```

**申诉结果**：✅ 成功。审核团队确认是实物商品，允许使用第三方支付。

---

**案例2：4.2 最小功能申诉成功**

> 被拒原因：App 功能太少，被认为是网页打包。

```
Dear App Review Team,

Thank you for your feedback regarding Guideline 4.2.

We would like to clarify that our app provides significant native
functionality beyond a simple web wrapper:

1. Push Notifications - Users receive real-time order updates
2. Offline Mode - Users can view cached content without internet
3. Face ID Login - Secure biometric authentication
4. Home Screen Widget - Quick access to order status
5. Haptic Feedback - Native touch feedback throughout the app

Our app uses a hybrid architecture where the content display is
web-based, but all the above features are implemented natively
using iOS SDKs.

We have attached a video demonstrating these native features:
[Video Link]

We kindly request a re-review.

Best regards,
Development Team
```

**申诉结果**：✅ 成功。审核团队确认 App 有足够的原生功能。

---

**案例3：5.1 隐私问题申诉成功**

> 被拒原因：隐私政策 URL 无法访问。

```
Dear App Review Team,

Thank you for your feedback regarding Guideline 5.1.

We have resolved the privacy policy URL issue. The previous URL
was temporarily unavailable due to a server migration. We have
now:

1. Updated the privacy policy URL to: https://example.com/privacy
2. Verified the URL is accessible from multiple devices and networks
3. Ensured the privacy policy is complete and up-to-date
4. Added a privacy policy link within the app (Settings > About > Privacy Policy)

We have also updated our App Store Connect data collection
declarations to accurately reflect all data our app collects.

We kindly request a re-review.

Best regards,
Development Team
```

**申诉结果**：✅ 成功。隐私政策 URL 已修复，审核通过。

### 沟通话术与技巧

| 技巧 | 说明 | 示例 |
|------|------|------|
| 保持礼貌 | 永远不要和审核员争吵 | "感谢您的反馈" 而不是 "你们搞错了" |
| 提供证据 | 用截图和视频说话 | 附上操作录屏链接 |
| 引用条款 | 引用审核指南支持你的观点 | "根据审核指南 3.1.3(a)..." |
| 解释而非争论 | 解释你的理解和做法 | "我们的理解是..." 而不是 "你们理解错了" |
| 承认问题 | 如果确实有问题，大方承认 | "我们已修复此问题" |
| 请求澄清 | 如果原因不清楚，礼貌提问 | "能否详细说明哪个功能不符合要求？" |

⚠️ **警告**：绝对不要在申诉中使用威胁性语言（如"我要投诉你们"、"我要找媒体曝光"），也不要对审核员进行人身攻击。这不仅无助于解决问题，还可能导致你的开发者账号被标记。

## 多次被拒的升级策略

> 🎯 **本节目标**：了解多次被拒后的升级策略，知道何时请求电话沟通、何时请求上诉委员会、如何申请加速审核。

### 请求电话沟通

**何时请求：**

| 情况 | 是否适合电话沟通 |
|------|:---------------:|
| 被拒 2 次以上，文字沟通效果不好 | ✅ 适合 |
| 审核原因不清楚，需要详细解释 | ✅ 适合 |
| 技术问题复杂，文字说不清楚 | ✅ 适合 |
| 首次被拒 | ❌ 不需要，先通过 Resolution Center 沟通 |
| 问题很简单，修复即可 | ❌ 不需要 |

**如何请求：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 在 Resolution Center 中回复 |
| 2 | 说明希望电话沟通 |
| 3 | 提供你的电话号码和方便通话的时间段 |
| 4 | 注明你的时区（如 GMT+8） |
| 5 | 等待 Apple 安排通话 |

**沟通技巧：**

| 技巧 | 说明 |
|------|------|
| 提前准备 | 列出要讨论的问题清单 |
| 保持冷静 | 不要激动，理性沟通 |
| 做好记录 | 通话中记录关键信息 |
| 确认行动项 | 通话结束前确认你需要做什么 |
| 通话后回复 | 在 Resolution Center 中总结通话内容 |

💡 **提示**：Apple 审核团队在美国加州，时区为太平洋时间（PST/PDT）。建议在工作日的北京时间凌晨 1 点到早上 9 点之间提供可通话时间，这样对应的是加州的工作时间。

---

### 请求上诉委员会

上诉委员会（App Review Board）是审核申诉的最终渠道，拥有最终裁定权。

**何时请求：**

| 情况 | 是否适合 |
|------|:--------:|
| 多次被拒且与审核团队无法达成一致 | ✅ 适合 |
| 你确信 App 符合审核指南但审核团队不认可 | ✅ 适合 |
| 审核团队的判断存在明显错误 | ✅ 适合 |
| 首次被拒 | ❌ 不需要 |
| 问题可以通过修改解决 | ❌ 不需要 |

**如何请求：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 在 Resolution Center 中选择"上诉"选项 |
| 2 | 填写上诉理由 |
| 3 | 提供详细的论据和证据 |
| 4 | 引用审核指南条款支持你的观点 |
| 5 | 提交上诉 |

**注意事项：**

| 注意事项 | 说明 |
|----------|------|
| 上诉是最终渠道 | 上诉委员会的决定是最终的，不能再上诉 |
| 理由要充分 | 上诉理由必须比 Resolution Center 的回复更详细 |
| 提供新证据 | 最好提供之前没有提供过的新证据 |
| 态度要专业 | 上诉不是抱怨，是理性陈述你的观点 |

---

### 请求加速审核

**何时请求：**

| 情况 | 是否适合 |
|------|:--------:|
| 紧急 Bug 修复 | ✅ 适合 |
| 安全漏洞修复 | ✅ 适合 |
| 法规合规更新 | ✅ 适合 |
| 重大事件相关 | ✅ 适合 |
| 常规功能更新 | ❌ 不适合 |
| 想早点上线 | ❌ 不适合 |

**如何请求：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 提交审核后，进入 App 详情页 |
| 2 | 点击"请求加急审核" |
| 3 | 选择加急原因 |
| 4 | 填写详细理由 |
| 5 | 提交申请 |

**加急审核理由模板：**

```
【加急原因】
紧急安全漏洞修复

【详细说明】
我们在 App 中发现了一个安全漏洞，可能导致用户个人信息
泄露。具体问题：[描述漏洞]。我们已修复此漏洞并提交了
新版本。

【影响范围】
所有用户均受影响。

【已采取措施】
1. 修复了安全漏洞
2. 增加了数据传输加密
3. 进行了安全审计

【期望】
希望尽快审核通过，减少用户风险。
```

## 国内额外审核要求应对

> 🎯 **本节目标**：了解国内（中国大陆）App 上架的额外审核要求，包括内容审核、资质要求和特殊行业要求，确保你的 App 在国内也能顺利上架。

### 内容审核

国内对 App 内容的审核比 Apple 审核更严格，需要额外注意。

**敏感内容规避：**

| 内容类型 | 是否敏感 | 说明 |
|----------|:--------:|------|
| 政治/时政 | ⚠️ 高度敏感 | 避免涉及政治话题 |
| 色情/低俗 | ⚠️ 高度敏感 | 严格禁止 |
| 暴力/恐怖 | ⚠️ 高度敏感 | 严格禁止 |
| 赌博 | ⚠️ 高度敏感 | 严格禁止，包括虚拟赌博 |
| 宗教 | ⚠️ 敏感 | 谨慎处理 |
| 社交/社区 | ⚠️ 需要审核 | UGC 必须有审核机制 |
| 新闻/资讯 | ⚠️ 需要资质 | 需要新闻资质 |

**用户生成内容审核：**

如果你的 App 有用户发布内容的功能（评论、帖子、图片等），必须具备：

```
✅ 关键词过滤系统（敏感词库）
✅ 人工审核团队（7×24 小时）
✅ 用户举报功能
✅ 违规内容快速删除机制
✅ 违规用户处罚机制
✅ 内容审核日志留存（至少 60 天）
```

**示例 — 评论功能的内容审核实现：**

| 步骤 | 操作 |
|------|------|
| 1 | 用户提交评论 |
| 2 | 系统自动进行敏感词过滤 |
| 3 | 通过过滤的评论先标记为"待审核"状态 |
| 4 | 人工审核通过后正式显示 |
| 5 | 其他用户可举报评论 |
| 6 | 被举报评论自动进入审核队列 |

---

### 资质要求

国内某些行业的 App 需要特定的资质才能上架。

**常见需要资质的行业：**

| 行业 | 所需资质 | 获取方式 |
|------|----------|----------|
| 电商 | ICP 经营许可证 | 向通信管理局申请 |
| 社交/社区 | ICP 经营许可证 + 安全评估报告 | 通信管理局 + 公安局 |
| 新闻/资讯 | 互联网新闻信息服务许可证 | 网信办 |
| 视频/直播 | 信息网络传播视听节目许可证 | 广电总局 |
| 游戏 | 版号 + 网络游戏出版运营许可证 | 新闻出版署 |
| 医疗 | 互联网医疗保健信息服务审核同意书 | 卫健委 |
| 金融 | 金融牌照（各类） | 银保监会/证监会 |
| 教育 | 办学许可证（部分） | 教育局 |
| 地图/导航 | 测绘资质 | 自然资源部 |

**如何获取资质：**

| 步骤 | 操作 |
|------|------|
| 1 | 确认你的 App 属于哪个行业 |
| 2 | 查询该行业需要的资质 |
| 3 | 准备申请材料（通常需要营业执照、法人信息等） |
| 4 | 向对应主管部门提交申请 |
| 5 | 等待审批（通常 1-6 个月） |
| 6 | 获得资质后，在 App Store Connect 中上传 |

💡 **提示**：个人开发者很难获取上述资质。如果你的 App 涉及这些行业，建议注册公司后再申请。部分资质只对公司开放，个人无法申请。

---

### 特殊行业要求

**金融类 App：**

| 要求 | 说明 |
|------|------|
| 金融牌照 | 必须有对应金融业务的牌照 |
| 风险提示 | 必须在显著位置展示投资风险提示 |
| 用户身份验证 | 实名认证、人脸识别等 |
| 资金安全 | 资金托管、交易加密 |
| 数据安全 | 金融数据加密存储和传输 |

**医疗类 App：**

| 要求 | 说明 |
|------|------|
| 医疗资质 | 互联网医疗保健信息服务审核同意书 |
| 医生资质 | 在线问诊的医生必须有执业资格 |
| 免责声明 | 不能替代线下就医的免责声明 |
| 隐私保护 | 医疗数据属于敏感个人信息，需要额外保护 |
| 药品信息 | 药品信息必须来自权威来源 |

**教育类 App：**

| 要求 | 说明 |
|------|------|
| 办学资质 | 部分教育 App 需要办学许可证 |
| 内容审核 | 教育内容必须符合教育方针 |
| 未成年人保护 | 面向未成年人的 App 需要防沉迷系统 |
| 收费规范 | 收费项目和标准必须明示 |
| 教师资质 | 在线教育的教师需要有相应资格 |

**新闻类 App：**

| 要求 | 说明 |
|------|------|
| 新闻资质 | 互联网新闻信息服务许可证 |
| 内容审核 | 新闻内容必须经过审核 |
| 来源标注 | 转载新闻必须标注来源 |
| 评论区管理 | 评论区必须有审核机制 |
| 纠正机制 | 发现错误信息必须有纠正和道歉机制 |

⚠️ **警告**：如果你的 App 在中国大陆上架，除了满足 Apple 的审核要求外，还必须满足国内的法律法规要求。两者缺一不可。建议在开发初期就确认所需资质，避免开发完成后无法上架。

## 小结

本章涵盖了审核被拒的全面应对策略，核心要点总结如下：

| 知识点 | 核心要点 |
|--------|----------|
| 审核指南 | 5 大板块：安全性/性能/商业/设计/法律，至少通读一遍 |
| 崩溃/Bug | 多设备多系统测试，做好网络异常处理 |
| 元数据问题 | 描述与截图必须与 App 实际功能一致 |
| IAP 支付 | 虚拟商品必须用 IAP，实物商品可用第三方支付 |
| 订阅问题 | 订阅说明要清晰，提供管理入口，免费试用要告知 |
| 模仿问题 | 原创设计，不抄袭界面和代码 |
| 最小功能 | 添加原生功能，不能只是网页打包 |
| 垃圾 App | 不重复提交相似 App，不换皮 |
| Apple 登录 | 有第三方登录就必须加 Apple 登录 |
| 隐私问题 | 提供隐私政策、如实声明数据收集、正确使用权限 |
| 后台定位 | 只在确实需要时请求，用途描述要充分 |
| 申诉流程 | Resolution Center → 电话沟通 → 上诉委员会 |
| 申诉信 | 礼貌专业、有理有据、逐条回应、提供证据 |
| 国内要求 | 内容审核、行业资质、特殊行业规范 |

**被拒应对清单：**

```
✅ 仔细阅读被拒邮件，理解每一条原因
✅ 判断问题是否可以修复
✅ 可以修复 → 修复后重新提交
✅ 无法修复 → 准备申诉材料
✅ 申诉信：礼貌、有据、逐条回应
✅ 首次申诉通过 Resolution Center
✅ 多次被拒可请求电话沟通
✅ 仍有异议可请求上诉委员会
✅ 紧急情况可申请加速审核
✅ 国内上架注意内容审核和资质要求
```
