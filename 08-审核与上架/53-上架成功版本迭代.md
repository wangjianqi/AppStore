## 上架后第一件事

> 🎯 **本节目标**：了解 App 上架后需要立即做的三件事——监控崩溃、关注评论、自测线上版本，确保上线后的 App 运行正常。

### 监控崩溃

App 上架后，最怕的就是用户一打开就崩溃。第一时间发现和修复崩溃是重中之重。

**为什么上架后要立即监控崩溃？**

| 原因 | 说明 |
|------|------|
| 测试环境 ≠ 线上环境 | 你的测试设备有限，用户设备千差万别 |
| 用户数据量更大 | 你测试了 10 种场景，用户可能有 1000 种用法 |
| 影响评分和留存 | 崩溃会导致差评，差评影响下载 |
| 越早修复影响越小 | 崩溃持续越久，受影响用户越多 |

**Xcode Organizer 查看崩溃：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 打开 Xcode → 菜单栏 Window → Organizer |
| 2 | 选择 "Crashes" 标签页 |
| 3 | 选择你的 App 和版本 |
| 4 | 查看崩溃报告列表 |
| 5 | 点击具体崩溃查看详情 |

**崩溃报告分析要点：**

| 要点 | 说明 |
|------|------|
| 崩溃次数 | 发生频率越高，优先级越高 |
| 影响用户数 | 受影响用户越多，越紧急 |
| 崩溃类型 | 是闪退、卡死还是 ANR |
| 崩溃堆栈 | 定位崩溃发生的代码位置 |
| 系统版本分布 | 是否只在特定系统版本上发生 |
| 设备型号分布 | 是否只在特定设备上发生 |

**优先修复原则：**

| 优先级 | 崩溃特征 | 处理时间 |
|:------:|----------|----------|
| 🔴 紧急 | 启动崩溃、影响 >50% 用户 | 立即修复，申请加急审核 |
| 🟠 高 | 核心功能崩溃、影响 >10% 用户 | 24 小时内修复 |
| 🟡 中 | 次要功能崩溃、影响 >1% 用户 | 下一版本修复 |
| 🟢 低 | 极少发生、影响 <1% 用户 | 排期修复 |

💡 **提示**：如果你的 App 集成了第三方崩溃监控（如 Crashlytics），上架后可以实时收到崩溃通知，不需要等用户投诉才发现问题。强烈建议在开发阶段就集成崩溃监控。

### 关注评论

用户的评论是最直接的反馈渠道，上架后要密切关注。

**App Store 评论监控：**

| 监控方式 | 操作 | 说明 |

| 邮件通知 | App Store Connect → 设置通知 | 有新评论时邮件提醒 |
| 第三方工具 | AppFollow、Appbot 等 | 自动聚合和分析评论 |

**及时回复评论：**

| 原则 | 说明 |
|------|------|
| 回复要及时 | 最好在 24 小时内回复 |
| 态度要友好 | 即使是差评也要礼貌回复 |
| 解决问题 | 如果是 Bug，说明修复计划 |
| 感谢好评 | 对好评表示感谢 |
| 不要争论 | 不要和用户在评论区辩论 |

**收集反馈：**

| 反馈来源 | 收集方法 | 价值 |

| 邮件 | 提供反馈邮箱 | ⭐⭐ |
| 朋友/同事 | 直接询问 | ⭐ |

### 自测线上版本

上架后，一定要从 App Store 下载正式版本，亲自测试一遍。

**为什么要自测线上版本？**

| 原因 | 说明 |
|------|------|
| 确认上架版本正确 | 有时上传了错误的构建版本 |
| 检查购买流程 | IAP 在沙盒环境和正式环境行为可能不同 |
| 验证网络请求 | 正式环境的服务器响应可能不同 |
| 确认广告/分析 | 第三方 SDK 在正式环境是否正常工作 |
| 体验用户视角 | 以用户身份完整体验一遍 |

**自测检查清单：**

```
✅ 从 App Store 下载并安装
✅ 首次启动流程正常
✅ 登录/注册功能正常
✅ 核心功能可用
✅ IAP 购买流程正常（如适用）
✅ 推送通知正常接收
✅ 网络请求正常
✅ 无明显 UI 问题
✅ 与 TestFlight 版本对比，功能一致
```

⚠️ **警告**：IAP 在沙盒环境（测试）和正式环境中的行为可能不同。上架后务必用真实 Apple ID 测试一次完整的购买流程，确认扣费和功能解锁都正常。

## 版本更新流程

> 🎯 **本节目标**：掌握版本更新的完整流程，包括版本号修改、Archive 提交和更新说明编写。

### 更新版本号

每次提交新版本，都需要更新版本号和构建号。

**版本号规则：**

| 字段 | 名称 | 格式 | 何时修改 | 示例 |
|------|------|------|----------|------|
| Marketing Version | 版本号 | 主.次.修 | 根据更新内容决定 | 1.0.0 → 1.1.0 |
| Build Number | 构建号 | 递增整数 | 每次打包必须递增 | 1 → 2 → 3 |

**版本号递增规则：**

| 更新类型 | 版本号变化 | 示例 | 说明 |
|----------|-----------|------|------|
| Bug 修复 | 修改第三位 | 1.0.0 → 1.0.1 | 小修小补 |
| 新增功能 | 修改第二位 | 1.0.1 → 1.1.0 | 新增了功能 |
| 重大更新 | 修改第一位 | 1.1.0 → 2.0.0 | 大改版、全新设计 |

**在 Xcode 中修改版本号：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 打开项目，选择项目文件 |
| 2 | 选择 Target → General → Identity |
| 3 | 修改 Version（如 1.0.0 → 1.1.0） |
| 4 | 修改 Build（如 1 → 2） |
| 5 | 确认修改 |

💡 **提示**：构建号（Build Number）每次上传都必须递增，即使版本号没变。如果上传了 Build 1 后发现问题需要重新上传，Build 必须改为 2 或更大的数字。

---

### Archive 与提交

版本更新的提交流程与首次提交基本相同。

**完整流程：**

| 步骤 | 操作 | 说明 |
|:----:|------|------|
| 1 | 修改版本号和构建号 | 按规则递增 |
| 2 | 修改代码和资源 | 实现新功能或修复 Bug |
| 3 | 充分测试 | 多设备、多场景测试 |
| 4 | Clean Build Folder | Shift + Command + K |
| 5 | Archive | Product → Archive |
| 6 | 上传构建版本 | Distribute App → App Store Connect → Upload |
| 7 | 等待处理 | 15-30 分钟 |
| 8 | 在 App Store Connect 中选择新构建版本 | 替换旧版本 |
| 9 | 更新"此版本的新增内容" | 填写更新说明 |
| 10 | 提交审核 | 点击"提交审核" |

**与首次提交的区别：**

| 对比项 | 首次提交 | 版本更新 |
|--------|----------|----------|
| 版本号 | 1.0.0 | 递增（如 1.1.0） |
| 截图 | 必须提供 | 可以沿用或更新 |
| 描述 | 必须填写 | 可以沿用或更新 |
| 更新说明 | 不需要 | ✅ 必须填写 |
| 审核信息 | 全部填写 | 可以沿用 |
| 审核速度 | 1-3 天 | 通常 1-2 天 |

### 更新说明编写

更新说明（What's New）是用户在 App Store 看到的版本更新内容，写得好能促进用户更新。

**更新说明编写原则：**

| 原则 | 说明 | ❌ 错误示例 | ✅ 正确示例 |
|------|------|-----------|-----------|
| 具体明确 | 说清楚更新了什么 | "修复了一些 Bug" | "修复了在 iOS 16 上启动崩溃的问题" |
| 用户视角 | 用用户能理解的语言 | "优化了网络请求模块" | "页面加载速度提升 50%" |
| 突出重点 | 把最重要的更新放前面 | 按代码改动顺序写 | 按用户关心程度排序 |
| 简洁有力 | 不要写太长 | 写了 500 字 | 控制在 3-5 条以内 |

**更新说明模板：**

```
🎉 新功能
- [新功能描述1]
- [新功能描述2]

🔧 优化
- [优化描述1]
- [优化描述2]

🐛 修复
- [修复描述1]
- [修复描述2]
```

**更新说明示例：**

```
🎉 新功能
- 新增暗黑模式，夜间使用更舒适
- 新增桌面小组件，一眼查看今日天气

🔧 优化
- 天气数据加载速度提升 50%
- 优化搜索功能，支持模糊搜索

🐛 修复
- 修复了定位权限被拒绝后 App 崩溃的问题
- 修复了部分城市天气数据不显示的问题
```

💡 **提示**：更新说明最多 4000 字符，但建议控制在 200 字以内。大多数用户只会看前几行，把最重要的内容放在最前面。

## 用户反馈处理

> 🎯 **本节目标**：学会回复 App Store 评论，建立多渠道反馈收集机制，掌握不同类型反馈的处理方法。

### App Store 评论回复

从 iOS 10.3 开始，开发者可以回复 App Store 上的用户评论。这是与用户直接沟通的重要渠道。

**如何回复评论：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 登录 App Store Connect |
| 2 | 我的 App → 选择 App → 活动 → 评分和评论 |
| 3 | 找到要回复的评论 |
| 4 | 点击"回复" |
| 5 | 编写回复内容 |
| 6 | 提交回复 |

**回复技巧：**

| 技巧 | 说明 | 示例 |
|------|------|------|
| 感谢用户 | 无论好评差评，先表示感谢 | "感谢您的反馈！" |
| 承认问题 | 如果是 Bug，承认并说明修复计划 | "我们已定位此问题，将在下个版本修复" |
| 提供解决方案 | 如果有临时解决方案，告诉用户 | "您可以尝试重新登录来解决此问题" |
| 引导联系 | 鼓励用户通过其他渠道详细反馈 | "欢迎发送邮件至 support@example.com" |
| 保持简短 | 回复不要太长 | 控制在 3-5 句话 |

**回复示例：**

| 评论类型 | 用户评论 | 开发者回复 |
|----------|----------|-----------|
| Bug 报告 | "App 一打开就闪退" | "非常抱歉给您带来不便！我们已定位此问题并将在 1.0.1 版本中修复，预计本周发布。如需帮助请邮件联系 support@example.com" |
| 功能建议 | "希望能加个暗黑模式" | "感谢您的建议！暗黑模式已在开发中，将在下个版本上线，敬请期待 🎉" |
| 差评 | "垃圾 App，不好用" | "感谢您的反馈。能具体说明哪里不好用吗？我们会持续改进。如有问题可邮件联系 support@example.com" |
| 好评 | "很好用，五星好评！" | "感谢您的支持和好评！我们会继续努力，为您提供更好的体验 🙏" |

⚠️ **警告**：回复评论时要保持专业和礼貌，绝对不要和用户争吵。你的回复所有用户都能看到，不专业的回复会损害 App 的形象。

### 反馈收集渠道

| 渠道 | 优点 | 缺点 | 推荐度 |
|------|------|------|:------:|
| App 内反馈 | 便捷、上下文信息丰富 | 需要开发 | ⭐⭐⭐ |
| App Store 评论 | 公开、影响评分 | 无法主动获取 | ⭐⭐⭐ |
| 邮件 | 详细、可追踪 | 响应慢 | ⭐⭐ |
| 社交媒体 | 传播广 | 信息碎片化 | ⭐⭐ |
| 微信群 | 互动性强 | 管理成本高 | ⭐ |

**App 内反馈功能实现：**

| 方案 | 说明 | 推荐度 |
|------|------|:------:|
| 系统邮件 | 调用 MFMailComposeViewController | ⭐⭐ |
| 自定义表单 | App 内表单提交到服务器 | ⭐⭐⭐ |
| 第三方 SDK | 如 Zendesk、友盟反馈 | ⭐⭐⭐ |

**App 内反馈入口建议：**

```
✅ 位置：设置页底部或"关于"页面
✅ 触发：按钮或摇一摇（开发阶段）
✅ 内容：自动收集设备型号、系统版本、App 版本
✅ 附件：支持截图上传
✅ 回复：用户能看到开发者的回复
```

### 常见反馈类型

| 反馈类型 | 特征 | 处理方法 | 优先级 |
|----------|------|----------|:------:|
| Bug 报告 | 描述具体问题，可能附截图 | 记录 → 复现 → 修复 → 回复用户 | 🔴 高 |
| 功能建议 | "希望增加 XX 功能" | 记录 → 评估 → 排期 → 回复用户 | 🟡 中 |
| 投诉 | 情绪化表达，可能要求退款 | 安抚 → 了解详情 → 解决 → 回复 | 🟠 高 |
| 咨询 | "怎么使用 XX 功能" | 回复使用方法 → 考虑优化 UI | 🟢 低 |
| 好评 | 正面反馈 | 感谢 → 记录亮点 | 🟢 低 |

**Bug 报告处理流程：**

```
收到 Bug 报告
    ↓
记录到问题跟踪系统（如 GitHub Issues、Jira）
    ↓
尝试复现问题
    ↓
┌──────────────────────────────┐
│  能复现？                      │
│  ├── 是 → 定位原因 → 修复      │
│  └── 否 → 请求更多信息         │
│           ↓                   │
│      用户提供更多信息后重试     │
└──────────────────────────────┘
    ↓
修复并测试
    ↓
回复用户，告知已修复
    ↓
在更新说明中提及修复
```

💡 **提示**：建议使用问题跟踪工具（如 GitHub Issues、Notion、Jira）来管理用户反馈。不要只用脑子记或微信收藏，反馈多了容易遗漏。

## 崩溃监控

> 🎯 **本节目标**：掌握 Xcode Organizer 查看崩溃的方法，学会分析崩溃日志，了解第三方崩溃监控工具的对比和选择。

### Xcode Organizer

Xcode 自带的 Organizer 可以查看 App 的崩溃报告。

**查看崩溃报告：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 打开 Xcode |
| 2 | 菜单栏 Window → Organizer |
| 3 | 选择 "Crashes" 标签页 |
| 4 | 选择你的 App |
| 5 | 选择版本号 |
| 6 | 查看崩溃列表 |

**崩溃报告信息：**

| 信息 | 说明 |
|------|------|
| 崩溃类型 | 如 EXC_BAD_ACCESS、SIGABRT 等 |
| 发生次数 | 该崩溃发生的总次数 |
| 影响用户数 | 受影响的用户数量 |
| 崩溃堆栈 | 代码调用栈，定位崩溃位置 |
| 设备信息 | 设备型号、系统版本 |
| 时间分布 | 崩溃发生的时间分布 |

**符号化崩溃日志：**

崩溃日志中的地址需要符号化才能看到具体的函数名和行号。

| 符号化条件 | 说明 |
|-----------|------|
| 上传了 dSYM | Archive 时勾选了"Upload your app's symbols" |
| 本地有 dSYM | 在 Organizer 中可以找到对应的 dSYM |
| Xcode 自动符号化 | 如果有 dSYM，Xcode 会自动符号化 |

💡 **提示**：每次 Archive 时务必勾选"Upload your app's symbols"选项，这样 Apple 服务器会自动符号化崩溃日志，你就能直接看到函数名和行号，而不是一堆内存地址。

### 崩溃日志分析

**常见崩溃类型：**

| 崩溃类型 | 含义 | 常见原因 |
|----------|------|----------|
| EXC_BAD_ACCESS | 访问了无效的内存地址 | 使用了已释放的对象、野指针 |
| SIGABRT | 程序主动中止 | 断言失败、未捕获的异常 |
| SIGSEGV | 段错误，访问了受保护的内存 | 空指针、数组越界 |
| SIGKILL | 系统强制终止 | 内存占用过大、看门狗超时 |
| SIGTERM | 系统请求终止 | 系统内存不足时终止后台 App |
| 0x8badf00d | "ate bad food" | 主线程卡住太久，被看门狗杀掉 |

**分析步骤：**

```
1. 查看崩溃类型（如 EXC_BAD_ACCESS）
2. 查看崩溃堆栈，找到你自己的代码（忽略系统框架）
3. 定位到具体的文件和行号
4. 分析该行代码可能的崩溃原因
5. 复现问题（这是最关键的一步）
6. 修复并测试
```

**分析示例：**

```
崩溃堆栈（简化）：
0  MyApp                    0x00000001  ViewController.viewDidLoad() + 145
1  UIKit                    0x00000002  -[UIViewController loadViewIfRequired] + 1000
2  UIKit                    0x00000003  -[UIViewController view] + 28

分析：
- 崩溃发生在 ViewController.viewDidLoad() 的第 145 字节偏移处
- 符号化后可能定位到第 28 行代码
- 常见原因：IBOutlet 连接丢失、强制解包 nil、数组越界等
```

**常见崩溃原因及修复：**

| 原因 | 代码示例 | 修复方法 |
|------|----------|----------|
| 强制解包 nil | `let name = user.name!` | 使用可选绑定 `if let name = user.name` |
| 数组越界 | `let item = array[5]` | 检查索引 `if array.count > 5` |
| IBOutlet 断开 | `label.text = "hello"` | 检查 IBOutlet 连接是否正常 |
| 主线程更新 UI | 后台线程修改 UI | 使用 `DispatchQueue.main.async` |
| 未处理的可选值 | `cell.imageView!.image = ...` | 使用可选链 `cell.imageView?.image = ...` |

### 第三方监控工具

Xcode Organizer 只能看到选择分享崩溃数据的用户报告，覆盖率有限。第三方工具能提供更全面的崩溃监控。

**主流工具对比：**

| 对比项 | Crashlytics (Firebase) | Bugly (腾讯) | Sentry |
|--------|:----------------------:|:------------:|:------:|
| 提供商 | Google | 腾讯 | Sentry |
| 费用 | 免费 | 免费 | 免费额度 + 付费 |
| 崩溃收集 | ✅ 实时 | ✅ 实时 | ✅ 实时 |
| 崩溃率统计 | ✅ | ✅ | ✅ |

**如何选择：**

| 场景 | 推荐 | 原因 |
|------|------|------|
| 只做国内市场 | Bugly | 国内访问稳定，中文文档 |
| 做国际市场 | Crashlytics | 全球覆盖，Google 生态 |
| 需要更多功能 | Sentry | 功能最全面，支持多平台 |
| 个人项目/小团队 | Bugly 或 Crashlytics | 免费且够用 |

**Crashlytics 集成步骤（简要）：**

```
1. 在 Firebase Console 中创建项目
2. 添加 iOS App，下载 GoogleService-Info.plist
3. 在项目中添加 Firebase SDK（CocoaPods 或 SPM）
4. 初始化 Crashlytics
5. 上传 dSYM 文件（自动或手动）
6. 测试崩溃上报
```

**Bugly 集成步骤（简要）：**

```
1. 在 bugly.qq.com 注册并创建应用
2. 下载 Bugly SDK
3. 集成到项目中（CocoaPods 或手动）
4. 在 AppDelegate 中初始化
5. 上传 dSYM 文件
6. 测试崩溃上报
```

💡 **提示**：强烈建议在开发阶段就集成崩溃监控，而不是上线后才加。这样 TestFlight 测试阶段的崩溃也能被收集到，提前发现和修复问题。

## App 分析数据查看

> 🎯 **本节目标**：学会在 App Store Connect 中查看下载量、销售额、使用情况和崩溃率等关键数据，用数据驱动 App 的持续优化。

### 下载量

**查看路径：**

```
App Store Connect → 我的 App → 选择 App → App 分析 → 获取数据
```

**关键指标：**

| 指标 | 说明 | 关注点 |
|------|------|--------|
| App 下载量 | 首次下载次数 | 整体增长趋势 |
| 更新下载量 | 用户更新到新版本的次数 | 版本更新率 |
| 每日下载量 | 每天的下载次数 | 日波动和趋势 |
| 每周下载量 | 每周的下载次数 | 周度趋势 |
| 每月下载量 | 每月的下载次数 | 月度趋势 |

**下载来源分析：**

| 来源类型 | 说明 | 优化方法 |
|----------|------|----------|
| App Store 搜索 | 用户搜索关键词后下载 | 优化关键词和 App 名称 |
| App Store 浏览 | 用户在 App Store 中浏览时发现 | 优化截图和描述 |
| App 引荐来源 | 从其他 App 跳转下载 | 推广和合作 |
| 网页引荐来源 | 从网页跳转下载 | 网站推广 |
| 不可归因 | 无法确定来源 | — |

**提升下载量的方法：**

| 方法 | 说明 | 效果 |
|------|------|:----:|
| ASO 优化 | 优化关键词、标题、描述 | ⭐⭐⭐ |
| 截图优化 | 使用吸引人的截图 | ⭐⭐⭐ |
| 评分维护 | 保持 4.5 分以上 | ⭐⭐ |

### 使用情况

**查看路径：**

```
App Store Connect → 我的 App → 选择 App → App 分析 → 使用情况
```

**关键指标：**

| 指标 | 说明 | 计算方法 |
|------|------|----------|
| DAU（日活） | 每日活跃用户数 | 当天打开 App 的用户数 |
| MAU（月活） | 每月活跃用户数 | 当月打开 App 的用户数 |
| DAU/MAU | 用户粘性 | 日活/月活 × 100% |
| 会话时长 | 每次使用的平均时间 | 总使用时间/会话数 |
| 会话频率 | 每个用户每天打开几次 | 总会话数/活跃用户数 |

**留存率：**

留存率是衡量 App 质量的核心指标，表示用户在下载后持续使用 App 的比例。

| 留存类型 | 说明 | 参考值 |
|----------|------|--------|
| 次日留存 | 下载后第 2 天还在使用的比例 | 30%-50% 为良好 |
| 7 日留存 | 下载后第 7 天还在使用的比例 | 15%-30% 为良好 |
| 30 日留存 | 下载后第 30 天还在使用的比例 | 8%-15% 为良好 |

**留存率参考标准：**

| App 类型 | 次日留存 | 7 日留存 | 30 日留存 |
|----------|:--------:|:--------:|:---------:|
| 工具类 | 40%-60% | 20%-35% | 10%-20% |
| 社交类 | 35%-55% | 18%-30% | 8%-18% |
| 游戏类 | 30%-50% | 12%-25% | 5%-15% |
| 资讯类 | 25%-40% | 10%-20% | 5%-12% |

**提升留存率的方法：**

| 方法 | 说明 |
|------|------|
| 优化首次体验 | 新手引导要简洁有效 |
| 推送通知 | 适时推送提醒用户回来 |
| 个性化内容 | 根据用户偏好推荐内容 |
| 持续更新 | 定期更新保持新鲜感 |
| 社交功能 | 让用户产生社交粘性 |

### 崩溃率

**查看路径：**

```
App Store Connect → 我的 App → 选择 App → App 分析 → 崩溃率
```

**关键指标：**

| 指标 | 说明 | 健康标准 |
|------|------|----------|
| 崩溃率 | 每次会话的崩溃比例 | < 1% 为良好 |
| 影响用户数 | 受崩溃影响的用户数 | 越少越好 |
| 无崩溃会话比例 | 没有崩溃的会话占比 | > 99% 为良好 |

**崩溃率等级：**

| 等级 | 崩溃率 | 说明 | 行动 |
|:----:|:------:|------|------|
| 🟢 优秀 | < 0.1% | 几乎不崩溃 | 保持 |
| 🟢 良好 | 0.1% - 0.5% | 偶尔崩溃 | 关注 |
| 🟡 一般 | 0.5% - 1% | 有一定崩溃 | 需要优化 |
| 🟠 较差 | 1% - 5% | 崩溃较多 | 必须修复 |
| 🔴 严重 | > 5% | 严重影响用户 | 紧急修复 |

**优先级排序：**

| 优先级 | 排序依据 | 说明 |
|:------:|----------|------|
| 1 | 崩溃率 × 影响用户数 | 综合影响最大的排最前 |
| 2 | 是否影响核心功能 | 核心功能崩溃优先修复 |
| 3 | 是否为新引入的崩溃 | 新版本引入的崩溃优先处理 |
| 4 | 修复难度 | 简单修复可以先做 |

💡 **提示**：崩溃率是 App 质量的"体温计"。建议每天查看一次崩溃率，如果某天崩溃率突然升高，说明新版本可能引入了问题，需要立即排查。

## 小结

本章涵盖了 App 上架后的运营和迭代知识，核心要点总结如下：

| 知识点 | 核心要点 |
|--------|----------|
| 上架后第一件事 | 监控崩溃、关注评论、自测线上版本 |
