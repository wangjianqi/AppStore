# 分阶段发布与版本回退

> 🎯 **本章目标**：掌握 App Store 分阶段发布（Phased Release）的配置和管理，学会在紧急情况下处理版本回退，保障线上 App 的稳定性。

---

## 分阶段发布（Phased Release）概述

### 什么是分阶段发布

分阶段发布（Phased Release）是 Apple 在 2017 年推出的一项 App Store 功能，允许开发者将 App 更新逐步推送给用户，而不是一次性推送给所有用户。

**核心机制：7 天自动推送**

当你启用分阶段发布后，Apple 会在 7 天内按照预设的百分比逐步将更新推送给用户：

| 天数 | 推送百分比 | 累计覆盖 | 说明 |
|:----:|:----------:|:--------:|------|
| 第 1 天 | 1% | 1% | 极小范围验证，发现严重问题的窗口 |
| 第 2 天 | 2% | 3% | 继续小范围扩展 |
| 第 3 天 | 5% | 8% | 逐步增加覆盖 |
| 第 4 天 | 10% | 18% | 覆盖近五分之一用户 |
| 第 5 天 | 20% | 38% | 覆盖近四成用户 |
| 第 6 天 | 50% | 88% | 大范围覆盖 |
| 第 7 天 | 剩余 100% | 100% | 全量推送 |

> 💡 **提示**：分阶段发布只适用于**自动更新**的用户。手动更新的用户可以随时在 App Store 搜索并更新到最新版本，不受分阶段发布限制。

### 为什么需要分阶段发布

| 场景 | 不分阶段的风险 | 分阶段的好处 |
|------|---------------|-------------|
| 大版本重构 | Bug 影响全部用户 | 只影响 1% 用户时就能发现问题 |
| 新功能上线 | 新功能崩溃导致全面差评 | 小范围验证后逐步放开 |
| 核心逻辑变更 | 数据迁移失败影响所有人 | 少量用户出问题时及时止损 |
| 第三方 SDK 升级 | SDK 不兼容导致大面积崩溃 | 提前发现兼容性问题 |
| UI 大改版 | 用户不适应导致差评潮 | 逐步让用户适应 |

### 分阶段发布 vs 立即发布

| 对比维度 | 分阶段发布 | 立即发布 |
|----------|-----------|---------|
| **推送速度** | 7 天逐步推送 | 立即全量推送 |
| **风险控制** | ✅ 可在早期发现问题 | ❌ 出问题影响全部用户 |
| **暂停能力** | ✅ 可暂停发布 | ❌ 无法撤回 |
| **适用场景** | 大版本更新、核心变更 | 小修复、紧急补丁 |
| **用户手动更新** | 不受限制，可手动更新 | 不受限制 |
| **审核时间** | 不影响 | 不影响 |

> ⚠️ **警告**：分阶段发布**仅适用于 App 更新**，不适用于首次上架的 App。首次上架的 App 会立即对所有用户可见。

## 配置分阶段发布

### App Store Connect 设置步骤

在 App Store Connect 中配置分阶段发布非常简单：

| 步骤 | 操作 | 说明 |
|:----:|------|------|
| 1 | 登录 App Store Connect | https://appstoreconnect.apple.com |
| 2 | 进入"我的 App" | 选择目标 App |
| 3 | 选择新版本 | 在左侧选择待发布的版本 |
| 4 | 滚动到"分阶段发布"区域 | 在版本信息页面下方 |
| 5 | 选择"使用分阶段发布" | 默认是"立即发布" |
| 6 | 确认发布 | 点击"发布"按钮 |

**App Store Connect 界面示意：**

```text
┌─────────────────────────────────────────────┐
│  版本发布方式                                │
│                                             │
│  ○ 立即发布                                 │
│    将更新立即推送给所有用户                    │
│                                             │
│  ● 使用分阶段发布                            │
│    在 7 天内逐步将更新推送给用户               │
│                                             │
│    ┌─────────────────────────────────────┐  │
│    │ 第1天: 1%  第2天: 2%  第3天: 5%     │  │
│    │ 第4天: 10% 第5天: 20% 第6天: 50%    │  │
│    │ 第7天: 100%                          │  │
│    └─────────────────────────────────────┘  │
│                                             │
│              [发布]                          │
└─────────────────────────────────────────────┘
```

### 通过 API 配置分阶段发布

Apple 提供了 App Store Connect API，可以通过编程方式管理分阶段发布：

```swift
import Foundation

struct ASCApiManager {
    let apiKeyId: String
    let issuerId: String
    let privateKey: String
    let baseUrl = "https://api.appstoreconnect.apple.com/v1"

    func enablePhasedRelease(for buildId: String) async throws {
        let url = URL(string: "\(baseUrl)/appStoreVersionPhasedReleases")!
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        request.setValue("Bearer \(try generateJWT())", forHTTPHeaderField: "Authorization")

        let body: [String: Any] = [
            "data": [
                "type": "appStoreVersionPhasedReleases",
                "relationships": [
                    "appStoreVersion": [
                        "data": [
                            "type": "appStoreVersions",
                            "id": buildId
                        ]
                    ]
                ]
            ]
        ]

        request.httpBody = try JSONSerialization.data(withJSONObject: body)
        let (_, response) = try await URLSession.shared.data(for: request)

        guard let httpResponse = response as? HTTPURLResponse,
              (200...299).contains(httpResponse.statusCode) else {
            throw PhasedReleaseError.enableFailed
        }
    }

    private func generateJWT() throws -> String {
        // JWT 生成逻辑
        // Header: {"alg": "ES256", "kid": apiKeyId, "typ": "JWT"}
        // Payload: {"iss": issuerId, "exp": expiration, "aud": "appstoreconnect-v1"}
        fatalError("实现 JWT 生成逻辑")
    }
}

enum PhasedReleaseError: Error {
    case enableFailed
    case pauseFailed
    case resumeFailed
}
```

### 分阶段发布状态查询

通过 API 查询当前分阶段发布的状态：

```swift
extension ASCApiManager {
    func getPhasedReleaseStatus(for versionId: String) async throws -> PhasedReleaseStatus {
        let urlString = "\(baseUrl)/appStoreVersions/\(versionId)/appStoreVersionPhasedRelease"
        let url = URL(string: urlString)!
        var request = URLRequest(url: url)
        request.setValue("Bearer \(try generateJWT())", forHTTPHeaderField: "Authorization")

        let (data, response) = try await URLSession.shared.data(for: request)

        guard let httpResponse = response as? HTTPURLResponse,
              (200...299).contains(httpResponse.statusCode) else {
            throw PhasedReleaseError.queryFailed
        }

        let json = try JSONSerialization.jsonObject(with: data) as! [String: Any]
        let attributes = json["data"]?["attributes"] as! [String: Any]
        let phase = attributes["currentDayNumber"] as! Int
        let state = attributes["phasedReleaseState"] as! String

        return PhasedReleaseStatus(
            currentDay: phase,
            state: PhasedReleaseState(rawValue: state) ?? .inactive
        )
    }
}

struct PhasedReleaseStatus {
    let currentDay: Int
    let state: PhasedReleaseState
}

enum PhasedReleaseState: String {
    case inactive = "INACTIVE"
    case active = "ACTIVE"
    case paused = "PAUSED"
    case complete = "COMPLETE"
}
```

## 各阶段百分比和暂停/恢复

### 阶段百分比详解

分阶段发布的每个阶段都有固定的推送比例，开发者**不能自定义百分比**：

| 阶段 | 天数 | 新增推送 | 累计覆盖 | 关键观察点 |
|:----:|:----:|:--------:|:--------:|-----------|
| 1 | 第 1 天 | 1% | 1% | 启动崩溃、核心功能可用性 |
| 2 | 第 2 天 | 2% | 3% | 崩溃率趋势、用户反馈 |
| 3 | 第 3 天 | 5% | 8% | 性能指标、ANR 率 |
| 4 | 第 4 天 | 10% | 18% | 评分变化、评论趋势 |
| 5 | 第 5 天 | 20% | 38% | 功能使用率、转化率 |
| 6 | 第 6 天 | 50% | 88% | 服务器负载、API 调用量 |
| 7 | 第 7 天 | 12% | 100% | 全面稳定性确认 |

> 💡 **提示**：前 3 天（累计 8%）是最关键的观察窗口。如果在这期间没有发现严重问题，后续阶段出大问题的概率会显著降低。

### 暂停分阶段发布

在分阶段发布过程中，如果你发现了问题，可以**暂停**发布：

**在 App Store Connect 中暂停：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 进入 App Store Connect → 我的 App |
| 2 | 选择当前正在分阶段发布的版本 |
| 3 | 在"分阶段发布"区域点击"暂停" |
| 4 | 确认暂停操作 |

**暂停后的效果：**

| 效果 | 说明 |
|------|------|
| 停止新用户自动更新 | 已覆盖百分比的用户不受影响 |
| 已更新用户不会回退 | 暂停不会让已更新的用户降级 |
| 手动更新仍可用 | 用户仍可手动搜索更新 |
| 可以恢复发布 | 修复问题后可以恢复 |

**通过 API 暂停：**

```swift
extension ASCApiManager {
    func pausePhasedRelease(for phasedReleaseId: String) async throws {
        let urlString = "\(baseUrl)/appStoreVersionPhasedReleases/\(phasedReleaseId)"
        let url = URL(string: urlString)!
        var request = URLRequest(url: url)
        request.httpMethod = "PATCH"
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        request.setValue("Bearer \(try generateJWT())", forHTTPHeaderField: "Authorization")

        let body: [String: Any] = [
            "data": [
                "type": "appStoreVersionPhasedReleases",
                "id": phasedReleaseId,
                "attributes": [
                    "phasedReleaseState": "PAUSED"
                ]
            ]
        ]

        request.httpBody = try JSONSerialization.data(withJSONObject: body)
        let (_, response) = try await URLSession.shared.data(for: request)

        guard let httpResponse = response as? HTTPURLResponse,
              (200...299).contains(httpResponse.statusCode) else {
            throw PhasedReleaseError.pauseFailed
        }
    }
}
```

### 恢复分阶段发布

暂停后，当你确认问题已解决或不需要处理时，可以恢复发布：

**在 App Store Connect 中恢复：**

| 步骤 | 操作 |
|:----:|------|
| 1 | 进入 App Store Connect → 我的 App |
| 2 | 选择当前暂停的版本 |
| 3 | 在"分阶段发布"区域点击"继续" |
| 4 | 确认恢复操作 |

> ⚠️ **警告**：恢复发布后，分阶段发布会从暂停时的阶段继续，**不会重新开始**。例如，在第 3 天暂停，恢复后从第 4 天继续。

### 完全停止分阶段发布

如果你想完全停止分阶段发布，让所有用户立即收到更新：

| 歈骤 | 操作 |
|:----:|------|
| 1 | 进入 App Store Connect → 我的 App |
| 2 | 选择当前分阶段发布的版本 |
| 3 | 在"分阶段发布"区域点击"立即发布" |
| 4 | 确认操作 |

> ⚠️ **警告**：此操作**不可逆**！一旦选择立即发布，所有用户将自动更新到新版本，无法再回到分阶段发布模式。

## 分阶段发布的适用场景和策略

### 适合使用分阶段发布的场景

| 场景 | 推荐程度 | 原因 |
|------|:--------:|------|
| 大版本更新（x.0.0） | ⭐⭐⭐⭐⭐ | 变更量大，风险高 |
| 核心业务逻辑重构 | ⭐⭐⭐⭐⭐ | 影响面广，需要验证 |
| 数据库/数据模型迁移 | ⭐⭐⭐⭐⭐ | 数据丢失风险高 |
| 第三方 SDK 大版本升级 | ⭐⭐⭐⭐ | 兼容性不确定 |
| UI 大改版 | ⭐⭐⭐⭐ | 用户适应期 |
| 新功能上线 | ⭐⭐⭐ | 需要验证稳定性 |
| 后端 API 变更 | ⭐⭐⭐ | 需要验证兼容性 |

### 不需要分阶段发布的场景

| 场景 | 推荐程度 | 原因 |
|------|:--------:|------|
| 紧急 Bug 修复 | ❌ | 需要尽快推送给所有用户 |
| 安全漏洞修补 | ❌ | 安全问题需要立即覆盖 |
| 小的 UI 调整 | ❌ | 风险极低，无需分阶段 |
| 文案修改 | ❌ | 几乎无风险 |
| 审核被拒后的小修改 | ❌ | 需要尽快重新上架 |

### 分阶段发布策略矩阵

根据变更类型和影响范围，选择合适的发布策略：

```text
                    影响范围小                    影响范围大
                ┌─────────────────┬─────────────────┐
  变更风险低    │   立即发布       │   分阶段发布      │
                │   (快速迭代)     │   (3天观察即可)   │
                ├─────────────────┼─────────────────┤
  变更风险高    │   分阶段发布     │   分阶段发布      │
                │   (5天观察)      │   (全程7天观察)   │
                └─────────────────┴─────────────────┘
```

### 分阶段发布配合测试的策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| TestFlight → 分阶段发布 | 先在 TestFlight 充分测试，再分阶段发布 | 所有场景 |
| 分阶段发布 + Feature Flag | 分阶段发布的同时用 Feature Flag 控制新功能 | 新功能上线 |
| 分阶段发布 + A/B 测试 | 结合 A/B 测试验证新功能效果 | 产品决策 |
| 分阶段发布 + 监控告警 | 设置崩溃率告警，超过阈值自动暂停 | 高风险变更 |

## 紧急修复：Expedited Review 请求

### 什么是加急审核

加急审核（Expedited Review）是 Apple 提供的一种特殊审核通道，允许开发者在紧急情况下请求 Apple 加快审核速度。正常审核可能需要 24-48 小时，加急审核通常在几小时内完成。

### 适用场景

| 场景 | 是否适合加急审核 | 说明 |
|------|:----------------:|------|
| 线上严重崩溃 | ✅ | 影响大量用户的启动崩溃 |
| 安全漏洞 | ✅ | 存在被利用的安全风险 |
| 法律合规问题 | ✅ | 需要立即修改的合规问题 |
| 侵权问题 | ✅ | 收到侵权通知需要立即处理 |
| 功能小优化 | ❌ | 不属于紧急情况 |
| 营销活动配合 | ❌ | 应提前规划 |
| 审核被拒后修改 | ❌ | 正常审核即可 |
| 想快点上线 | ❌ | 不是正当理由 |

> ⚠️ **警告**：Apple 对加急审核的审批非常严格。滥用加急审核可能导致后续请求被拒绝。建议每年使用不超过 2-3 次。

### 请求加急审核的步骤

| 步骤 | 操作 | 说明 |
|:----:|------|------|
| 1 | 提交新版本到 App Store Connect | 正常提审流程 |
| 2 | 进入 App Store Connect 帮助中心 | 点击右上角"？"图标 |
| 3 | 选择"联系我们" | Contact Us |
| 4 | 选择"App 审核" → "加急审核请求" | Expedited App Review |
| 5 | 填写请求表单 | 说明紧急原因 |
| 6 | 提交请求 | 等待 Apple 回复 |

**请求表单填写要点：**

| 字段 | 填写建议 |
|------|----------|
| App 名称 | 填写完整 App 名称 |
| Apple ID | 填写 App 的 Apple ID |
| 版本号 | 填写需要加急审核的版本号 |
| 紧急原因 | 用英文简明扼要说明，附上证据 |
| 影响范围 | 说明受影响的用户数量和严重程度 |

**紧急原因模板（英文）：**

```text
Subject: Expedited Review Request - Critical Crash Fix

Dear App Review Team,

We are requesting an expedited review for version X.X.X of our app
[App Name] (Apple ID: XXXXXXXXX).

Reason: A critical crash is affecting approximately XX% of our users
upon app launch. The crash occurs on iOS XX when [specific condition].

This update fixes the crash by [brief description of the fix].

Crash report reference: [Firebase/Crashlytics crash ID]

We have verified the fix through extensive testing on TestFlight
with XX beta testers.

Thank you for your consideration.
```

### 加急审核的注意事项

| 注意事项 | 说明 |
|----------|------|
| 不是所有请求都会被批准 | Apple 会根据紧急程度判断 |
| 审核标准不会降低 | 加急审核的标准和正常审核一样 |
| 不要频繁请求 | 一年最多 2-3 次 |
| 提供充分证据 | 崩溃日志、用户反馈截图等 |
| 英文沟通更高效 | Apple 审核团队主要使用英文 |
| 加急审核 + 分阶段发布 | 可以同时使用，先加急通过再分阶段发布 |

## 版本回退策略

### App Store 没有直接回退功能

这是很多开发者不知道的一个重要事实：**App Store 不支持直接回退到之前的版本**。一旦新版本发布，你无法让用户自动降级到旧版本。

| 操作 | 是否支持 | 说明 |
|------|:--------:|------|
| 暂停分阶段发布 | ✅ | 停止新用户自动更新 |
| 回退到上一版本 | ❌ | App Store 不支持 |
| 下架当前版本 | ❌ | 无法单独下架某个版本 |
| 让已更新用户降级 | ❌ | 用户只能通过更新来改变版本 |

> ⚠️ **警告**：这是 App Store 的硬性限制，没有任何方法可以绕过。所以预防远比补救重要。

### 版本回退的替代方案

既然不能直接回退，我们需要采用替代方案：

```text
┌──────────────────────────────────────────────────────────┐
│                    版本出问题后的应对策略                    │
│                                                          │
│  ┌──────────────┐                                        │
│  │ 发现问题      │                                        │
│  └──────┬───────┘                                        │
│         │                                                │
│         ▼                                                │
│  ┌──────────────┐     是                                 │
│  │ 还在分阶段？  │────────► 暂停分阶段发布                  │
│  └──────┬───────┘                                        │
│         │ 否                                              │
│         ▼                                                │
│  ┌──────────────┐     是                                 │
│  │ 有Feature Flag│───────► 关闭问题功能                    │
│  └──────┬───────┘                                        │
│         │ 否                                              │
│         ▼                                                │
│  ┌──────────────┐                                        │
│  │ 紧急修复版本  │───────► 提交新版本 + 加急审核             │
│  └──────────────┘                                        │
└──────────────────────────────────────────────────────────┘
```

### 替代方案对比

| 方案 | 响应速度 | 影响范围 | 实现难度 | 适用场景 |
|------|:--------:|:--------:|:--------:|----------|
| 暂停分阶段发布 | 分钟级 | 阻止新用户更新 | ⭐ | 分阶段发布中 |
| Feature Flag 关闭功能 | 分钟级 | 所有用户 | ⭐⭐⭐ | 有远程开关的功能 |
| 服务端降级 | 分钟级 | 所有用户 | ⭐⭐ | 后端可控的逻辑 |
| 紧急修复新版本 | 小时~天级 | 所有用户 | ⭐⭐ | 任何场景 |
| 引导用户手动降级 | 不可行 | — | — | App Store 不支持 |

## 降级方案：新版本修复与 Feature Flag 控制

### 方案一：提交紧急修复版本

这是最直接的方案——修复 Bug 后提交新版本。

**紧急修复版本流程：**

| 步骤 | 操作 | 时间 |
|:----:|------|:----:|
| 1 | 定位 Bug 根因 | 1-2 小时 |
| 2 | 编写修复代码 | 1-3 小时 |
| 3 | 本地验证修复 | 30 分钟 |
| 4 | TestFlight 快速验证 | 30 分钟 |
| 5 | 提交审核 + 请求加急审核 | 30 分钟 |
| 6 | 等待审核通过 | 2-12 小时 |
| 7 | 启用分阶段发布 | — |

**紧急修复版本的注意事项：**

| 注意事项 | 说明 |
|----------|------|
| 只修复关键 Bug | 不要在紧急版本中加入其他改动 |
| 版本号递增 | 使用新的版本号，不能和已发布版本重复 |
| 充分测试 | 即使紧急也要充分测试，避免引入新 Bug |
| 请求加急审核 | 同时提交加急审核请求 |
| 使用分阶段发布 | 修复版本也建议使用分阶段发布 |

### 方案二：Feature Flag 控制

Feature Flag（功能开关）是一种更优雅的降级方案，允许你远程控制功能的开启和关闭，无需发布新版本。

**Feature Flag 架构：**

```swift
import Foundation

final class FeatureFlagManager: ObservableObject {
    static let shared = FeatureFlagManager()

    @Published private(set) var flags: [String: Bool] = [:]

    private let serverURL = "https://api.yourapp.com/feature-flags"

    func fetchFlags() async {
        guard let url = URL(string: serverURL) else { return }

        do {
            let (data, _) = try await URLSession.shared.data(from: url)
            let decoded = try JSONDecoder().decode([String: Bool].self, from: data)
            await MainActor.run {
                self.flags = decoded
            }
        } catch {
            print("Feature flags fetch failed: \(error)")
        }
    }

    func isEnabled(_ feature: Feature) -> Bool {
        flags[feature.rawValue] ?? feature.defaultValue
    }

    func setFlag(_ feature: Feature, enabled: Bool) {
        flags[feature.rawValue] = enabled
    }
}

enum Feature: String, CaseIterable {
    case newDashboard
    case aiRecommendation
    case socialSharing
    case premiumOnboarding
    case newPaymentFlow

    var defaultValue: Bool {
        switch self {
        case .newDashboard: return true
        case .aiRecommendation: return false
        case .socialSharing: return true
        case .premiumOnboarding: return false
        case .newPaymentFlow: return true
        }
    }

    var description: String {
        switch self {
        case .newDashboard: return "新版仪表盘"
        case .aiRecommendation: return "AI 推荐功能"
        case .socialSharing: return "社交分享"
        case .premiumOnboarding: return "付费引导"
        case .newPaymentFlow: return "新支付流程"
        }
    }
}
```

**在 SwiftUI 中使用 Feature Flag：**

```swift

            LegacyDashboardView()
        }
    }
}
```

### 方案三：服务端降级

对于依赖后端 API 的功能，可以通过服务端控制实现降级：

```swift
struct APIConfig {
    static var useNewAPI: Bool {
        get async {
            guard let url = URL(string: "https://api.yourapp.com/config") else {
                return false
            }
            do {
                let (data, _) = try await URLSession.shared.data(from: url)
                let config = try JSONDecoder().decode(ServerConfig.self, from: data)
                return config.useNewAPI
            } catch {
                return false
            }
        }
    }
}

struct ServerConfig: Codable {
    let useNewAPI: Bool
    let maintenanceMode: Bool
    let fallbackAPIURL: String?
    let maxSupportedVersion: String?
}
```

### 三种降级方案对比

| 对比维度 | 紧急修复版本 | Feature Flag | 服务端降级 |
|----------|:----------:|:------------:|:----------:|
| 响应速度 | 小时~天级 | 分钟级 | 分钟级 |
| 需要审核 | ✅ 需要 | ❌ 不需要 | ❌ 不需要 |
| 实现成本 | ⭐ 低 | ⭐⭐⭐ 高 | ⭐⭐ 中 |
| 适用范围 | 任何 Bug | 功能级控制 | API 级控制 |
| 前置要求 | 无 | 需要提前集成 | 需要后端支持 |
| 推荐程度 | 所有场景 | 中大型项目 | 有后端的项目 |

> 💡 **提示**：最佳实践是**三种方案结合使用**。日常开发中集成 Feature Flag，上线时使用分阶段发布，出问题时先通过 Feature Flag 或服务端降级，同时准备紧急修复版本。

### 自动化告警

设置自动化告警，当关键指标超过阈值时立即通知：

```swift
import Foundation

final class ReleaseAlertManager {
    private let crashRateThreshold: Double = 0.01
    private let anrRateThreshold: Double = 0.005
    private let ratingThreshold: Double = 3.5

    func checkAlerts(metrics: PhasedReleaseMonitor) -> [ReleaseAlert] {
        var alerts: [ReleaseAlert] = []

        if metrics.crashRate > crashRateThreshold {
            alerts.append(ReleaseAlert(
                type: .crashRateHigh,
                severity: .critical,
                message: "崩溃率 \(String(format: "%.2f%%", metrics.crashRate * 100)) 超过阈值 \(String(format: "%.2f%%", crashRateThreshold * 100))",
                recommendation: "建议立即暂停分阶段发布"
            ))
        }

        if metrics.anrRate > anrRateThreshold {
            alerts.append(ReleaseAlert(
                type: .anrRateHigh,
                severity: .warning,
                message: "ANR 率 \(String(format: "%.2f%%", metrics.anrRate * 100)) 超过阈值",
                recommendation: "建议密切观察性能指标"
            ))
        }

        if metrics.averageRating < ratingThreshold && metrics.newReviewsCount > 10 {
            alerts.append(ReleaseAlert(
                type: .ratingDrop,
                severity: .warning,
                message: "平均评分 \(String(format: "%.1f", metrics.averageRating)) 低于阈值 \(ratingThreshold)",
                recommendation: "建议查看差评内容并评估影响"
            ))
        }

        return alerts
    }
}

struct ReleaseAlert {
    let type: AlertType
    let severity: AlertSeverity
    let message: String
    let recommendation: String
}

enum AlertType {
    case crashRateHigh
    case anrRateHigh
    case ratingDrop
    case negativeReviewSpike
}

enum AlertSeverity {
    case warning
    case critical
}
```

```swift
        default:
            throw MigrationError.unsupportedVersion

            "转换旧格式日期数据",

            try executeMigrationStep(step)
        }
```

## 分阶段发布常见问题

### FAQ

| 问题 | 回答 |
|------|------|
| 分阶段发布可以自定义百分比吗？ | ❌ 不可以，Apple 固定了 7 天的百分比 |
| 手动更新的用户受影响吗？ | ❌ 不受影响，用户可以随时手动更新 |
| 分阶段发布期间可以提交新版本吗？ | ✅ 可以，但建议等当前版本全量发布后再提交 |
| 暂停后恢复会从头开始吗？ | ❌ 不会，从暂停时的阶段继续 |
| 首次上架可以用分阶段发布吗？ | ❌ 不可以，只有更新版本才能使用 |
| 分阶段发布影响审核速度吗？ | ❌ 不影响，审核通过后才开始分阶段发布 |
| 可以中途改为立即发布吗？ | ✅ 可以，但不可逆 |
| 已更新的用户会回退吗？ | ❌ 不会，暂停只阻止新的自动更新 |
| 分阶段发布有额外费用吗？ | ❌ 没有，完全免费 |
| macOS App 支持分阶段发布吗？ | ✅ 支持 |

### 常见错误和避免方法

| 错误 | 后果 | 避免方法 |
|------|------|----------|
| 不使用分阶段发布直接全量 | 出问题影响所有用户 | 大版本更新必须使用分阶段发布 |
| 分阶段发布期间不监控 | 问题扩散才发现 | 设置告警，每天检查指标 |
| 暂停后不及时处理 | 用户持续受影响 | 暂停后立即制定修复方案 |
| 加急审核滥用 | 后续请求被拒绝 | 只在真正紧急时使用 |
| 不准备降级方案 | 出问题只能干等 | 提前集成 Feature Flag |
| 分阶段发布中加入太多改动 | 难以定位问题来源 | 每次发布控制变更范围 |

## 本章小结

本章详细介绍了 App Store 分阶段发布（Phased Release）的完整流程和最佳实践：

| 知识点 | 要点 |
|--------|------|
| 分阶段发布机制 | 7 天自动推送，1% → 2% → 5% → 10% → 20% → 50% → 100% |
| 配置方法 | App Store Connect 或 API 设置 |
| 暂停/恢复 | 可暂停分阶段发布，恢复后从暂停处继续 |
| 加急审核 | 紧急情况可请求加急审核，但不要滥用 |
| 版本回退 | App Store 不支持直接回退，需要替代方案 |
| Feature Flag | 远程控制功能开关，无需发版即可降级 |
| 灰度发布最佳实践 | 发布前检查 + 发布中监控 + 发布后复盘 |
| 监控指标 | 崩溃率、ANR 率、评分、用户反馈 |

**核心原则：预防胜于补救。分阶段发布是你的安全网，Feature Flag 是你的降落伞。**

> 💡 **提示**：对于独立开发者来说，即使你的 App 用户量不大，也建议在大版本更新时使用分阶段发布。养成这个习惯，当你的用户量增长后，你会感谢自己。
