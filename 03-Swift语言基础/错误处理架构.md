# 错误处理架构

> 🎯 **本章目标**：掌握系统化的错误处理架构设计，学会领域错误分层与跨层映射，理解错误恢复策略，建立全局错误处理与上报机制，能够设计用户友好的错误展示架构。

---

## 为什么需要错误处理架构

Swift 提供了 `throw`、`try`、`catch` 和 `Result` 等错误处理语法，这些是语言层面的基础设施。但在真实工程中，仅有语法远远不够——你需要一套**系统化的错误处理架构**，让错误从发生到展示的整个链路清晰可控。

### 没有架构的痛点

当项目缺少统一的错误处理架构时，常见问题会逐步积累：

| 痛点 | 表现 | 后果 |
|------|------|------|
| 错误被吞 | `catch { }` 空捕获、`try?` 静默忽略 | 问题难以排查，用户反馈无法复现 |
| 日志丢失 | 各处自行 `print`，格式不统一 | 线上问题无法追踪，关键信息缺失 |
| 技术性文案暴露 | 直接将 `error.localizedDescription` 展示给用户 | 用户体验差，甚至泄露敏感信息 |
| 重复处理 | 同类错误在不同页面有不同处理逻辑 | 维护成本高，行为不一致 |
| 恢复策略缺失 | 出错后只能关闭页面或重启 App | 用户流失，可恢复错误变成致命错误 |

### 错误处理架构的核心原则

一套成熟的错误处理架构应遵循四个核心原则：

1. **分层（Layering）**：错误按所属层级定义，底层错误不直接暴露给上层
2. **映射（Mapping）**：跨层传递时，错误必须经过映射转换，保证每层只看到自己关心的错误
3. **恢复（Recovery）**：不是所有错误都需要中断流程，架构应支持自动重试、降级等恢复策略
4. **友好（Friendly）**：最终呈现给用户的信息必须是可理解的、有引导性的

> 💡 **提示**：错误处理架构不是"过度设计"。在一个 10 个页面的 App 中，你可能感受不到它的价值；但当项目增长到 50+ 页面、多人协作时，统一的错误架构能节省大量调试和沟通成本。

## 领域错误分层

### 三层错误模型

在 iOS 应用中，推荐使用三层错误模型，将错误按职责分层：

```
┌─────────────────────────────────┐
│          UIError                │  ← 面向用户的展示层
├─────────────────────────────────┤
│         DomainError            │  ← 业务领域层
├─────────────────────────────────┤
│        NetworkError             │  ← 底层网络/数据层
└─────────────────────────────────┘
```

每一层只关心自己的错误类型，层与层之间通过映射函数转换。

### NetworkError 层

底层网络和数据错误，描述技术层面的失败原因：

```swift
enum NetworkError: Error {
    case invalidURL(String)
    case requestFailed(HTTPStatusCode)
    case timeout
    case noConnection
    case decodingFailed(Error)
    case serverError(Int, String)
    case unauthorized
}

enum HTTPStatusCode: Int {
    case badRequest = 400
    case unauthorized = 401
    case forbidden = 403
    case notFound = 404
    case internalServerError = 500
    case serviceUnavailable = 503
}
```

### DomainError 层

业务领域错误，将底层技术错误转换为业务语义：

```swift
enum DomainError: Error {
    case loginFailed(reason: LoginFailureReason)
    case contentNotFound(identifier: String)
    case contentLoadFailed(identifier: String)
    case operationForbidden(feature: String)
    case sessionExpired
    case dataSyncFailed(context: String)
    case quotaExceeded(limit: Int)

    enum LoginFailureReason {
        case invalidCredentials
        case accountLocked
        case networkUnavailable
        case serverBusy
    }
}
```

### UIError 层

面向用户的展示错误，只包含用户可理解的信息和操作引导：


### 跨层错误映射

映射是分层架构的关键。每层定义从下层错误到本层错误的映射规则：

```swift
extension DomainError {
    init(networkError: NetworkError) {
        switch networkError {
        case .unauthorized:
            self = .sessionExpired
        case .noConnection, .timeout:
            self = .loginFailed(reason: .networkUnavailable)
        case .serverError(503, _):
            self = .loginFailed(reason: .serverBusy)
        case .requestFailed(let code) where code == .forbidden:
            self = .operationForbidden(feature: "default")
        case .notFound:
            self = .contentNotFound(identifier: "unknown")
        default:
            self = .dataSyncFailed(context: networkError.localizedDescription)
        }
    }
}

extension UIError {
    init(domainError: DomainError) {
        switch domainError {
        case .loginFailed(let reason):
            switch reason {
            case .invalidCredentials:
                self = UIError(
                    title: "登录失败",
                    message: "用户名或密码不正确，请重新输入",

                    actions: [.dismiss]

            case .accountLocked:
                self = UIError(
                    title: "账户已锁定",
                    message: "多次输入错误密码，账户已被临时锁定，请30分钟后重试",
                    icon: "lock.fill",

                )
            case .networkUnavailable:
                self = UIError(
                    title: "网络不可用",
                    message: "请检查网络连接后重试",
                    icon: "wifi.exclamationmark",
                    actions: [.retry, .dismiss]

            case .serverBusy:
                self = UIError(

        case .contentNotFound:

            self = UIError(
                title: "已达上限",
                message: "当前限额为 \(limit) 次，请升级套餐或稍后重试",
                icon: "exclamationmark.shield",
                actions: [.dismiss]
            )
        }
    }
}
```

### 完整映射流程

```swift
class ContentRepository {
    private let apiClient: APIClient

    func loadContent(id: String) async -> Result<Content, DomainError> {
        let result = await apiClient.request(.content(id: id))
        switch result {
        case .success(let data):
            do {
                let content = try JSONDecoder().decode(Content.self, from: data)
                return .success(content)
            } catch {
                return .failure(.contentLoadFailed(identifier: id))
            }
        case .failure(let networkError):
            return .failure(DomainError(networkError: networkError))
        }
    }
}

class ContentViewModel: ObservableObject {
    @Published var content: Content?
    @Published var uiError: UIError?

    private let repository: ContentRepository

    func loadContent(id: String) async {
        let result = await repository.loadContent(id: id)
        switch result {
        case .success(let content):
            self.content = content
            self.uiError = nil
        case .failure(let domainError):
            self.uiError = UIError(domainError: domainError)
        }
    }
}
```

> 💡 **提示**：映射函数使用 `init` 而非静态方法，这样可以在调用处写出更自然的 `DomainError(networkError:)` 语法，语义清晰。

## 错误恢复策略

错误处理的最高境界不是"告诉用户出错了"，而是"自动恢复，用户无感知"。对于无法自动恢复的错误，则应提供明确的用户操作路径。

### 重试策略

对于网络波动、服务端临时故障等场景，自动重试是最有效的恢复手段：

```swift
struct RetryPolicy {
    let maxAttempts: Int
    let baseDelay: TimeInterval
    let maximumDelay: TimeInterval
    let jitter: Bool

    static let `default` = RetryPolicy(
        maxAttempts: 3,
        baseDelay: 1.0,
        maximumDelay: 30.0,
        jitter: true
    )

    func delay(for attempt: Int) -> TimeInterval {
        let exponential = baseDelay * pow(2.0, Double(attempt - 1))
        let capped = min(exponential, maximumDelay)
        if jitter {
            return capped * Double.random(in: 0.5...1.5)
        }
        return capped
    }
}

func withRetry<T>(
    policy: RetryPolicy = .default,
    operation: () async throws -> T
) async throws -> T {
    var lastError: Error?
    for attempt in 1...policy.maxAttempts {
        do {
            return try await operation()
        } catch {
            lastError = error
            if attempt < policy.maxAttempts {
                let delay = policy.delay(for: attempt)
                try await Task.sleep(nanoseconds: UInt64(delay * 1_000_000_000))
            }
        }
    }
    throw lastError!
}
```

### 降级策略

当主路径失败时，降级到备选方案：

```swift
class ContentDataService {
    private let apiClient: APIClient
    private let cache: ContentCache

    func loadContent(id: String) async -> Result<Content, DomainError> {
        let result = await apiClient.fetchContent(id: id)
        switch result {
        case .success(let content):
            cache.store(content, forKey: id)
            return .success(content)
        case .failure:
            if let cached = cache.retrieve(forKey: id) {
                return .success(cached)
            }
            return .failure(.contentLoadFailed(identifier: id))
        }
    }
}

class FeatureFlagService {
    private let remoteProvider: RemoteFeatureFlagProvider
    private let localDefaults: UserDefaults

    func isEnabled(_ feature: String) -> Bool {
        if let remote = remoteProvider.value(for: feature) {
            return remote
        }
        return localDefaults.bool(forKey: "feature_\(feature)")
    }
}
```

### 用户操作策略

对于需要用户介入的错误，提供明确的操作引导：

```swift
extension ErrorAction {

        switch self {
        case .retry: return "重试"

        case .loadCached: return "查看缓存"

    }

        case .retry: return nil
        case .goToSettings: return nil
        case .contactSupport: return nil
        case .loadCached: return nil
        }
    }
```

### 策略选择表

| 错误类型 | 恢复策略 | 用户感知 | 示例 |
|----------|----------|----------|------|
| 网络超时 | 自动重试（指数退避） | 无感知（重试成功时） | 列表加载请求超时 |
| 服务端 5xx | 自动重试 + 缓存降级 | 可能短暂延迟 | 首页数据请求失败 |
| 401 未授权 | 自动刷新 Token 重试 | 无感知 | Token 过期自动续期 |
| 403 禁止访问 | 用户操作（升级权限） | 需要用户决策 | VIP 功能限制 |
| 数据解析失败 | 缓存降级 + 上报 | 显示缓存数据 | 响应格式变更 |
| 无网络连接 | 用户操作（检查网络） | 需要用户介入 | 飞行模式下的请求 |
| 账户锁定 | 用户操作（联系客服） | 需要用户介入 | 多次密码错误 |
| 配额超限 | 用户操作（升级套餐） | 需要用户决策 | 免费用户达到调用上限 |

> ⚠️ **警告**：不要对所有错误都盲目重试。对于业务逻辑错误（如参数校验失败、权限不足），重试只会浪费资源，甚至导致更严重的问题。重试策略应只应用于**可恢复的瞬态错误**。

## 全局错误处理

### 统一错误日志记录

全局错误日志是排查线上问题的关键基础设施：

```swift
protocol ErrorLogger {
    func log(_ error: Error, context: ErrorContext)
}

struct ErrorContext {
    let file: String
    let function: String
    let line: Int
    let timestamp: Date
    let additionalInfo: [String: String]

    static func current(
        file: String = #file,
        function: String = #function,
        line: Int = #line,
        additionalInfo: [String: String] = [:]
    ) -> ErrorContext {
        ErrorContext(
            file: file,
            function: function,
            line: line,
            timestamp: Date(),
            additionalInfo: additionalInfo
        )
    }
}

class DefaultErrorLogger: ErrorLogger {
    func log(_ error: Error, context: ErrorContext) {
        let fileName = (context.file as NSString).lastPathComponent
        print("[ERROR] \(context.timestamp) | \(fileName):\(context.line) \(context.function)")
        print("  Error: \(error)")
        if !context.additionalInfo.isEmpty {
            print("  Context: \(context.additionalInfo)")
        }
    }
}
```

### 错误上报机制

将错误上报到第三方平台，实现线上问题监控：

```swift
protocol ErrorReporter {
    func report(_ error: Error, context: ErrorContext)
}

class CompositeErrorReporter: ErrorReporter {
    private let reporters: [ErrorReporter]

    init(reporters: [ErrorReporter]) {
        self.reporters = reporters
    }

    func report(_ error: Error, context: ErrorContext) {
        reporters.forEach { $0.report(error: error, context: context) }
    }
}

class SentryErrorReporter: ErrorReporter {
    func report(_ error: Error, context: ErrorContext) {
        let extra: [String: Any] = [
            "file": context.file,
            "function": context.function,
            "line": context.line,
        ].merging(context.additionalInfo) { _, new in new }
    }
}

class FirebaseErrorReporter: ErrorReporter {
    func report(_ error: Error, context: ErrorContext) {
        let params: [String: Any] = [
            "error_description": error.localizedDescription,
            "file": context.file,
            "line": context.line,
        ].merging(context.additionalInfo) { _, new in new }
    }
}
```

### 未捕获异常处理

Swift 本身没有"未捕获异常"的概念，但 ObjC 运行时和信号层面的崩溃需要处理：

```swift
class CrashHandler {
    static func install() {
        NSSetUncaughtExceptionHandler { exception in
            let info: [String: String] = [
                "name": exception.name.rawValue,
                "reason": exception.reason ?? "unknown",
                "user_info": String(describing: exception.userInfo),
            ]
            CrashLogStore.shared.save(info)
        }

        signal(SIGABRT) { _ in
            CrashLogStore.shared.save(["signal": "SIGABRT"])
            kill(getpid(), SIGKILL)
        }
    }
}

class CrashLogStore {
    static let shared = CrashLogStore()
    private let defaults = UserDefaults.standard
    private let key = "pending_crash_logs"

    func save(_ log: [String: String]) {
        var logs = defaults.array(forKey: key) as? [[String: String]] ?? []
        logs.append(log)
        defaults.set(logs, forKey: key)
    }

    func consumePendingLogs() -> [[String: String]] {
        let logs = defaults.array(forKey: key) as? [[String: String]] ?? []
        defaults.removeObject(forKey: key)
        return logs
    }
}
```

### SwiftUI 环境中的全局错误处理

在 SwiftUI 中，可以通过环境值和修饰符实现全局错误处理：

```swift
struct ErrorHandlingKey: EnvironmentKey {
    static let defaultValue: (Error) -> Void = { _ in }
}

extension EnvironmentValues {
    var handleError: (Error) -> Void {
        get { self[ErrorHandlingKey.self] }
        set { self[ErrorHandlingKey.self] = newValue }
    }
}

struct ErrorHandlingViewModifier: ViewModifier {
    @State private var currentError: UIError?
    @State private var isPresented = false

    let logger: ErrorLogger
    let reporter: ErrorReporter

    func body(content: Content) -> some View {
        content
            .environment(\.handleError, handleError)
            .alert(
                isPresented: $isPresented,
                error: currentError
            ) {
                if let error = currentError {
                    ForEach(error.actions.indices, id: \.self) { index in
                        Button(
                            error.actions[index].label,
                            role: error.actions[index].role
                        ) {
                            handleAction(error.actions[index])
                        }
                    }
                }
            } message: {
                if let error = currentError {
                    Text(error.message)
                }
            }
    }

    private func handleError(_ error: Error) {
        let context = ErrorContext.current()
        logger.log(error, context: context)
        reporter.report(error, context: context)

        if let domainError = error as? DomainError {
            currentError = UIError(domainError: domainError)
        } else {
            currentError = .unknown
        }
        isPresented = true
    }

    private func handleAction(_ action: ErrorAction) {
        switch action {
        case .goToSettings:
            if let url = URL(string: UIApplication.openSettingsURLString) {
                UIApplication.shared.open(url)
            }
        default:
            break
        }
    }
}

extension View {
    func withErrorHandling(
        logger: ErrorLogger = DefaultErrorLogger(),
        reporter: ErrorReporter = CompositeErrorReporter(reporters: [])
    ) -> some View {
        modifier(ErrorHandlingViewModifier(logger: logger, reporter: reporter))
    }
}
```

### 错误处理中间件

在异步操作链中插入错误处理中间件，统一处理日志、上报和恢复：

```swift
actor ErrorMiddleware {
    private let logger: ErrorLogger
    private let reporter: ErrorReporter
    private let retryPolicy: RetryPolicy

    init(
        logger: ErrorLogger,
        reporter: ErrorReporter,
        retryPolicy: RetryPolicy = .default
    ) {
        self.logger = logger
        self.reporter = reporter
        self.retryPolicy = retryPolicy
    }

    func execute<T>(
        operation: String,
        recoverable: Bool = true,
        work: () async throws -> T
    ) async throws -> T {
        do {
            return try await work()
        } catch {
            let context = ErrorContext.current(additionalInfo: ["operation": operation])
            logger.log(error, context: context)
            reporter.report(error, context: context)

            if recoverable && isRecoverable(error) {
                return try await withRetry(policy: retryPolicy) {
                    try await work()
                }
            }
            throw error
        }
    }

    private func isRecoverable(_ error: Error) -> Bool {
        guard let networkError = error as? NetworkError else { return false }
        switch networkError {
        case .timeout, .noConnection, .serverError:
            return true
        case .unauthorized, .requestFailed, .invalidURL, .decodingFailed:
            return false
        }
    }
}
```

> 💡 **提示**：中间件模式的优势在于"透明"——业务代码只需调用 `try await middleware.execute(operation: "loadContent") { ... }`，日志、上报、重试全部自动完成，无需在每个调用点重复编写。

### 错误展示组件设计

不同严重程度的错误需要不同的展示方式：

| 展示方式 | 适用场景 | 侵入性 | 持续时间 |
|----------|----------|--------|----------|
| Toast | 轻量提示（自动保存失败等） | 低 | 2-3 秒自动消失 |
| Alert | 需要用户确认或操作 | 中 | 用户手动关闭 |
| 内联错误 | 表单字段校验 | 低 | 持续显示直到修正 |
| 全屏错误页 | 页面级加载失败 | 高 | 用户操作后消失 |

### 不同错误类型的展示策略

```swift
class ErrorPresenter {
    static func present(
        _ uiError: UIError,
        in viewController: UIViewController?
    ) {
        guard let viewController = viewController else { return }

        switch determinePresentationStyle(uiError) {
        case .toast:
            presentToast(uiError, in: viewController)
        case .alert:
            presentAlert(uiError, in: viewController)
        case .fullScreen:
            presentFullScreen(uiError, in: viewController)
        }
    }

    private enum PresentationStyle {
        case toast
        case alert
        case fullScreen
    }

    private static func determinePresentationStyle(_ error: UIError) -> PresentationStyle {
        let hasRetryAction = error.actions.contains(.retry)
        let hasMultipleActions = error.actions.count > 1

        if error.actions == [.dismiss] {
            return .toast
        } else if hasMultipleActions || hasRetryAction {
            return .alert
        } else {
            return .fullScreen
        }
    }

    private static func presentToast(_ error: UIError, in vc: UIViewController) {
        let toast = ToastView(
            message: error.message,
            icon: error.icon,
            style: .error
        )
        let hosting = UIHostingController(rootView: toast)
        hosting.view.backgroundColor = .clear
        hosting.view.translatesAutoresizingMaskIntoConstraints = false
        vc.view.addSubview(hosting.view)
        NSLayoutConstraint.activate([
            hosting.view.centerXAnchor.constraint(equalTo: vc.view.centerXAnchor),
            hosting.view.bottomAnchor.constraint(equalTo: vc.view.safeAreaLayoutGuide.bottomAnchor, constant: -20),
        ])
        DispatchQueue.main.asyncAfter(deadline: .now() + 3) {
            hosting.view.removeFromSuperview()
        }
    }

    private static func presentAlert(_ error: UIError, in vc: UIViewController) {
        let alert = UIAlertController(
            title: error.title,
            message: error.message,
            preferredStyle: .alert
        )
        for action in error.actions {
            let alertAction = UIAlertAction(title: action.label, style: .default)
            alert.addAction(alertAction)
        }
        vc.present(alert, animated: true)
    }

    private static func presentFullScreen(_ error: UIError, in vc: UIViewController) {
        let fullScreen = UIHostingController(
            rootView: FullScreenErrorView(uiError: error) { _ in
                vc.dismiss(animated: true)
            }
        )
        fullScreen.modalPresentationStyle = .fullScreen
        vc.present(fullScreen, animated: true)
    }
}
```

> ⚠️ **警告**：永远不要将 `NetworkError.decodingFailed(Swift.DecodingError.keyNotFound(...))` 这类技术性错误信息直接展示给用户。即使你暂时来不及做完整的错误映射，也至少用一个通用的"操作失败，请稍后重试"替代原始错误描述。

## 错误处理最佳实践

### 错误类型设计原则

| 原则 | 说明 | 正确做法 | 错误做法 |
|------|------|----------|----------|
| 语义化 | 错误名称应表达业务含义 | `sessionExpired` | `error401` |
| 携带上下文 | 关联错误信息应作为关联值 | `contentNotFound(id: "abc")` | `contentNotFound` |
| 不可变 | 错误一旦创建不应被修改 | 使用 `enum` / `struct` | 使用 `class` 并修改属性 |
| 可测试 | 错误应可被断言和比较 | `case loginFailed(reason:)` | 嵌套闭包或泛型错误 |
| 最小暴露 | 只暴露当前层需要的错误 | 每层定义自己的错误类型 | 全局共用一个 Error 枚举 |

### 常见反模式

**反模式一：吞错误**

```swift
do {
    try performOperation()
} catch {
}
```

即使当前无法处理错误，也应至少记录日志：

```swift
do {
    try performOperation()
} catch {
    logger.log(error, context: .current())
}
```

**反模式二：过度日志**

```swift
do {
    try performOperation()
} catch {
    print("Error: \(error)")
    print("Error description: \(error.localizedDescription)")
    print("Error localized: \(error.localizedDescription)")
    logger.log(error, context: .current())
    reporter.report(error, context: .current())
}
```

日志和上报应通过中间件统一处理，而非在每个 `catch` 中重复。

**反模式三：技术性文案**

```swift
let message = error.localizedDescription
```

`localizedDescription` 通常包含技术细节（如 "The operation couldn't be completed. ...decodingError"），应通过映射转换为用户友好的文案。

### 错误处理 Checklist

在每次代码审查时，检查以下项目：

- [ ] 所有 `catch` 块都有实际处理（非空捕获）
- [ ] 底层错误不直接暴露给 UI 层
- [ ] 用户看到的错误信息是友好的中文文案
- [ ] 可恢复错误有重试或降级策略
- [ ] 关键错误有日志记录和上报
- [ ] 错误映射覆盖了所有枚举 case
- [ ] 表单校验使用内联错误展示
- [ ] 网络错误区分无连接和超时，给予不同提示
- [ ] Token 过期有自动刷新机制
- [ ] 未捕获异常和信号崩溃有处理

### AI 辅助错误处理

AI 工具在错误处理方面可以发挥重要作用：

**生成错误映射代码**：给定底层错误枚举，让 AI 生成完整的映射函数骨架，确保所有 case 都被覆盖。

**审查错误处理遗漏**：将代码提交给 AI 审查，检查是否存在空 `catch`、未映射的错误、缺失的恢复策略。

**生成本地化文案**：让 AI 根据错误语义生成多语言的友好提示文案，确保用户看到的是自然语言而非技术术语。

**编写错误测试用例**：让 AI 为每个错误路径生成单元测试，确保映射逻辑和恢复策略的正确性。

> 💡 **提示**：使用 AI 生成错误处理代码时，务必检查映射是否完整覆盖了所有 case。AI 有时会遗漏枚举的某些分支，导致编译错误或运行时崩溃。

## 小结

| 知识点 | 核心内容 | 关键要点 |
|--------|----------|----------|
| 错误处理架构必要性 | 语法 ≠ 架构 | 分层、映射、恢复、友好四大原则 |
| 领域错误分层 | NetworkError → DomainError → UIError | 每层定义自己的错误类型，通过映射函数跨层转换 |

| 重试策略 | 指数退避 + 抖动 | 仅用于可恢复的瞬态错误 |
| 降级策略 | 缓存回退、默认值、功能降级 | 主路径失败时的备选方案 |
| 用户操作策略 | 重试按钮、设置引导、联系客服 | 需要用户介入的错误提供明确操作 |
| 全局错误日志 | ErrorLogger + ErrorContext | 统一格式，记录文件、函数、行号 |
| 错误上报 | CompositeErrorReporter | 同时上报多个平台 |

| SwiftUI 全局处理 | Environment + ViewModifier | 一次配置，全局生效 |

| LocalizedError | errorDescription + recoverySuggestion | 支持多语言错误展示 |
| 错误展示组件 | Toast / Alert / 内联 / 全屏 | 根据严重程度选择展示方式 |
